## 2. 서사 설계 원칙

### 2.1 한 문장과 근거의 역할

- 기본 문장: **무슨 회차/수집 상황인가 → 서버가 무엇을 확인했나 → 누가 무엇을 하면 되나**.
- 예: “회차는 끝났고 38명 중 36명의 수신 기록이 확인됐어요. 코치는 수신 미확인 2명에게 앱 재접속을 안내해 주세요.”
- 헤드라인은 한 메시지로 구성하고 모바일에서 자연스럽게 2~3줄까지 줄바꿈한다. 의미를 잘라 말줄임하지 않는다.
- 문장 아래 작은 근거 줄: `참여자 36/38명 · feature 6,900/7,200창 · 원시 345/360건`.
- 상태 색상보다 텍스트·아이콘을 먼저 쓴다. 백분율·숫자로 사람이나 회차의 품질을 평가하지 않는다.
- 기준 설명은 항상 짧게 `서버 수신 기준`으로 노출. 신호별 수치·폰 잔량·리포트 선택은 상세로 이동.
- 원인은 사실과 분리한다. “서버 등록 후 대기”는 관측 사실, “네트워크가 끊겼다”는 서버만으로 확인 불가.
- 수신 변화의 이전 스냅샷이 없으면 “늘고 있어요” 대신 “현재 N건 수신을 확인했어요”를 쓴다.
- 대표 CTA는 한 개. `안내 보기`는 안내문을 여는 행동이며 메시지 자동 발송이 아니다.
- 와이파이 연결·앱 재실행은 사용자가 직접 하는 안내다. 서버 버튼으로 폰을 조작하거나 업로드를 강제하지 않는다.

### 2.2 총량 대비 근거 계약 — SDD-264 확인 후 확정할 제안

| 근거 | 표시와 의미 | 금지할 계산·예외 처리 |
|---|---|---|
| 참여자 M/N명 | N=확인된 수집 대상, M=그 대상 중 수신 기록이 있는 사람. M은 전체 대조된 사람 수가 아님 | 전체 등록 인원·미착용·opt-out·대기열을 무조건 N에 넣지 않음. 대상 미확인 인원은 별도 표시 |
| feature Y/X창 | 동일 대상·동일 스트림 범위의 실제 수신/확정 기대 창 수 | 회차 길이÷1초·5초, 최대 sequence로 X 추정 금지. SDD-264 정의와 다른 경우 계약에 맞춰 변경 |
| 원시 Q/P건 | 동일 신호·스트림·segment 범위의 실제 수신/확정 기대 조각 수 | 등록 건수는 기대 총량이 아님. `uploaded/registered`를 Q/P로 바꾸지 않음 |
| 일부 기대량 미확인 | `feature 6,900창 수신 · 전체 기대량 미확인` + 상세에 확인된 범위 따로 표시 | 알려진 분모만 합친 값을 전체 수집률로 표시하지 않음. null을 0으로 변환 금지 |
| N=0 또는 X/P=0 | 증거가 있으면 `수집 대상 없음`/`해당 데이터 수집 대상 아님` | 0/0 비율을 만들지 않음. 기존 수신 기록이 있으면 숨기지 않음 |
| Y>X 또는 Q>P | `기대 범위와 수신 기록의 대조가 필요해요` | 값을 상한으로 잘라 완료처럼 표시하지 않음 |
| 모두 수신 | 종료 보고·기대 집합 확정·같은 범위 대조 충족·결측/실패/대기 없음일 때만 `확인된 기대 범위 모두 수신` | 수량 일치만으로 전체 대조 판정 금지. 진행 중 잠정 분모·미보고 스트림이 있으면 사용 금지 |
| 현재 수집 제외 + 과거 수신 | 과거 기록 유지 + 현재 제외 사유 병기, 기간별 대상 집합으로 대조 | 과거 수신을 지우거나 현재 대상 분모에 무조건 더하지 않음 |

- feature와 원시는 별도 근거이며 합산 비율·종합점수를 만들지 않는다. 리포트 반영 여부·품질은 별도 사실이다.
- 현재 계약만 연결된 경우 세 비율 모두 확정된 것처럼 표시하지 않는다. `수신 N건 · 기대량 미확인`으로 후퇴한다.

### 2.3 상태 → 서사·원인·역할별 다음 행동 매핑

- 우선순위: 접근/조회 실패 → 관측된 실패·결측·오래된 등록 대기 → 수집 제외/명시적 미착용 → 등록 대기 → 기대 범위 대조 → 미수신.
- 혼합 상태는 가장 먼저 조치할 이유 하나를 헤드라인에, 나머지 사유는 상세에 모두 유지한다. 제외·대기열은 조치 대상 인원에 섞지 않는다.
- 아래 각 행의 회원 문구는 본인 데이터에만 적용한다. 코치·기관관리자는 허용된 회차 범위만 본다.

| 상태 조합·서버 근거 | 한 줄 헤드라인 예시 | 원인 해석 | 코치 문구·행동 | 회원 문구·행동 | 기관관리자 문구·행동 |
|---|---|---|---|---|---|
| 1. 종료, 대상 38명 중 36명 수신, 나머지 수신 0 | 회차는 끝났고 2명의 수신 기록이 아직 확인되지 않았어요 | 폰 상태·생성 여부 미확인 | 해당 참여자에게 앱 재접속을 안내해 주세요 → 안내 보기 | 측정했다면 앱을 켜 둔 채 와이파이를 연결해 주세요 → 안내 보기 | 담당 코치에게 해당 참여자 확인을 요청해 주세요 → 담당 코치 확인 |
| 2. raw failed>0 | 서버 등록 원시 2건이 실패 상태여서 확인이 필요해요 | 실패 기록 확인, 실제 원인은 미확인 | 참여자에게 앱 재접속을 안내해 주세요 | 앱을 켠 채 와이파이 연결 후 다시 확인해 주세요 | 담당 코치에게 실패 상태를 확인해 주세요 |
| 3. feature/raw 내부 결측>0 | 받은 기록 사이에 비어 있는 구간이 있어요 | 앞·뒤·폰 잔량은 알 수 없음 | 이어올림을 기다린 뒤 지속되면 문의해 주세요 | 앱을 켜 둔 채 와이파이를 연결해 주세요 | 담당 코치에게 수신 구간 확인을 요청해 주세요 |
| 4. raw pending>0, 등록 60초 미만 | 서버에 등록된 3건의 수신을 기다리고 있어요 | 업로드 실행 여부까지는 미확인 | 이어올림을 기다려 주세요 | 앱을 켜 둔 채 와이파이 연결을 유지해 주세요 | 담당 코치가 수신 상태를 확인할 수 있어요 |
| 5. raw pending 60초 이상 | 등록한 뒤 1분 넘게 수신되지 않은 건이 있어요 | 지연 원인·폰 잔량 미확인 | 참여자에게 앱 재접속을 안내해 주세요 | 측정 종료 후에도 같다면 앱을 다시 실행해 확인해 주세요 | 담당 코치에게 오래된 대기 건 확인을 요청해 주세요 |
| 6. 수신>0, 기대량 null, 알려진 실패 없음 | 수신 기록은 있지만 전체 기대량은 미확인이에요 | 대조 근거 부족, 손실 판정 불가 | 새로고침으로 최신 기록을 확인해 주세요 | 현재 받은 기록만 확인할 수 있어요 → 상세 보기 | 담당 코치가 대조 근거를 확인할 수 있어요 |

| 9. 명시적 미착용 + 수신 없음 | 밴드를 착용하지 않은 회차로 확인됐어요 | 착용 이력 증거 필요; 현 계약에는 없음 | 재업로드를 요청하지 않아도 돼요 | 밴드 데이터 수신을 기다릴 필요가 없어요 | 확인된 미착용 기록을 담당 코치와 확인할 수 있어요 |

| 11. 현재 조회 실패 + 이전 성공 데이터 | 최신 현황을 확인하지 못해 마지막 조회 결과를 보여요 | 관리자 화면 네트워크와 참여자 폰 상태 분리 | 인터넷 연결 후 새로고침해 주세요 | 연결 후 다시 확인해 주세요 | 최신 조회가 된 뒤 담당 코치를 확인해 주세요 |
| 12. 진행 중 + 확정된 현재 범위 일부 수신 | 수업 중이며 현재 확인된 범위에서 N건 수신을 확인했어요 | 최종 기대량 아님 | 실패·결측이 없으면 수신을 기다려 주세요 | 앱을 켠 채 측정을 이어가 주세요 | 필요하면 담당 코치에게 현재 수신 상황을 확인해 주세요 |

- `문의`는 기존 문의 경로가 확인될 때만 이동 CTA로 제공하고, 없으면 안내 문구로 둔다. 앱 재실행 안내는 진행 중 측정에 기본 노출하지 않는다.
- 자동 갱신 중 헤드라인을 매번 읽어 주지 않는다. 최초 조치 상태 변화만 접근성 알림으로 안내한다.

## 3. 세 가지 안

### A안 — 한 문장 요약 + 10건 표 + 상세 시트 (추천)

- 핵심: 첫 화면에서 ‘지금 상태·다음 행동’을 읽고, 목록에서 대상을 고른 뒤 근거를 본다.
- 코치 목록: 최근 회차 10건, 각 행은 회차/코치·서사·수집 근거·상세. 요약은 **이 페이지 10회차** 범위라고 명시.
- 코치 상세: 클래스 > 회차(담당 코치) 경로, 회차 전체 서사, 전체 대상 대비 근거, 참여자 표 10명.
- 회원: 최근 참여 회차 10건의 간결한 표(회차·일시), 선택 시 해당 회차의 본인 서사와 근거만 시트에 표시. 목록 10개에 summary API 20회를 호출하지 않는다.
- 모바일: 2열 표(대상/현황), 제목 아래 보조 문장과 근거; 신호별 상세는 하단 시트. 데스크톱은 4열 표 + 오른쪽 패널.

```text
[데이터 현황]                        [새로고침]
[현재 페이지 10회차 중 2회차 확인 필요 · 대상 보기]
[서버 수신 기준 · 마지막 조회 14:32] [갱신 설정]
[검색________________] [필터·그룹 2]
회차·코치                 현황
호흡 > 3회차              종료 후 2명 수신 미확인  >
                          참여자 36/38 · 근거 보기
… 최근 회차 최대 10건 …
[이전 10개]               [다음 10개]

회차 상세: [호흡 > 3회차(코치)]
[2명에게 앱 재접속을 안내해 주세요] [안내 보기]
[36/38명 · feature 6900/7200 · 원시 345/360]
[이름 검색] [필터·그룹] → 참여자 10명 표 → 상세 시트

회원: [내 데이터 저장 현황] [검색] [필터·그룹]
회차·일시 표 10건 → 선택 시 본인 상세 시트
[서버 등록 3건의 수신을 기다리고 있어요]
[앱을 켜 둔 채 와이파이를 연결해 주세요] [방법 보기]
[feature Y/X · 원시 Q/P] [수신 근거 펼치기]
```

| 항목 | 설계 |
|---|---|
| 페이지네이션 | 코치·회원 회차는 최신순 10건 교체형 이전/다음. 참여자는 확인 필요 우선·이름·ID 순 10명, 전체 배열에서 로컬 페이지 분할 |
| 서사 노출 | 상단 1문장, 행은 짧은 상태와 근거, 상세에서 원인 미확인·역할 조치·신호별 근거 |
| 장점 | 비교·탐색 유지, 화면 길이 상한 명확, 기존 표와 계약 재사용 범위 큼 |
| 단점 | 회원이 회차를 고르기 전 개별 수신 상태는 보이지 않음; 상세 열기 한 단계 필요 |
| 구현 난이도 | 중간. 행 축소·시트 접근성·페이지 상태 복원·역할별 서사 매핑 |
| API 필요 | 회차 cursor, 회원 통합 회차 목록, SDD-264 기대량 확장 필요. 참여자 상세는 기존 전체 조회 유지 가능 |
| 위험 | 상단 페이지 요약을 전체 회차 요약으로 오독; 반드시 범위 라벨. 시트 닫기 시 원래 행·스크롤 복원 |

### B안 — 확인할 대상 우선 + 접히는 그룹

- 핵심: 최근 10건 안에서 조치할 대상만 먼저 펼쳐 운영자의 탐색을 줄인다.
- 코치 목록: 최근 10회차를 먼저 선정한 뒤 ‘확인 필요/수신 대기/그 외’로 그룹, 확인 필요만 기본 펼침.
- 코치 상세: 전체 참여자에서 확인 필요 우선으로 10명 페이지 선정, 그룹별 접기. 나머지 인원을 그룹 제목에서 항상 확인 가능.
- 회원: 회차 선택 목록은 최근 10건. 선택한 본인 회차에서 ‘지금 할 일’을 먼저 펼치고 수신 근거는 접는다.
- 모바일: 그룹 아래 2열 표, 상세는 단일 행 아코디언(한 번에 하나). 데스크톱: 그룹 표 + 행 안 상세.

```text
[최근 10회차 중 확인할 회차가 2개 있어요]
[검색] [필터·그룹]
▼ 확인 필요 2회차 → 회차 | 서사 | 조치
▶ 수신 대기 1회차
▶ 그 외 7회차
[이전 10개] [다음 10개]

회원 회차 선택 → ▼ 지금 할 일: 앱을 켜 두고 와이파이 연결
                 ▶ 수신 근거: feature Y/X · 원시 Q/P
```

| 항목 | 설계 |
|---|---|
| 페이지네이션 | 그룹별 10개가 아니라 **그룹 합계 10개**. 페이지 이동 시 새 그룹 개수 표시. 접기는 데이터 제외가 아님 |
| 서사 노출 | 그룹 제목이 상황, 행이 대상, 펼침이 근거·다음 행동. 제외 상태는 조치 대상으로 분류하지 않음 |
| 장점 | 다인 현장 운영에서 우선 확인할 대상에 빠르게 접근; 평상시 화면이 가장 짧음 |
| 단점 | 접힌 곳의 데이터를 놓칠 수 있음. 최근순 위치와 그룹 순서가 달라 기억하기 어려움 |
| 구현 난이도 | 중상. 그룹·페이지·펼침 상태 유지, 폴링에 따른 행 이동 방지 |
| API 필요 | A와 동일. 모든 과거 회차에서 확인 필요를 먼저 찾으려면 페이지 전 서버 상태 필터 필요 |
| 위험 | 최근 10건 밖의 오래된 문제를 숨길 수 있음. ‘전체 기간 확인 필요’ 필터를 별도 제공하고 페이지 처음으로 이동 |

### C안 — 회차별 이야기 요약 + 목록·근거 분리

- 핵심: 선택한 회차의 ‘수업 상황 → 수신 상태 → 다음 행동’을 하나의 읽기 영역에 담는다.
- 코치 목록: 최근 10건 간결한 회차 표, 선택한 회차의 서사 요약을 데스크톱 옆 패널에 표시. 모바일은 별도 상세 화면.
- 코치 상세: 상단 이야기 요약, 참여자 표는 ‘참여자 40명 보기’로 펼침; 펼쳐도 10명씩.
- 회원: 최근 10회차 선택 표에서 한 회차 상세로 이동; 본인 데이터 이야기와 핵심 근거, 신호별 내역은 상세 접기.
- 시간 흐름처럼 보여도 실제 저장된 이벤트 이력으로 오해하게 하지 않는다. 현재 스냅샷에서 확인한 회차 상태와 수신 사실만 표현.

```text
[최근 참여 회차] [검색] [필터·그룹]
회차 | 일시 → 10건 표 → [이전] [다음]
선택 후:
[호흡 > 3회차(코치)]
수업: 회차가 종료됐어요
수신: 38명 중 36명의 기록이 확인됐어요
다음: 코치가 2명에게 앱 재접속을 안내해 주세요
[feature Y/X · 원시 Q/P] [참여자 보기]
```

| 항목 | 설계 |
|---|---|
| 페이지네이션 | 회차 표 10건 교체, 참여자 표 10명 교체. 모바일 상세에서 뒤로 가면 선택 페이지·필터·스크롤 유지 |
| 서사 노출 | 전체 회차는 짧은 행, 선택한 회차에서 세 문장을 한 단락처럼 읽음. 회원은 본인 행동만 표시 |
| 장점 | 데이터 지식이 적은 회원에게 맥락이 명확; 한 회차에 집중 가능 |
| 단점 | 여러 회차·참여자의 즉시 비교가 약함. 선택·이동 단계가 A보다 많음 |
| 구현 난이도 | 중상. 목록/상세 이동 및 상태 복원, 화면 크기별 다른 배치 |
| API 필요 | A와 동일. 사실 이력 타임라인을 추가하려면 별도 이벤트 API가 필요하므로 이번 안에서는 제외 |
| 위험 | ‘종료→수신→다음’ 도식을 완료 단계로 오독. 체크마크·단계 달성 표현 대신 사실 라벨 유지 |

## 4. 추천안과 공통 요구

### 4.1 선택 근거

| 비교 항목 | A 한 문장·표·시트 | B 문제 그룹 우선 | C 회차 이야기 |
|---|---|---|---|
| 최근 10건 탐색 | 날짜순 위치 유지 | 그룹 위치 변화 있음 | 날짜순 위치 유지 |
| 다음 행동 발견 | 상단과 선택 상세 | 확인 필요 그룹에서 가장 빠름 | 선택한 회차에서 명확 |
| 여러 회차 비교 | 간결한 표로 유지 | 펼친 그룹 범위에서 가능 | 상세 이동 필요 |
| 회원 적용 | 같은 문장·근거 구조 재사용 | 운영 중심 그룹은 회원에 축소 적용 | 설명은 쉽지만 이동 증가 |
| 구현 범위 | 기존 행 축소 + 공통 시트 | 그룹/폴링 재정렬 제어 추가 | 별도 이야기 배치·내비게이션 추가 |

- **A 추천 이유**: 요구의 핵심인 짧은 목록·서사·역할별 행동을 기존 표 구조 위에서 가장 균형 있게 충족한다.
- B의 ‘확인 필요’는 A의 필터로 제공하되 기본 최신순을 바꾸지 않는다. C의 시간 서사는 A 상세 문장에 활용한다.
- 채택 전 디자인 목표: 390×844 기본 글꼴에서 상단 요약·검색·첫 행이 보이게 구성. 200% 확대에서는 자연스러운 스크롤 허용. 실제 달성 여부는 후속 시안에서 측정한다.

### 4.2 공통 컴포넌트·반응형 규칙

| 컴포넌트(제안 식별자) | 책임 |
|---|---|
| `UploadNarrative` | 역할·관측 근거로 문장 생성, 원인 불명·기대량 미확인 보존, 실패 시 이전 상태와 구분 |
| `CollectionEvidence` | M/N·Y/X·Q/P와 분모 범위·확정 여부. 합성 점수 없음 |
| `UploadActionGuide` | 코치 안내문/회원 와이파이·종료 후 재실행 설명/기관관리자 담당 코치. 자동 발송 없음 |
| `CompactUploadTable` | 390px 대상/현황 2열, 데스크톱 4열. 검색·필터·그룹과 10행 제한 |
| `UploadEvidenceSheet` | 신호별 상세·전체 사유·조회/수신 시각·폰 잔량 미확인·리포트 선택 분리 |
| `TenItemPager` | 교체형 이전/다음, 로딩·실패·마지막 페이지 처리. 무한 누적 금지 |
| 기존 갱신 바 축약 | 마지막 조회 노출, 정지/재개 접근 유지, 마지막 수신은 별도 라벨. 서버 권장 주기·오프라인 중단 유지 |

- 보라 계열·흰 배경·20px 카드·얇은 구분선 유지. 요약을 여러 카드로 쪼개지 않고 한 영역에 묶는다.
- 검색은 상시, 필터·그룹은 모바일 버튼 하나로 열고 적용 조건 칩 노출. 데스크톱은 한 줄 도구 모음.
- 회차는 최신순 10개(유효시각 내림차순 + ID 동률 정렬)로 제안. 현행 ‘진행 중 우선’은 기본 정렬에서 제거하고 필터로 제공한다.
- 회차의 날짜가 같으면 같은 정렬 키로 안정화. 참여자는 시간 개념 대신 확인 필요 우선→이름→ID로 10명씩 표시한다.
- 페이지 이동은 기존 행을 교체하며 표 상단으로 포커스 이동; 상세 닫기는 트리거로 복귀. 모바일 하단 탭·safe-area·키보드에 CTA가 가리지 않게 한다.
- 필터·검색·기관 변경은 첫 페이지로 이동. 그룹은 페이지 선정 뒤 적용하고 `이 페이지 기준`을 표시한다.
- 폴링은 선택 행·펼침·페이지를 유지한다. 목록 구성 변화는 ‘목록 갱신’으로 알리고 명시적 새로고침 때 페이지를 재구성한다.

### 4.3 API 요구 — 현행과 제안을 구분

| 항목 | 현행 확인 | 제안·필요 여부 |
|---|---|---|
| 코치 회차 10건 | SDD-263 `limit=1..50`, cursor 없음. status는 후보 자른 뒤 필터 | **진짜 다음 페이지는 API 변경 필수**. `limit=10`, 불투명 `cursor`, `next_cursor`, `has_more`, 고정 정렬 기준시각 제안 |
| 전체 검색·상태 필터 | FE는 받은 최대 50개만 검색·그룹 | 검색·상태·기간·클래스·권한 조건을 페이지 절단 전에 서버 적용. 기존 사후 필터와 의미가 달라 계약 버전/호환 경로 결정 필요 |
| 요약 범위 | 기존 summary는 응답 items 범위 | 기본 `page_summary`만 사용. 전체 집계 필요 시 별도 범위 필드와 서버 비용 검증; 미구현 전체 건수는 노출하지 않음 |
| 회원 최근 회차 | `/classes` + 클래스별 회차; 전역 cursor 없음 | 본인 참여 회차를 최신순 10개 반환하는 통합 읽기 API 제안. 본인 권한·attendance·명상 범위 유지, 상담 회차 확대 없음 |
| 회원 상세 | 본인 feature/raw summary 두 요청 | 선택한 1회차만 호출. SDD-264 기대량·근거를 본인 권한으로 받을 계약 필요. 관리자 API를 회원에게 공개하지 않음 |
| 참여자 10명 | SDD-261 한 회차 전체 조회 | 40명 규모는 API 변경 없이 FE 페이지 분할 가능. 상단은 전체 회차 근거, 표는 필터 결과/현재 페이지 범위 표시 |
| 기대량·대조 | 261 expected null, 263 상태별 인원, 262 기대량 없음 | SDD-264 확정 계약 연동 필요. 기대 범위·산출 근거·미확인 대상·종료 여부·대조 결과를 받아 FE 추산 제거 |
| 회차 맥락 | 263 계약에는 host_name이 없고 FE는 started_at만 session_at으로 사용 | 담당 코치 최소 표시명과 정렬에 쓰는 유효시각을 명시적으로 반환. 코치 미확인 시 이름을 추정하지 않음 |
| 캐시·폴링 | 261/263 ETag·서버 권장 주기, 262 진행 중 5초 | 페이지·필터별 키, 권한 검사 먼저, 304는 기존 데이터 유지. 신규 필드도 ETag 지문에 반영 |
| 예외·개인정보 | 401/403/404 처리, 이름 최소 공개 | 권한 상실 시 이전 이름·수치 즉시 제거. 5xx는 마지막 성공 시각과 오래된 결과 표시. 폰 잔량 null 유지 |

- cursor는 사용자·기관·필터·정렬에 결합하고 다른 조건의 cursor는 거부한다. 이전 페이지는 클라이언트 cursor 이력으로 이동한다.
- 신규 회차가 들어와도 페이지 사이 중복·건너뜀을 줄이도록 첫 조회 기준시각을 유지한다. 상태 필터는 실시간 변동 가능하므로 엄밀한 스냅샷이 아니면 그 한계를 명시한다.
- 더 보기 문구를 쓰더라도 `다음 10개 보기`로 기존 페이지 교체. 처음 50개를 받아 10개씩 잘라 보이는 임시안은 가능하나 51번째 탐색을 충족하지 못하므로 최종안으로 삼지 않는다.
- 회원 목록 API가 없으면 현재 후보를 10건씩 나누는 제한안만 가능. 일부 클래스 조회 실패를 ‘참여 회차 없음’으로 숨기지 않고 부분 조회 실패로 알려야 한다.
- 오래된 회차는 현행 최대 90일 범위를 유지하며 화면에 기간을 표시한다. 더 긴 보관 탐색은 이번 기획에서 확정하지 않는다.
- 구현 전 검증 항목: 0/1/10/11/50/51회차, 40명→4페이지, 필터 후 0건, 전원 제외, 기대량 일부 null·0·수신 초과, 권한 회수, 조회 실패, 폴링 중 페이지 이동, 390px/WebView 시트 복귀.
- 위 항목은 후속 Stage ③ verify에 옮길 요구이며 이번에 실행한 테스트가 아니다.
