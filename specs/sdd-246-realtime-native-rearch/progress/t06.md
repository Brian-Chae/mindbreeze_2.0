- 재시작 복구 지연처럼 보였던 것은 시험 데이터 문제였다: 서버가 재구성한 snapshot 의 metric 은 설계상 `stale` 이고(오래된 값을 fresh 로 보이지 않기 위함), 실제 1Hz 스트림이 다시 들어와야 숫자가 뜬다. 실제 스트림처럼 1초 간격 주입으로 측정했다.

## 남은 일 / 위험

1. **브라우저 실경로 미검증**: web 타깃 WASM 산출물·Worker 번들(T12) 이후 Chrome 에서 raw→Worker→live:metric 을 다시 확인해야 한다. 현재 브라우저는 `core_unavailable`(서버 요청 0, 수업은 정상).
2. **앱 자동 시작 미연결**: `native` 경로는 웹 수집을 막는 데까지. 화면에서 `startWithCredentials` 를 부르려면 (a) JS bluetooth-le 가 쥔 밴드를 놓는 순서(`setJSBandOwnership(false)` → native 소유), (b) 토큰 출처(웹 `tokenStorage` refresh)와 인계 후 웹 사본 정리 정책(T08b 위험 6 — **T06 결정 미정**, 보안 판단이라 감독 확인 필요), (c) Android start 입력이 계약과 다름 — 셋 다 정해진 뒤 연결.
3. **v1 feature 업로드와 중복 저장 가능성**: v2 web_wasm 수집 중에도 `useBand` 의 v1 feature 업로드(REST/WS)가 그대로 돈다. 둘 다 `eeg_feature_windows` 에 들어가고 `play_group_id` 만 다르다(v2=stream_id) → 리포트·통계 중복 가능. v2 수집 중 v1 업로드를 끌지 T09 결정 필요.
4. 밴드가 끊기면 경로가 `off` 가 되어 session stop → `capture.close('client_stopped')`, 재연결 시 새 stream(gen+1). BLE 가 자주 끊기는 환경이면 stream 이 많이 생긴다(`reconnecting` 상태 보고 없이 닫음).
5. envelope `clock_uncertainty_ms` 는 300000 고정(서버는 이 값을 쓰지 않고 probe 로 판정). `serverNowMs` 는 RTT/2 미보정 근사.
6. 왕복 실측은 로컬 루프백·단일 회원. 20명×1Hz 부하·투영 락 경합은 T11.
7. 전체 vitest 기준선 17 fail / 8 파일(agent-counselor-page 등 타 Task)은 그대로. 전체 실행이 `specs/sdd-234-mobile-type-polish/screens` 를 바꾸므로 매번 `git checkout` 으로 원복했다.
