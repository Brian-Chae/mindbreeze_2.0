## 설계 결정

1. **무조건부 command**: v1 은 expected_epoch/client_generation/expected_entity_version/expected_grant_version/expected_revision/checkin_revision 을 알 수 없다 → 전부 `None`/미생성. 이 때문에 `waiting.set_ready`(checkin_revision 필수)는 변환하지 않고 `UnsupportedLegacyOp`로 거절한다(v1 회차는 T05 가 기존 소켓 경로 유지). fixture 가 가짜 최신성 필드 부재를 검증한다.
2. **command_id**: ① `Idempotency-Key` 가 있으면 `uuid5(session|actor|key)`. ② 없으면 actor 의 **가장 최근** ledger 행이 같은 kind·본문이고 30초 이내면 그 ID 재사용(ACK 유실 재시도→원 결과 재생). 사이에 다른 명령이 끼면 새 ID 라서 "들기→내리기→다시 들기"가 재시도로 오인되지 않는다. 그 외에는 `uuid5(session|actor|body_hash|n)`(n=동일 본문 누적 횟수).
3. **회차 protocol 고정**: 전용 컬럼이 없어(소유권 밖) T03 ledger 에 시스템 행(`actor=SYSTEM_ACTOR_ID, command_id=uuid5(session), kind=protocol.pin`)으로 영속. epoch 행 락 아래 first-writer-wins, 이후 인자가 달라도 불변. 8 스레드 경합 시험 통과. 첫 접촉 pin 이 없으면 v1/`legacy_unknown`.
4. **capability 규칙** (`admit_client`): v1 회차=누구든 v1 유지(신규 웹엔 안내 notice만, 회차 도중 전환 없음). v2 회차 + v2 미지원/ hello 없음 → 426 + 업데이트 안내, 부작용 0. v2 회차 + `ble_capture` 부족 → 입장은 허용, `capture_available=False`(밴드 없음을 이유로 구 프로토콜을 강요하지 않음).
5. **오류 변환**: CommandRejected 코드 → 구 상태코드·한국어 메시지(`map_error`). `idempotency_conflict`=409, handler 미등록=503 등.
6. **쓰지 않는 호출**: `features`/`feature`(측정 ingest), `participation_heartbeat`/`waiting_room`(휘발성 presence)은 command 가 아니라 `UnsupportedLegacyOp`.

## T05 가 호출할 인터페이스 (`app.services.session_live_legacy`)

```python
execute_v1(db, actor, op, session_id, params, *, idempotency_key=None, now=None, hello=None, flow="entry") -> LegacyOutcome
# op: raise_hand | lower_hand | set_speaking | transition(action=open|start|end|cancel) | enter | leave
#     | waitlist_cancel | chat_enabled | quiet_signal | waiting_room_remind | audio_sync
# 실패: LegacyError(status_code, detail, code)  → REST 는 HTTPException(e.status_code, e.detail), 소켓은 {"ok": False, "error": e.detail}
# LegacyOutcome.body: 구 응답 dict(hand/speaking/waitlist/remind). body=None 이면 refetch(session|chat_room|entry)로 T05 가 기존 직렬화 조회.
pin_session_protocol(db, session_id, protocol=None|1|2)  # 회차 생성 시(create/new-run) 호출. 이미 있으면 불변
get_session_protocol(db, session_id) -> ProtocolPin | None
admit_client(pin, hello, flow="entry"|"capture") -> Admission   # live:hello 의 ClientHello.from_wire(msg)
normalize / derive_command_id / to_live_command / to_legacy_response  # 단계별 사용 가능
annotate_legacy_rows(rows) / legacy_snapshot_cursor(pin)         # read adapter (구행 meta, v1 cursor=None)
shadow_compare_participant(db, session_id, participant_id, legacy_body) -> ShadowReport   # read-only
```

T05 선행 조건: 위 kind 들의 handler(`register_handler`)를 등록해야 `execute_v1` 이 동작(미등록이면 503, 부작용 0). 어댑터 테스트는 hand.set/hand.lower 대역 handler 로 검증했고, 나머지 kind 의 실제 업무 handler 는 T05 소관.

## 소유권 밖 변경 요청 / 위험

1. (요청) T03 소유: `live_session_epoch` 에 `protocol`/`protocol_origin` 전용 컬럼이 있으면 ledger 시스템 행 대신 쓸 수 있다. 현재 방식은 마이그레이션 없이 동작하지만 `live_command_ledger` 에 시스템 행이 섞인다(kind=`protocol.pin` 으로 구분, `derive_command_id` 는 이를 제외).
2. (위험) 키 없는 재시도 판정은 휴리스틱(30초 창·직전 명령 동일). 같은 본문을 30초 안에 의도적으로 두 번 보내도(예: 연타) 한 번으로 취급된다. 손들기/내리기 등 toggle 성 명령에는 안전하지만, 클라이언트가 `Idempotency-Key` 를 보내도록 T06/T07/T08 에 권고한다.
3. (위험) `to_legacy_response` 의 hand/speaking 응답은 commit 후 현재 DB 상태를 읽는다. 중복 재생(duplicate) 응답이 원 시점이 아니라 "현재" 상태를 반영한다(구 API 의 멱등 동작과 같다).
4. (위험) 구 앱 응답에 `waiting.set_ready`/presence 는 이 어댑터로 처리되지 않는다. v1 회차에서 T05 가 기존 소켓 경로를 유지해야 한다.
5. 기존 `waiting.remind` 의 명시 대상(participant_ids)은 command 본문에 못 넣어(v2 는 target_scope 만) `LegacyOutcome.extra` 로 돌려준다 — 구 소켓 emit 은 T05 가 이를 사용.
6. 실제 앱 클라이언트(구 앱 HTTP 호출 로그) 대비 실측은 하지 않았다(합성 fixture 만). 14일 dual-run 에서 확인 필요.
