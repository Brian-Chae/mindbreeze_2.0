## 설계 결정

1. **한 경로**: WS·REST·v1 어댑터 모두 `run_live_command` → `apply_command`(T03) → commit → `ob.drain`(T04) → `publish_pending`(방송). 업무 로직은 기존 서비스 함수의 commit 없는 단계를 같은 트랜잭션에서 호출한다(전이는 `transition_tx(commit=False)`).
2. **방송**: room `live2:<session>:<audience>`(public / host / member:<pid>)를 AsyncRedisManager 가 프로세스 간 중계. `publish_pending` 은 Redis 워터마크(`emitted`)+분산 락으로 **클러스터 단일 발행자**, emit 이 모두 성공한 뒤에만 워터마크 전진(실패 시 다음 호출이 이어서 — at-least-once, 클라이언트는 event_id/seq 로 폐기). 5초 heartbeat 루프가 self-heal 로 같은 함수를 호출해 방송 유실을 메운다.
3. **ACK**: `applied`/`duplicate` = DB commit + Redis projection 완료 후 cursors 포함. Redis 불가/미projection 이면 `retryable committed:true`(같은 ID 재시도 = ledger 재생), 일시 거절(epoch 불일치)은 `retryable committed:false`, ScopeStale 은 `retryable scope_stale`.
4. **상태머신**: CONNECTING(hello) → RESYNCING(join: room 가입 → snapshot → 방송 flush → sync_complete) → **클라이언트 `live:applied` 후에만 READY** → DEGRADED(Redis 불가) → RESYNCING. transport connect 와 READY 는 분리. READY 전 `live:metric/device` 는 `not_ready`, join 전 command 는 `not_joined`.
5. **회차 protocol**: `live:join` 은 pin 이 없을 때 **열리기 전(ready/scheduled) 회차만 v2 로 첫 pin**, 진행 중·완료 회차는 v1 로 pin(회차 도중 전환 없음). 생성 REST 는 플래그 on 이면 `_pin_new_run`. v1 회차에 `live:join` → `protocol_v1_session`.
6. **v1 REST 연결**: 플래그 on **그리고** 회차 pin=v2 일 때만 `execute_v1`. 그 외는 기존 서비스 경로(회귀 0). REST 에는 hello 가 없어 `X-Live-Protocol: 1,2` 헤더로 v2 지원을 알리며, 없으면 v2 회차에서 426(T10 규칙). 전이는 force/충돌 확인 옵션이 있으면 기존 경로.
7. **참가자 제거(추방)**: v2 회차면 같은 commit 에 `participant.removed` tombstone + `auth_revision` 증가 + capture stream expelled 차단. 방송 시 해당 member 소켓에 `live:access_revoked`+room 닫기(모든 프로세스).
8. **종료**: `transition_tx` → `session.changed`(payload.status completed/cancelled → T04 가 24h TTL) → `end_session_cutoff`(T03) → audio stop. 영상/음성 마감·알림은 commit 이후 `transition_after_commit`(best-effort).
9. **플래그**: 기동 시점에 off 면 `live:*` 핸들러 자체를 등록하지 않는다(현행 핸들러 집합과 동일, `test_tq06` 유지). on 으로 바꾸면 재기동 필요.

## 위험 / 후속

1. `live:metric`/`live:device` 의 저장·순서·신선도는 T09. 여기서는 상태 게이트와 sink 훅만 있다.
2. **Redis 소실 후 `emitted` 워터마크**도 소실 → 재구축 직후 첫 `publish_pending` 이 전체 outbox 를 재방송할 수 있다(클라이언트가 snapshot 으로 새로 시작하고 seq 로 폐기하므로 무해하나 트래픽 급증 가능). rebuild 에서 `emitted=applied` 로 맞추는 후속이 필요(T04 소유 영역 `ob.rebuild` 변경 요청).
3. 방송 발행자 락(`emit-lock` 5초 TTL)은 emit 이 5초를 넘기면 중복 발행 가능 — at-least-once 로 허용(클라이언트 폐기).
4. `waiting.set_ready`/`waiting.remind`/presence 는 v1 에서 기존 소켓 경로 유지 — v2 회차의 구 클라이언트는 어차피 426. v1 회차에서의 `live:*` 는 거부.
5. 명령은 `asyncio.to_thread` 동기 DB 로 실행(기존 소켓 코드와 같은 방식). 20명 회차의 지연은 T11 부하에서 측정 필요.
6. `speaking.set` 의 LiveKit 권한 반영(`apply_livekit_publish_permission`)은 commit 후 best-effort 이며 **실제 LiveKit 서버로는 검증하지 않았다**(키 없음). 실패는 로그만 — DB 정본과 어긋날 수 있어 T11 실기기/스테이징 검증 필요.
7. 플래그는 환경변수 `LIVE_PROTOCOL_V2`(또는 settings 필드)이고 켜려면 재기동. `settings` 에 필드는 추가하지 않았다(config.py 소유권 밖) — T12 가 필드/배포 설정 결정.
8. `session.changed` 의 entity_version 은 outbox 기준 단조 증가(`state_version` 과 무관).
9. 소유권 밖 수정 없음. (세션 서비스/라우터는 T05 소유 경로.)

## 결정과 근거

### device.changed — 스키마를 서버에 맞춤(스키마 갱신 쪽)
- 서버 payload 는 *stream 수명*(generation·status·clock_uncertain·cutoff_code) 이고, T01 `DeviceEntity` 는 *밴드 상태*(device_seq·band_state·contact·sqi·battery_pct·state_reason) 였다. 둘은 같은 `device` 도메인·같은 entity(participant) 를 두 출처가 갱신한다.
- 서버를 스키마에 맞추면 fencing 세대·cutoff(추방/동의철회/수료)를 어디에도 실을 수 없어 native/호스트가 owner 교체·권한 회수를 판단할 수 없다 → 스키마를 **합집합**으로 갱신: `required=[participant_id, stream_id]`, stream 필드는 선택, 밴드 필드는 선택.
- 병합 규칙(서버): `live:device` 보고는 stream 필드 + 밴드 필드 전부, `capture.*`/cutoff event 는 *같은 stream 의 마지막 밴드 필드를 보존*해 싣는다(`_emit_device` → `last_device_payload`). 소비자는 밴드 필드 부재 = 미보고.
- `generation` 은 u64 십진 문자열로 통일(기존 서버는 JSON int 였다 — 계약 위반 수정).

### participant_id 획득 규칙
- 서버는 인증 문맥의 `actor.participant_id` 만 신뢰한다. 클라이언트는 `capture.start` ACK `result.participant_id`(= snapshot `audiences` 의 `member:<pid>` 와 동일 값)를 envelope 에 넣는다. 다르면 `participant_mismatch`(해당 창만 rejected, durable:false). 타인 stream 은 `stream_not_found`(존재 여부 비노출).

| 신선도(서버 판정) | clock_uncertain 또는 anchor 없음 → `time_uncertain`(observed_at=null). 아니면 수신시각−창 종료(서버시계): ≤5s fresh, ≤30s delayed, 초과 stale |
| 투영(고빈도 대책) | 한 배치에서 *가장 새 창 하나*만 `metrics.updated` outbox event(audience host + 본인 member). `entity_version=(generation<<31)|sequence`, 이미 더 새 값이 있으면 건너뜀. 투영 조건 = 수락 + active + lease 유효. outbox 가 정본 → T04 재구축 대상 |
| dedupe 키 | metrics 는 Redis dedupe 키를 만들지 않는다(`METRIC_DEDUPE_TTL_S=0`, Lua 분기) — 1Hz×N 의 키·`keys` 집합 폭증 방지. 중복 방어는 `rev<=applied` watermark |
| 값 규칙 | invalid/warming_up/gap 은 null 저장(0 치환 금지). display 값은 raw 에서 재계산 가능해 저장 안 함. 종합점수·unknown 필드 거절 |
| device | 본인 active stream 만, `device_seq` 단조(작거나 같으면 `duplicate`, outbox 미기록). v1 호환으로 `band_connected/band_battery` 갱신 |
| 실패 격리 | 투영/방송 실패는 ACK 를 막지 않는다(feature·outbox 는 이미 commit, heartbeat 가 이어서 방송) |

## T06/T07/T08 이 맞춰야 할 변경

1. **capture.start ACK**: `ack.result.stream_id / participant_id / owner_generation / lease.expires_at_ms` 를 바로 쓴다(device.changed 대기 불필요). `generation`·`owner_generation` 은 u64 십진 **문자열**.
2. **device.changed 소비**: `payload.generation`(문자열)·`status`·`clock_uncertain`·`cutoff_code` 로 owner 교체/권한 회수 판단. 밴드 필드는 선택(부재 = 미보고). 문자열 u64 파싱 필수(iOS 의 payload `generation` 정수 가정 제거).
3. **live:metric 응답**: 성공 시 `{protocol_version, schema_version, acks:[MetricAck…]}`; 검증 실패는 `{ok:false, code, field?}`; READY 전 `not_ready`(retryable). 창별 `status`: accepted/duplicate(durable:true) 만 제거, `rejected`+`stale_owner_generation|participant_mismatch|stream_not_found|window_after_cutoff|feature_hash_conflict|…` 는 재전송해도 같은 결과이므로 **재시도 금지**(feature_hash_conflict 는 알고리즘 결정성 위반 신호). `sequence` ≤ 2^31−1.
4. **live:device 보고**: `Device` wire 스키마 그대로(`session_id`·`stream_id`·`device_seq` 단조). `stream_not_active`(superseded 등) 수신 시 보고 중단. 응답 `{…, status: accepted|duplicate, durable:true}`.
5. **metric 의 participant_id**: ACK `result.participant_id` 를 그대로 사용(snapshot `audiences` 에서 뽑지 말 것).
6. **observed_at_ms**: 서버는 신뢰하지 않는다. 신선도는 서버가 판정해 `metrics.updated.freshness` 로 내려준다(`time_uncertain` 이면 `observed_at_ms=null`) — 클라 표시는 이 값을 따른다. reanchor(clock_probe 10초 내)가 없으면 항상 `time_uncertain`.
7. **iOS**: `registerCredential` 요청에 `accessToken/refreshToken` 이 들어가는 건 계약상 허용(웹→native 1회). 결과로는 `credentialHandle` 만. **Android**: `handoffCredentials`. 둘 다 토큰을 결과·이벤트로 되돌리면 계약 검증 실패.
8. **Android 라이브러리 고정**: `io.socket:socket.io-client 2.1.2`(websocket-only). 버전 변경 시 `wire-compat.json` 갱신 필수.

## 위험 / 후속

1. 투영은 한 배치당 1 이벤트라 호스트 화면은 배치 도착 간격(native 1~수 초)만큼 갱신된다. 매초 실시간(회원 클래스 요구)이 필요하면 native 가 창마다(또는 1초 배치) 보내야 한다 — T11 에서 20명 부하와 함께 측정.
2. 투영(`_project_latest`)이 회차 epoch 락을 잡는다(명령과 같은 락). 20명×1Hz 에서 명령 지연이 늘 수 있음 → T11 측정.
3. 저장(`_persist_feature_items`)은 동기 DB·배치 1 commit. 배치≤60창이라 허용하나 T11 확인 필요.
4. `feature_hash_conflict` 는 영구 거절(durable:false) — native 가 같은 sequence 로 다른 값을 재생성하면(코어 비결정성/재시작) 해당 창이 서버에 안 들어간다. 로컬 journal 에는 남음.
5. 기존 v1 `eeg_feature_windows` 와 같은 테이블이라 report/통계 경로가 v2 창을 그대로 읽는다. `play_group_id`=stream UUID 라 pause/resume 세그먼트 규칙과 충돌 없음. 단 `quality`/`signal_quality` 는 sqi 에서 파생(null 이면 unknown).
6. metrics 경로의 BAND 연결/배터리(`participant.band_*`) 갱신은 `live:device` 에서만 한다(metric 에서는 안 함).
7. 서버 신선도 임계(5s/30s)는 임시 상수 — 제품 결정 필요 시 조정.
8. 소유권 밖 변경: `contracts/**`(감독 승인), `live_redis/{client,scripts}.py`·`session_live_outbox.py`(T04 소유, 요청 3·dedupe 대응), `session_live_commands.py`(T03 소유, ACK result·DeviceEntity 정합). `frontend/ios/android` 0.
