## 한계·위험 (정직하게)
1. 서버 manifest는 "분할 부모"를 모른다: 부모 행이 없어 expected에서 빼는 것(클라이언트)과 자식의 first/last 순번 연속에 의존. 부모가 이미 서버에 올라간 뒤 자식도 올리는 경우는 다루지 않음(과대 객체는 서버가 거절하므로 발생 안 함).
2. 단일 행이 1MiB를 넘거나 gzip 불가·해석불가 객체는 미복구(원본 보존, `oversize_unrecoverable`). raw 청크는 재생성 정보가 없어 분할하지 않음.
3. 자식 sequence = 1,000,000 + 부모 seq×1000 + 순번(서버 int32 내). 부모 seq가 2,000 이상이면 상한 근접 — 현재 수집 길이(2시간)에선 여유 있으나 장기 회차 전 재검토 필요.
4. `Retry-After` 헤더는 apiClient가 노출하지 않아 본문 `retry_after`만 읽는다.
5. 실제 S3 PUT 만료·네트워크는 모의(스토리지 검증 모의) — 실기기/실 S3 증거 아님. T11 독립 검증 대상.
6. 훅은 v3 경로에서 `time_review`/`dead_letter` 건수를 기존 `blockedCount`로만 노출(UI 구분은 T06 범위).
