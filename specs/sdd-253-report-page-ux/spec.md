## 1. 문제와 목표

모바일 카드의 읽기 흐름은 유지한다. 데스크톱은 리포트 문서의 속성을 나열하는 화면에서, 필요한 일을 찾아 처리하는 화면으로 바꾼다.

대표가 제공한 현재 화면 관찰: 필터 4줄, 그룹마다 반복되는 표 헤더, 11개 컬럼으로 인한 칩·보기 링크의 세로 줄바꿈, 회차 제목·날짜 중복, 성별·생년월일의 상시 노출, 두 종류 문서가 별도 행으로 분산, 의미가 드러나지 않는 NEW, 검토 대기와 주요 행동의 낮은 가시성.

이 관찰을 현재 코드와 대조했다. 캡처는 운영 데이터가 아닌 현재 워크트리 소스 + 합성 API이다. 대표 스크린샷 원본은 이번 세션에 첨부되지 않았으므로 픽셀 단위 동일 재현이라고 주장하지 않는다.

목표:

- 상담사는 첫 화면에서 검토 대상 수·실패 수와 다음 행동을 구분한다.
- 회원·회차로 찾고, 같은 회차의 회원용·상담사용을 같은 맥락에서 연다.
- 회원은 새로 도착한 리포트를 먼저 열고, 지난 승인 기록을 찾아 나란히 읽는다.
- 승인, 회원 공개, 메일 전달, 읽음 상태를 서로 다른 사실로 표시한다.
- 데스크톱 1440px에서 필터 컨트롤은 한 줄, 본문 최대폭 1200px, 상태·CTA는 한 줄로 읽힌다.
- 명상·웰니스는 서사와 변화량만 사용한다. 종합점수·순위·좋음/나쁨·치료·진단 효능 표현을 추가하지 않는다.

## 3. 역할별 사용자 작업과 단 하나의 주 CTA

### 상담사

1. 검토 대상 처리: 목록 **검토 시작** → 해당 회원용 미리보기 → 코멘트 선택 입력 → **저장하고 미리보기** → **승인하고 공개** → 다음 대상. 단계마다 주 버튼 하나만 채운 보라색으로 표시한다.
2. 회원·회차 찾기: 검색 + 활동·담당자·기간·정렬 + 그룹핑. 이미 승인된 행의 주 행동은 **열기**.
3. 생성 실패 대응: 행 **실패 확인** → 대상·사유·기존 성공 문서 확인 → 권한·안전한 재시도 계약이 있을 때 **다시 생성**. 진행 중에는 중복 버튼 비활성.
4. 승인 후 메일: 공개 완료를 먼저 안내하고, 메일은 별도 전달 영역에서 수신 주소·결과 확인. 주 행동은 **메일 보내기** 또는 **메일 다시 보내기**. 이 영역을 연 때만 해당 버튼을 주 CTA로 삼는다.

### 기관관리자

- 기관 범위의 검토 대기·실패를 확인하고 담당자를 찾는다. 목록 주 CTA는 **처리 현황 보기**, 상세는 읽기 전용 **담당자 확인**.
- 상담사에게 별도 알림을 자동 발송하는 기능은 범위 밖이다. 담당자 이름·연결 화면 확인까지만 제공한다.
- 기관관리자에게 편집·승인을 새로 허용하지 않는다. 겸직 계정의 권한은 역할 문자열 대신 서버 capability로 판정한다.

### 회원

- 목록 주 CTA **새 리포트 열기**. 미열람이 없으면 가장 최근 승인 리포트 **리포트 열기**. 검토 중인 최신 회차 때문에 오래된 승인 리포트 접근을 막지 않는다.
- 상세 주 CTA **지난 리포트와 함께 보기**. 비교 가능한 지난 승인 기록이 없으면 버튼 대신 해당 안내와 **목록으로**를 제공한다. PDF는 사용 가능할 때만 보조 행동.
- 준비 중 상세는 **목록으로**, 목록 실패는 **다시 불러오기**, 검색 빈 결과는 **필터 초기화**.

## 4. 개선 정보 구조와 화면 규격

### 4.1 데스크톱 목록

- 본문 최대폭 1200px. 1440px 시안의 본문은 좌우 120px. 앱 내비게이션은 기존 공통 셸을 재사용한다. 시안의 상단 가로 내비게이션은 내용 폭을 보여주기 위한 프레임이며 전체 앱 셸 교체 제안이 아니다.
- 페이지 제목 → 검토 요약(미처리 회원용 N건, 생성 실패 별도) → 한 줄 검색·필터 → 처리 상태 탭 → 표 → 페이지 이동.
- 운영 설정·샘플·일괄 승인은 보조 메뉴로 둔다. 자동 승인 정책을 여기서 새로 변경하지 않는다. 일괄 승인은 첫 구현에서 기존 기능을 보조 메뉴로 유지하며, 필터 결과를 선택 승인하는 기능으로 몰래 의미를 바꾸지 않는다. 전체 대상 수·코멘트 생략·공개 효과를 확인창에 명시한다.
- 검색은 회원 표시명/안정 식별번호, 클래스명, 회차 제목으로 찾는다. 생년월일을 검색·노출 수단으로 쓰지 않는다. 동명이인은 기관 내 식별번호로 구분한다. 이메일은 필요한 상세 수신 확인 영역에서만 표시한다.
- 활동 종류(명상/상담/기타), 담당자(권한 범위), 기간, 최신 회차순 정렬. 그룹핑은 없음/처리 상태별을 기본 시안으로 제시하고 클래스별·회원별 그룹은 후속 동일 컨트롤의 확장 범위. **회차 내 문서 묶음은 항상 적용**, 선택 그룹핑과 별개다.
- 상태 탭은 전체 / 검토 필요 / 생성 중 / 생성 실패 / 승인 완료. 상단 업무 요약은 전체 권한 범위, 탭 카운트는 적용 검색·필터 범위라는 기준을 레이블로 구분한다. 숫자는 서버 집계가 없으면 전체로 표시하지 않는다.
- 표 5컬럼: `회차·활동`(제목+날짜·시각 보조줄), `회원`(마스킹 이름+식별번호), `리포트 구성`(회원용/상담사용), `처리 상태`(다음 행동에 필요한 요약+사유), `행동`(최소 104px). 문서 종류·상태칩·버튼은 줄바꿈 금지, 제목만 최대 두 줄.
- 성별·생년월일 컬럼 제거. 회원/비회원은 이름 보조줄로 축소. 날짜를 그룹 제목·행 제목·날짜 컬럼에 반복하지 않는다. 헤더는 표 위에 한 번, 그룹 제목은 tbody의 colspan 행.
- 1:1은 session_id 회차 행 안에 회원용/상담사용 두 문서를 연결한다. 문서가 한 종류만 있어도 가짜 문서를 만들지 않는다.
- 그룹 클래스는 session_id 상위 행(참여자 N명, 회원용 검토 N건, 상담사용 1건), 펼침은 participant_id별 회원용 행. 상담사용은 회차 공통 링크이며 사람마다 복제하지 않는다. 일부만 생성·승인되면 `회원용 검토 2 / 승인 8 / 실패 1`처럼 구성별 카운트를 제공하고 대표 상태 우선순위는 실패 > 검토 필요 > 생성 중 > 승인 완료. 승인 완료는 승인 대상이 모두 완료한 경우이며 approval_required=false를 대기 수에 포함하지 않는다.
- 페이지 단위는 회차이다. 문서 레코드 페이지를 먼저 자른 후 회차를 묶으면 두 문서나 참여자가 다음 페이지로 갈라질 수 있으므로 서버 그룹 조회가 필요하다.

### 4.2 데스크톱 검토 분할 보기

- 1200px 안에서 왼쪽 345px 대기 목록, 오른쪽 855px 읽기·편집 영역. 오른쪽 상단은 회원·회차·날짜·상태, 본문은 회원용 미리보기/상담사용 참고, 하단은 단계별 주 CTA.
- 기존 상세 URL은 보존하고, 목록 필터·페이지·스크롤·선택 행을 돌아왔을 때 복원한다. 모달 호환 딥링크도 유지한다. 모바일은 전체화면 dialog 유지.
- 승인할 대상은 현재 선택한 회원용 report_id. 상담사용 참고 화면에서 회원용 승인 버튼을 잘못 노출하지 않는다. 클래스 상담사용은 승인 버튼이 없다.
- 코멘트는 선택. 저장 실패 시 입력을 보존하며 승인으로 넘어가지 않는다. 미저장 입력이 있으면 저장 후 미리보기 또는 변경 취소를 선택한다. 데이터·기록·코멘트가 모두 없을 때는 내용이 없음을 명시하고 별도 확인 후 승인한다. 유용한 수치를 합성하지 않는다.
- 저장·미리보기 이후 **승인하고 공개**. 공개 대상·내용을 보여주고 중복 클릭을 막는다. 승인 성공·목록 재조회 실패를 분리하여 이미 승인된 건을 재발송하지 않는다.
- 승인 완료는 회원 공개 사실만 안내. 메일은 미신청/예약/전송 확인/실패/확인 불가를 별도로 보여준다. 현 DTO에 메일 상태가 없으면 **메일 상태 확인 필요**로 표시한다. 예약을 전달 완료로 표현하지 않는다.

### 4.3 회원 데스크톱 목록·상세

- 목록은 새 리포트 요약+한 줄 필터+4컬럼 표(회차, 상담사, 읽음 상태, 열기). 같은 클래스·회차의 승인된 본인 회원용만 열며 상담사용·다른 참여자 정보는 보이지 않는다.
- NEW → **아직 읽지 않음**, 본문 열람 후 읽음. 상담사 업무 대기에는 이 배지를 쓰지 않는다. 전체 읽음은 보조 메뉴.
- 승인 전은 `준비 중` 또는 `상담사 확인 중`으로 안내하고 본문·지표·코멘트 초안·원문 오류를 노출하지 않는다. 오래 걸릴 때는 지연 안내만 추가한다.
- 상세는 왼쪽 목차(210px) + 오른쪽 서사 본문. 오늘의 이야기 → 몸·마음의 변화 → 상담사 코멘트 → 지난 기록. 문서 폭 전체에 문장을 길게 늘이지 않는다.
- 변화량은 같은 회차의 전반/후반, 또는 같은 클래스·호환 측정 조건의 본인 승인 자료만 사용한다. 기준·단위·비교 기간·자료 유무를 명시하고 결측은 0으로 바꾸지 않는다. 다른 조건은 수치 비교 없이 두 서사를 나란히 읽는다.
- 1회 기록, 미착용, 측정 부족, 일부 누락에서는 비교 불가 이유를 표시한다. 점수·순위·좋고 나쁨·증상 개선을 생성하지 않는다. 밴드 없이도 참여 기록·코멘트·서사 중심 리포트가 존재할 수 있다.
- 토큰 링크 열람은 현재 단일 문서 권한을 유지하며 지난 리포트 탐색을 제공하지 않는다. 만료 시 최신 메일 링크 안내. 샘플은 지속적인 `예시 데이터` 표기.

### 4.4 용어와 상태

- `타입` → **리포트 구성** 또는 **문서 종류**: 회원용/상담사용. API의 client/counselor는 그대로 유지한다. 비회원도 받는 일반 사용자용은 **참여자용**, 회원 화면은 **내 리포트**로 표시한다. 시안은 회원 사례라 회원용을 쓴다.
- `구분` → **참여자 유형**: 회원/비회원. 업무에 필요한 경우 보조줄만.
- `세션유형` → **활동**: 명상/상담/기타. 구체적 임상·최면 분류는 필터·상세에서 확인한다.
- `검토중` → **검토 필요**(업무 대기), `분석중` → **생성 중**, `실패` → **생성 실패**, `승인됨` → **승인 완료**. 회원에게는 준비 중/상담사 확인 중/열람 가능 문맥으로 바꾼다.
- `생성 상태` 독립 컬럼은 제거하되 실제 모델은 분리 유지한다. partial+error면 실패 확인, partial이지만 usable이면 일부 자료만 생성과 누락 사유, 생성 중이면 단계·지연을 상세에서 확인한다. 미측정 자체를 실패로 분류하지 않는다.
- `보기` → **검토하기 / 실패 확인 / 진행 보기 / 열기**. 재시도는 실패 확인 안에서 안전성·권한 확인 후 제공한다.

### 4.5 모바일·접근성·기타 상태

- 현재 카드·전체화면 상세·하단 내비게이션을 유지한다. 390px에서는 필터를 작은 여러 줄로 허용하고 상세 필터는 접어둔다. 데스크톱 표를 축소해서 넣지 않는다.
- 공통 용어·개인정보 마스킹·상태별 행동만 맞춘다. 카드 전체 클릭과 명시 버튼이 중복 포커스를 만들지 않도록 구현한다.
- 이름은 기본 마스킹, 성별·생년월일은 목록 제거. 이메일은 마스킹 예외지만 목록 상시 노출은 하지 않는다. 상세에서 개인정보 펼침이 필요하면 기존 정책·권한을 따른다. 화면 숨김만으로 민감한 API 응답 문제가 해결되는 것은 아니므로 projection도 검토한다.
- 첫 이용 빈 상태는 상담사 클래스 보기/회원 나의 클래스 보기. 검색 빈 상태는 필터 초기화, 목록 네트워크 실패는 다시 불러오기, 생성 중은 진행 보기, 생성 실패는 대상·재시도, 권한 없음은 읽기 전용/담당자 확인.
- 44px 이상 터치 영역, 키보드 포커스, 표 scope, 상태 텍스트, 저장·승인 피드백의 live region, 모달 focus trap·닫기 후 복귀를 유지한다. 색으로만 상태를 구분하지 않는다.

## 5. 구현 경계·서버 변경 필요 여부

이번에는 어떤 구현도 하지 않는다. 다음 단계의 범위를 정확히 나누기 위한 계약 요구사항이다.

프론트에서 가능한 표현 변경:

- 폭·필터 배치·컬럼 축소·마스킹·용어·상태별 버튼·보조 메뉴 우선순위, 기존 상세 컴포넌트의 읽기 구조.
- 기존 코멘트 PATCH → 승인 POST → 재조회 순서를 보존한 단계 UI. 기존 권한을 확대하지 않는다.

서버 지원이 필요한 완성 범위:

- 회차 단위 페이지네이션·그룹핑, 전 범위 검색/필터/정렬, 전체 및 필터 집계. 현재 문서 단위 total을 그대로 회차 수로 바꾸지 않는다. 기존 /reports 계약을 깨지 않도록 확장 또는 별도 read endpoint를 Plan에서 선택한다.
- 응답에 안정적인 회차/클래스 식별자, 참여자 묶음, 문서별 report_id/type/status/approval_required, 미생성 대상, 필요한 클래스 작업 식별자를 제공한다. 기관·역할별 projection·페이지 경계를 함께 보장한다.
- can_view/can_edit_comment/can_approve/can_retry와 이유를 서버 계산. 현재 진행자·주강사 대행·기관관리자 차이를 반영한다. 클라이언트 역할만으로 추정하지 않는다.
- 메일 상태·마지막 시도·수신 설정을 위한 최소 read projection. sent_at 재활용 금지. 전송 성공과 실제 수신/배달 확인을 구분한다. 배달 확인이 없는 환경은 `전송 확인`까지만 표시한다.
- 실패 재시도는 허용 상태·참가자·작업 식별·멱등성·중복 실행·기존 승인 결과 보존을 검증한다. 기존 클래스 job retry와 일반 생성이 섞이지 않게 별도 계약 확정. 계약이 없으면 `다시 생성` 대신 `담당자 확인`을 유지한다.
- 지난 기록은 기존 클래스 본인 trend API(`backend/app/api/v1/class_reports.py:88`) 활용 가능성을 검토하되 범용 리포트 비교가 이미 있다고 간주하지 않는다. 읽기 전용 승인 기록 선택은 현재 소유권 검사를 재사용한다. 비교 가능한 자료 없으면 서사 병치만 제공한다.

DB 마이그레이션·신규 메일 발송 정책·자동 승인 정책 변경은 기본 범위가 아니다. 기존 필드로 메일 상태를 제공할 수 있는지 Plan에서 확인 후 필요하면 별도 승인받는다.

## 6. 대안과 대표 결정 필요 사항

모든 항목은 미승인 제안이며 권한·자동 승인 정책은 기존 유지가 기본이다.

### D1 — 목록의 업무 단위

- 추천: **회차 중심 묶음 + 그룹 회차의 참여자 펼침**. 두 문서 비교와 승인 대상 탐색이 가장 명확하다.
- 대안: 현재 리포트별 행 유지+컬럼만 축소. 작업량은 작지만 중복 행·페이지 분리 문제가 남는다.

### D2 — 상세 방식

- 추천: **데스크톱 분할 검토, 모바일 현재 전체화면 상세 유지**. 직접 URL 상세와 딥링크도 유지한다.
- 대안: 기존 큰 모달만 정리. 빠르지만 여러 대기 건을 연속 처리할 때 맥락 전환이 반복된다.

### D3 — 기관관리자의 역할

- 추천: **조회·담당자 확인**. 현 서버 권한과 맞추고 잘못된 승인 안내를 수정한다.
- 대안: 기관관리자 대행 승인 신설. 업무 책임·감사·회원 공개 권한 설계가 필요하여 별도 기능으로 분리한다.

### D4 — 승인과 전달의 표현

- 추천: **승인하고 공개**, 메일 전달은 별도 상태·별도 행동. 신청 이메일의 기존 자동 예약은 유지한다.
- 대안: 승인하고 발송으로 통합. 승인과 메일 실패가 분리되는 현 구조에서 오해가 커서 비추천. 원한다면 전달 보장 정책부터 별도 설계해야 한다.
