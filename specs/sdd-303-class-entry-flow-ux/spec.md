# SDD-303 — 클래스 코드 입력~입장 과정 UX 개선 기획

- 상태: 사용자 시안 승인 및 통합 동의 구현 승인. Astra 구현·독립 로컬 검증 완료, 사용자 최종 리뷰·배포 대기.
- 작성일: 2026-11-05 / 브랜치: `sdd/303-class-entry-flow-ux`
- 최신 작업 범위: 승인된 통합 동의 실제 UI·기존 동의 API 연계 구현 및 로컬 검증. 연결 코어·코드 입력 화면 불변. 커밋·푸시·PR·배포·메일·삭제는 수행하지 않음. 기존 기획 산출물은 보존.

## 문제와 목표
회원은 코드 확인 뒤에도 입장, 고지, 상태 질문, 밴드 연결, 권한 안내, 기기 점검, 준비 요약을 지나야 한다. 특히 EEG 선택의 ‘동의하고 LINK BAND 연결하기’는 실제 연결을 시작하지 않고 다음 화면에서 다시 연결 버튼을 요구한다.

목표는 로그인 회원이 코드 입력 또는 회차 선택 한 번으로 준비 흐름에 들어가고, 필요한 동의만 확인한 뒤 선택적으로 밴드를 연결해 대기실에 도달하는 것이다. 수업 시작 시 자동 진입은 현행을 유지한다.

## 결정된 제약
- 11/11 운영은 로그인 필수. 현재 비회원 경로가 남은 코드와 운영 방침을 혼동하지 않는다.
- 밴드는 선택. 미사용·동의 거절·연결 실패도 수업 참여를 막지 않는다.
- 개인정보·녹음 안내와 해당 동의, EEG 수집 선택, 리포트 선택은 보존한다. 한 화면 배치는 일괄 동의를 뜻하지 않는다. 연구 활용도 독립 선택으로 유지한다.
- 같은 목적·버전·적용 범위에 유효한 서버 동의가 있으면 재질문하지 않는다. 거절도 유효한 선택으로 존중한다. 새 회차별 선택과 전역 동의를 구분한다.
- 동의 조회 실패·구 응답의 undefined를 동의로 간주하지 않는다. 저장 성공 전에 수집을 시작하지 않는다.
- SDD-293: 접촉을 확인하는 동안 JS가 상태를 표시하고 밴드 단계에서 나온 뒤 네이티브로 인계한다. UI 단축을 이유로 adoptBand를 앞당기거나 네이티브 수락 후 JS를 해제하는 인계 순서를 유지하고 이중 측정 소유를 방지한다.
- OS 권한과 기기 선택은 실제 사용자 제스처로 유지한다. iOS 제약은 브리프 요구이며 실기기 검증 전이다.

## 제안 범위
A안(채택 제안): 코드 → 필요한 동의/선택 한 화면 → 밴드 선택/연결 한 화면 → 대기실 → 시작 시 자동 진입. 상태 질문과 온라인 기기 점검은 대기실에서 선택적으로 수행한다. 밴드 화면은 ‘밴드 연결하기’ 주 행동과 ‘밴드 없이 입장’ 보조 행동으로 구분한다.
B안: 코드 → ‘입장하기’가 있는 통합 준비 화면에서 동의·밴드·기기를 모두 처리한다. 화면 수는 적지만 입장 버튼이 OS 권한·동의 저장·연결을 동시에 의미하여 실패 원인을 알기 어렵다. 첫 사용 40명 행사에는 A안이 더 설명하기 쉽다.

## 수용 기준
- 단계·탭 수는 plan.md의 조건과 단위로 계산한다. 실제 사용자 측정 결과로 표현하지 않는다.
- 중복 입장 확인과 준비 요약의 필수 진행 버튼을 없애고 대기실 안에 현재 준비 상태를 표시한다(행사 후 목표).
- 신규 동의는 명시 선택, 재입장은 서버 기록 확인 후 해당 화면 생략. 접촉 미확인 상태를 정상으로 단정하지 않는다.
- 코드 오류·정원·시작 전·밴드 실패·재입장에 복구 경로를 제공한다.
- 시안은 390px·768px에서 첫 입장·재입장·밴드 없음·현재 흐름을 확인한다. 금지 문구는 화면 텍스트에서 0건이어야 한다.
- 문서와 시안은 합성 기획이다. 서버·권한·BLE·40명 부하·앱 동작을 검증한 결과가 아니다.

## 대표 결정 질문
1. 11/11 전에는 문구·권한 설명 중복 정리만 적용하고, 단계 구조 변경은 행사 후로 나눌까요?
2. 행사 후 ‘오늘의 상태’ 질문과 온라인 기기 점검을 대기실의 선택 항목으로 옮길까요?
3. 클래스 코드로 처음 가입하는 회원에게는 가입 의사 확인을 유지하고, 이미 가입한 회원·회차가 하나인 경우만 자동으로 준비 화면에 보낼까요?

## 최신 승인과 구현 경계 (2026-11-05)
사용자: “동의 화면 통합까지 진행: 연결 코어는 유지하되 동의 처리 변경을 별도 검증”. 구현은 Astra가 맡는다. 이전 행사 전/후 분리 및 제품 수정 금지 기획 범위는 이 승인으로 변경되었다.

이번 실제 구현은 통합 동의와 중복 동의 제거에 집중한다. CodeEntryPage와 CodeEntryView는 그대로이며 코드 입력 이전/정보 화면 흐름은 바꾸지 않는다. 설문·기기점검·준비요약의 이동과 전체 9→3탭 목표는 이번 결과로 주장하지 않는다. 보호 manifest와 implementation-plan.md를 현재 구현 기준으로 삼는다. 기존 상세 고지·버전·동의 서버 계약을 그대로 활용한다.
