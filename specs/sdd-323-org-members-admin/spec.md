## 1. 문제와 목표

- 대시보드의 초대 폼·초대 현황과 구성원·센터 관리 화면의 권한 관리가 분산되어 있다.
- 기관 관리자가 구성원 한 화면에서 코치와 관리자를 찾고, 초대 상태를 확인하고, 가입 요청을 처리한다.
- 선택: 구성원에 4개 탭을 둔다. 근거: 역할별 명단과 처리 대기 업무를 나누면서 기관 맥락을 유지할 수 있다.
- 대시보드는 활성 코치·활성 관리자·초대 대기·가입 요청 숫자와 구성원 관리 링크만 제공한다. 초대 입력과 개별 처리 버튼은 구성원으로 이동한다.
- 성공 기준: 초대부터 역할 관리까지 다른 관리 페이지로 이동하지 않고 처리할 수 있고, 기관 간 권한·정보가 섞이지 않는다.

## 3. 정보 구조와 동선

- 기본 경로 `/counselors?tab=coaches`. 탭은 `coaches`, `admins`, `invites`, `requests`.
- 기관명·구성원 제목·현재 탭을 유지하고 탭별 검색·필터를 URL에 보존한다. 뒤로 가기는 직전 필터·선택 행을 복구한다.
- 기존 센터 관리 구성원 영역은 새 경로로 연결한다. 본인 가입 신청 내역은 별도 기능으로 유지한다.

| 탭 | 정보 | 주요 행동 |
|---|---|---|
| 코치 | 이름·이메일·상태·기관 내 클래스 수·최근 활동·개인상담소 배지 | 초대, 상세, 개인정보 수정, 정지/재활성, 소속 해제, 관리자 지정 |
| 기관 관리자 | 이름·이메일·활성 여부·대표/본인 표시 | 관리자 초대, 기존 코치 승격, 권한 회수, 대표 이전 |
| 초대·가입 현황 | 역할·신규 가입/소속 추가·초대일·만료일·대기/만료/가입됨 | 재발송, 역할 필터, 상태 필터 |
| 가입 요청 | 신청자·신청일·상태·거절 사유 | 승인, 거절(사유 입력), 처리 결과 조회 |

- PC: 표 + 이름/이메일 검색 + 상태 필터 + 상태별/개인상담소 여부 그룹핑. 모바일: 같은 정보의 카드, 칩은 줄바꿈하지 않는다.
- 활성 명단과 초대 대기를 합산하지 않는다. 초대 탭의 가입됨은 현 소속 활성 사용자에 한정하며 과거 초대 이력 전체를 의미하지 않는다.
- 상세: 기관 내 담당 클래스·담당 회원 요약, 세션/리포트 메타데이터만 표시. 녹음·상담 본문은 포함하지 않는다.
- 최근 활동은 기관 내 마지막 세션 시작 시각. 로그인 시각과 혼용하지 않고 데이터 없으면 ‘활동 없음’.
- 이메일은 불변 아이디. 코치의 이름·성별·생년월일·전화·주소를 사유와 함께 수정한다. 공유 프로필이므로 다른 소속에도 반영됨을 안내한다.

## 4. MVP와 후속

### MVP — 행사 이후

- 4개 탭, PC 표/모바일 카드, 검색·필터·그룹핑, 대시보드 요약 이동.
- 코치/관리자 초대와 재발송, 기존 코치 승격·관리자 권한 회수, 대표 이전.
- 코치 개인정보 수정과 기관 범위 활동·담당 현황. 계정 정지/재활성 및 소속 해제의 영향 확인.
- 최소 활성 관리자 1명, 자기 자신 권한 회수·소속 해제 금지, 대표 관리자 보호.
- 신규 엔드포인트 1개, 기존 조회·변경 계약 보강. 사업 결정 3건 확정 후 Stage ②로 진행.

### 후속

- 초대 취소·발송 이력 전체 조회·일괄 초대/역할 변경·예약된 권한 이전·세분화된 관리자 권한.
- 대규모 기관의 서버 페이지네이션·서버 그룹핑. MVP는 기존 목록 기반 필터로 시작하고 규모 상한은 Plan에서 측정한다.
- 기관 소속만 정지하는 기능은 계정 정지와 별도 설계. MVP에서 이름만 바꾸어 전역 정지를 숨기지 않는다.

## 5. API 계약 — 존재와 보강 구분

경로는 `org.py`의 `/org` 라우터 기준이며 서버 공통 API 접두사는 생략한다. 아래는 코드 존재를 확인한 것이며 실행 검증을 뜻하지 않는다.

| 구분 | 메서드·경로 | 용도 / 필요한 변경 |
|---|---|---|
| 기존·확장 | GET `/org/{org_id}/counselors` | 두 역할 목록·초대 상태·만료 시각 제공. `is_primary_admin`, 기관 내 `class_count`, `last_activity_at`, 변경 가능 행동/차단 사유 추가. 계정 상태와 소속 상태 분리. 집계 N+1 방지 |
| 기존 | POST `/org/{org_id}/counselors/invite` | name/email/role, 코치·관리자 모두 지원. 기존 계정 여부 비노출 응답 유지 |
| 기존 | POST `/org/{org_id}/counselors/{user_id}/resend-invite` | invited 대상 재발송, 만료·쿨다운 처리 |
| 기존·보강 | PUT `/org/{org_id}/counselors/{user_id}` | role/reason. 자기 자신 강등 차단, 기관 membership 기준 응답, 동시 요청 시 마지막 관리자 보호 |
| 기존 | GET/PATCH `/org/{org_id}/counselors/{user_id}/profile` | 정보 조회/수정, 사유·감사·알림. 이메일 변경 불가. 관리자 개인정보 편집 제외 |
| 기존·보강 | POST `/org/{org_id}/counselors/{user_id}/suspend` | 전역 계정 정지. MVP는 다기관 소속 대상 차단 및 진행 회차 정리 전 차단을 제안. 서버 가드 필요 |
| 기존·보강 | POST `/org/{org_id}/counselors/{user_id}/unsuspend` | 전역 재활성. 다기관 대상의 기관 관리자 재활성도 차단하고 플랫폼 관리로 연결 |
| 기존·확장 | GET `/org/{org_id}/counselors/{user_id}/activity` | 현재 host_id 조회에 org 범위 필수 추가. 담당 클래스/회원 메타데이터를 동일 응답에 추가 |
| 기존·보강 | DELETE `/org/{org_id}/counselors/{user_id}` | 계정 삭제 아닌 소속 해제. 자기 자신 보호, 사유 입력 계약 보강. 진행 세션·활성 연결 가드 재사용 |
| 기존 | GET `/org/{org_id}/requests` | 기관에 접수된 가입 요청 목록 |
| 기존 | PUT `/org/{org_id}/requests/{req_id}` | 승인/거절. 기존 status/reason 스키마 사용, 이미 처리된 요청 재검증 |
| 신규 1 | PUT `/org/{org_id}/primary-admin` | 기존 활성 관리자로 대표 이전. `target_user_id`, `expected_primary_admin_id`, `reason`, `If-Match` 기관 버전 |

### 대표 이전 신규 계약

- 선택: 현재 대표 관리자만 실행, 플랫폼 관리자의 복구 기능은 별도. 근거: 일반 관리자의 기관 통제권 이전을 제한한다.
- 새 대상은 해당 기관의 활성 org_admin이어야 한다. 초대 대기·정지·탈퇴 대상과 자기 자신을 대상으로 한 이전은 거절한다.
- 기관 행 잠금 안에서 현재 대표·버전·대상 자격 재확인, primary_admin_id 갱신·감사 이력 저장을 한 트랜잭션으로 처리한다.
- 403 권한 부족, 404 기관 내 대상 없음, 409 보호 조건 충돌, 412 버전 변경, 422 사유/형식 오류, 428 버전 누락.
- 200 응답: 기관 ID·대표 ID·갱신 버전. 이전 대표는 일반 관리자로 남고 권한 회수는 별도 행동이다.
- 개인상담소 소유자 이전은 이 기능 범위 밖. 기관 kind=individual이면 차단한다.

## 6. 권한·감사·알림

| 행동 | 기관 관리자 | 현재 대표 | 코치 |
|---|---|---|---|
| 기관 내 조회·코치/관리자 초대·가입 요청 처리 | 허용 | 허용 | 불가 |
| 다른 코치 승격 / 다른 일반 관리자 회수 | 허용(보호 조건) | 허용(보호 조건) | 불가 |
| 자기 자신 회수·소속 해제 | 불가 | 불가 | 본 화면 불가 |
| 대표 이전 | 불가 | 허용 | 불가 |
| 코치 개인정보 수정 | 허용(기존 대상 제한 유지) | 허용 | 본인 설정만 |

- 서버가 매 요청 active org_admin membership을 검사한다. 화면 버튼 숨김만으로 권한을 대체하지 않는다.
- 권한 회수 시 다음 요청부터 접근 거절. 다른 기관 role과 소속은 변경하지 않는다.
- 감사: 기관·행위자·대상·행동·이전/이후 역할·시각·사유·요청 식별자를 남긴다. 개인정보 원문·토큰을 일반 로그에 넣지 않는다.
- 사유 필수: 역할 회수/지정, 대표 이전, 정지/재활성, 소속 해제, 개인정보 수정, 가입 거절.
- 초대/재초대는 메일, 역할/대표/상태 변경은 대상자 인앱 알림. 대표 이전은 양쪽 대상자에 통지한다. 발송 실패는 변경 성공과 분리하고 재시도 상태를 표시한다.
- 메일은 서비스 기능 범위다. 이번 기획·시안 작업에서 테스트 메일도 발송하지 않는다. 구현 검증은 발송 대역으로 수행하고 실제 발송은 별도 승인한다.

## 7. 보호 조건과 엣지

- 다중 기관: 역할은 현재 기관 membership만 바꾼다. 활동·담당 회원·클래스는 현재 기관으로 제한한다. 타 기관 이름·회원 정보를 노출하지 않는다.
- 정지: 현재 구현은 전역 계정 정지다. 선택: MVP에서 다기관 대상은 차단하고 플랫폼 관리로 안내. 단일 기관이라도 진행 회차가 있으면 담당 변경/종료 후 재시도한다. 예정 명상 회차 재배정 처리는 기존 로직을 보존한다.
- 소속 해제: 진행·예정·대기 세션/활성 회원 연결 보호가 있으나 일부 예정 명상 회차는 재배정으로 넘긴다. 다른 기관까지 host_id로 차단하는 현재 범위는 Plan에서 기관 기준으로 검증·보강한다.
- 개인상담소: 기존 자동 개설 및 마지막 기관 이탈 시 복귀 정책을 재사용한다. 다른 active 소속이 남아 있으면 기존 소속을 유지한다. 개인 기관 소유자는 역할 변경/소속 해제를 차단한다.
- 마지막 관리자: 활성 계정 + 활성 관리자 membership 기준으로 계산. 동시 강등/정지/해제 모두 기관 잠금 아래 최소 1명을 보존한다.
- 자기 자신: 대표 여부와 무관하게 권한 회수·소속 해제·정지 차단. 현재 change_counselor는 대표 보호는 있으나 일반 관리자 본인에 대한 명시적 차단이 없어 보강 대상이다.
- 초대 만료: pending + expires_at 경과만 만료. 시각 미제공은 ‘만료 정보 없음’으로 표시하고 임의 만료 처리 금지. 쿨다운 중 재발송 비활성, 실패 시 기존 초대 상태 유지.
- 대기 초대자의 역할 변경은 허용하지 않는다. 역할 선택 오류는 후속 초대 취소 정책이 마련되기 전 운영 절차로 처리한다.
- 빈 목록/검색 결과 없음/조회 실패를 구분하고 오류에는 재시도를 제공한다. 중복 제출을 막고 성공 후 목록·요약을 재조회한다.

## 8. 수용 기준 — Stage ③ 작성의 입력

1. 대시보드에는 초대 입력·재발송·권한 변경 버튼이 없고 요약 링크가 해당 구성원 탭을 연다.
2. 코치/관리자/초대/요청 4개 탭이 동일 기관 맥락을 유지하며 이름·이메일 검색, 상태 필터, 그룹핑이 함께 작동한다.
3. 1440px에서 사이드바는 216px, 본문은 x=288~1353, 상단 제목은 31px이다. 390px에서 표가 카드로 바뀌고 상태 칩은 한 줄이다.
4. 두 뷰포트에서 페이지 가로 넘침·텍스트 잘림·동작 요소 겹침이 없고 일반 텍스트 대비가 4.5:1 이상이다. 키보드로 탭·모달 진입/복귀가 가능하다.
5. 관리자 초대는 role=org_admin으로 전달되고 기존 계정 존재 여부를 다른 문구로 노출하지 않는다. 만료 초대 재발송/쿨다운/메일 실패를 구분한다.
6. 자기 자신, 대표, 마지막 활성 관리자에 대한 금지 행동은 직접 API 요청에서도 거절되고 데이터가 바뀌지 않는다. 동시 요청에서도 관리자 1명을 남긴다.
7. 대표 이전은 기존 대표만 실행하며 stale 버전·대기 대상·비소속 대상을 거절한다. 이전 대표 역할은 org_admin으로 유지한다.
8. 두 기관 소속 코치의 역할을 바꿔도 다른 기관의 역할·활동·담당 정보가 바뀌거나 노출되지 않는다.
9. 코치 프로필의 성별·생년월일·전화·주소 수정은 사유·감사·대상자 알림을 남기며 이메일은 변경할 수 없다.
10. 다기관 대상 정지/재활성, 진행 회차가 있는 대상 정지는 차단 사유를 표시한다. 소속 해제는 이관 조건과 개인상담소 복귀를 각각 검증한다.
11. 가입 요청 승인/거절은 기관 소속 관리자만 가능하고 중복 처리·타 기관 요청을 거절한다.
12. 시안은 합성 데이터만 쓰며 서버 요청·메일·DB 변경이 발생하지 않는다. 제품 검증과 시안 검증을 별도로 보고한다.

## 9. 리스크와 대표 결정 — 최대 3건

**대표 결정 확정 (11/9)**

1. **대표 이전**: 대표 관리자만 실행한다. 이전 후 기존 대표는 일반 관리자로 바뀐다.
2. **코치·관리자 상태**: 기관 관리자는 자기 기관 **소속 해지**와 **재초대**만 할 수 있다. 계정 **정지·재활성은 기관 관리자 권한에서 제거**한다(다기관 여부 무관) — 당사자 본인 또는 플랫폼 관리자만 결정한다. 기존 `org.py` 정지/활성화 엔드포인트의 기관 관리자 허용을 막는다.
3. **관리자 권한 범위**:
   - 일반 관리자: 코치 초대, 다른 관리자 초대(재발송 포함) **가능**.
   - 일반 관리자: 코치→관리자 **승격 불가**, 관리자 권한 **회수 불가**.
   - 승격·회수는 대표 관리자만 실행한다(결정 1과 같은 기준).

| 행동 | 대표 관리자 | 일반 관리자 | 플랫폼 관리자 |
|---|---|---|---|
| 코치 초대·재초대 | ✅ | ✅ | ✅ |
| 관리자 초대·재초대 | ✅ | ✅ | ✅ |
| 소속 해지(코치·관리자) | ✅ | ✅ (관리자 해지는 대표만, 자기 자신·대표 해지 불가) | ✅ |
| 코치→관리자 승격 | ✅ | ❌ | ✅ |
| 관리자 권한 회수 | ✅ | ❌ | ✅ |
| 대표 이전 | ✅ | ❌ | ✅ |
| 계정 정지·재활성 | ❌ | ❌ | ✅ (본인 탈퇴/휴면은 본인) |

- 화면: 일반 관리자에게는 승격·회수·대표 이전·정지 버튼을 노출하지 않는다(숨김, 비활성 아님). 서버도 같은 기준으로 403.

- 기술 리스크: 전역 User.role/상태와 membership 혼용, 활동 조회 기관 필터 누락, 일부 API 응답의 membership 미전달, 감사와 알림의 트랜잭션 분리가 있다. 구현 전 Verify에서 각각 회귀 시나리오로 다룬다.
- 확인 한계: 인증 후 미리보기와 실제 API 동작은 미검증. GET 제한 때문에 로그인 요청은 실행하지 않았다. 비교 PNG의 실제 화면은 로그인 페이지이며 기관 화면과의 직접 시각 정합은 추가 확인 대상이다.
