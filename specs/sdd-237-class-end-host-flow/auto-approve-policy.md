# SDD-237 — 자동 승인 정책 개편 — C안 결정

- 작성: 2026-10-23. **10/23 C안·유예 기본 10분 채택. 제품 구현·운영 정책 전환은 미실행**이다.
- 연계: [회차 요약 기획](spec.md), [시안 안내](../../designs/class-end-host-flow/README.md).
- 근거는 이 워크트리의 제품 코드 정적 확인이다. 서버·DB·환경파일·실사용자 데이터·메일 전송은 확인하지 않았다. 아래 필드·유예시간·상태는 명시한 현행 이외에는 신규 제안이다.

## 1. 결정과 범위

**10/23 결정: 상담/명상 영역별 자동 승인 켜기와 유예 시간 선택을 제공하는 C안을 채택한다. 유예 기본값은 10분, 선택지는 0·5·10·30분이다.** 0분이면 해당 리포트 준비·조건 충족 즉시 자동 승인한다. 즉시 승인 시점은 현행과 같지만, 비공개 메모 자동 초안 제외·데이터 없는 리포트 자동 승인 제외는 새 정책이다.

유예는 **메일만 늦추는 기능이 아니라 승인 자체를 늦추는 기능**이다. 유예>0일 때만 예정 시각과 [이번 회차 보류]를 제공한다. 0분 회차 요약에는 ‘자동 승인 즉시 적용’만 표시하고 보류 버튼을 두지 않는다. 승인 전에는 회원 본문 공개·알림·AI 대화·메일을 시작하지 않는다. 미착용은 정상 참여이며 조건 미충족은 수동 검토로 안내한다.

신규 계정은 양쪽 모두 수동 승인으로 시작하고, 켜진 자동 승인의 유예 기본값은 10분으로 설계한다. 기존 켜짐/꺼짐은 보존한다. 설명·적용 시점 기록 후 미래 회차에 새 정책을 적용하고, 과거/진행 중 작업 소급 변경·일괄 승인·재발송은 하지 않는다. 아래 이관 필드·구현 구조는 후속 plan/verify에서 검증할 기술 제안이다.

**제외·파기·이메일 미보유를 ‘모든 알림이 차단됨’으로 묶어 설명하면 부정확하다.** 이메일 미보유 회원도 인앱 알림 대상이 될 수 있다. 새 정책에서는 제외·파기 참여자에 대한 승인 대상 선별과 모든 부수효과의 마지막 검사를 일관되게 설계해야 한다. 현행에 실제 개인정보 노출이 발생했다는 주장이나 운영 검증은 아니다.

### 2.1 공개 코멘트와 비공개 기록의 경계

- 공개 코멘트는 `Report.content.counselor_comment`. 수동 AI 초안 API는 초안/source를 반환하며 저장하지 않는다. 편집 저장은 pending_review에서만 가능하다(`report_comment_service.py:43–72`).
- 자동 승인에서는 client 코멘트가 비어 있으면 Gemini 초안을 생성·저장한다. 기존 글은 보존한다. Gemini 실패·키 부재·타임아웃은 규칙 템플릿으로 대체하며, 예외도 승인 자체를 막지 않는 best-effort이다(`report_comment_service.py:75–96,213–233,284–289`).
- **비그룹의 초안 입력에는 AI 요약과 비공개 counselor_notes가 포함될 수 있다.** 그룹 및 리포트 제외 참여자는 공통 메모·요약을 제외한다. 본인 EEG narrative(valid/degraded)는 선택 입력이다(`report_comment_service.py:139–173`).
- ‘내부 메모 원문 인용 금지’는 프롬프트 지시일 뿐 내용의 의미가 공개 초안에 섞이지 않는다는 보장이 아니다(`report_comment_service.py:177–209`). 상담 기록을 ‘참여자에게 직접 표시되지 않는 기록’이라고 설명하되, AI 초안 소재 사용과 자동 전달 가능성을 숨기지 않아야 한다.
- client 본문 생성기는 counselor_notes를 직접 넣지 않고 counselor 본문에만 넣는다(`report_task.py:366–407`). **직접 원문 필드 제외와 AI를 통한 간접 사용을 구분한다.** 공개 메일용 보기에는 counselor_comment가 렌더된다(`report_email_service.py:373–383`).

### 2.2 EEG·AI 기록이 모두 없는 경우

현행 UI는 EEG 없음 + ai_record.not_available이면 ‘측정 데이터가 없습니다. 코멘트를 작성해 내담자에게 전달해 주세요’를 표시한다(`ReportDetailView.tsx:242–245`, `CounselorCommentCard.tsx:104–110`). 이는 수동 편집 안내이지 자동 승인 차단 조건이 아니다.

서버의 자동 승인 조건에는 데이터 충분성·공개 코멘트의 수동 확인·유예시간 검사가 없다. 따라서 무데이터여도 생성 결과가 pending_review이면 기존 공개 코멘트가 사용되거나 AI/규칙 초안이 보완되고 승인·전달 경로에 들어갈 수 있다. 내부 메모가 있어야만 발송되는 것도 아니다. **‘데이터 없음 → 상담사가 반드시 작성 → 승인’은 현행 정책이 아니다.** STT off도 자동 승인 off를 뜻하지 않는다.

## 3. 대안 비교

| 안 | 상담사 경험 | 리스크·개인정보 | 구현 범위(DB·마이그레이션 포함) | 기존 사용자 영향 |
|---|---|---|---|---|
| A. 상담/명상 분리 | 두 영역에서 수동/기존 즉시 자동을 각각 선택. 이해와 운영이 가장 단순 | 상담을 수동으로 고를 수 있으나 켜진 영역의 AI 비공개 내용 혼입·즉시 발송 위험은 남음 | User에 영역별 mode 2개, 정책 API/목록 UI, 모든 자동 승인 호출 통합. 기존 bool을 두 영역에 동일 복사 | true는 둘 다 기존 즉시 자동, false는 둘 다 수동. 이관 자체는 행동 변화 없음. 신규/변경분 적용 시점 안내 필요 |
| B. 클래스별 재정의 | 계정 기본 + 클래스별 상속/수동/자동. 클래스 성격별 운영에 유리 | 진행자 교체·공동 강사 때 누구 설정인지 혼동. 클래스에는 없는 1:1 상담은 별도 필요. 자동 켜진 클래스의 즉시 공개 위험은 남음 | A + Class override 컬럼, 설정 권한·감사 이력·우선순위·세션 snapshot. 기존 Class는 inherit. 상담 관계 override는 별도 범위 | 기존 클래스 inherit으로 보존. 계정 기본 변경의 확산, 담당자 교체 영향 안내 필요. 재발송 없음 |
| **C. 영역 분리 + 조건부·유예 선택(채택, 기본 10분·옵션 0/5/10/30)** | A에 ‘조건 확인 후 자동 승인’ 선택. 회차 요약에서 즉시 적용 또는 유예>0의 기한·보류 확인. 양수 유예를 선택하면 검토 시간 확보 | 유예를 놓치면 공개됨. 큐 중복/중단과 보류 경합 처리 필요. 비공개 메모 제외·코멘트 출처를 함께 다뤄야 의미 있음 | A + 정책 version/유예시간, 회차 snapshot, report별 예약·보류·조건 사유·revision, 실행 worker/outbox·감사 이력·멱등성 | 기존 즉시 자동을 강제 전환하지 않음. 새 C 모드는 명시 선택 이후 미래 회차만. 과거/진행 중 작업 소급 변경·재발송 없음 |

채택 이유: A는 필수 기반이고, C는 상담 민감정보와 종료 직후 오발송을 다룰 구체적 통제 수단을 제공한다. B는 다중 강사 우선순위·권한 비용에 비해 이번 회차 요약 문제에 필수적이지 않아 후속으로 둔다. 수동 승인만으로 충분한 상담사는 C를 켤 필요가 없다.

## 4. 채택 C안 상세 계약 (정책 결정 반영, 구현 구조는 제안)

### 4.1 정책 모드와 자동 승인 조건

- 영역별 자동 승인 켜기/끄기와 `delay_minutes` 0·5·10·30을 제공한다. 기본 유예는 10분이다. 내부 모드 `manual | legacy_immediate | guarded_delay`는 구현 제안으로, legacy는 전환 전 현행 설명용이며 설정 UI의 선택지로 노출하지 않는다. 신규 기본은 manual, guarded_delay는 0분도 지원한다.
- 영역은 참가자 수/성별/이름이 아니라 서버 도메인으로 결정. 현행 class_id 없는 레거시 세션의 counseling 분류를 이관 때 보존하고 모호한 건은 신규 자동 예약하지 않는다.
- 타이머 시작은 세션 종료가 아니라 **해당 리포트의 생성 종료와 조건 충족이 확정된 시점**. 기본 10분이면 즉시 승인, 10분을 선택하고 준비 14:00이면 승인 예정 14:10. ‘10분 후 메일 도착’이라는 도달 시간 보장은 하지 않는다.
- 대상은 client이며 participant 포함·미파기·대기열 아님·권한 유효, report pending_review. 처리 중·생성 실패·불명·EEG degraded/invalid/insufficient/lost 등 경고는 검토 대기. 다른 참여자의 결과로 조건을 대신 충족하지 않는다.
- **데이터 없는 리포트는 자동 승인에서 제외한다.** AI/규칙 인사 초안이나 수동 공개 코멘트만으로 이 제외 조건을 우회하지 않는다. 무데이터도 공개 코멘트 작성 후 **수동 승인**으로 전달할 수 있으며 내부 기록은 필수가 아니다. 데이터가 있는 결과의 세부 유효 조건은 후속 verify에 고정한다. 본인 EEG `valid`·생성 완료를 기본 검증 사례로 두며 품질 경고가 있으면 수동 검토한다.
- STT 정책 생략 자체를 장애로 보지 않는다. generation_status=partial만 보고 일괄 거부/허용하지 않고 실제 사유를 검사한다. AI 요약이 있다는 이유만으로 상담 민감정보가 안전하다고 판정하지 않는다.
- 공개 코멘트가 필요한 경우 생성 결과/source와 사람이 확인했는지를 별도 저장한다. 신규 guarded_delay의 **자동 생성 초안에는 비공개 counselor_notes를 입력하지 않는다(10/23 결정)**. 기존 legacy 경로는 설명 없이 바꾸지 않으며, 신규 모드 동의에서 차이를 명확히 안내한다. 수동 초안의 내부 기록 참고 여부는 명시 선택 후 사람이 검토하는 후속 범위로 분리한다.
- 자동 필터만으로 비공개 의미 유출을 100% 검출한다고 약속하지 않는다. 비공개 입력 제외·참여자 격리·정해진 공개 입력 사용을 먼저 보장하고, 출처 불명 코멘트/이전 내부 메모 기반 초안은 guarded_delay에서 수동 검토한다.

### 4.2 보류·동시성·이메일

- 0분은 조건 확인 후 `eligible → approved`, 유예>0은 `eligible → scheduled → approved` / `scheduled → held` / `scheduled → review_required`를 서버에서 관리한다. 실제 report.status는 승인 전까지 pending_review를 유지하고 별도 예약 상태를 둔다.
- 유예>0일 때만 제공하는 [이번 회차 보류]는 **아직 승인되지 않은 예약만** 회차 범위로 취소/보류한다. 단건 보류도 제공. 보류 후 자동 재개하지 않으며 [직접 검토] 또는 확인 후 [다시 예약]을 선택한다. 다시 예약하면 현재 시점부터 전체 유예시간을 부여한다.
- 저장 성공 전에 보류됨을 표시하지 않는다. 실행 worker와 보류 요청은 같은 report 행 잠금/버전 비교로 직렬화하고, 먼저 승인 완료된 건은 ‘이미 승인되어 보류할 수 없음’과 실제 결과를 반환한다. 발송된 메일을 회수했다고 표시하지 않는다.
- 코멘트/본문 변경, 재생성, 참가자 제외/파기, 권한 변경은 예약 revision을 무효화한다. 이전 큐 메시지는 no-op, 다시 조건 검사 후 새 예약. 보류 상태는 자동 재생성으로 풀리지 않는다.
- 서버 재시작·지연·재시도에도 영속 예약을 읽고 조건/권한/제외·파기를 재검사한다. report + revision 유일 실행 키와 트랜잭션 outbox 등으로 승인 부수효과 중복을 방지한다. 브라우저 countdown이나 Celery ETA 하나만으로 정책을 구현하지 않는다.
- 승인 시 기존 알림/메일/AI 훅을 재사용하되 제외·파기 검사를 각 전달 직전에 보강한다. 메일 수신 주소가 없으면 이메일만 건너뛰며 승인/인앱 전달과 구분한다. 지연 중에는 아직 미승인이므로 기존 회원 본문 마스킹 유지(`report_service.py:266–283`).
- [지금 승인]은 리포트 상세의 공개 내용 확인 후 단건 명시 승인으로만 허용한다. 계정 전체 approve-all을 회차 요약에서 호출하지 않는다.

### 4.3 데이터 구조·이관·호환

| 대상 | 제안 필드/변경 | 이관·검증 원칙 |
|---|---|---|
| User | meditation/counseling approval_mode, delay_minutes, policy_version, policy_selected_at | old bool=true → 두 영역 legacy_immediate, false → 두 영역 manual. 새 C안 유예 기본 10분·옵션 0/5/10/30. 기존 legacy는 전환 전 보존용 |
| Session 정책 snapshot | domain, mode, delay, version, host_id, captured_at | 신규 회차 시작 시 snapshot(설정 변경은 시작 전 회차부터). 기존 진행/완료 회차에 새 타이머를 만들지 않음 |
| Report 예약 | state, due_at, held_at/by, eligibility_reason, content_revision, policy_version | 기존 행은 예약 없음. completed·sent_at·approved_at·participant 발송 이력 불변. 임의 백필 승인/발송 없음 |
| 감사/작업 | 정책 변경·회차 보류 이력, report/revision 유일 키, 영속 작업/outbox | 누가 무엇을 변경했는지 기록, 코멘트 원문·이메일·토큰은 감사 로그에 복제하지 않음 |
| API/클라이언트 | 영역별 설정, 현재/미래 적용 범위, 회차 예약/보류, 실제 실행 시각 | 구 enabled API를 둔 채 새 분리 설정을 덮어쓰게 두면 안 됨. 전환 후 구 쓰기는 명시적 업데이트 필요 오류 또는 버전 협상으로 차단; 구 클라이언트 읽기는 모호한 상태를 false로 꾸미지 않음 |

마이그레이션은 additive로 시작하고 기존 컬럼을 즉시 삭제하지 않는다. 모든 생성 경로(단건 직접 bool 검사 포함)가 동일 resolver를 쓰도록 통합하는 구현 계획·사전 검증이 필요하다. DB 이관은 정책값/새 예약 없음만 바꾸며 메일/알림 함수를 호출하지 않는다. 롤백 시 신규 예약을 보류하고 조용히 즉시 자동으로 되돌리지 않는다. 기존 앱 버전·worker 혼재를 포함한 배포 순서는 구현 plan에서 확정한다.

## 5. 회차 요약·설정 화면 UX

| 위치/상태 | 표시·행동 |
|---|---|
| 회차 요약 · 유예 0분 | ‘자동 승인 즉시 적용’만 표시. 예정 시각·countdown·보류 버튼 없음. [승인 설정]은 다음 회차부터 바꿀 설정으로 이동 |
| 회차 요약 · 유예>0 | 선택한 유예와 승인 예정 시각 + [이번 회차 보류]. 10분은 기본값이며 리포트 준비·조건 충족 후부터 계산 |
| 생성 중 | ‘생성 완료 후 조건을 확인합니다. 아직 승인 예약 없음.’ 유예 시작 전 countdown 금지 |
| 예약 중 · 유예>0 | ‘자동 승인 예정 14:10 · 2명 / 검토 필요 1명’ + [이번 회차 보류] [참여자 결과 확인]. 서버 due_at 및 최신 갱신 시각 표시 |
| 무데이터/경고 | ‘직접 확인이 필요한 리포트가 있어요’ + 대상·구체 사유. 미착용을 실패/0점으로 표기하지 않음 |
| 보류 후 | ‘이번 회차 자동 승인 보류 · 아직 승인되지 않은 2건’ + [직접 검토]. 이미 승인된 1건은 별도 표시 |
| legacy | ‘기존 즉시 자동 승인 적용 · 준비된 결과는 바로 승인될 수 있어요’ + [정책 비교/설정]. 현재 회차도 10분 보호되는 것처럼 표시 금지 |
| 승인 완료 | ‘승인됨’과 ‘이메일 대기/발송/실패/주소 없음’을 별도 표기. 설정 변경으로 취소·재발송되지 않음 |
| 설정 화면 | 상담/명상 각각 자동 승인 켜기 + 유예 0·5·10·30분 선택(기본 10분). 데이터 없는 리포트 자동 승인 제외·비공개 메모 자동 초안 제외 안내. 진행 기록 안내 끄기 제공. [변경 내용 확인]에 기존→새 모드와 적용 시작(이후 시작 회차)을 명시 |
| 권한/실패 | 조회 권한과 설정/보류 권한 분리. 진행자 본인 계정 설정만 수정. 클래스 주강사 대행 승인 권한이 타인 계정 설정 변경 권한이 되지 않음. 실패 시 이전 서버 상태·재시도 표시 |

시안의 설정 저장·보류는 합성 상태 전환만 한다. 회차별 전체 policy override는 B안의 범위이므로 채택 시안에는 넣지 않는다. C안의 이번 회차 보류는 pending 예약을 중단하는 안전 조작이며, 계정 설정이나 완료 건을 바꾸지 않는다.

## 6. 구현 전 수용 기준

- [ ] 기존 true/false를 영역별로 동일하게 이관하며 기존 승인·메일 이력과 진행 중 작업을 변경하지 않는다. 이관 자체의 알림/발송은 0건이다.
- [ ] 새 정책 명시 선택 및 적용 시점이 기록된다. 페이지 진입·설정 조회로 예약/승인/메일이 실행되지 않는다.
- [ ] 단건·회차 생성 등 모든 자동 승인 진입이 같은 정책을 사용한다. 인원 1명의 명상을 상담으로 오분류하지 않는다.
- [ ] 무데이터(수동 코멘트가 있어도 자동 승인 제외), 데이터 경고, 내부 기록 출처 불명 코멘트는 자동 조건 미충족. 내부 기록을 쓰지 않아도 수동 공개 코멘트와 승인 가능.
- [ ] 신규 자동 초안에서 비공개 메모와 타 참여자 데이터가 입력·출력되지 않는다. 상담/그룹 각각 입력 spy 및 공개 응답 검증.
- [ ] 서버 시간·재시작·지연·중복 작업·보류/승인 경합·내용 수정/revision·권한 변경을 테스트한다. 승인 전 본문은 회원에게 비공개.
- [ ] 제외·파기 참여자는 자동 승인/공개/알림/메일/AI 부수효과에서 제외. 이메일 미보유와 게스트의 인앱/이메일 차이를 검증한다.
- [ ] 보류/설정 변경은 이미 승인·발송된 결과를 취소하거나 재발송하지 않는다. 회차 범위 밖 결과를 변경하지 않는다.
- [ ] 기본 10분·옵션 0/5/10/30, 영역별 켜기, 0분 보류 미노출·양수 유예 예정 시각/보류, 진행 기록 안내 끄기를 검증한다.
- [ ] 자동 승인와 실제 이메일 전달 성공을 독립적으로 표시한다. 화면은 390/1440, 13px 이상·조작 44px 이상 유지.

## 7. Brian 결정 기록 (2026-10-23)

1. **C안 채택:** 상담/명상 영역별 자동 승인 켜기와 조건부 자동 승인. 클래스별 B는 후속.
2. **유예 기본 10분·옵션 0/5/10/30분:** 0분은 ‘자동 승인 즉시 적용’만 표시하고 보류 버튼 없음. 유예>0만 승인 예정 시각과 [이번 회차 보류].
3. **콘텐츠 조건:** 비공개 메모는 자동 초안 제외, 데이터 없는 리포트는 자동 승인 제외. 수동 검토·승인은 가능.
4. **진행 기록 안내:** 설정 화면에 전체 안내 끄기 제공. 자동 승인 설정·기존 기록에 영향 없음.

이번 작업의 완료는 문서·시안 갱신이다. 정책 코드·DB 마이그레이션·예약 worker·메일 동작은 구현하지 않는다.
