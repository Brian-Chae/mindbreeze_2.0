- 배포된 BE SHA, dev DB head, cron 설치, 실제 알림/LiveKit 결과는 미확인.

## 2. 첫 번째 출시 — BE

1. 실제 배포 직전 DB head가 055인지 확인한다. 다른 head면 적용하지 않고 단일 체인을 먼저 맞춘다.
2. 세 스위치를 모두 off로 둔다: `CLASS_SCHEDULING_ENABLED`, `CLASS_ROLLING_ENABLED`, `CLASS_TEAM_READ_ENABLED`.
3. BE 앱과 056 가산 스키마를 배포하고 같은 이미지에서 `alembic upgrade head`를 실행한다. 056은 자동 downgrade로 이력을 삭제하지 않는다.
4. 인증·기존 상담 생성·클래스 읽기·D-28·리포트 승인을 실제 dev에서 확인한다.
5. 편성 스위치를 켜고 합성 8회 생성·편집·강사 변경·소속 해제·기존 명상 생성 우회 차단을 점검한다. 구 FE 명상 생성은 이 시점에 클래스 편성 API로 교체되어야 하므로, BE 출시 점검 후 FE 출시까지 일반 사용자 편성 진입은 노출하지 않는다.
6. 배포 산출물에 포함된 서버 작업 두 개의 설치·실행을 확인한다. 실제 설치는 이번 작업에서 수행하지 않았다.
   - 매분: backend 작업 디렉토리·운영 Python에서 `python class_operations_cron.py`.
   - 매시: `python class_rolling_cron.py`. 함수 내부에서 KST 02시에만 생성하며 두 스위치가 모두 on이어야 한다.
   - dev: `deploy-dev.yml` 번들에 진입점 두 파일을 포함하고 `flock -n -E 0`으로 중복 실행을 막는 crontab 두 행을 등록한다. 등록 과정은 세 스위치를 켜지 않는다.
   - 운영: `deploy/jobs.tsv`의 활성 timer 17개에 두 작업을 포함한다. `env-manifest.tsv`는 스위치 세 개를 선택 SSM 값으로 읽으며 미지정은 앱 기본 false다.
   - dev의 실제 환경 파일 선택(`.env` 우선, 없으면 `.env.dev`)과 프로세스가 읽는 세 스위치 값을 확인한다. 시크릿 전체를 출력하지 않는다.
   - 기존 notification outbox/리마인더/push 소비자도 실행 중인지 확인한다. 스크립트 파일 존재만으로 예약 작업이 등록된 것으로 판정하지 않는다.
7. 새 세션의 effects가 정상 소비되는지 확인한 뒤 rolling 스위치를 켠다. 요청 만료·72h/24h·종료일·동일 작업 재실행을 확인한다.
8. 실패 시 편성/롤링/팀 스위치를 끈다. dev 자동 복귀는 배포 전 클래스 cron 두 행과 진입점 두 파일을 함께 복원한다. 배포 도중 추가된 다른 cron은 유지한다. 가산 스키마를 유지하고 호환 앱으로 복구한다. 테스트 데이터 전제가 실데이터 삭제 허용을 뜻하지 않는다.

### 실행 전 권한·대상 확인

- 최초 지시의 push·배포·머지 금지를 유지한다. 감독자 추가 지시에 따라 push는 감독자가 담당하고 이 워커는 자기 파일만 명시적으로 stage해 로컬 커밋한다. 실제 dev 반영 범위는 감독자가 확인한다.
- 현재 `Deploy Dev` 워크플로는 기존 FE 빌드도 함께 배포한다. 현재 인계에는 FE 제품 코드도 포함된다. 이를 BE 전용 배포라고 보고하지 않는다. 1차 출시는 BE 기능 출시이며 배포 대상 FE SHA·빌드도 함께 확인한다.
- 실제 반영 시 대상 브랜치·SHA·dev 서버와 동시 배포 유무를 확인한다. `workflow_dispatch` 주석의 “항상 develop”과 달리 checkout의 ref는 고정돼 있지 않으며 concurrency 그룹은 ref별이다. 다른 ref와 동시에 dev 배포하지 않는다.

## 3. 두 번째 출시 — FE

- FE 코드는 로컬 통합됐고 사용자 확인을 거쳤다. 실제 FE 기능 출시는 BE 준비 확인 후 진행한다. dev 반영 여부는 아직 미확인이다.
- 4단계 편성, 4개 배정 방식, 회차 표/모바일 카드/시트, 강사·주강사·대강·양도, 복제·밀기·보강·최소 멤버십을 연결한다.
- host nullable·class/session ID·`?sessionId=`·operation_key·최신 revision·충돌 fingerprint·push 선호를 실제 HTTP 계약으로 연결한다.
- CH04~06, CH10~15, CH20, CH30의 히어로·사이드바·행 스타일을 시안 기준으로 마감한다. SDD-215의 픽셀 차이 중앙값 59%는 이전 측정이며 이번 UI의 결과가 아니다.
- SDD-215 리플레이를 재사용해 원본/앱/diff/overlay와 4뷰포트 결과를 기록한다. fit 통과만으로 시각 수용 기준을 통과하지 않는다.
- D-05 고지 문구·class-team-v1 저장·회원 기본 제외·연구 선택 분리, D-28 관리 UI를 검증한다.
- 실제 LiveKit에서 참관자의 송출/제어 거절, 제거·정지·고지 조건 변경 후 이미 연결된 참관자 회수, 재접속 거절을 확인한다. WS 단일 워커 전제와 실제 배포 구성을 대조한다. 확인 전 팀 스위치 off.
- BLE 미착용, 실제 모바일/태블릿, 메일·푸시·ETA 전달은 모의 결과와 따로 기록한다.

## 4. 아직 통과로 표시하지 않는 항목

- 실제 BE 배포·dev 마이그레이션·cron 설치/실행.
- 실제 LiveKit·WS 배포 토폴로지·브라우저 참관 제어·회수 지연.
- 실제 메일·푸시·리마인더 전달과 사용자 기기 수신.
- FE 전체 시안 리플레이·실기기·두 번째 출시 검증. 로컬 FE 구현은 summary의 후속 결과를 따른다.
- verify의 79개 행 전체 통과 및 T00~T39 전체 완료. 로컬 테스트 함수 수와 QA 시나리오 수는 다르다.

## 5. dev 반영 승인과 정기 작업 설정 보완 (2026-10-19)

- 사용자 “반영하고 배포해” 지시로 해당 브랜치 push·dev 배포를 승인받았다. 머지는 하지 않는다.
- 구현 전 검증 항목: 두 클래스 cron의 `--dev-env` 실행은 앱 import 전에 같은 디렉터리의 `.env.dev`를 읽는다. `.env`가 함께 있어도 dev 값을 사용한다. 옵션 없는 실행은 기존 환경 값을 유지한다.
- dev cron 등록 명령의 옵션 포함·멱등성·실패 복귀를 격리 테스트한다. 전체 BE 회귀는 로컬에서 실행하지 않는다.
