# dev HRV 재산출 이상 조사 (2026-11-16, 조사만 — 코드·DB 변경 없음)

## 결론
1. **엔진 알고리즘 결함이 아니라 "입력 신호에 맥박이 없는 구간을 재산출 대상에 넣은 것"이 원인이다.** 재산출 예제 엔진(`recompute_ppg_hrv.rs`)은 착용 판정(`WearState`, `engine.rs:368~413`)을 거치지 않고 원시 전체를 `ppg::analyze`에 그대로 넣는다. 라이브 엔진은 미착용 구간을 걸러내므로 **재산출 경로와 서비스 경로의 입력이 다르다.**
2. `1df2153e`: 저장값이 있는 구간(5.8~17.6분)은 IR DC ≈ 6,100, 1~5Hz 교류 성분 표준편차 ≈ 2 카운트의 **잡음**이다. 앞 5분만 실제 착용(DC 142만, 교류 80)이고 그 구간의 저장값은 **전부 null**이다. 61.8→109.2는 "잡음값 → 다른 잡음값"이다(HR 109 고정이 잡음의 징표).
3. 지배 회차 `401d48c5`·`e6523c7a`는 40명 중 맥박 있는 참가자가 **1명**(401의 `3a291e65`)뿐이다. 나머지는 기기가 놓여 있거나 느슨한 상태의 잡음이라, 어느 알고리즘이든 RMSSD가 ≈65~70 근방으로 수렴한다. 재산출 결과가 그대로인 것은 정상 동작이며 "원래 정상값"이 아니다.
4. 감소한 5개 회차 중 맥박 있는 참가자(`2a11d64c`, `d38140c8`, `c44cb210`, `83a39b18`의 1명, `b46d3125`의 1명)의 값은 독립 재계산과 맞는다. 20~60ms까지 안 내려가는 회차는 대부분 잡음 참가자가 섞여서다.

## 수정안 (제안, 적용 안 함)
1. **재산출 도구에 착용 게이트 추가** — `packages/measurement-core/examples/recompute_ppg_hrv.rs:22~30`에서 샘플마다 `WearState::update`(`engine.rs:387`)를 거쳐, 상태가 바뀌면 `ring.clear()` + `hrv`를 `reset_for_not_worn()` 한 뒤 미착용 샘플은 링에 넣지 않는다. 틱은 미착용 구간에서 값을 비워(빈 칸) 내보내 서비스 쪽 "건드리지 않음"으로 연결. 효과: `1df2153e`의 109.2 오염 제거, 미착용 구간 덮어쓰기 0.
2. **신호 품질(맥박) 게이트 추가** — DC 규칙만으로는 DC 31만~88만 잡음을 못 걸러낸다. 재산출 틱 단위로 1~5Hz 교류 성분(영위상 필터 후 표준편차, 창 10초 이상)이 임계(제안 **≥6 카운트**, 관측 잡음 최대 3.0 / 실제 최소 9.6)이고 유효 RR 비율이 일정 이상(제안 ≥50%)일 때만 값을 낸다. 구현 위치: `ppg.rs::analyze` 안(SQI 옆)이 이상적이나 라이브 값이 바뀌므로 먼저 재산출 예제에서만 적용하고 별도 SDD로 라이브 반영 판단.
3. **재산출 시 제외·보류 규칙(서비스)** — `hrv_recompute_service.py`의 `plan_participant`에서 (a) 해당 참가자 전 구간에서 맥박 게이트 통과 틱이 전체의 10% 미만이면 참가자 전체 미변경, (b) 틱 단위 게이트 탈락 윈도우는 기존 값 유지 대신 **기록만 하고 건너뜀**. 별도로 "기존 저장값이 잡음 구간 값"인 창은 덮어쓰지 않으면 저장값(잡음)이 남으므로, 정리는 별도 결정 필요(null 처리는 대표 승인 건).
4. **기존 `--apply` 금지 유지** — 현재 도구로 apply하면 미착용 창 706개(1df 1건 기준)가 109로 덮이고 착용 구간 null은 그대로라 데이터가 오히려 나빠진다.

## 운영 위험
- 잡음 입력이 DC 31만~88만에서도 "착용"으로 통과하는 문제는 운영에도 있다. 밴드를 쓰지 않고 세션만 연 참가자·그룹 수업에서 미착용 밴드가 섞이면 같은 모양으로 RMSSD가 65~70 근방으로 저장·집계된다. 이는 **재산출 도구뿐 아니라 라이브 저장·리포트에도 이미 영향을 주는 상태**로 보이며(dev 저장 중앙 56~146이 이를 반영), 리포트 변화량(전·후반 SDNN ±5ms)에도 잡음이 섞인다.
- 재산출 도구는 apply 전에 위 1~3이 필요하다. 운영 실행은 보류 권고.

## 남은 불확실성
- `1df2153e` 착용 구간 저장값 null의 직접 원인(웹 쪽 게이트/락인/전환 과도기) 미확정. 라이브 원시와 웹 로그가 있어야 재현 가능.
- 83a39b18 맥박 구간의 RMSSD 100~150이 생리적으로 맞는지는 미확인(알고리즘 간 일치만 확인).
- `c44cb210`의 DC 6.3k·교류 9.6 구간은 약한 맥박인지 잡음인지 판단 불가 — 교류 임계 6 근처라 임계 튜닝 필요.
- 독립 재계산은 하네스 원본(`harness*.ts`)이 아니라 같은 정의의 scipy 구현(2차 버터워스 1~5Hz 영위상, 피크 간격 15샘플 이상, 포물선 보간, 300~2000ms, 1분 중앙값 ±25% 게이트)이다. 절대값 비교보다 일치/불일치 판단에 사용.
- 조사 도구: 원시는 읽기만 했고 서버 `/tmp/hrv1116_*`·로컬 스크래치는 삭제했다.
