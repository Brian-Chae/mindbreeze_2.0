# SDD-280 — 시안 v2: 본문 스크롤과 데스크톱 2열

대표 결정인 B안, 오른쪽 회원 목록·왼쪽 폼, 양쪽 화면의 하단 버튼 상시 노출을 반영한 정적 시안이다. 기존 design/ v1을 보존했다. 제품 소스·API·계정 연결 없이 합성 데이터로만 검증한다.

## 비교

| 항목 | B2-1 · 검색은 폼 | B2-2 · 검색은 목록 패널 |
|---|---|---|
| 데스크톱 1024px 이상 | 왼쪽 40% 폼 / 오른쪽 60% 목록 | 왼쪽 38% 폼 / 오른쪽 62% 검색·목록 |
| 겹침 방지 | 본문 `minmax(0,1fr)` + `overflow-y:auto`, 목록 자연 높이 | 동일. 검색은 목록 패널 맨 위의 자연 흐름에 배치 |
| 스크롤 모델 | 본문 한 곳만 스크롤. 목록 내부 스크롤 없음 | 동일. 왼쪽 전체가 가용 높이에 들어갈 때만 sticky; 짧은 화면·칩 12개로 길어지면 자연 흐름 |
| 하단 바 | 화면 grid의 별도 행. 본문과 공간을 분리하고 하단 padding 32px | 동일. 바를 overlay로 띄우지 않아 높이 중복 계산이 필요 없음 |
| 모바일·태블릿 | 1023px 이하 공통 1열, 요약→탭→검색→선택 요약→목록→사유 | 같은 순서, sticky 해제 |
| 빈 목록·짧은 목록 | 목록 패널은 내용 높이만 사용, 나머지는 배경. 왼쪽이 길어도 목록을 억지로 늘리지 않음 | 동일. 좌우 `align-items:start`; 폼이 길 때 sticky 해제로 마지막 사유까지 접근 |
| 비회원 탭 | 검색 숨김, 오른쪽 제목이 ‘입력한 이메일 목록’으로 변경, 이메일 textarea와 입력 목록 표시 | 동일 |
| 구현 난이도 추정 | 중간. 기존 검색·힌트·선택 분리와 데스크톱 grid 필요 | 중간~높음. 검색 패널 이동과 높이 조건 sticky 추가 필요 |
| 변경 파일 추정 | `class-scheduling.css`, `class-scheduling-wizard.tsx`의 4단계, `components/class/structure/class-member-picker.tsx` | 동일. picker의 검색·선택·목록 영역 분리 또는 slot 설계 추가 |
| 기존 일관성 | 폼에 검색을 유지해 현재 입력 흐름과 가까움 | 검색과 결과를 같은 패널에 묶음. 보라색·반경·행·마스킹 이메일은 기존 표현 유지 |
| 위험 | 검색을 변경할 때 결과가 다른 열에 있어 연결이 약할 수 있음 | 반응형 재배치 시 DOM 순서·포커스 이동을 추가 검증해야 함. 높이 조건 sticky 로직 필요 |

**우선안: B2-2.** 검색 입력과 그 결과를 같은 패널에 두고, 가로 화면에서 62%를 목록에 배정한다. 본문 스크롤은 한 곳이며 검색 패널과 행은 겹치지 않는다. 초기 sticky 검색 실험에서는 행 위로 검색 영역이 겹치는 것을 독립 측정으로 발견해, 검색을 패널 맨 위의 정적 흐름으로 수정했다. 왼쪽은 높이가 충분할 때만 고정해 폼과 선택 요약을 유지한다. 이는 구조와 측정에 근거한 판단이며 사용성 실험 결과는 아니다.

태블릿 768~1023px은 1열을 선택했다. 2열을 강제하면 약 300px 이하의 폼 폭에서 한국어 안내·사유·칩이 줄바꿈되고 폼이 과도하게 길어지기 때문이다. 1024px부터 두 열을 적용한다. 짧은 화면에서는 고정보다 모든 입력에 도달하는 것을 우선한다.

## 제품 재현과 범위

- `class-scheduling.css:8-43`의 색·반경·폰트 토큰을 복사했다. 배경은 실제 wizard가 사용하는 `frontend/public/images/background4.webp`를 시안 폴더에 복사했다.
- 상단 제목, 4단계 점, 일정·담당 요약과 연필, 일정 충돌 없음, 회원/이메일 탭, 검색·안내, 선택 요약·CSV, 센터 관리자 전용 사유, 이니셜·마스킹 이메일·체크박스, 하단 이전·생성 버튼을 반영했다.
- 기존 `min-height:320px`(312줄)와 `max-height:none`(325줄)을 시안에 가져오지 않았다. 행 자체는 자연 높이이며 본문의 overflow 경계가 footer 위에서 끝난다.
- 화면 프레임 안에는 시안·기술 설명을 넣지 않았다. `index.html` 프레임 바깥에서 상태·해상도를 변경한다. 프레임 가로 스크롤은 실제 1440px 폭을 축소하지 않고 비교하기 위한 것이다. 제품 프레임 가로 넘침과 구별한다.
- 상태: 회원 0/4/20/60명, 선택 0/3/12명, 관리자 사유 표시/숨김, 검색 결과 없음, 회원/이메일 탭. 선택 수는 현재 필터 결과 수와 독립이다. 0명 결과에 12명 선택 등 극단 상태도 레이아웃 스트레스 조건으로 유지한다.
- 선택 토글·선택 칩 제거·가상 이름 검색·정확한 합성 이메일 검색·비회원 이메일 입력은 로컬에서 동작한다. CSV·연필·이전·생성은 표시 전용이다. 실제 CSV 파싱·클래스 생성·전송은 하지 않는다.

## 접근성

- 회원 선택은 native label/checkbox, 전체 행 최소 72px을 클릭 영역으로 사용한다. 24px checkbox 도형과 44px 이상 실제 터치 영역을 구별해 측정했다.
- 검색·사유·이메일 입력에 이름을 제공하며 탭은 `aria-pressed`, 선택 수는 `role=status`와 `aria-live=polite`를 사용한다. 칩 제거 이름에 대상을 포함한다.
- 하단 바는 본문과 별도 행으로 공간을 확보한다. 본문 `scroll-padding:24px`과 초점 outline을 적용했다. `focusin` 시 본문 경계를 벗어난 입력·행을 본문 `scrollTop`을 경계 차이만큼 조정해 보정한다. 회원 체크 뒤 DOM 재생성 시 같은 체크박스로 focus를 복원한다.
- 모바일은 CSS 재배치로 시각적 순서를 맞췄다. B2-1 데스크톱 DOM의 사유가 목록보다 앞서는 점은 남아 있다. 실제 구현에서는 모바일의 시각/읽기/탭 순서가 일치하도록 DOM을 구성해야 한다. 스크린리더 실사용·모바일 OS 가상키보드는 미검증이다.

## 검증

측정값·상세 실패 여부는 `validation.json`이 원본이다. `verify-browser.py`로 재실행한다(Python websocket-client와 로컬 Chrome 필요). 앱 빌드·앱 서버·prod 접속 없이 file URL + Chrome headless CDP를 사용한다.

- 실제 `innerWidth/innerHeight`를 CDP Emulation으로 적용: 1440×900, 1280×720, 1024×768, 390×844, 390×600, 1280×600.
- 두 안 × 화면 6개 × 회원 수 4개 × 관리자 2개 × 선택 수 3개 × 검색 없음 2개 × 탭 2개 = 1,152조합.
- 시작/200px/중간/끝 스크롤에서 overflow clipping을 반영한 요소 사각형 교차를 검사한다. 조상과 자손의 정상 포함 관계는 제외한다.
- 하단 바 viewport 하단 고정, 본문/바 교차, 가로 넘침, 터치 영역, 마지막 회원 행 scrollIntoView 도달, 사유 입력 도달을 측정한다.
- `shots/`는 각 안 1440·1024·390, 20명·관리자·3명 선택 상태다. PNG 직접 열기로 가독성과 레이아웃을 확인한다.

최종 결과: **1,152/1,152조합 통과, 실패 0**. 하단 바 가림·요소 겹침·가로 넘침 0, 마지막 행·사유 입력 도달 통과, 터치 영역 44px 이상. 낮은 화면 390×600/1280×600에서 두 안 각각 12명 선택 상태의 81개 초점 대상 검사 4/4 통과(가림 0, 체크박스 재선택 후 초점 유지). 비교 페이지 4개 프레임의 상태 반영·실제 폭 1440/390·모바일 순서 4/4 통과. 기본 PNG 6장과 낮은 화면 초점 PNG 4장을 보존했다. 초점 검사는 CDP focus emulation을 활성화해 실제 `focusin` 이벤트가 발생하는 조건에서 수행한다.
