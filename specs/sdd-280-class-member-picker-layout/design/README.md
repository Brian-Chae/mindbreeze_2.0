## 사용과 한계
- index.html: 1000px 데스크톱·390px 모바일 iframe 비교. 각 안 링크로 원래 크기 열기.
- 20명/4명 토글과 대행 사유 토글 제공. 검색은 가상 이름 부분 일치, 선택/칩 해제 작동. C는 ‘가상’을 입력해 결과 확인.
- CSV·이메일 탭·생성은 표시 전용. 실제 동작 불변이라는 요구는 후속 구현의 조건이며 이 시안으로 입증하지 않는다.
- 토큰은 class-scheduling.css:8-43에서 복사. 보라 #5F0080, 라벤더 #B373EF, 텍스트 #F7F4F0, 반투명 카드 rgba(24,12,36,.58), 반경 24/16px. 폰트 스택 동일, 외부 폰트 다운로드 없음.
- before는 코드 높이 충돌을 축약한 합성 재현. 실제 앱 또는 제공 스크린샷 픽셀 복제가 아니다.
- validation.json: Chrome headless에서 화면 너비·사유 표시별 스크롤·겹침·선택·검색 측정. shots/: 원본 시안 PNG. 실제 기기/WebView·OS 키보드·스크린리더는 미검증.
- pencil-design·design-mockup-loop SKILL.md는 로컬 검색에서 발견되지 않아 적용하지 못했다.
- 서버 :8001은 조작하지 않고 공유 폴더에 복사만 한다. 원격 URL 접근 여부는 미확인.

## 측정 해석
- CDP Emulation으로 실제 innerWidth 1440/390을 확인했다. 초기 window-size 방식은 최소 500px 제약이 있어 폐기했으며 `initial-measurement-harness.html`은 초기 진단 기록으로만 보존한다.
- before: 사유 표시 여부와 무관하게 목록이 카드·푸터 경계를 침범한다. 관리자는 목록과 사유도 겹친다. 다만 합성 하네스에서는 목록 scrollTop=100 이동이 가능하므로, 신고된 ‘스크롤 불가’까지 재현한 것은 아니다. 실제 DOM의 가림·입력 이벤트·브라우저 상태 추가 확인이 필요하다.
- A/C: 목록 내부 scrollTop=100, B: 본문 scrollTop=100 확인. B의 전체 목록 사각형은 스크롤 영역 밖까지 이어지지만 실제 보이는 영역은 main의 overflow:auto로 잘린다. `visibleListPastFooter`는 그 클리핑을 반영한 지표다.
- 3안 각각 2개 화면 × 관리자 상태 2개에서 선택 1명과 검색 결과 1개 확인. 키보드·스크린리더는 구조 검토만 했으며 실사용 테스트는 아니다.
- 재실행: `python3 verify-browser.py` (로컬 Chrome, Python websocket-client 필요). 검증용 별도 임시 Chrome 프로필을 사용하고 해당 프로세스만 종료한다. 공유 서버 조작 없음.
- 구현자와 다른 사람/에이전트의 독립 리뷰는 이번 실행에서 하지 않았다. 앱 적용 승인 전에 별도 검증이 필요하다.

B안 최종 보정: body를 100dvh flex 열로 두고 header/footer 높이를 먼저 확보했다. 본문만 남은 높이에서 스크롤하며 푸터는 화면 배분으로 고정된다. 초기 sticky 방식의 데스크톱 가림을 수정한 뒤 12조건에서 visibleListPastFooter=false를 재확인했다.
