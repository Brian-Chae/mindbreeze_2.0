# SDD-282 — 11/4 행사 데이터 유실 원인 분석 및 복구

- 상태: Stage ① Spec — 대표 go/no-go 대기
- 브랜치: `sdd/282-event-1104-data-loss-rca`
- 작성일: 2026-11-04
- 인계 문서: `handoff-1104.md` (분석 결과·가설·다음 작업의 정본)

## 1. 배경

11/4 대구교육청 오프라인 클래스(회차 `1a74e4c9-a54e-4454-8505-22840922811c`, 10:12~11:27 KST, 정원 50)에서
참여 행 63개 중 **6명만 분석 데이터가 끝까지 정상 수집**되었고, 나머지는 튕겼거나 데이터가 없거나 부분 수집이었다.
정상 6명은 모두 회원·밴드 연결·Android 푸시 등록 기기라는 공통점이 있고, 비회원은 사실상 전멸이었다(데이터 있는 행 5개, 모두 10초~2분 후 중단).

## 2. 해결할 문제 (사용자 관점)

1. 같은 행사에서 어떤 참가자는 안정적이었고 어떤 참가자는 실패한 **원인을 확정**한다(추정 아님).
2. 서버에 이미 올라온 데이터(원시·분석 파일)로 **복구 가능한 사람을 복구**하고 리포트를 다시 만든다.
3. 다음 행사에서 **같은 실패가 재발하지 않도록** 수정 범위를 정한다.

## 3. 범위

### 포함
- 실패 유형별 원인 확정: (a) 비회원 재입장·정원·대기열, (b) 분석 표만 빈 회원, (c) 밴드 연결 표시(`band_connected`) 누락, (d) iOS 참가자, (e) 11:23~11:30 실시간 방송 오류 반복(`log_truncated`)
- 입장 시 **플랫폼·앱 빌드 기록 부재**로 인한 사후 대조 불가 문제
- 복구 가능성 검증 및 복구안(운영 DB 쓰기는 건별 승인 후 별도 단계)
- 수정안 SDD 분할 제안

### 제외
- 11/4 행사 당일 운영 서버 변경(이미 종료됨)
- App Store·Play 심사 대응(별도 카드)
- 참가자 개인정보 조회·출력(건수·집계만)

## 4. 성공 기준

- 실패 유형 각각에 대해 "원인 확정 / 가설 / 모름"이 근거(쿼리 결과·코드 줄)와 함께 분류돼 있다.
- 복구 대상 인원·복구 가능 행 수가 숫자로 제시돼 있다.
- 재발 방지 수정이 SDD 번호 단위로 분할되어 대표가 우선순위를 정할 수 있다.

## 5. 제약

- 운영 DB는 **읽기 전용**. 쓰기·삭제는 건별 승인, 배포 전 스냅샷 확보.
- 운영 조회는 SSM(인스턴스 `i-0487c67fb0db7dcba`)으로만, 개인정보는 건수만.
- 금지 표현(점수·종합점수·좋음·나쁨·완료·보증·100% 단정)은 신규 화면에 쓰지 않는다.
- 푸시·배포는 대표 지시 후.

## 6. 대표 결정 필요

1. 이 SDD를 진행(go)할지.
2. 복구(운영 DB 쓰기)는 분석 완료 후 별도 승인 요청.
