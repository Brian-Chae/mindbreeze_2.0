## 2. 단계 구성

### 단계 0 — 선행 조사 (읽기 전용, 이 SDD 안에서)
- T0-1. 리포트 재생성 경로 확인: `class_report_stats_service.compute_class_stats` 호출부, `reports` 행의 `generation_status`·`approved_*`·`delivery_status` 처리, 재생성 시 이미 발송된 리포트 덮어쓰기 여부.
- T0-2. 복구 변환 스크립트를 **로컬 SQLite/테스트 DB**에서 시험(운영 접속 없이): feature 파일 샘플 → `_feature_item` → `_persist_feature_items` 결과가 정상 경로와 같은 컬럼 값을 만드는지(F6 확장).
- T0-3. `log_truncated` 시각(11:23~11:30 KST)의 서비스 재시작·Redis 재구축 이력 확인(`systemctl` 재시작 시각, journald 공백).
- T0-4. 4명 기기 확인 요청서 작성: 대표가 해당 참가자에게 앱 로그/미전송 창 확인 가능한지 (H1′ 확정 목적).

### 단계 1 — 복구 (운영 DB 쓰기, **대표 건별 승인 필수**)
- R1. 사전: RDS 스냅샷, 대상 4명·12,540행·예상 중복 0 확인 문서화.
- R2. 재적재 스크립트(멱등, dry-run 기본): feature 파일 → `eeg_feature_windows`. 키 = (참가자, 해당 `capture_stream.id`, window_index=sequence), `ingest_path='recovery_sdd282'` 표식(롤백 시 이 표식으로만 삭제).
- R3. 리포트 재생성: 4명 대상. 이미 발송/승인된 리포트인지에 따라 덮어쓰기·재발송 여부는 대표 결정(메일 임의 발송 금지 → 초안/승인 경로).
- R4. 사후 검증: 행 수, 리포트 본문 길이·`data_credibility`, 이전 대비 diff. 기기에 남은 나머지 창(약 6,500행 추정)은 별도 회수 가능 여부만 보고.
- `b5eed5`: 데이터 있음. 본인의 리포트 반영 선택이 필요하므로 대표가 본인 연락/권한 경로를 결정.

## 3. 대표 결정 필요

1. 복구 진행 여부(4명 12,540행) 및 리포트 재발송/덮어쓰기 정책.
2. 하위 SDD 우선순위(위 제안 순서 그대로 갈지).
3. 비회원 뇌파 동의 기본값 정책(현재 "미동의로 시작"이 비회원 62% 업로드 불가의 한 축).
4. H1′ 확정용 기기 확인이 가능한 참가자 연락 가능 여부.

## 4. 리스크

- 복구 후 리포트가 이미 발송/승인된 상태면 재생성이 참가자에게 노출될 수 있음 → T0-1에서 확인 후 결정.
- 파일에는 앞부분 약 57~93%만 있음 → 복구 리포트는 "부분 구간" 표기가 필요(금지 표현·점수 환원 금지 규칙 준수).
- H1′는 정황 추론이므로 하위 SDD 1번은 재현 테스트(귀속 전 창 + ACK 유실)로 먼저 증명한 뒤 수정.
