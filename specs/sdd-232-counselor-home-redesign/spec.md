# SDD-232 — 상담사 홈 화면을 회원 홈처럼 정리

- 상태: Stage ① Spec + 디자인 시안 — Brian 결정 대기 (구현 착수 아님)
- 브랜치: `sdd/232-counselor-home-redesign`
- 작성일: 2026-10-22
- 이번 산출물: 이 스펙, `designs/counselor-home/index.html`, Chrome headless 캡처·측정 결과
- 요청: 상담사 홈의 카드와 반응형 레이아웃을 회원 홈과 같은 시각 언어로 정리하되 업무 기능 유지.

## 1. 문제와 목표

1. 회원 홈은 자연 사진 히어로 → 4개 요약 타일 → 큰 제목·진행률·다음 회차가 있는 클래스 카드 흐름이다. 상담사 홈은 보라색 다음 세션 카드와 좁은 2열 회차 카드, 우측 타일로 분산돼 같은 서비스처럼 느껴지지 않는다.
2. 상담사 홈의 `ClassCard`는 이름과 달리 세션(회차) 한 건을 표현한다. 같은 클래스의 여러 회차가 반복돼 제목만으로 구분하기 어렵다. 회원 홈의 카드는 부모 클래스 한 건이다. 단순 CSS 교체로는 해결되지 않는다.
3. 모바일에서 기존 좌측 업무·모든 카드 뒤에 우측 타일·대화·알림이 쌓여 업무 요약을 늦게 보게 된다.
4. 회원 카드의 누락 필드마다 `ReadField`가 '데이터 없음'을 출력해 읽기 흐름을 깨뜨린다. 결측·조회 실패·예정 없음은 구분할 필요가 있다.

목표: 다음 행동을 빠르게 찾고, 클래스 단위 현황을 읽으며, 모든 기기에서 동일한 섹션 순서로 업무를 이어간다. EEG 착용 여부와 무관하게 이용 가능하며 명상 결과를 점수화하지 않는다. 카드 진행률은 완료한 정규 회차 비율이다.

## 2. 범위와 비범위

## 4. 디자인 기준과 충돌 해석

`DESIGN.md`는 Clinical Garden 다크·Inter/Playfair와 스톡 히어로 금지를 기술하지만, 현행 회원 홈은 라이트 `.sh-scope`·`.cs-structure`와 이미 저장된 자연 사진을 사용한다. 이번 요청이 '회원 홈처럼'이며 기존 이미지 사용을 명시하므로 **현행 회원 홈의 라이트 셸을 이 범위의 기준으로 제안**한다. 전역 `DESIGN.md`나 토큰은 변경하지 않는다. 새 스톡 사진이나 원격 폰트 다운로드 없음.

사용 기준:
- `shell-kit.css`: `#5F0080`, `#F5EDFC`, `#F7F4F0`, `#1F1F1F`, `#6F6F6F`, `#ECE6F0`.
- `member-home-layout.css`: 카드 반경 20px, 24px 섹션 간격, 16px 카드 간격, 280×304px 데스크톱 카드, 은은한 그림자.
- Pretendard → Noto Sans KR → 시스템 폰트 스택. 시안은 같은 폰트 스택 중 저장소 `backend/app/assets/fonts/NotoSansKR.ttf`의 Noto Sans KR을 우선 지정해 실제 Noto Sans KR 렌더링을 보장한다(제품 폰트 배포 변경 없음).
- 사진 `frontend/public/images/background8.webp`. 이후 구현은 기존 `heroBackdrop`의 안정적인 선택 정책 재사용.
- 글자 12px 이상, 본문 13~15px, 제목 18~30px. 조작 대상 44px 이상. 사진 위 어두운 오버레이와 밝은 텍스트. 프로그레스는 회차 수와 함께 표시.

## 5. 제안 A — 회원 홈 흐름 + 하단 업무 영역 (추천)

### 데스크톱: 1194px 이상 (1440 포함)

- 기존 AppShell 내비게이션/알림/드로어/인증 유지. 컨텐츠 최대 1280px, 좌우 40px, 섹션 간격 24px.
- 헤더: 인사·소속 / 클래스 목록·지금 바로 시작·새 클래스. '지금 바로 시작'은 기존 `/classes/now` 화면으로 이동하는 링크다.
- 전체 폭 사진 히어로: 진행 중 우선, 없으면 가장 가까운 미종료 예정 회차. 좌측 상태·클래스명/회차·일시, 우측 단일 주 CTA.
- 검토 대기 > 0이면 바로 아래 전체 폭 검토 배너. 타일과 같은 집계·같은 검토 대상 `/reports?status=pending`을 가리킨다.
- 전체 폭 업무 타일 4개: 진행 중 **회차**, 검토 대기 **리포트**, 오늘 예정 **회차**, 총 참여자 **명**. 회원의 타일 모양을 따르되 상담사 업무 지표와 기존 집계 함수를 보존한다.
- 전체 폭 '내 클래스': 부모 ID 기준 1장, 상태 칩·큰 제목·완료/전체 회차·진행 막대·다음 회차·일시·지도사. 오른쪽 전체 보기. 280px 카드 가로 탐색·화살표·키보드 조작·첫/끝 비활성 상태. 시안은 재현 가능한 이동을 위해 즉시 스냅, 제품은 reduced-motion 설정을 존중하는 기존 동작을 유지한다.
- 하단 2열: 좌측 `minmax(0,1fr)` 오늘·다가오는 일정(최대 5회차), 지난 회차/기록 진입, 접이식 상담사 코드. 우측 320px 최근 대화·새 알림(각 최대 3개).
- 지난 클래스는 캐러셀 뒤쪽, 지난 회차는 일정 아래 접기 영역. 클래스와 회차를 다시 섞지 않는다.

### 태블릿: 768~1193px

- 기존 셸 중단점 유지가 구현 원칙. 시안에서는 축소 사이드바 200px, 본문 좌우 24px로 공간 확인.
- 히어로 CTA를 본문 아래로, 타일 4열·가로 카드 탐색 유지.
- 하단 업무 영역은 1열로 내리고 대화·알림은 서로 2열. 헤더 조작은 줄바꿈한다. 1194px부터 데스크톱 2열로 복귀.

### 모바일: 767px 이하 (390)

- 인사 → 기존 목록/지금 바로 시작/새 클래스 진입 → 히어로 → 검토 배너 → 2×2 타일 → 내 클래스 → 일정·지난 회차·상담사 코드 → 대화 → 알림.
- 좌우 16px, 섹션 20px, 카드 20px 반경, CTA 전체 폭. 스크롤 문서 자체는 가로 넘침 없음.
- 카드 1장 + 다음 카드 일부 노출하는 로컬 가로 탐색(카드 영역 내부만 스크롤); 별도 좌우 버튼도 유지. 전체 보기는 기존 목록으로 이동.
- 기존 모바일 내비게이션 동작·safe-area 유지. 시안의 하단 메뉴는 비교용 단순화이고 제품 메뉴 개편 대상이 아니다.
- 타일을 카드보다 위에 두어 첫 화면 아래에서 즉시 업무 요약을 찾게 한다. 대화·알림을 제거하거나 기본 접지 않는다.

### 다른 배치 검토

B안(별도 시안 없음): 히어로 옆에 검토·일정 레일을 계속 둔다. 일정 접근은 빠르지만 1194px에서 히어로/카드 폭이 좁고 회원 홈과 다른 시각적 분산이 유지된다. A안을 추천한다. 업무 배너를 상단에 유지해 A안의 업무 접근성을 보완한다.

## 6. 재사용과 필요한 어댑터

- `AppShell` 또는 `StructureShell role="host"`: 셸 재사용. `StructureShell` 도입 시 스크롤 소유자 하나만 유지, 기존 프로필·기관탈퇴 안내·알림 기능 유지.
- `ClassHero` / `ClassHeroData`: 사진·상태·메타·CTA의 표현을 재사용. 현재 props가 place/mode/band를 필수로 요구하고 dashboard에는 place/band가 없으므로 임의 기본값을 넣지 않는다. 상담사용 최소 데이터·선택적 메타를 받도록 작은 호환 확장, 또는 회원 구조형 홈처럼 `.sh-hero` 표현을 공통 추출. 기존 회원 인터페이스는 보존한다.
- `ClassHeroEmpty`: 회원 신청하기 문구/동작은 재사용 불가. 같은 표현에서 역할별 문구·CTA만 주입하는 빈 히어로로 분리한다.
- `MemberClassCard` / `MemberProgress` / `MemberSessionMeta`: 카드 본문을 공통 표현으로 추출하고 `href`와 역할별 보조 문구를 주입. 회원 wrapper는 기존 경로 유지, 상담사 `/classes/:classId`.
- `MemberClassStrip`: `ClassReadModel[]`와 회원 카드에 결합돼 있으므로 `renderCard` 또는 동등한 카드 슬롯을 추가한 공통 strip으로 분리. 기존 export 호환. 모바일 스와이프·방향 버튼도 반응형 규칙 확장.
- `StatTile` (`components/dashboard/stat-tile.tsx`): 이미 링크·접근성·값 색상 지원. 회원 요약은 페이지 인라인이므로 회원 홈 전체를 공통화하지 않고 이 기존 타일을 4열/2열로 배치한다.
- `adaptHostClass` / `adaptMemberClass`, `displayField`, read-state 구분 및 `useClasses`: 기존 조회/정규화 사용. 실패와 값 없음 구분 유지.
- `dashboardSessionPath`, `home-stats`, `home-links`: 기존 집계·상담 플래그·검토/오늘/회원 경로 유지. 단 `liveTileTarget`은 본인 host를 검증하지 않고 1회차면 player로 보내므로 이번 카드 어댑터에서는 이를 그대로 사용하지 않는다. 진행 중 타일도 1개면 해당 회차 상세, 복수면 기존 전체 목록을 거쳐 진행·참관을 확인한다(타일 집계 의미는 동일). 대화·`NotificationRow`·상담사 코드 복사/마스킹 로직 유지.
- `MemberHomeView`는 과거 rows·회원 코드 입장/신청 문맥이므로 상담사 홈 전체로 재사용하지 않는다. `flow/shell/ClassCard`도 회차 표현이며 이번 캐러셀의 부모 클래스 카드와 다르다.

## 7. 데이터 계약과 백엔드 규모

### 기존 API로 충분한 항목

- `GET /dashboard/counselor`: 지금 열려 있는 회차·다가오는 일정·참여 수·검토 수. `ClassSummary.id`는 세션 ID, `class_id`는 부모 ID. 기존 `visibleClasses` 필터와 `home-stats`를 유지한다. 부모 카드 수와 타일의 진행 중 회차 수는 다른 지표다.
- `GET /classes` (`getClasses`, `useClasses`): 부모 카드 `id,title,status,progress,session_count,next_session,has_open_session,is_instant`. 완료/분모는 서버 제공 값을 그대로 사용하며 회차 데이터를 임의 합산해 새 progress를 만들지 않는다.
- `next_session`: `id,seq,scheduled_at,status,host`. 지도사/다음 일정 메타에 충분하다. null이면 즉시 '일정 미정'이라고 단정하지 않는다.
- `GET /classes/:id` / `/classes/:id/sessions`: 이미 상세 화면에서 권한·진행자를 판단. 홈 기본 로딩 때 카드마다 상세 조회하지 않는다.
- 기존 대화/알림 API와 `authStore.user.counselor_code`를 유지한다. 인증정보·실사용 코드 값을 조사/출력하지 않는다.

### 중요한 경계

1. `class_read_service._next_session`은 미래 시각의 미종료 회차만 고른다. 진행 중이거나 시작 시각이 지난 회차가 `next_session`에 없을 수 있다. `has_open_session`은 상태 존재만 알려주며 열린 회차 ID가 아니다. 따라서 히어로 진행 중은 dashboard rows로 선택하고, 카드 열린 상태는 '열린 회차 확인' + 클래스 상세 이동으로 처리한다. 다른 ID를 추정하지 않는다.
2. 기본 히어로 CTA: 진행 중/open·미래 예정 모두 '회차 상세 보기'. dashboard에는 host_id/host_state/capabilities가 없고 팀 지도사 회차도 포함된다. `components/class/structure/class-session-detail.tsx`의 본인 진행자·배정 완료 검증과 비진행 팀 지도사 참관 흐름을 따른다. 홈 버튼이 바로 열기/시작 쓰기 API를 호출하지 않는다. 별도 시작 권한·배정 상태를 알 수 없으므로 '시작하기'로 확정하지 않는다. 부모 ID 없는 구회차는 기존 `dashboardSessionPath` fallback 유지.
3. 부모 카드의 참여자 수는 API에 없어 생략한다. dashboard의 회차 참여 수를 클래스 등록 회원 수처럼 쓰지 않는다. 회차별 입장 코드 복사·참여/게스트 수·기록은 일정 행/회차 보조 작업에서 기존 기능으로 유지한다. 진행 입장은 상세 경유로 본인 진행·팀 참관을 구분한다. 5행 밖의 회차도 전체 보기에서 기존 상세·기록 작업에 접근할 수 있다. 권한 없는 코드가 부모 카드로 확산되지 않게 한다.
4. `/classes`는 접근 가능한 강사/회원/기관 역할의 클래스가 반환된다. 이번 홈은 기존 상담사 클래스 목록과 같은 가시 범위를 따른다. 이름을 '직접 개설한 클래스'로 좁혀 표현하거나 현 응답에 없는 소유 여부를 추정하지 않는다.
5. 홈은 `getClasses()`의 페이지 생략 계약(전체 가시 목록)으로 받아 활성/준비 → 열린 회차 → 다음 시각 → 안정 ID 순으로 정렬, 종료 항목을 뒤에 배치한다. 실제 홈 카드 렌더링은 우선 8개로 제한하고 전체 보기를 제공한다. 응답 total을 8개로 잘라 전체 개수로 표시하지 않는다. 대규모 목록의 서버 정렬/홈 전용 집계 API는 별도 과제다.
6. 클래스 조회 실패는 해당 섹션의 재시도 상태. dashboard/chat/notifications 성공 화면은 유지. 미조회 수치를 0으로 대체하지 않는다. 상담 공개·AI 공개 플래그, 기관탈퇴 안내, 프로필 미완성 배너·닫기를 보존한다. 시안의 브리핑/프로필 링크는 위치 설명용이며 제품의 조건부 노출을 무조건 링크로 바꾸지 않는다.
7. `total_participants`는 기존 dashboard 집계 그대로 표시한다. 별도 인원 dedupe나 기관 범위 변경은 이 리디자인에 포함하지 않는다.

판정: **추천 A + 모든 회차 상세 경유 CTA + 카드 참여 수 생략은 백엔드 변경 불필요(0 엔드포인트/0 마이그레이션)**. 기존 API 호출 1계열(`/classes`)을 홈에 추가하는 프런트 어댑터·공통 표현 추출이 필요하다. API 응답·실제 권한 실행·성능은 라이브 접속 없이 소스 계약만 확인했다.

예상 규모(견적, 확정 plan 아님): 프런트 홈/스타일 2~3파일, 어댑터 1파일, 공통 카드·strip·hero 호환 확장 3~5파일 및 관련 회귀 검증. 총 6~9개 소스 파일 수준의 중간 규모. 공통 빈 값 정책 승인 시 회원 카드도 영향받아 회원 경로/권한 회귀 검증이 필요하다. 홈 직접 시작 버튼이나 클래스 등록 회원 수 추가 요구가 생기면 API 계약 재검토 후 별도 범위 결정.

## 8. 공통 카드 빈 값 개선안 (결정 2 전에는 제품 반영 안 함)

카드에서 필요한 한 줄 안내만 남기고 선택 메타는 생략한다. 읽기 오류를 숨기는 방식으로 적용하지 않는다.

- 제목 없음 → '이름 없는 클래스'(카드 식별과 링크의 접근성 이름 유지).
- 다음 회차 없음 + 완료 → '모든 회차를 마쳤어요'.
- 다음 회차 없음 + `has_open_session=true` → '열린 회차가 있어요' + 상세 확인. 미래 next 부재와 충돌하지 않게 열린 상태 우선.
- 다음 회차 없음 + 미완료 → '다음 일정이 아직 없어요'. '아직 편성하지 않았다'는 원인을 추정하지 않는다.
- next 존재·일시 null → '다음 일정 확인 중' 1줄. 순번만 없으면 '다음 회차'로 표시, 지도사 이름은 없으면 해당 행 생략. 존재하지 않는 지도사를 '미배정'이라고 단정하지 않는다.
- 전체 회차 수가 없거나 0 → 진행 막대 생략. 완료 수가 확실하면 '완료한 회차 N회', 그렇지 않으면 진행률 영역 생략. 0/0, 가짜 0%, 빈 막대 반복 없음.
- 조회 실패/권한 회수 → 기존 오류·접근 상태와 재시도 유지. 정상 빈 카드로 바꾸지 않는다.
- 적용 위치는 공통 카드 표현에 국한. `ReadField`의 전역 기본값은 유지한다.

## 9. Brian 결정 항목

1. **레이아웃**: A 회원 홈 흐름 + 하단 업무 영역 / B 히어로 옆 업무 레일 유지. **추천 A**. 시안의 라이트 셸·기존 사진 사용을 포함한 결정이다.
2. **빈 값 개선 범위**: A 상담사·회원 공통 카드에 함께 적용 / B 이번 상담사만 / C 이번에는 보류. **추천 A**. 동일 카드 언어를 맞추고 전역 ReadField는 건드리지 않는다.
3. **히어로 행동**: A 예정·진행 중은 회차 상세 보기, 빈 일정은 지금 바로 시작 / B 홈에서 직접 회차 열기·시작까지 수행. **추천 A**. 기존 권한 확인 흐름을 유지하며 백엔드 변경을 피한다. B는 추가 설계·견적 대상.

세 항목의 추천값은 작성자 제안이며 Brian 승인으로 간주하지 않는다. 가장 먼저 1번 방향을 결정한 뒤 2·3번을 순차 확정한다.
