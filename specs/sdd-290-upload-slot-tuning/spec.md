# SDD-290 — 행사 업로드 동시성 슬롯 상향·서버 설정 튜닝

- 상태: Stage ① Spec
- 브랜치: `sdd/290-upload-slot-tuning`
- 작성일: 2026-11-04
- 근거: `specs/sdd-283-system-network-load-audit/{analysis,plan}.md`(워커 보고, 감독이 일부 재검증), 운영 설정 읽기 확인(11/4 밤)

## 1. 문제
11/4 행사(09:30~12:00 KST)에서 원시·분석 파일 업로드 경로가 동시성 슬롯 한도에 걸려 429로 거절됐다.
- `biosignal-raw/presign` 151건, `biosignal-raw/ack` 147건, `biosignal-artifacts/presign` 101건, `biosignal-artifacts/ack` 107건, 합계 약 506건.
- 운영 설정(감독 확인): `archive_max_concurrent=16`, `archive_slot_wait_sec=0.5`, uvicorn 프로세스 1개, DB 풀 20+20, 기본 executor 32, anyio 64. 운영 `prod.env`에는 이 값들의 덮어쓰기가 없다(코드 기본값 사용).
- 429를 받은 클라이언트는 재시도하지만, 재시도 중 지연이 쌓이면 분석 파일 업로드가 늦어진다. 11/4 실패 4명에게서는 원시·분석 파일 업로드 자체는 성공했으므로 이것이 실패의 직접 원인은 아니다(비교 분석 결과).

## 2. 목표 (최소 변경)
40~50명 동시 수업에서 업로드 슬롯 거절(429)을 줄인다. 앱 재빌드 없이 서버 설정만으로 적용한다.

## 3. 범위
- 포함: 슬롯 한도(`archive_max_concurrent`) 16→32, 대기 시간(`archive_slot_wait_sec`) 0.5→1.5 후보를 검토하고, 근거가 있을 때만 변경. 변경 방법 확정(코드 기본값 변경 vs `prod.env` 값). 롤백 방법. dev 40명 부하시험 합격선.
- 제외: uvicorn 프로세스 수 증가(소켓 모듈이 단일 워커 전제, `ws/session_live_namespace.py:45-56`), 업로드 경로 분리 서버(설계만 별도), 세션 폴링 304, 403 재시도 차단(별도 SDD), 앱 변경.

## 4. 성공 기준
- dev에서 40명 동시 시나리오(원시 3센서 10초 청크 + 분석 파일)에서 429 비율이 현 설정 대비 감소하고, DB 연결 사용량이 풀 한도(40)의 70%를 넘지 않는다.
- 운영 반영은 코드 배포 없이 값 변경 또는 최소 코드 변경으로 가능하고, 롤백이 재시작 1회로 끝난다.

## 5. 확인할 것 (워커가 코드로 확정)
1. `archive_upload_slot`이 정확히 어떤 요청을 세는가(presign과 ack가 같은 슬롯인가, 슬롯을 쥔 채 S3 HEAD를 하는가). 슬롯을 쥔 시간이 길면 한도만 올리는 것이 아니라 보유 시간을 줄여야 한다.
2. 한도를 32로 올릴 때 anyio 스레드(64)·DB 풀(40)과의 관계(슬롯이 스레드·연결을 동시에 쓰는가).
3. 운영에서 값을 바꾸는 실제 경로(`/etc/mindbreeze/prod.env`가 SSM 파라미터에서 렌더링되는지, 코드 기본값 변경이 더 단순한지).
