## 2. 목표

1. **트랙 2(서버)**: 착용 40명 1Hz feature 수신에서 거절 0·유실 0·회차 락 Traceback 0. 영상·음성·상태(device/command/renew) 통신이 같이 유지된다.
2. **트랙 1(클라이언트)**: 원시 데이터는 폰 로컬 저장 후 완결성 있게 서버로 올린다. 클래스 종료는 업로드를 기다리지 않고, 비정상 종료 후에도 앱이 다시 실행 기회를 얻으면 화면과 무관하게 미완료 업로드를 자동 재개한다.
3. 11/3 go/no-go 를 위한 dev 40명 재시험·실밴드 시험 합격선을 하나로 확정한다(verify.md).

- 범위(대표 지시 10/31 "완결성 우선"): `plan.md` Phase 0~5 전부. P1 서버 안정화 → P2 원시 업로드 완결성 → P3 복귀 재개·feature 재생·24h 검역 접수·iOS 백그라운드 → P4 pending 투영·적응형 백프레셔 → P5 다중 워커. 11/4 는 목표 마일스톤이며 G1+G2 통과가 현장 적용 조건.

## 4. 제약

- 앱 웹 번들은 내장(`frontend/capacitor.config.ts` `webDir: 'dist'`, `server.url` 없음) → 프런트 변경도 앱 재빌드·재설치가 필요하다. 네이티브 측정 경로(`measurement-path.ts`: 앱이면 항상 `native`)가 현장 기본이므로 트랙 1 필수는 네이티브 코드 기준이다.
- 모든 서버 변경은 env 플래그로 즉시 롤백 가능해야 한다. 마이그레이션은 2단계(조건부)에만 있다.
- 구현자 ≠ 검증자. verify.md 는 구현 전에 확정하고 사후 수정하지 않는다. 실밴드 시험은 구현 후 수행(대표 결정).
- 서버 변경은 즉시 적용, 앱 변경은 사용자 업데이트 필요 → 서버는 구버전 앱과 호환되게 additive 로만.
