## 2. 목표 (10/31 대표 지시 순)

> 11/4 부터는 모두 **오프라인 클래스**다. 코치 실시간 모니터링은 룩시드랩스 전담 코치용이라 중요도가 낮다. 아래 1~3 을 "무조건 완결성 있게" 만족시키는 전제로 계획한다.

1. **[A] 저장 완결성**: 회원 데이터(feature 창·원시 청크)가 빠짐없이 서버 DB·S3 에 저장된다. 저장은 실시간 연결 상태(READY/DEGRADED/소켓 끊김)와 **무관**해야 하며, 종료·재접속·강제종료 후에도 이어 올린다. live 에서 거절·폐기된 창은 이미 올라가는 feature archive 로 서버가 복구한다.
2. **[B] 리포트·회원 자기 화면**: 리포트가 나온다(결측은 "데이터 확인 중"으로 표기하고 데이터가 들어오면 재생성). 회원 자기 화면은 서버 장애·소켓 끊김 중에도 로컬 값을 계속 보여 준다.
3. **[C] 코치 실시간 모니터링**: 착용 40명에서 호스트 수신 지연·투영 구조·다중 워커. 참고 지표이며 [A] 를 막는 경로(락·스레드풀·heartbeat)만 [A] 위험으로 다룬다.
4. 11/3 go/no-go 합격선을 "**저장 완결성 100% · 리포트 생성 성공 · 회원 자기 화면 정상**" 으로 확정한다(verify.md). 호스트 지연은 참고 지표.

## 3. 범위 / 비범위

- 범위: `plan.md` Phase 0~6 전부. 새 순서 = **P1 저장 연결 독립화·저장을 막는 서버 요인 제거 → P2 feature archive→DB 재생·24h 검역 접수(서버 단독, 구앱 즉시 수혜) → P3 업로드 완결성(앱)+자기 화면 로컬 우선 → P4 리포트 보장 → P5 실시간 투영 구조 → P6 다중 워커**. 11/4 는 목표 마일스톤이며 G1+G2(+G4 의 R1) 통과가 현장 적용 조건. 앱 변경(P3)은 설치가 필요하므로 서버 단독으로 살릴 수 있는 것을 먼저 한다.
- 비범위: metrics outbox 탈출(Redis 직접 투영), 대형 객체 multipart, 임의 기기 간 원본 이전, 셀룰러·배터리 세부 정책(대표 결정 5 뒤 별도).

## 4. 제약

- 앱 웹 번들은 내장(`frontend/capacitor.config.ts` `webDir: 'dist'`, `server.url` 없음) → 프런트 변경도 앱 재빌드·재설치가 필요하다. 네이티브 측정 경로(`measurement-path.ts`: 앱이면 항상 `native`)가 현장 기본이므로 트랙 1 필수는 네이티브 코드 기준이다.
- 모든 서버 변경은 env 플래그로 즉시 롤백 가능해야 한다. 마이그레이션은 2단계(조건부)에만 있다.
- 구현자 ≠ 검증자. verify.md 는 구현 전에 확정하고 사후 수정하지 않는다. 실밴드 시험은 구현 후 수행(대표 결정).
- 서버 변경은 즉시 적용, 앱 변경은 사용자 업데이트 필요 → 서버는 구버전 앱과 호환되게 additive 로만.
