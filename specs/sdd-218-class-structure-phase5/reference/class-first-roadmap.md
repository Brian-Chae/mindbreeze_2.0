> 이 문서는 **전체 Phase 로드맵(Phase 0~8)** 을 먼저 그린다. 각 Phase 는 후속 SDD 한 건으로 쪼갤 수 있는 단위다. 구현은 이 문서 승인 후 별도.

## 출시 순서 조정 (2026-10-19)

**클래스를 먼저 출시하고, 상담 Phase 6·7은 출시 이후 기능 업데이트로 진행한다.** 기존 Phase 번호는 문서·SDD 참조를 위해 유지한다. 이 절과 아래 변경된 출시 순서가 원안의 병렬 진행·MVP 컷보다 우선한다. 이는 출시 범위 조정이며 후속 구현·정책 전체에 대한 일괄 승인은 아니다.

- **현재 기반**: Phase 0(SDD-211)·1(SDD-214)은 완료, Phase 2(SDD-215)는 develop 반영 상태다. Phase 2 실환경 검증·디자인 마감·최종 리뷰는 별도 확인한다.
- **클래스 우선 출시 범위**: Phase 2 마감 → Phase 3 편성·강사 → Phase 4 멤버십·출석·보강 → Phase 5 클래스 리포트 → 아래 Phase 8-A 출시 점검.
- **후속 업데이트**: 클래스 출시 후 별도 착수 승인으로 Phase 6 상담 → Phase 7 비회원 상담 → Phase 8-B 공통 정리. 상담 전용 정책 결정·화면 완성을 클래스 출시의 선행 조건으로 삼지 않는다.
- **기존 상담 기반**: 이미 추가한 상담 테이블·읽기 API는 유지한다. 상담 메뉴·진입점의 첫 출시 공개 여부는 출시 전 정할 항목이며, 이번 문서 변경으로 숨김·차단 구현까지 승인된 것으로 보지 않는다. 비공개로 결정하면 메뉴뿐 아니라 직접 URL·생성 유형·알림 진입점의 처리도 함께 정의한다.
- **공유 기능 경계**: Phase 4의 비회원 클래스 참여는 클래스 범위에 포함한다. Phase 7의 비회원 상담과 함께 미루지 않는다. 인증·동의·리포트 등 공유 경로는 클래스 출시 때 검증하고, 자동 승인처럼 상담에 영향을 줄 수 있는 동작은 공개 범위에 맞춰 격리를 확인한다.
- **완료 기준**: 클래스 생성 → 편성·초대 → 입장·진행·종료 → 출석·보강 → 리포트 승인·열람의 실제 백엔드 연동 검증, 주요 뷰포트·권한·LINK BAND 미착용 흐름 검증, prod 반영 사전 점검 및 릴리스 승인. 각 구현 단계의 Spec·Verify 승인 게이트는 유지한다.

## 2. 문제 정의

### 2.1 현재 상태

- `sessions` 테이블 1개가 **단회차 단위**이고 화면은 이를 "클래스"라고 부른다(SDD-208/209 가 "세션 → 클래스"로 치환). 상위 개념이 없다. `run_id`·`is_template` 는 회차 개념이 아니다(`run_id` 는 한 행의 재실행 표식으로 프론트 호출 0건, `is_template` 은 유형 설정 저장본) (`R1 §4`, `R5 §2.4`).
- 프론트는 "서버가 주는 세션 1건 = 화면의 클래스 1건"으로 목록·홈 히어로·상세·만들기·입장·알림 라우팅까지 한 타입(`SessionDto`, 22개 파일)에 걸려 있다(`R3 §1`). 진행 화면(플레이어)·입장 준비·대기실·종료·리포트 진행은 세션 1건 단위로 닫혀 있어 새 모델의 "세션 = 회차"로 그대로 쓸 수 있다.
- 명상과 상담이 **같은 마법사·같은 용어·같은 리포트 정책**을 쓴다. 상담의 종결·보관·교체 기능이 없고(`client_counselor_links` 의 `ended` 로 바꾸는 코드 0건), 비회원은 type 무관 4자리 코드로 상담 세션에도 들어가며 1:1 에서 코드를 아는 아무나 먼저 들어가 선점할 수 있다(`R10 §6.1`).

### 2.2 못 하는 것

| 영역 | 현재 불가능한 것 |
|---|---|
| 지도사 | 8회 프로그램 일괄 개설(반복 일정 없음, 날짜 1개 스텝퍼), 강사 2명 번갈아 진행(`host_id` 단일·변경 코드 없음), "지난 기수 그대로"(세션 복제만 있음), 클래스 단위 리포트 일괄 처리(`approve-all` 은 호스트 전체 범위, 재생성·재발송은 단건) |
| 회원 | 내가 참여한 클래스 보기(프로그램 개념이 없음), 결석·보강·중간 합류·이탈 구분, 클래스 단위 변화 서사 |
| 상담사 | 상담 관계 단위 이력, 반복 상담 예약, 종결·재개, 상담사 교체, 비회원 내담자 재방문·기록 연결 |
| 센터 | 강사 이탈 시 미래 회차 재배정(계정 삭제는 일정이 **조용히 사라지게** 만듦), 클래스 현황 |
| 공통 | 영역별 용어(알림·메일은 `세션`, 화면은 `클래스` 혼재), 승인 전 리포트 회원 노출 여부 미검증 |

### 2.3 목표

1. **클래스 = 프로그램(상위), 세션 = 회차(하위)** 로 구조를 바로잡는다. 상담은 **상담 관계(내담자 1 + 상담사 1)** 가 상위, 상담 세션이 회차다.
2. 명상 클래스와 상담을 **별도 제품·메뉴**로 나누되 진행·입장·뇌파·녹음/STT/요약·리포트 엔진·알림은 **공유**한다. 모든 사용자에게 두 메뉴를 열고(기관 단위 on/off 없음) 한 계정이 두 영역을 쓴다.
3. 지도사의 편성(고정형·정기형·강사 배정·복제)과 회원의 "내 클래스/내 상담", 클래스 단위 리포트 관리를 일급 기능으로 만든다.
4. 기존 단회차 데이터를 **삭제 없이** 새 구조로 이전하고, 구 앱(Capacitor 번들, 강제 업데이트 없음)이 계속 동작한다.

### 2.4 비목표 (이번 로드맵 밖)

휴회(일시중지) · 클래스 채팅방 단위 변경(회차 채팅방 유지) · 센터 룸(공간) 관리와 장소 충돌 차단 · 타 센터 강사 공유 · 인계(대기실 이후 진행자 교체) · 개인 장기 기준선 기반 회차 간 수준 비교 · 클래스 마무리 리포트 · 강사별 통계(**만들지 않음**) · 클래스 소유 이관 UI · 알림 설정의 영역별 분리 UI · 의료기기 목적의 진단 표현.

## 4. 개념 모델

### 4.1 용어

| 용어 | 명상 영역 | 상담 영역 |
|---|---|---|
| 상위 | **클래스**(프로그램). 예: MBSR 봄 클래스 | **상담 관계**. 예: 채용욱 상담 |
| 하위 | **세션(회차)**. `MBSR 봄 · 3회차` | **상담 세션(회차)**. `채용욱 상담 · 4회차` |
| 진행자 | 지도사(화면) / 강사(데이터·권한) | 상담사 |
| 참여자 | 회원(참가자) | 내담자 |
| 코드 | 클래스 코드(4자리) | 상담 코드(4자리, 비회원 전용) |
| 데이터·API | `classes`, `class_instructors`, `class_members` | `counseling_relationships`, `counseling_guests` |
| 공통 하위 | `sessions` (진행·입장·뇌파·녹음·리포트 엔진 공유) | |

화면 문구 규칙은 영역별 용어 사전 한 곳에서 읽는다(`R8 §4`): 명상 = `클래스`/`N회차`/`지도사`, 상담 = `상담`/`상담 세션`/`상담사`/`내담자`. 명상 화면에 `세션`·`수업`·`오픈` 금지, 상담 화면에 `클래스`·`수업`·`오픈` 금지(단독 `세션` 금지, `상담 세션` 허용).

### 4.2 개체 관계 (ER 텍스트)

```
organizations 1 ──< classes 1 ──< class_instructors >── users          [명상]
                    classes 1 ──< class_members     >── users | (비회원)
                    classes 1 ──< sessions (회차, class_id, seq, host_id→class_instructors)

organizations 1 ──< counseling_relationships                           [상담]
   counseling_relationships ── counselor (현재 담당) ── counseling_relationship_counselors (이력)
   counseling_relationships ── client_user_id (회원) | client_guest_id → counseling_guests (비회원)
   counseling_relationships ── link_id ── client_counselor_links (약결합, 자동 생성 금지)
   counseling_relationships 1 ──< sessions (회차, counseling_relationship_id, seq, host_id)

sessions 1 ──< session_participants (회차 출석 행; member_id → class_members | guest_client_id → counseling_guests)
sessions 1 ──< reports | session_records | audio/video chunks | eeg_* | chat_rooms | ...   [엔진, 무변경]
sessions: (class_id) XOR (counseling_relationship_id)   -- 비템플릿 세션은 정확히 하나

보조: class_member_events · counseling_relationship_events · session_host_history ·
      guest_claim_events · session_migration_map · class_templates
```

### 4.3 개체·속성·불변식 표

| 개체 | 핵심 속성 | 상태 | 핵심 불변식 (전체: `기획-상세-상태머신권한.md` §6, `기획-상세-강사모델.md` §5) |
|---|---|---|---|
| **클래스** `classes` | 이름, 센터(`organization_id` 스냅샷), 개설자, `schedule_mode`(`fixed`/`rolling`), 계획 횟수, 정원, 참여 방식, LINK BAND 모드, 녹음 설정, 기본 일정(`recurrence_rule`)·배정 규칙(`assignment_rule`), 클래스 코드 | `draft`·`active`·`completed`·`cancelled`·`archived` | 활성 강사 ≥1·주강사 ≥1, 코드는 활성 클래스 간 유일, 삭제=숨김(진행/완료 회차가 있으면 보관만) |
| **클래스 강사** `class_instructors` | 사용자, 역할(`lead`/`assistant`/`guest`), `status`(`active`/`removed`), `scope_session_id`(guest 한정) | | `(class_id, user_id)` 유일, 제거는 soft(행 삭제 금지) |
| **멤버십** `class_members` | 회원/비회원, 상태, 합류 경로, `first_session_id`, 리포트 반영 기본값, 비회원 PII | `invited`·`waitlisted`·`active`·`completed`·`left`·`removed`·`declined` | 한 사람 한 클래스 1행(재가입은 되살림), 이탈해도 과거 출석·리포트는 가시 |
| **상담 관계** `counseling_relationships` | 상담사, 내담자(회원/비회원), 표시명, 상담 유형, 기본값, 관계 코드 | `pending`·`active`·`closed`·`archived` | 내담자 정확히 1명, 현재 상담사 정확히 1명, 같은 쌍의 비-archived 관계 최대 1개, 종결·보관은 데이터를 지우지 않음 |
| **세션(회차)** `sessions` | 부모 FK 2개 중 1개, `seq`, `session_kind`(`regular`/`makeup`), `host_id`(진행자), `host_state`, 일정·방식·상태 | `ready`·`scheduled`·`open`·`in_progress`·`completed`·`cancelled` (현행) | 진행자 정확히 1명(해당 클래스 강사), `seq` 유일·재사용 금지, `id` 불변 |
| **출석** `session_participants` | `member_id`/`guest_client_id`, `attendance_status`, `attendance_kind`, `makeup_for_session_id`, 입장 시각, 리포트 반영·동의 | `expected`·`attended`·`absent`·`excused`·`withdrawn` | `(session_id, member_id)` 최대 1행, 합류 전 회차 행 없음, `id` 불변 |
| **비회원 내담자** `counseling_guests` | 이름·이메일·(성별·생년월일), 재방문 자격 해시·버전, 동의 증빙, 전환 정보 | `registered`…`scrubbed` | 평문 비밀 저장 금지, 상담사 단위 격리, 스크럽 후에도 참조 유지 |
| **리포트** `reports` | 회차×참여자×유형, 승인축·생성축 상태, `approved_by_user_id`·`approved_at` | `pending_analysis`·`pending_review`·`completed`·`error` | 결석은 행 없음, 제외 참여자는 모든 파생물에서 제외, 승인 후 소유 불변 |

### 4.4 명상 클래스와 상담의 차이 (`브리프-추가2.md` 표 검증·보완)

| | 명상 클래스 | 상담 |
|---|---|---|
| 상위 단위 | 클래스(프로그램) | 상담 관계(내담자 1 + 상담사 1) — 기존 `client_counselor_links` 를 **확장하지 않고 신설**(§5 #1) |
| 하위 단위 | 세션(회차), 진행 강사 정확히 1명 | 상담 세션(회차), 진행자 = 관계의 상담사 |
| 강사 | 클래스 강사 ≥1, 세션별 1명 배정 | 상담사 1명(관계 단위). 교체/이관은 별도 시나리오(Phase 8) |
| 정원·대기열 | 있음(멤버 정원 + 회차 상한) | 없음(1:1, 서버가 강제) |
| 4자리 코드 | 클래스 코드 | 관계 코드(비회원 전용), 회원은 로그인 기반 |
| 비회원 | 클래스 멤버(장기 자격 + 지도사 병합) | 비회원 내담자(관계 단위 신원 + 재방문 자격 + 회원 전환) |
| 마법사 | 4단계 + 완료 | 3단계 + 완료 |
| 리포트 | 클래스 단위 추이·서사 + 변화량(점수 환원 금지), 일괄 승인 | 상담사용 + 내담자용, 기록지·승인 흐름(상담사 승인 필수, 자동 승인 기본 off, 기본 포함) |
| 종결 | 클래스 `completed`/`archived` | 관계 `closed`/`archived`(데이터 보관) |
| 회원 쪽 | **내 클래스** | **내 상담** |
| 공유 엔진 | 진행 화면(SDD-208), 입장 전 흐름(SDD-209), 뇌파, 녹음·STT·요약, 리포트 생성, 알림 | (동일) |

### 4.5 엔진 공유 가능성

`sessions.type`(clinical·hypnosis·meditation·custom)으로 **엔진이 갈라지는 곳은 3종뿐**(STT 화자 프롬프트, 요약 템플릿, 신규 입력에서 사실상 무효인 정원 정규화)이라 엔진 무변경이 가능하다(`R10 §0`). 영역은 type 이 아니라 부모 FK 로 결정한다.

## 5. 확정 · 기술 기본값 · 조사 간 충돌 정리

조사 10건이 독립적으로 수행되어 같은 사안에 다른 제안이 나온 곳을 한 줄로 확정한다. **기술 선택이므로 Brian 결정 항목이 아니다**(번복 시 이름 치환 수준의 영향만 있다). 비즈니스 성격이 남는 것만 `D-nn` 으로 넘긴다.

| # | 사안 | 제안들 | 이 문서의 확정(기본값) | 근거 |
|---|---|---|---|---|
| 1 | **상담 관계의 뿌리** | R1·R5: `counseling_relationships` 신설 + `link_id` 약결합 / R10: `client_counselor_links` 확장 | **신설 + 약결합** | 링크는 회원 전용·`ended` 로 바꾸는 코드 0건·`ended` 의미가 "상담사 접근 차단"이라 반대·생성이 채팅/AI 비서 권한을 자동 부여·계정 삭제 시 DELETE. 이전 시 링크를 자동 생성하지 않는 것을 테스트로 고정(`기획-상세-상담.md` §2) |
| 2 | 상위 구조(상위가 둘) | A 부모 테이블 2개 + `sessions` FK 2개 중 1개 / B 공통 `programs` / C 별도 세션 테이블 | **A** | 상담 1:1 을 컬럼 구조로 보장, 명상 전용 컬럼이 상담에 NULL 로 퍼지지 않음, MATCH SIMPLE 복합 FK, C 는 엔진 FK 13개 + 값 6개와 충돌(`R1 §7`) |
| 3 | 진행자 컬럼 | `instructor_id` 신설(브리프) vs `host_id` 의미 확정 | **`host_id` 유지**(이름·NOT NULL), 의미를 "진행 강사"로 확정 | 코드 89줄/23파일·테스트 72줄·구 앱 응답 필드, 이중 저장 방지(`R1 §13`) |
| 4 | 회차 번호 컬럼 | `session_no`(R2) vs `seq`(R1·R5) | **`seq`**, 보강 구분 `session_kind`(`regular`/`makeup`) | 취소돼도 재사용하지 않음 |

| 6 | 비회원 신원 테이블명 | `counseling_guest_clients`(R1) vs `counseling_guests`(R10) | **`counseling_guests`**(컬럼은 R1 안) | |
| 7 | 상담 관계 상태 이름 | `closed`(R1) vs `ended`(R10) | **`pending`·`active`·`closed`·`archived`** | `ended` 는 링크의 반대 의미와 충돌 |

| 19 | 에러 문구 | 서버 `detail` 일괄 치환 / 프론트 코드 매핑 | **프론트 코드 매핑**, 서버 `detail` 은 로그·API 계약 유지 | 서버 `detail` 63곳 |
| 20 | 클래스 룸 WS | 클래스 룸 신설 / 알림 경로 | **룸 신설 안 함**(`session:{sid}` 형식 하드코딩 구 앱 보호), 알림 `params` 가산 | 룸 수명·권한 표면 증가 |

## 6. 사용자 시나리오

각 시나리오는 **사용자 행동 → 시스템 동작 → 관련 상태/결정** 순이다. 화면 문구는 해요체이며 대표 예시다.

### 6.1 상담사·지도사

#### S-A1. 8회 MBSR 봄 클래스 — 개설 → 초대 → 회차 진행 → 결석 → 보강 → 중간 합류 → 이탈 → 마무리

| 단계 | 사용자 행동 | 시스템 동작 | 상태·결정 |
|---|---|---|---|
| 1 개설 | 지도사 김지수가 `명상 클래스 → 클래스 만들기`. ① 이름 `MBSR 봄`, 온라인, 정원 12 ② `정해진 횟수`, 11/3 시작, 월요일, 19:00, 60분, 8회, 리마인더 하루 전 ③ 회차 표 확인(모두 김지수) ④ 초대(회원 5명 선택 + 이메일 3개) → 만들기 | **한 트랜잭션**: 클래스(`active`) + 회차 8행 + 강사(김지수 `lead`) + 리마인더 예약 + 클래스 코드 1개 + 멤버 5명 `active`(출석 `expected` 8행씩) + 비회원 초대 메일 3통. 알림은 클래스 단위 1통 | C2, M1, A1 / 충돌 있으면 `겹쳐요` 표시만 |
| 2 코드 공유 | 완료 화면에서 4자리 코드 복사 | 클래스 코드 유효(클래스 `active` 동안) | |
| 3 회차 진행 | 1회차 15분 전 홈 `곧 열 회차`에서 `열기` → 대기실 → `시작하기` → 종료 | 세션 `open` → `in_progress` → `completed`. 입장자 `attended`. 종료 후 STT → 요약 → 리포트 체인, 출석 확정 훅 | 엔진 무변경 |
| 4 결석 | 3회차에 회원 A 가 입장하지 않음 | 종료 후 A 의 3회차 `absent`(system). 지도사 화면 `결석 2명`, 알림 `class_absence_recorded` | A5, `D-06` |
| 5 보강 | 지도사가 클래스 상세 `회차`에서 `보강 회차 추가`(11/29, 대상 A) | `session_kind='makeup'`, A 의 `makeup` 출석 `expected`. A 에게 `makeup_offered` 알림 | A1, `makeup_for_session_id`, 분모(N) 불포함 |
| 6 중간 합류 | 4회차 전 새 회원 B 가 코드로 입장 | 멤버십 `active`(정원 여유), `first_session_id`=4회차, 4회차~ `expected` 행만 생성, 지난 회차 행 없음 | M1, `D-07` |
| 7 이탈 | 회원 C 가 6회차 전 `클래스에서 나가기` | 멤버십 `left`, 6~8회차 `withdrawn`, 정원 반환·대기자 승격, 지도사 알림. C 의 지난 리포트 열람 유지 | M6, A6, `D-12` |
| 8 마무리 | 8회차(및 보강) 종료 | 클래스 자동 `completed`, 코드 무효화, 멤버십 `completed`, 완료 알림 | C5, M8 |
| 9 리포트 | 클래스 상세 `리포트` 탭에서 `대기 중인 리포트 모두 승인` | 건별 멱등 승인, `skipped`/`failed` 내역 표시, 코멘트 없는 N건 경고 | `D-36` |

#### S-A3. 상담 1:1 (상담사 채용욱 ↔ 내담자 회원 김하늘) — 시작 · 반복 · 종결 · 재개

|---|---|---|---|
| 1 시작 | `상담 → 새 상담 시작`. A `기존 내담자` 선택 → B 매주 목 19:00, 50분, `4회 먼저 잡기` → C 확인·동의 안내 | 관계 생성(회원이면 `active`), 첫 회차 `seq=1` 외 4개, 리마인더, 내담자에게 상담 초대 알림. **클릭 4번 목표** | R2, `D-02`·`D-03` |

| 단계 | 사용자 행동 | 시스템 동작 |

| 7 보관·삭제 | 종결 후 | 비회원 PII 는 종결일 + 90일 후 스크럽(`D-50`), 스크럽 후 리포트 재발송·본인 재확인 불가 고지 |

### 6.2 회원

#### S-M1. 결석 → 보강 안내 → 보강 참석

| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| 1 | 회원 A 가 3회차에 못 간다고 미리 알림(`그날 못 가요`) | 출석 `excused`, 회차 정원에서 빠짐 |
| 2 | 홈 `내 클래스` 카드에 `보강 대기 1` 배지, 클래스 상세 `놓친 회차가 1개 있어요. 보강으로 채울 수 있어요` | 파생 상태: 결석 행이 있고 `makeup` 출석 없음 |
| 3 | 알림 `makeup_offered` → 보강 회차 `11/29` 선택 | 출석 `makeup` `expected`(회차 정원 상한 검사) |
| 4 | 보강 입장·참석 | `attended`, 보강 리포트는 보강 회차 소속, 추이에서 원 회차 위치에 `보강` 표식. 카드 `내 참석 7회 · 결석 1회 · 보강 완료 1회` (등급·% 없음) |

#### S-M2. 중간 합류 · 비회원 장기 참가

| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| 1 | 회원이 4회차 전에 코드 입력 | 멤버십 생성, 4회차부터 `expected`. 지난 회차는 일정만 보임, `합류 전 회차예요` |
| 2 | 비회원이 같은 코드로 입장, 이름·성별·생년월일·이메일 입력(클래스당 1회) | `class_members(kind='guest')` + 클래스 단위 장기 자격 발급 |
| 3 | 다음 회차 | 자격 유효 → 코드 재입력 없이 같은 멤버로 출석. 앱 홈은 없고 `/class/{id}` **한 화면**(다음 회차·내 출석 요약·본인 리포트 링크) |
| 4 | 기기를 바꿈 | 새 멤버가 만들어질 수 있음 → 지도사 `같은 사람 합치기` |

#### S-M3. 내 상담 (회원)

| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| 1 | 홈 `내 상담`에서 `상담 신청하기` | 상담사에게 채팅 메시지 신청(현행 방식), 상담사가 관계 생성 |
| 2 | 알림 `{상담사}님이 상담에 초대했어요` → 다음 상담 카드 | 관계 `active`, 회원이면 로그인 기반 입장(코드 불필요) |
| 3 | 상담 후 리포트 | 상담사 승인 후 `상담 리포트가 준비됐어요`, 내 리포트 목록에 영역 칩 |
| 4 | `상담 마무리하기` | 회원도 종결 가능, 이후 읽기 전용, `다시 시작하기`로 재개(내담자가 종결한 건은 단독 재개) |

#### S-M4. 이탈 후에도 지난 기록 보기

| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| 1 | 회원이 `클래스에서 나가기` → 확인 시트 | 멤버십 `left`, 미래 출석 `withdrawn`, **과거 출석 행에 `removed_at` 을 쓰지 않음** |
| 2 | 지난 리포트 열람 | 허용(본인 데이터, `Report.user_id` 기준) |
| 3 | 재가입 | 같은 행 되살림, 이탈 중이던 회차 행은 만들지 않음 |

### 6.3 센터(기관) 관리자

#### S-C1. 강사 퇴사에 따른 미래 회차 재배정

| 단계 | 시스템·행동 |
|---|---|
| 1 | 박서연 계정 정지 → 미래 회차 3개가 **숨겨지지 않고** `needs_reassign`, 센터 관리자·주강사에게 `session_host_released` 알림 |
| 2 | 센터 관리자가 클래스 상세에서 일괄 재배정(대행) |
| 3 | 시작 72h/24h 전까지 남으면 재알림 + 홈 최상단 `진행자 필요` 배지. 회원 알림은 재배정/취소 **확정 시점**에만 |

#### S-C2. 현황 점검

센터 관리자 화면은 **메타·업무 지표만**: 클래스 목록, 회차 수, 미배정 회차, 클래스별 승인 대기 건수·가장 오래된 대기 일수. 강사별 순위·성과 화면은 없다. 상담 영역은 건수·일정만, 기록·리포트 본문은 비공개 (`D-28`·`D-35`·`D-41`).

#### S-C3. 상담사 교체(이관)

상담사 퇴사/휴직 시 센터 관리자가 이관 → 기존 관계 `closed`(reason=`counselor_transfer`) + 새 상담사와 새 관계(이전 관계 연결). 과거 세션·리포트 귀속은 이전 상담사 그대로, 새 상담사는 **요약·리포트만(내담자 동의)** 열람, 예정 세션은 취소 후 재예약. 승인 대기 리포트는 센터 관리자가 대리 승인. (Phase 8, `D-58`·`D-59`)

#### S-C4. 클래스 개설·강사 구성 대행

센터 관리자는 강사 추가·제거, 주강사 지정, 회차 편성·변경을 **대행**할 수 있으나 회차를 직접 열기·시작·종료하지 못하고 리포트 승인도 하지 못한다 (`D-25`).

  2. 분류 함수 1개(백필과 `POST /sessions` shim 공유, 순수 함수 + 단위 테스트 8행 + 경계).

  5. 읽기 API: `GET /classes`, `GET /classes/{id}`, `GET /classes/{id}/sessions`, `GET /counseling`, `GET /counseling/{id}`. 기존 응답에 `class_id`·`class_title`·`seq`·`area` **가산**.

### Phase 8 — 출시 점검·공통 정리 (8-A / 8-B 분리)

**8-A — 클래스 출시 전 점검**: Phase 0~5 이후 진행한다. 클래스 관련 홈·센터 관리자 현황 및 문구·알림에서 출시 필수 누락을 선별하고, Phase 2 이월 항목을 출시 필수/후속으로 분류한다. 상담 공개 여부에 따른 메뉴·직접 진입·공유 권한을 점검한다. 실제 통합 여정, 배포·운영 점검과 릴리스 승인을 완료한다. 이 구분은 출시 순서에 맞춘 계획 조정이며 상세 작업은 후속 SDD에서 확정한다.

**8-B — 상담 업데이트 이후 공통 정리**: 아래 원안 중 상담사 이관·상담 현황·두 영역 통계와 남은 레거시 제거를 담당한다. 전체 contract·구 앱 지원 종료를 클래스 첫 출시의 필수 조건으로 두지 않는다. SDD-214에서 이미 적용한 부모 제약은 재구현하지 않고 실제 스키마 기준으로 잔여 항목을 재산정한다.

- **목표**: 임시 호환 장치를 걷어내고 두 영역을 정합시킨다.
- **포함**: 홈 통계 `by_area` · **상담사 이관**(관계 종결 + 새 관계, 새 상담사 열람은 내담자 동의) · 센터 관리자 클래스·상담 현황(메타·업무 지표) · **contract M6**(`ck_sessions_one_parent` CHECK, `seq`/부모 필수화, `sessions.access_code` 쓰기 중단) · 템플릿 → `class_templates` 이사, `run_id`/`new-run` 폐기 결정 · 레거시 라우트·shim 정리 · 구 앱 호환 종료 · 서버 문구 코드 매핑 마무리.
- **선행**: Phase 0~7, 구 앱 지원 종료 확인 · **규모**: BE M / FE S
- **롤백**: **M6 이후 구 코드 복귀 불가**(구 INSERT 가 CHECK 위반) → M0 와 같은 수동 스냅샷 선행, 레거시 호출이 0 에 수렴한 뒤에만
- **출시 단위**: 2회 — 정리(비파괴) → M6
- **완료 기준**: 레거시 호출 0 수렴, V1~V19 재통과, 스냅샷 확보
- **관련 결정**: `D-58`·`D-59`·`D-61`

### 의존 관계

```text
P0 → P1 → P2 마감 → P3 → P4 → P5 → P8-A → 클래스 우선 출시
                                              ↓ 별도 착수 승인
                                      P6 → P7 → P8-B
```
상담은 구조상 Phase 1·2 기반을 재사용할 수 있으나, 출시 계획에서는 Phase 3~5와 병렬 착수하지 않는다. 클래스 운영 기능을 먼저 완성하고 상담은 후속 업데이트로 제공한다. 이미 구현된 상담 기반과 상세 기획은 후속 작업에 재사용한다.

### 11.3 이전 규칙 요약 (`R7 §4`, `기획-상세-상담.md` §9)

단일 분류 함수: 템플릿 제외 → `meditation` → 명상 클래스 / `clinical`·`hypnosis` 는 활성 참여자 수로 분기(≥2 → 클래스·라벨 유지, =1 회원 → 관계(회원 쌍 묶기), =1 비회원 → 관계(세션당 1), =0 → placeholder 관계) / `custom` 은 그룹이거나 ≥2 → 클래스, 아니면 상담(+라벨 지정표). 세션은 `class_id`/`counseling_relationship_id` + `seq` 만 채우고 **기존 컬럼은 건드리지 않는다**(세션이 유효값 보유). 명상: `class_instructors(host_id, lead)` 1행, 참여자마다 `class_members` 1행(상태 백필: `removed_at` → `removed`/`withdrawn`, `waitlist_cancelled_at` → `left`/`withdrawn`, `is_waitlisted` → `waitlisted`/`expected`, 입장 → `attended`, 입장 정보 없음 → **결석으로 단정하지 않고 `expected`**). 링크는 생성하지 않음. 숨김 세션도 이전(원시 SQL, ORM 필터 우회). 테스트 데이터도 삭제하지 않는다. 분류 불가는 `unclassified` 보고 후 중단.

### 11.4 호환 요약 (`R7 §6`)

구 앱은 서버가 앱 버전을 구분할 수 없어(버전 헤더·강제 업데이트 코드 0건) 호환을 **무조건 적용**한다. 세션 id·참여자 id 불변으로 알림 딥링크·초대 메일(코드만 본문)·입장 자격 JWT(24h)·리포트 토큰(7일)·S3 키·Celery 인자·WS 룸 이름이 변환 없이 산다. `/sessions/*` 61개 경로 유지(응답은 필드 가산만), 구 앱의 클래스 단위 필드 수정은 `origin ∈ {migrated, shim}` 이고 세션 1개뿐일 때만 클래스에 동기화(write-through), 마지막 가시 세션 삭제 시 클래스도 숨김.
