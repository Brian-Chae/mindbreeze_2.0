# 체크인 질문 화면 — 디자인 검토용 3안

제품 구현 전 시안만 제작했다. `frontend/` 제품 코드는 수정하지 않았다.

## 보기

`index.html`을 Chrome에서 직접 열면 비교 페이지가 나온다. 웹 서버나 빌드가 필요 없다. 상단 버튼으로 세 안을 동시에 집중/감정, 선택 전/후로 전환한다. 각 프레임에서 실제 선택·다음·건너뛰기를 시험할 수 있다. 데스크톱은 ‘전체 화면 열기’ 링크를 사용한다.

- A: `index.html?v=A` — 질문이 먼저. 중앙의 큰 질문과 독립적인 밝은 카드로 읽는 순서를 단순하게 만든다. 사진 위에는 블러 대신 균일한 어두운 스크림을 사용한다.
- B: `index.html?v=B` — 한 장에 모으기. 불투명한 종이색 패널 안에 질문과 연결된 세로 보기를 모은다. 사진은 주변에서 자연 이미지 톤을 유지한다.
- C: `index.html?v=C` — 느낌의 흐름. 숫자·아이콘 없이 단어만 이어지는 5단계 선택. 데스크톱은 가로 연속 스케일, 모바일은 위→아래 연속 목록이다. 감정 라벨이 길어도 줄임 없이 읽힌다.

직접 열기 URL 예: `index.html?v=B&q=emotion&selected=4`. `4`는 원래 내부 선택 값이며 화면에 점수로 노출하지 않는다.

## 추천

**B를 추천한다.** 질문·보조문구·내부 진행·보기를 한 불투명 패널에 모아 사진의 밝은 구름과 시선 경쟁을 줄인다. 회원이 지금 상태를 묻는 질문과 답을 가장 안정적으로 읽을 수 있다. 기존 세로 라디오 구조를 유지하므로 C보다 적용·회귀 검증 범위가 작다. A는 자연 사진의 몰입감, C는 단계 사이 연속성을 더 강조하고 싶을 때의 대안이다.

## 두 진행 표시의 역할

상단 점 다섯 개는 클래스 **입장 전체 진행**, 집중·편안함·감정·전할 말은 **체크인 내부 문항 진행**이다. 현재 코드도 클릭 가능한 탭이 아닌 상태 표시이므로 시안 역시 비대화형 목록으로 유지한다. `aria-current="step"`으로 현재 문항을 알린다.

- A: 질문 아래 네 항목을 얇은 밑줄로 표시한다.
- B: 패널 맨 위에 네 항목을 모아 질문 영역과 구분한다.
- C: 현재 문항만 밝은 캡슐로 강조한다.

상단에 ‘클래스 입장 준비’를 더해 두 진행 표시를 구분했다. 전체 진행의 활성 위치는 시안용 예시이며, 실제 적용 시 기존 `steps` 값을 유지한다. 점은 요구대로 5개를 남겼고 내부 문항용 점은 추가하지 않았다.

## 실제 자산·문구

- 사진: `frontend/public/images/background3.webp` — 현재 `FadingImageBackground.tsx`가 쓰는 10개 자연 이미지 중 하늘·구름 사진을 정지시켰다.
- 토큰: `player/shared/player-tokens.css`의 `#5F0080`, `#D2AEFC`, `#F7F4F0`, `#CFC6D6`, 반경 16/24px. 어두운 텍스트는 `DESIGN.md`의 `#241B2E`를 재사용했다. 새 시안 보조색 `#51415D`는 밝은 패널용으로 별도 정의했다.
- 글꼴: 제품 `mb-tokens.css`의 Pretendard Variable 및 Noto Sans KR 로딩을 재사용한다. 인터넷 연결이 없으면 기존 토큰의 OS 글꼴 fallback이 적용된다. 캡처 시 Pretendard 로딩 확인.
- 질문: `member-survey.ts`의 제목·보조·칩, `checkin.ts`의 `SAM_AXES` 보기·값을 추출한 `survey-data.js`. 집중·편안함·감정·전할 말을 모두 시험할 수 있다.
- 다음: 축 질문 미선택 시 비활성, 선택 시 활성. 전할 말은 선택 입력, 200자 제한이다.
- 건너뛰기: 기존 `onSkip`처럼 전체 체크인 종료를 모사한다. 현재 문항만 넘기지 않는다. 초안은 유지하고 실제 저장/API/클래스 입장은 수행하지 않는다.
- 선택 상태는 색뿐 아니라 A/B의 라디오 표시, C의 면과 테두리로 구분한다. 라디오 그룹은 방향키·Home·End 및 스페이스 선택을 지원한다.

## 측정·검증 결과

Chrome 실행 파일은 `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`. 모바일 390×844, 데스크톱 1440×900, DPR 1. A/B/C 각각 집중·감정 × 선택 전·후 × 두 뷰포트 = **24개 캡처**이며 `screenshots/`에 저장했다. `comparison.png`는 비교 페이지다.

실제 구름 사진을 렌더한 상태에서 글자만 투명하게 만든 두 번째 캡처를 만들고, 각 텍스트 노드의 사각형에 포함된 **모든 배경 픽셀**과 실제 computed 전경색 사이 WCAG 상대휘도 대비의 최솟값을 계산했다. 글자 안티앨리어싱 픽셀을 대비에 포함하는 방식이 아니다. 불투명 카드·패널은 그 합성 표면색을, 사진 위 문구는 사진+스크림 합성색을 측정한다. 제목·보조·단계·보기·다음·건너뛰기·상단 안내를 포함하며 비제품 시안 라벨은 제외한다.

- **A 최소 7.811:1**, 24개 상태 중 A 8개 화면의 전체 텍스트 최소값.
- **B 최소 8.128:1**, B 8개 화면의 전체 텍스트 최소값.
- **C 최소 8.128:1**, C 8개 화면의 전체 텍스트 최소값.
- 제목: 모바일 모두 28px / 데스크톱 A 40px, B 36px, C 44px.
- 보기: 모두 18px. 선택 영역 높이 A 58px+, B 60px+, C 모바일 58px+·데스크톱 112px+.
- 모든 버튼 너비·높이 48px 이상, 문서 가로·세로 넘침 없음, blur/backdrop-filter 없음.
- A/B/C 실제 클릭으로 선택→다음, 방향키 선택 변경, 전체 건너뛰기 및 초안 보존 검증 통과.
- 독립 검증자가 6개 대표 캡처와 소스 문구·동작을 교차 검토했다. 초기 A/C 제목 색 상속 문제를 발견해 시안 내 명시 색으로 수정 후 전 캡처·측정 재실행.

수치 원본은 `capture-metrics.json`, 텍스트별 대비·최저 배경 RGB는 `contrast-results.json`. 캡처 재현: 저장소 루트에서 `node designs/checkin-question/capture.cjs` 다음 `python3 designs/checkin-question/measure-contrast.py`. Playwright는 원본 저장소 설치본을 절대 경로 require로 재사용하며 필요하면 `CHECKIN_PLAYWRIGHT`로 경로를 지정한다. Python Pillow가 필요하다. node_modules 설치·심링크는 생성하지 않았다.

측정은 위 사진·뷰포트·정지 상태에 대한 증거다. 실제 제품의 10개 사진 교차 페이드, 모바일 키보드, 실제 저장 중/실패 상태 및 API 연결 검증을 대신하지 않는다. 모든 이미지에서 대비를 보장하려면 실제 적용 단계에서도 사진 교체 시 확인이 필요하다. B 본문 패널은 불투명하므로 사진 변화의 영향을 받지 않는다.
