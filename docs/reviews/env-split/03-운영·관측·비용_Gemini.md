## 2. 목표 상태

### 2-1. 관측·모니터링 체계 (비용 비교 및 최소 구성 추천)

| 도구 후보 | 월 추정 비용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **CloudWatch + Sentry** | **월 $25~35** | AWS 네이티브 메트릭 + 상세 코드 스택/에러 추적 전문. 설정 간결 | 메트릭/에러 콘솔 분리 | **강력 추천 (최소 비용 최적 효율)** |
| Datadog / New Relic | 월 $150+ | 올인원 APM(애플리케이션 성능 모니터링) | 초기 스타트업 비용 부담 극심 | 탈락 (과투자) |
| Grafana + Loki + Prometheus | 월 $20 (자원비) | 라이선스 무료 | 단일 EC2 자원(RAM/CPU) 잠식 심각, 운영 공수 과다 | 탈락 (운영 부담) |

- **헬스체크 심화**: Liveness(`/health/live`, 프로세스 생존)와 Readiness(`/health/ready`, DB SELECT 1 + Redis PING + Celery PING)로 분리.
- **알림 채널 & 심각도**: Telegram 봇 연동 (비용 $0, 모바일 즉시 수신).
  - P1 (치명: 전면 다운, DB 접속 불가): 즉시 호출, 30분 내 조치.
  - P2 (중대: Celery 큐 적체 > 100건, 리포트 생성 실패율 > 5%): 1시간 내 확인.
  - P3 (경미: 단발 500 에러, cron 1회 실패): 익일 업무시간 확인.

### 2-2. 서비스 수준 목표 (SLO / SLA 초안)

| 지표 | 목표 (SLO, Service Level Objective) | 대외 약속 (SLA, Service Level Agreement) | 측정 방식 |
|---|---|---|---|
| **가용성** | 월간 99.5% (월 허용 다운타임 ~3.6시간) | 월간 99.0% (초과 시 이용료 보상) | 외부 업타임 모니터(BetterStack/UptimeRobot 무료) |
| **API 응답 지연** | p95 < 500ms (일반 CRUD) | p95 < 1,500ms | CloudWatch / Sentry 트레이싱 |
| **EEG 스트리밍** | 왕복 지연 < 150ms, 연결 끊김 < 1% | 왕복 지연 < 300ms | Socket.IO 핑퐁 메트릭 |
| **에러율** | 전체 HTTP 요청 중 5xx 비율 < 0.1% | 5xx 비율 < 0.5% | Nginx 액세스 로그 분석 |

### 2-3. 부하 용량 & 확장 트리거 (실측: 2vCPU 한계 80~100 RPS, EEG 동시 80명)

- **Phase 1~2 prod 권장**: EC2 t4g.medium (2vCPU / 4GB RAM) + RDS db.t4g.small (Single-AZ 암호화).
- **확장 트리거**: ① CPU 5분 평균 > 70% ② 동시 뇌파 측정 세션 > 40건 ③ RPS > 60 지속 도달 시 → EC2 2대 분리(API/워커 분리) 승격.

## 3. 단계별 로드맵 (실사용자 무중단/저중단 전환 계획 포함)

### Phase 0 — 즉시 관측·방어선 구축 (1~2일, 비용 $0, 운영 없이 적용)

| 산출물 | 내용 | 선행조건 | 롤백 |
|---|---|---|---|
| 헬스체크 분리 | `/health/ready` 신설 (DB/Redis 점검). 배포 스크립트 롤백 트랩 연동 | 없음 | 구 `/health` 복원 |
| 로그 고갈 방지 | cron 로그 14개(`/var/log/mindbreeze-*.log`)에 logrotate 적용 | 없음 | crontab 복원 |
| Telegram 긴급 알림 | 백엔드 미처리 500 및 Celery 태스크 최종 실패 시 Telegram 웹훅 발송 | Bot 생성 | 핸들러 비활성화 |
| 외부 업타임 감시 | BetterStack(무료) 1분 주기 감시 + 장애 시 SMS/전화 알림 연동 | 계정 생성 | 감시 해제 |

### Phase 1 — 관측 도구 정착 & 점검 모드 준비 (3~5일)

- 산출물: Sentry 연동(FastAPI + React), CloudWatch 메트릭 경보(디스크 80%, CPU 70%), Nginx 503 점검 모드(`maintenance.html` 서빙 + 관리자 IP 우회).
- 선행조건: Phase 0 완료, D11·D12 결정.
- 롤백: 환경변수 플래그 비활성화.

### Phase 2 — 운영 데이터 이관 & 전환(컷오버) (1일, 30~60분 점검창)

- **전환 절차**:
  1. **사전 공지**: 내담자/상담사에 D-3, D-1 점검 일정 안내 (야간 22:00~23:00).
  2. **쓰기 차단**: dev Nginx 점검 모드 활성화 (503 응답으로 신규 쓰기 차단).
  3. **데이터 이관**: RDS dev 스냅샷 → prod 복원(암호화 적용) → 최신 변경분 검증.
  4. **도메인 컷오버**: DNS `mindbreeze.looxidlabs.com`, `api.mindbreeze.looxidlabs.com`을 prod 인프라로 연결.
  5. **스모크 테스트**: 로그인, 실시간 EEG 수신, 리포트 생성, 이메일 발송 검증.
  6. **점검 해제**: prod Nginx 정상 오픈, dev 도메인은 유지보수/개발 모드로 전환.
  7. **dev DB 비식별화**: 뇌파 Raw/음성/전사 텍스트 파기, 개인정보 마스킹 후 개발 데이터로 격하.
- 롤백: DNS 레코드를 즉시 dev로 복구 (점검 중 쓰기가 차단되었으므로 데이터 정합성 손실 0).

### Phase 3 — 운영 프로세스 & 규정 준수 안정화 (2~3주)

- 산출물: 뇌파·상담 기록 열람 감사 로그 테이블, 데이터 정정 수동 쿼리 승인 절차서, 개인정보 사고 대응 매뉴얼, 포스트모템 템플릿 정착.

## 6. 에이전트가 알아서 처리할 기술 사항 (결정 불필요)

- FastAPI `/health/ready` 엔드포인트 구현 (SQLAlchemy `SELECT 1`, Redis `PING`, Celery `inspect.ping`).
- Unhandled Exception 핸들러 및 Celery failure 핸들러에 Telegram 알림 훅 연결.
- Nginx 점검 안내 템플릿(503 Maintenance) 및 토글 스크립트 작성.
- `/var/log/mindbreeze-*.log` 파일에 대한 일 단위 `logrotate` 설정 적용.
- CloudWatch 에이전트 설치 스크립트 및 기본 대시보드(CPU/Memory/Disk/DB Connection) 구성.
- 표준 포스트모템(장애 보고서) 및 릴리스 체크리스트 템플릿 문서화.
