# MIND BREEZE 2.0 — 개발/운영 환경 분리 + 안정적 개발·운영 시스템 기획 (조사 브리프)

## 임무 공통 규칙
- 이 작업은 **기획 리뷰**다. 코드/인프라를 수정하지 말고 `읽기 전용`으로 저장소(/Volumes/Looxid SSD/looxid/repository/mindbreeze_2.0)를 조사한다. (서버 SSH·AWS 변경 금지)
- 한국어, **개조식**. 한정용어(영문 약어 남발) 금지, 표준 약어만 허용(CI/CD, RDS, SLO 등은 최초 1회 풀이).
- 모든 주장은 `파일:라인` 또는 아래 [확정 사실]에 근거. 추측은 "추정"이라 표기.
- 결과는 지정된 산출 파일 1개에 마크다운으로 저장. 분량 200줄 이내, 표 적극 사용.
- 비즈니스 결정(비용·위험 감수·일정)과 기술 처리(에이전트가 알아서 할 것)를 **분리**해서 적는다. 결정 항목은 선택지+추천+근거 3줄 이내.

## 서비스 개요
뇌파(EEG) 기반 심리상담·명상 플랫폼. 사용자: 상담사/내담자/기관관리자. 웹(React SPA)+Capacitor 하이브리드 앱(Android/iOS)+FastAPI 백엔드+Celery 워커+LiveKit(화상)+Redis+PostgreSQL(RDS). 실사용자가 이미 **dev 서버를 실서비스처럼** 쓰고 있다(운영 환경 없음).

## [확정 사실] (2026-10-10 실측)
### 환경
- 운영(prod) 환경 **없음**. 배포 워크플로는 `.github/workflows/deploy-dev.yml` 하나뿐(develop push 시 자동). `main`은 2026-06-05 이후 방치(develop과 565커밋 차이, 마이그레이션 74개 파일 차이).
- 프론트 `.env.prod`(api.mindbreeze.looxidlabs.com)는 있으나 해당 도메인 DNS 없음. CORS 허용목록의 prod 도메인은 주석 처리(`backend/app/main.py:57-66`).
- dev 주소 하드코딩: `backend/app/config.py:50,68`(report_email_base_url·frontend_base_url 기본값), `backend/app/main.py:57-60`, `frontend/src/hooks/useLiveKit.ts:10`, `useMemberLiveKit.ts:20`(wss://dev-api…/livekit).
- `backend/app/config.py:72` `environment` 기본값이 "production"(서버 .env.dev에는 ENVIRONMENT 키 존재, 값은 비공개).
- Capacitor 앱은 `capacitor.config.ts`에 server.url 없음 → **빌드 시점 dist에 박힌 VITE_API_BASE_URL(dev-api)** 을 호출. 앱 스토어 배포 시 환경 분리 필요.
### 서버(dev, 단일 EC2: 2vCPU / 3.8GB RAM / 디스크 19GB 중 69% 사용, 가동 18주)
- 한 대에서 동시 구동: nginx(프론트 정적+API 프록시+TLS), mindbreeze-backend(uvicorn), mindbreeze-worker(STT/요약/리포트/영상병합), email-worker, export-worker(Celery), redis-server, livekit(화상). DB만 RDS 분리.
- cron 14개(1분·5분 단위 outbox/알림/리마인더/정리 + 일 단위 배치). 각 줄에 DATABASE_URL을 `.env.dev`에서 grep으로 꺼내 export 하는 방식(중복·취약).
- 서버 홈에 배포 잔재(tar.gz 다수, 2026-08-27 백업 tar)가 쌓임. 자동 백업·모니터링 에이전트 없음(sysstat·certbot만). CloudWatch 에이전트 없음.
- 비밀값(.env.dev): JWT, RESEND, GEMINI/OPENAI/DEEPSEEK API키, AWS 액세스키(IAM 사용자 키), LiveKit 키, FCM 서비스계정, VAPID 개인키가 **서버 평문 파일 1개**. 앱 푸시용 Firebase는 dev 프로젝트 1개만.
### 배포 파이프라인(`.github/workflows/deploy-dev.yml`, 287줄)
- 프론트 빌드 → 번들(프론트+백엔드 소스) SCP 전송 → SSH로 압축 해제·alembic upgrade·systemd 재시작·cron 재등록. 직전 버전 폴더 복사 + 실패 시 롤백 트랩(코드만, **DB 마이그레이션은 롤백 불가**). 배포 후 공개 health 확인(`/health`는 단순 200, DB·Redis 점검 없음: `backend/app/main.py:99`).
- 배포 중 서비스 **중단 있음**(단일 서버 재시작). 무중단(blue-green/롤링) 없음. 배포 승인·수동 게이트 없음(develop push = 즉시 반영). 다른 사람/에이전트 커밋이 곧바로 사용자에게 노출.
- 이번 세션에서 push 이벤트로 배포가 늦게/누락 트리거된 사례 있음(수동 dispatch 불가: workflow_dispatch 트리거 없음).
### CI(`.github/workflows/ci-feature.yml`)
- 프론트: tsc·eslint(차단) / 단위 테스트는 `continue-on-error: true`(비차단). 백엔드: pytest(차단) 단 `test_sprint4_integration.py` 제외·PDF 메트릭 1건 제외.
- 프론트 전체 vitest에 **기존 실패 16건 상존**(리포트 목록·모달, 브라우저 .cjs 등). CI가 실패하는 상태가 오래 이어졌고 develop 배포는 CI와 독립(CI 실패해도 배포됨). 배포가 CI 통과를 요구하지 않음.
- 테스트 규모: 백엔드 tests 136 파일, 프론트 tests 66 파일. E2E(Playwright)는 dev 서버(5175)에 의존, CI 미연결.
### 데이터
- RDS `mindbreeze-dev`(PostgreSQL 16.14, **db.t4g.micro**, Multi-AZ 아님, 자동백업 7일, 스토리지 20GB, **암호화 꺼짐**, 삭제방지 꺼짐, 비공개). 개발·테스트·실사용 데이터가 한 DB. Alembic 74 마이그레이션, 파괴적 변경 롤백 정책 문서화 안 됨(downgrade는 비가역 UPDATE 마이그레이션 존재).
- S3 버킷 `looxid-las`에 `mindbreeze-dev/`·`prod/` 접두사로 공유(prod 접두사 사용 여부 미확인). 서버 IAM 사용자 키로 접근.
- 부하 실측(dev 2vCPU): 한계 약 80~100 RPS, WebSocket 200연결 OK, 동시 80명+ EEG 스트리밍 시 prod 스케일업 필요(메모).
