# 수업 중 밴드 끊김·재연결·교체 — 사용자 경험 진단과 해결안

출발점: 1차 조사 `ble-disconnect-1121/report.md`(11/18 운영 데이터)를 다시 조회하지 않고 인용. 시안: `design/index.html`

## 1. 3줄 요약
1. **대표 가설은 "부분적으로 맞음".** 밴드가 광고(재연결 대기)를 하다 타임아웃 뒤 sleep에 들어갔다는 흐름은 데이터와 맞는다(추정). 그러나 **"앱이 끊긴 뒤 잘못된 방식으로 연결해서 못 붙었다"는 코드에서 확인되지 않았다.** 앱은 끊긴 연결을 정리하고(close), 같은 기기로 직접 연결을 반복한다. 진짜 결함은 *재연결 방식*이 아니라 **밴드가 광고를 멈춘 뒤 앱이 취할 수 있는 수단이 없다는 것**이다(스캔 복귀 없음 · 사용자 안내 없음 · Android 앱의 "수동으로 다시 연결" 버튼이 아무 일도 안 함).
2. **확정된 결함 3개**: ① Android 앱에서 수업 중 "수동으로 다시 연결"이 동작하지 않는다(`native-measurement/index.ts:340`, Android 플러그인에 `reconnectBand` 없음). ② 앱 어디에도 **재연결이 길어졌을 때 "밴드를 깨우세요" 안내가 없고**, "다른 밴드로 바꾸기" 경로 자체가 수업 중에는 없다. ③ 재연결은 광고를 못 찾아도 **저장된 기기 ID로만 계속 시도**하고 스캔으로 돌아가지 않는다(iOS는 타임아웃 없는 대기 연결, JS 경로는 10초 시도 반복).
3. **P0(다음 앱 빌드)**: 단계형 재연결 상태 머신(연결 시도→스캔 복귀→"깨우기 안내"→수동 재연결), Android 수동 재연결 구현, 진단 계측. 서버 쪽은 지금 바로 가능한 "신호 없음 N분" 코치 표시. **대표 결정**: §7.

## 2. 대표 가설 판정

| 가설 요소 | 판정 | 근거 |
|---|---|---|
| 밴드는 끊김을 인지하고 연결을 계속 시도하다 sleep | **추정(데이터와 일치)** | 마음돌봄 P11·P15 재연결 카운터 37, 15:11 동시 복귀(1차 조사). 이 숫자는 **JS 경로에서 10초 연결 시도 + 백오프(1·2·4·8·15·30초 상한) 반복을 22분 35초(=1,355초) 돌렸을 때 37회**와 같다(검산: 사이클 10초 가정 시 37회, Android 네이티브 30초 워치독 가정 시 25회). 즉 **앱은 정상적으로 시도했지만 매번 10초 안에 붙지 못했다** = 밴드가 광고하지 않았다. sleep 진입 자체는 서버로 못 봄 |
| 앱이 끊긴 GATT 객체를 정리하지 않고 재사용 | **틀림(확정)** | JS: 연결 실패 시 Android 플러그인이 타임아웃 핸들러에서 `disconnect()+close()`(`Device.kt setConnectionTimeout`), 끊김 콜백에서도 `close()+null`. 다음 시도 때 `connect`가 `bluetoothGatt?.close()` 후 새 `connectGatt`(`Device.kt:331`). iOS도 타임아웃에서 `cancelConnect`. 네이티브: Android `connect()`가 `gatt?.close()` 후 새 연결(`BandGattClient.kt:86`), 세대 펜싱으로 늦은 콜백 무시 |
| stale deviceId로 직접 connect | **부분(구조적 한계)** | `useBand.ts:1373`이 캐시 ID로만 연결, `scan()`은 캐시가 없을 때만. Android는 MAC이라 안정, iOS는 앱 설치 단위 UUID. **ID가 낡아서 틀리는 게 아니라, 밴드가 광고를 안 하면 어떤 ID여도 못 붙는다.** 이때 스캔으로 돌아가도 광고가 없으면 마찬가지이므로 스캔 복귀의 가치는 "다른 밴드로 교체했을 때(새 ID)"와 "iOS ID 무효화"에 있다 |
| 진행 중 플래그 고착 | **가능성 있으나 미확인** | `bandConnectInFlight`(`useBand.ts:96,1338,1346`)는 `finally`에서만 해제. 플러그인 `connect`는 10초 타임아웃이 있어 보통 풀린다. 다만 연결 성공 *이후* 단계(`loadStreamCursor`·`stream.start()`)에는 타임아웃이 없어 거기서 멈추면 이후 재시도가 "중복 connect 무시"(`:1339`)로 건너뛰어진다(코드상 가능, 발생 증거 없음) |
| 알림(notify) 구독 미재설정 | **틀림** | 재연결 때마다 `StreamProcessor` 새로 만들고(`useBand.ts:1485~`), 어댑터가 구독 전 `stopNotifications`로 중복을 지움(`capacitor-ble-adapter.ts:107~`) |
| 밴드는 "연결됨"으로 착각해 대기만 | **확인 불가(펌웨어)** | 앱이 먼저 끊고 재접속하는 경로(`reconnectBand` iOS, `useBand` 복귀)가 있어 밴드가 "앱이 연결 중"으로 오인하는 순서가 생길 수는 있으나, 펌웨어가 ① 끊김 후 광고를 언제까지 하는지 ② 어떤 상태에서 sleep인지 ③ 버튼으로 깨우는지는 **저장소·docs에 없음 → 펌웨어 확인 필요**. SDK 사이트(linkband.looxidlabs.com) 공개 페이지에도 sleep 조건 기재 없음 |

**결론**: "앱이 잘못된 방식으로 연결을 시도했다"가 아니라 **"밴드가 광고를 멈춘 뒤 앱과 사람이 그 상황을 해결할 도구가 없었다"**. 고쳐야 할 것은 연결 호출 한 줄이 아니라 *막힌 상태를 사람에게 보여주고 풀게 하는 흐름*이다. 단, 펌웨어가 "앱이 끊기지 않은 상태로 남은 연결"을 오래 붙잡아 광고하지 않는 경우(대표 직관의 두 번째 갈래)는 펌웨어 확인 전까지 배제하지 않는다.

## 3. 현재 구조 (이 문서 판단의 전제)
수업 중 밴드를 쥐는 주체가 **경로 3개**이고 화면 버튼의 동작이 경로마다 다르다.

| 경로 | 쓰이는 때 | 재연결 방식 | 코드 |
|---|---|---|---|
| JS(웹 BLE 플러그인) | 웹·게스트·네이티브 측정 미적용 회원 | 캐시 ID 직접 연결, 10초 시도, 백오프 1→30초 무제한 | `useBand.ts:1309~`, `reconnect-policy.ts` |
| Android 네이티브 | 앱 로그인 회원(SDD-246/293) | `BandGattClient` 1→30초 무제한 + 단계 워치독(연결 30s·MTU 5s·발견 10s·구독 20s)·무수신 5초 | `BandGattClient.kt:109`, `LinkWatchdog.kt` |
| iOS 네이티브 | 동일 | `BandLink` 1→15초 백오프, **연결 요청은 타임아웃 없는 대기 연결**(`BandBLE.swift:204`), 상태 복원 구현 | `BandBLE.swift:216` |

대기실에서 밴드를 연결하면 JS가 잡은 밴드를 네이티브가 **보류(hold)로 인계**받고 JS는 해제한다(SDD-293, `use-native-band-hold.ts:32`, `bluetoothService.ts:1037`). 이 뒤 JS의 자동 재연결은 의도적으로 차단된다(`scheduleReconnect`의 `isReleasedForNative`).

## 4. 여정별 진단

### 4.1 수업 중 일시 끊김 → 자동 재연결
| 항목 | 내용 |
|---|---|
| 현재 동작 | JS: 끊김 콜백→`cleanup`(deviceId 비움·lastDeviceId 유지)→`scheduleReconnect`→10초 시도 반복. 연결되면 새 `StreamProcessor`·구독 재설정·갭 로그 닫기(`useBand.ts:1506~1540`). 네이티브: 위 표 |
| 사용자가 겪는 것 | 화면은 "연결이 끊겼어요 · 자동으로 다시 연결하고 있어요" 한 문구뿐(`MemberSheets.tsx:313`). 25초 이내 복구가 대부분(1차 조사)이라 평소엔 충분 |
| 문제 | 오래 가도 문구가 안 바뀜. 시도 횟수·경과·밴드가 보이는지 알 수 없음. JS 연결 후 단계(커서 로드·스트림 시작)에 타임아웃 없음 `useBand.ts:1380~1470` |
| 확정/추정 | 문구·무제한 반복 **확정**, 플래그 고착 **추정** |

### 4.2 장시간 끊김 → 밴드 sleep → 사용자가 깨웠을 때
| 항목 | 내용 |
|---|---|
| 현재 동작 | 앱은 계속 직접 연결을 시도한다. 밴드를 깨우면 광고를 재개하므로 **JS(10초 주기)와 Android(1~30초)는 몇 초~30초 안에 자동으로 붙을 것으로 보인다.** iOS는 대기 연결이라 OS가 광고를 감지하면 붙음 |
| 사용자가 겪는 것 | 11/18에 22분 35초 만에 복귀한 P15와 같은 시각 복귀 사례가 이 흐름과 맞다. 문제는 **"깨우면 된다"는 사실을 아무도 알려주지 않아 현장이 22분 걸린 것** |
| 문제 | ① 안내 없음 ② 백오프 상한 30초(Android·JS) 때문에 깨운 직후 최대 30초 지연 ③ "내가 깨웠다"를 앱에 알릴 버튼 없음(Android) ④ 코치는 이 상태를 볼 수 없음(서버에 끊김 이벤트 없음) |
| 확정/추정 | 안내·버튼 부재 **확정**, 자동 복귀 속도는 코드 기반 **추정** |

### 4.3 사용자가 "다시 연결"을 직접 시도
| 항목 | 내용 |
|---|---|
| 현재 동작 | 끊김 시트에 "수동으로 다시 연결" 버튼(`MemberSheets.tsx:316` → `onBandRetry`, `MemberClassContainer.tsx:809`). 네이티브 소유면 `reconnectBand(platform)`, 아니면 `band.connect()` |
| **확정 결함** | `native-measurement/index.ts:340`: `platform !== 'ios'`이면 **`false`로 즉시 반환**. 저장소 Android 플러그인(`MeasurementPlugin.kt`)에 `reconnectBand`가 아예 없다(검색 0건). → **Android 앱에서 수업 중 이 버튼은 눌러도 아무 일도 안 일어나고 오류도 안 보인다.** 화면 위 주석이 "JS로 붙으면 같은 밴드를 두 클라이언트가 잡는다"고 막아 둔 때문 |
| iOS | `reconnectBand`가 밴드를 끊었다가 다시 붙임(`MeasurementManager.swift:254`) — 끊긴 상태에선 무해, 연결 중에 누르면 멀쩡한 연결을 끊는다 |
| 문제 | 눌렀을 때 시각 반응·결과 문구 없음 |

### 4.4 다른 밴드로 교체
| 항목 | 내용 |
|---|---|
| 현재 동작 | **수업 중 교체 경로가 없다.** 대기실 `BandStepView`에서만 연결·해제(`BandStepContainer.tsx:87`). 수업 중 `onBandDisconnect`는 네이티브 소유면 **아무것도 안 함**(`MemberClassContainer.tsx:803`, `undefined`). 네이티브가 밴드를 쥐면 JS가 새 기기를 스캔·선택하는 것도 막힘 |
| 서버 기록 | `session_participants.linkband_device_id`(최신 1개) + `session_band_devices`(참가자×시리얼 이력, 재보고는 last_seen 갱신)(`band_device_service.py`). **이력 구조는 교체를 담을 수 있다.** 단, 스토어 앱(11/10 빌드)은 이 보고 기능이 없어 현재 운영 데이터엔 시리얼이 비어 있다(1차 조사) |
| 데이터 이어붙임 | 스트림은 `capture stream`(참가자 단위) 커서(`loadStreamCursor`)로 이어지므로 밴드가 바뀌어도 같은 회원 스트림에 이어 쓸 수 있는 구조. **실기기 검증 전엔 확정 아님**: 새 밴드의 장치 시계 카운터 리셋 처리(`timestampSync.reset()`은 있음, `bluetoothService.ts` cleanup) |
| 사용자가 겪는 것 | 배터리 소진·고장 때 현장에서 밴드를 바꾸려면 앱을 종료하고 재입장하는 수밖에 없다. 그러면 4.5의 위험을 모두 진다 |
| 문제 | 교체 UI·교체 이벤트·이전 밴드 해제 순서·교체 구간 표기가 모두 없음 |

### 4.5 앱 백그라운드·화면 꺼짐·전화 수신·앱 튕김 후 재입장
| 항목 | 내용 |
|---|---|
| 현재 동작 | 복귀 시 JS는 끊김 진행 중이면 백오프 타이머를 건너뛰고 즉시 재시도, 연결 중이면 배터리 읽기로 실제 연결 검증(`useBand.ts:1630~`, `capacitor-ble-adapter.ts:156`). Android는 포그라운드 서비스(connectedDevice)로 화면 꺼짐 유지, iOS는 `bluetooth-central` 백그라운드 모드 + 상태 복원(`BandBLE.swift:236`) |
| 확인 안 됨 | 전화 수신·Doze 때의 실제 거동은 코드에 별도 처리가 없고 기기 테스트 필요. 앱 프로세스가 죽은 뒤 재실행 시 iOS 복원은 코드가 있으나 *"재입장 → 어느 밴드를 우선"* 정책이 문서화돼 있지 않음. 크래시 로그 수집 없음(1차 조사) |
| 문제 | 재입장 시 "아까 쓰던 밴드를 자동으로 다시 찾는다"가 보장되지 않고, 사용자는 그것을 알 수 없음 |

### 4.6 코치가 끊김을 알고 도와주는 흐름
| 항목 | 내용 |
|---|---|
| 현재 동작 | 코치 화면에 회원별 밴드 상태(`lost`/`leadoff`/`low`…)와 칩 "끊김 N". SDD-330이 "입장 N명 · 이상 M명"을 추가(`isAbnormal`: 입장자 중 끊김·접촉불량·배터리부족·미접속, 브랜치 `sdd/330-class-field-usability`, 미머지) |
| 문제 | `lost`는 **밴드가 서버에 마지막으로 보고한 10초 무수신(`EEG_STALE_MS`)** 기준이라 *얼마나 오래*인지·*밴드를 깨워야 하는 상황인지* 구분이 없다. 코치가 회원 화면에 **안내를 보낼 수단이 없다**(신호 토스트는 회원→코치 방향). 1차 조사에서 복구 실패 4명 모두 서버에 끊김 이벤트가 안 남아 코치는 알 수 없었음 |
| 연결점 | SDD-330 요약 줄의 "이상 M명"에 **경과 시간·단계**를 붙이면 곧바로 현장 도움이 된다(§5.5, 시안 ④) |

### 4.7 iOS·Android 차이
| 항목 | Android | iOS |
|---|---|---|
| 연결 요청 | 30초 워치독이 끊고 재시도(네이티브) / 10초 타임아웃(JS) | **타임아웃 없는 대기 연결**(`BandBLE.swift:204`) — 광고가 오면 OS가 깨우나, 오래 걸려도 "실패"가 안 생겨 시도 횟수·상태가 앱에 안 보임 |
| 객체 정리 | 모든 경로에서 `close()` 호출 확인. **GATT 133 등 상태 코드별 분기는 없음**(비정상이면 일괄 재시도) | `cancelPeripheralConnection`(해제), 실패 시 `scheduleRetry` |
| 백오프 | 1→30초 | 1→15초 |
| 백그라운드 | FGS 있음, **배터리 최적화 제외 안내는 SDD-330이 추가 중(미머지)** | 상태 복원 있음, 실기기 검증 이력 없음 |
| 수동 재연결 | **없음(결함)** | 있음 |
| 식별자 | MAC | 설치 단위 UUID(재설치·기기 변경 시 무효 가능) → 스캔 복귀 필요성이 더 큼 |

## 5. 해결안

### 5.1 앱 재연결 상태 머신 재설계 (P0)
공통 상태 머신으로 JS·Android·iOS 모두 같은 단계와 같은 사용자 문구를 쓴다.

| 상태 | 진입 조건 | 하는 일 | 사용자에게 보이는 것 | 다음 |
|---|---|---|---|---|
| `LIVE` | 수신 중 | — | 연결됨 | 끊김 → `RETRY` |
| `RETRY`(0~30초) | 연결 끊김 | 정리(구독·GATT 해제) 후 직접 연결, 시도마다 **10~15초 타임아웃**, 백오프 1·2·4·8초 | "다시 연결하는 중이에요" | 성공→`LIVE`, 3회 실패→`SCAN` |
| `SCAN`(30초~60초) | 직접 연결 3회 실패 | 이름 접두 `LINK BAND`·서비스 UUID로 **스캔 복귀**. 같은 시리얼(광고 이름)이면 새 ID로 갈아탐, 다른 시리얼이면 사용자 확인 | "밴드를 찾고 있어요" + 안내 3단계(착용·버튼·거리) | 발견→연결, 60초→`WAKE` |
| `WAKE`(60초~3분) | 스캔에서 못 찾음 | 스캔·직접 연결을 **15초 주기로 교대**(상한 30초→15초), 화면 켜짐 유지 | "밴드가 잠들었을 수 있어요 — 버튼을 눌러 깨워 주세요" + **"깨웠어요 — 다시 연결"** | 사용자 누름→즉시 `SCAN`(백오프 초기화) |
| `HELP`(3분~) | 계속 실패 | 주기 30초로 지속(포기 없음), 코치에게 상태 보고 | "코치님께 알리기" · "다른 밴드로 바꾸기" · "밴드 없이 계속" | 어느 단계에서든 성공 시 `LIVE` |

정리 순서(전 경로 공통): ① 새 연결 시도 전 `inflight` 해제·**이전 시도 취소** → ② 알림 구독 해제(오류 무시) → ③ 플랫폼 연결 객체 해제(Android `close`, iOS `cancelPeripheralConnection`) → ④ 새 `connect` → ⑤ 서비스 발견 → ⑥ 구독 재설정 → ⑦ 갭 로그 닫기·커서 이어붙이기. **각 단계에 타임아웃을 달아 어느 단계에서 멈춰도 `RETRY`로 돌아오게** 한다(JS 연결 후 단계 포함).
iOS는 대기 연결(타임아웃 없음)도 유지하되 앱이 **15초마다 한 번 끊고 다시 거는 "주기 점검"** 대신, 대기 연결과 별도로 스캔을 병행해 상태를 앱이 직접 관측한다(상태 복원·백그라운드 보존은 해치지 않게 포그라운드에서만).

| 항목 | 우선 | 작업량 | 앱 빌드 |
|---|---|---|---|
| 상태 머신(JS 경로) + 단계별 타임아웃 + `inflight` 강제 해제 | P0 | M | 필요(웹뷰 코드지만 스토어 앱 번들 포함) |
| 직접 연결 3회 실패 시 스캔 복귀(JS·Android·iOS) | P0 | M~L | 필요(네이티브) |
| `WAKE` 단계 주기 단축·"깨웠어요" 즉시 재시도 | P0 | S | 필요 |
| 상태 코드별 처리(Android GATT 133·status≠0 → close 후 지연 재시도) | P1 | S | 필요 |

### 5.2 Android 수동 재연결·교체 허용 (P0)
- `MeasurementPlugin.kt`에 `reconnectBand`를 추가해 `BandGattClient`의 `disconnect→connect`(백오프 초기화)를 호출. iOS와 동일한 의미(끊긴 상태에서만 동작, 정상 연결 중엔 무시 + "이미 연결돼 있어요" 반환).
- 누르면 즉시 화면 문구가 "다시 연결하는 중이에요"로 바뀌고 결과(성공/실패)를 한 줄로 알림.
- 작업량 S~M · **앱 빌드 필요**. 빌드 전 임시책: 현장 안내로 "앱을 완전히 닫지 말고 입장 화면으로 다시 진입"(1차 조사 §6.3).

### 5.3 밴드 교체 흐름 (P0~P1)
시안 ③. 순서:
1. 회원이 "다른 밴드로 바꾸기" → 확인 화면(기록은 이어진다고 안내)
2. 앱이 **이전 밴드를 먼저 해제**(네이티브 `releaseBand`/JS `disconnect`) 후 새 밴드 스캔
3. 새 밴드 선택 → 연결 → 서버에 새 시리얼 보고(`PUT band-device`, 기존 이력 유지) + **교체 이벤트**(이전→새 시리얼, 시각) 기록
4. 같은 회원 스트림 커서에 이어서 저장, 사이 구간은 "측정이 쉬었던 구간"
| 항목 | 우선 | 작업량 | 앱 빌드 | 서버 |
|---|---|---|---|---|
| 수업 중 교체 UI·흐름(`onBandDisconnect` 네이티브 소유 시에도 동작) | P1 | M~L | 필요 | — |
| 교체 이벤트 기록(`session_band_devices`에 `replaced_from`·이벤트 시각) | P1 | S | — | 필요(스키마 컬럼 1개, 마이그레이션) |
| 새 밴드 시계 리셋 시 데이터 이어붙임 실기기 검증 | P0(검증) | S | — | — |

### 5.4 사용자 안내 UX (P0)
시안 ①②. 원칙: **지금 무슨 상태인지 + 내가 할 한 가지 + 기록은 안전하다**를 한 화면에. 점수·등급 없음. 단계는 시간 경과로 자동 전환, 버튼 위치·이름 고정("다시 연결"). 안내문은 "밴드가 잠들었을 수 있어요"처럼 *추정*임을 드러내 펌웨어 사실과 어긋나지 않게 한다(펌웨어 확인 뒤 문구 확정).

### 5.5 코치 지원 (P1, 서버·웹 위주 → 앱 빌드 불필요 부분 큼)
시안 ④. SDD-330 "입장 N명 · 이상 M명" 위에:
- 이상 회원 행에 **상태 + 경과 시간**("다시 연결 중 2분", "신호 없음 14분") — 서버가 참가자별 마지막 수신 시각으로 계산하므로 **앱 빌드 없이 가능**(서버: 무수신 감지 M, 1차 조사 §6.1과 동일).
- 코치→회원 **현장 안내 보내기**(밴드 깨우기·착용 안내·교체 순서): 기존 라이브 소켓 명령에 알림 종류 추가, 회원 화면에 토스트/시트. 작업량 M, 회원 쪽 표시는 앱 빌드 없이 웹뷰 갱신으로 가능하나 구버전 앱은 못 받음.
- 앱이 `HELP` 단계에 들어가면 "재연결 중(앱 보고)" 이벤트를 서버로 보내 코치 목록에 즉시 반영(P1, S, 앱 빌드 필요).

## 7. 대표 결정이 필요한 항목
1. **다음 앱 빌드에 P0 4건(수동 재연결·상태 머신·안내 UX·계측)을 포함할지.** 포함 시 실기기 검증(§8) 후 심사. 미룰 경우 11월 말 수업은 현장 체크리스트와 코치 무신호 표시(서버)로만 대응.
2. **펌웨어 팀에 확인 요청**(이게 없으면 안내 문구와 WAKE 단계의 시간값을 확정할 수 없음): ① 끊김 후 광고를 몇 초/몇 분 하는가 ② sleep 진입 조건과 깨우는 방법(버튼 길게/짧게) ③ 앱 쪽이 끊지 않은 "반쯤 열린 연결"을 밴드가 언제 정리하는가 ④ sleep 중 광고 여부. 질문 초안은 §9.
3. **수업 중 밴드 교체를 이번 빌드에 넣을지(P1)**. 넣으면 서버 스키마 1개 추가.
4. **"밴드 없이 계속하기"를 수업 중에도 항상 보이게 할지**(현재 `unsupported`일 때만) — 끊김이 길어진 회원의 이탈을 줄이는 대신 데이터 유실을 용인하는 정책 결정.

## 9. 남은 불확실성
- **밴드 sleep의 사실 여부와 조건 — 펌웨어 확인 필요.** 가설의 "밴드가 끊김을 알고 광고하다 sleep"은 서버 데이터와 앱 시도 횟수(37)로 *앞뒤가 맞을 뿐* 직접 증거는 없다.
- **스토어 앱(11/10)의 정확한 소스 커밋**: SDD-293 보류 인계(11/5)·SDD-301이 포함됐는지는 저장소 기록으로 특정 못 함. `session_band_devices`가 비어 있어 SDD-326(11/12)은 *미포함*으로 보인다. 본 문서는 origin/main 기준이며 운영 앱과 다를 수 있음.
- 앱 "튕김"의 실체(프로세스 종료인지 화면 상태인지)는 크래시 수집이 없어 구분 불가.
- 11/18 사례가 JS 경로였는지 네이티브 경로였는지 서버에서 구분 불가(37이 JS 모델과 일치하는 것은 근거이지 확정이 아님).
- 교체 시 이어붙임, 전화·Doze 거동은 실기기 전엔 코드 기반 추정.
