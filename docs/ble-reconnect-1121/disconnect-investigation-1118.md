# 11/18 운영 수업 LINK BAND 연결 끊김·재연결 실패 조사

작성 2026-11-21 · 운영 DB·서버 로그 읽기 전용 조회 + 저장소(origin/main) 코드 읽기. 회원은 입장 순서의 익명 번호(P01…)이며 회차마다 번호가 다르다(사후분석 문서의 "회원 NN"과 번호 체계가 다름).

## 1. 3줄 요약
1. **"끊겼다가 자동으로 붙은" 경우는 정상 복구됐다.** 몸돌봄 5명 23건, 마음돌봄 2명 3건으로 대부분 25초 이내(중앙값 몸 6.4초·마음 4.7초)에 복구됐다. 문제는 **복구되지 않은 경우**다. 몸돌봄 2명(P01, P11)과 마음돌봄 2명(P01, P15)은 끊긴 뒤 수업 끝까지 돌아오지 않았거나(P15는 22분 35초 뒤 복귀했다가 32초 만에 재중단) 아예 시작하지 못했다.
2. **복구 실패 사례는 서버에 "끊김 이벤트"조차 남지 않았다.** 앱이 이벤트를 보내려면 한 번은 붙어 있어야 하는데, 실패 구간은 BLE가 계속 연결 시도 중이었기 때문이다. 마음돌봄 P11·P15에는 재연결 시도 횟수가 37회까지 쌓여 있고, 이 둘이 15:11대에 거의 동시에 복귀했다. "밴드가 sleep에 들어가 앱이 재시도만 계속하다가, 현장에서 밴드를 직접 깨우자 붙은" 흐름과 맞는다. 단, 밴드의 sleep 진입 사실 자체는 서버 데이터로 확인되지 않는다(추정).
3. **현재 앱 재연결 코드의 약점 3가지가 이 증상을 설명한다**: ① 연결 호출에 타임아웃이 없어 한 번 멈추면 재시도 루프가 "중복 연결 무시"로 영구 정지될 수 있고, ② 밴드가 광고를 멈춘 경우 스캔으로 되돌아가지 않으며, ③ 사용자에게 "밴드를 눌러 깨우세요" 같은 안내가 없다. 또 앱이 튕긴 직접 증거(크래시 로그)는 서버에 없다.

**대표 결정이 필요한 것**: (a) 다음 앱 빌드에 BLE 재연결 개선(P0)·진단 계측을 포함할지, (b) 밴드 펌웨어의 sleep 조건 확인을 펌웨어 팀에 요청할지, (c) 현장 체크리스트(§6.3)를 11/19~ 운영부터 적용할지.

### 2.3 "앱 튕김" 관련 관측
- 같은 회원이 다른 참가자 행으로 재입장한 사례는 없었고(두 회차 모두 0), 참가자별 수집 스트림 수도 전원 3개(EEG/PPG/ACC 각 1)로 같다. 즉 **서버 기록상 앱 재시작·새 세션 재입장 흔적은 보이지 않는다**(관측).
- 크래시 로그·앱 오류 로그·소켓 참가자별 로그를 담는 서버 테이블은 없다(client_error_logs 등 부재). 서버 로그에는 참가자 단위 소켓 입퇴장이 거의 남지 않는다. 따라서 "튕김"이 앱 프로세스 종료인지, 화면이 연결 끊김 상태로 바뀐 것인지 구분할 수 없다(불확실, §7).
- 입장 403: 몸돌봄 36건, 마음돌봄 20건(기존 사후분석). P01(몸돌봄)처럼 같은 시각대(10:18)에 입장 403 2건이 있었으나 참가자를 특정하지 못해 P01과의 연관은 미확인이다.
- 확인한 참가자 전원에서 `session_band_devices`(밴드 시리얼·펌웨어·기기 OS 보고)가 비어 있다 → 이 값을 보고하는 최신 기능(SDD-326)이 스토어 앱에 아직 없다는 뜻이며, **기기 OS·밴드 시리얼별 분석은 지금 데이터로 불가능**하다.

## 4. 코드 근거 (origin/main, 읽기 전용)
- 재연결 정책 `frontend/src/lib/ble/reconnect-policy.ts`: 1→2→4→8→15→30초 상한, ±20% 지터, **횟수 제한 없음**(무한).
- `frontend/src/hooks/useBand.ts` (`scheduleReconnect`, `connectInternal`): 끊김 시 캐시된 deviceId로 `BleClient.connect`를 재호출. **`bandConnectInFlight`가 true이면 "중복 connect 무시" 후 다음 백오프만 예약**한다(약 1318·1330행 부근). 연결 호출이 끝나지 않고 멈추면(finally가 실행되지 않으면) 플래그가 풀리지 않아 이후 재시도가 전부 건너뛰어질 수 있다(코드상 가능성이며 실제 발생은 미확인). 연결 호출에 별도 타임아웃 래퍼는 없다(`bluetoothService.ts`의 타임아웃은 다른 용도뿐).
- `frontend/src/lib/ble/capacitor-ble-adapter.ts`: `BleClient.connect(deviceId, …)`에 timeout 옵션을 넘기지 않음. 재연결은 **스캔(requestDevice)으로 돌아가지 않는다.** 밴드가 sleep으로 광고를 멈추면 iOS는 연결 요청이 보류 상태로 남고, Android는 실패 후 재시도를 반복하는 것이 일반적 동작이다(플러그인 동작 기반 추정).
- 복귀 처리: `useAppLifecycle`(onResume)에서 재연결 중이면 타이머를 건너뛰고 즉시 재시도, 연결 중이면 배터리 읽기로 실제 연결을 검증. 화면 복귀에는 대응하지만 **끊긴 채 화면이 켜져 있는 경우**는 같은 백오프에 의존.
- 사용자 안내: 끊김 시 문구는 "자동 재연결 시도 중" 한 줄뿐이며 "밴드 전원/착용 확인" 안내와 수동 재연결 버튼 연계가 없다.
- 네이티브: Android `MeasurementService`(포그라운드 서비스 connectedDevice)·`BandGattClient`(1→30초 무한 백오프, 링크 워치독)가 있고, iOS는 `UIBackgroundModes: bluetooth-central, audio`가 설정돼 있다. 다만 **스토어 앱(11/10 운영 앱)이 어느 커밋인지 저장소 기록으로 특정하지 못했다**(`session_band_devices` 비어 있음으로 보아 SDD-326보다 이전). 위 분석은 현재 코드 기준이며 스토어 앱과 차이가 있을 수 있다.
- LINK BAND 펌웨어의 sleep 진입 조건·깨우는 방법은 저장소 코드·docs에서 찾지 못했다 → **펌웨어 확인 필요**(SDK 문서 `linkband-sdk.looxidlabs.com` 직접 조회는 이번 범위에서 하지 않음).

## 5. 데이터 한계
- 서버는 앱이 붙어 있는 동안만 이벤트를 받는다. 연결 시도 중·sleep 중에는 기록이 없어 **복구 실패의 시작 시각은 마지막 특징값 시각으로만 추정**했다.
- 클라이언트 진단 이벤트(재연결 단계, 에러 코드, 앱 상태)와 앱 버전·기기 OS 정보가 없다.
- 서버 로그는 참가자별 소켓 이벤트가 없어 "튕김" 재구성에 쓸 수 없다.

### 6.3 현장 운영 절차 (체크리스트)
1. 입장 전 밴드 완전 충전·전원 확인, 착용 후 앱에서 "수신 중" 확인을 마친 사람부터 입실.
2. 수업 시작 직후 3분과 중간에 한 번, 상담사가 참가자별 "수신 중" 상태 점검.

## 7. 남은 불확실성과 계측 제안
앱에 넣을 진단 이벤트(세션·참가자 단위, 개인정보 없음):
- `ble_state_change`(연결/끊김/재연결 시작/성공/실패, 시각, 이유 코드)
- `ble_connect_attempt`(시도 번호, 소요 시간, 타임아웃 여부, 오류 코드)
- `ble_scan_fallback`(스캔 시작/발견/미발견)
- `band_signal`(마지막 패킷 이후 경과 초, 배터리 %)
- `app_lifecycle`(포그라운드/백그라운드/종료 복원, 화면 켜짐 여부)
- `app_fatal_error`(오류 종류·위치)
- `device_info`(OS·버전·기기 모델·앱 빌드 번호·밴드 시리얼/펌웨어)
- 밴드 쪽: sleep 진입 조건·광고 중단 시점(펌웨어 문서 확인)

해소하지 못한 것: ① 밴드가 실제로 sleep에 들어갔는지, ② P01·P11이 영구 중단된 구체 원인(앱 정체/밴드 sleep/배터리 소진), ③ 앱 "튕김"의 실체, ④ 마음돌봄 15:11대 동시 복귀의 공통 원인, ⑤ 스토어 앱의 정확한 소스 커밋.
