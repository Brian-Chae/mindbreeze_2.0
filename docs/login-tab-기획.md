# 로그인 탭 통합 기획안

- 작성일: 2026-09-16
- 상태: 서비스 기획 제안 / 검토용. 구현·디자인 확정·배포 승인 문서가 아님.
- 목표: `/login`에서 **회원 / 상담사 / 기관** 중 이용 목적을 선택하고 로그인한다.
- 권고: 공개 3탭 + 플랫폼 관리자 별도 진입 유지 + 공통 로그인 화면 통합.
- 범위: 로그인 진입, 탭별 콘텐츠, 인증 요청 정책, 로그인 후 이동, 기존 링크 호환.
- 제외: 실제 코드 수정, 신규 기관 가입 서비스, 다중 역할 계정, 인증 제공자 교체, 홈페이지 전체 개편.

## 1. 현재 구조와 문제

### 코드에서 확인한 구조

- `/login` → `LoginPage`: 상담사·기관 관리자·플랫폼 관리자 공용 진입.
- `/login/client` → `ClientLoginPage`: 회원 대상 전용 화면.
- `/login?role=platform_admin`: 플랫폼 관리자 모드. Google Workspace 로그인만 표시하고 이메일 폼은 숨긴다.
- `LoginPage.loginRole`: `platform_admin` 쿼리일 때만 관리자, 나머지는 `counselor`.
- 이메일 로그인은 두 화면 모두 `login(email, password)`를 호출한다. 선택 역할을 서버에 전달하거나 일치 여부를 검사하는 계약은 현재 없다.
- `LoginPage.resolvePostLoginPath`는 응답 `user.role`로 이동을 결정한다.
  - `platform_admin` → 허용된 `next` 또는 `/admin/orgs`.
  - `org_admin` → `/dashboard/org`.
  - `counselor` → `/dashboard`.
  - `client` → 온보딩 완료 시 `/app`, 미완료 시 `/onboarding/client`.
- `ClientLoginPage`는 회원용 화면이지만 실제 로그인 결과에 상담사 분기도 있다. 상담사 미온보딩 시 `/onboarding/counselor`로 보내므로 두 페이지의 정책이 일치하지 않는다.
- 두 페이지 모두 Google 인증과 이메일·비밀번호를 지원한다. 현재 회원 화면도 이메일 폼이 먼저 나온다.
- 페이지 우측 상단의 회원/상담사 링크로 서로 이동한다. 기관 전용 진입 표시는 없다.
- `DevRoleSimulationPanel`은 `VITE_ENABLE_ROLE_SIM === 'true'`일 때만 표시한다.
- 업무 대상 역할은 `client`, `counselor`, `org_admin`, `platform_admin` 4종이다. 프런트 `UserRole`에는 레거시 `admin`도 남아 있으나 이번 공개 탭으로 추가하지 않는다.

### 사용자 경험 문제

- 기본 `/login`이 “상담사 로그인”이라 신규 회원이 자신의 진입점을 잘못 찾았다고 느낄 수 있다.
- 회원은 별도 주소, 플랫폼 관리자는 쿼리 파라미터로 진입하여 역할 선택 방식을 한눈에 알기 어렵다.
- 기관 관리자는 상담사 화면을 사용해야 해 계정 유형과 화면 문구가 어긋난다.
- 두 화면의 폼·오류 처리·이동 로직 중복으로 향후 정책 변경 시 동작 차이가 생기기 쉽다.
- 위 문제는 코드와 화면 구성에 근거한 가설이며, 이탈률이나 실제 사용자 혼란 정도를 측정한 결과는 아니다.

## 2. 권고 UX: 하나의 화면, 세 개의 탭

### 화면 구조

- 상단: 공통 로고와 홈 이동 링크.
- 제목: “MIND BREEZE 로그인”.
- `TabMenu`: **회원 | 상담사 | 기관** 순서, 기본 선택은 회원.
- 탭 아래 콘텐츠 영역만 교체: 설명, 로그인 수단의 우선순위, 버튼 문구, 가입·도움말 링크.
- 탭 전환 때 페이지 전체를 새로 열거나 역할 선택 중간 화면을 추가하지 않는다.
- 기존 우측 상단 회원/상담사 전환 링크는 탭과 중복되므로 제거한다.
- 공통 배경·폼 폭·주요 버튼 위치를 유지한다. 홈페이지 콘텐츠 개편으로 범위를 넓히지 않는다.

### 회원 탭 (`client`)

- 설명: “상담과 명상을 이용하는 회원을 위한 로그인입니다.”
- 첫 번째 주요 버튼: “Google로 회원 로그인”.
- 다음 영역: 구분선 + 이메일·비밀번호 + “이메일로 회원 로그인”.
- 보조 링크: 회원가입 `/register?role=client`, 비밀번호 찾기 `/forgot-password`.
- 이용 조건 안내: 초대·상담사 연결 관련 기존 정책을 유지한다. 로그인 성공과 서비스 이용 승인을 같은 의미로 표시하지 않는다.

### 상담사 탭 (`counselor`)

- 설명: “상담사 계정으로 세션과 회원을 관리하세요.”
- 첫 번째 영역: 이메일·비밀번호 + “상담사 로그인”.
- 보조 버튼: “Google로 상담사 로그인”. 기존 상담사 계정만 이용하며 신규 자동 가입은 허용하지 않는다.
- 보조 링크: 상담사 가입 `/register?role=counselor`, 비밀번호 찾기.
- 기관 코드 등 기존 가입 요건은 유지한다. 이번 작업에서 가입 자격을 확대하지 않는다.

### 기관 탭 (`org_admin`)

- 탭 이름은 요구사항대로 “기관”, 설명은 “기관 관리자 계정으로 로그인하세요.”로 명확히 한다.
- 이메일·비밀번호 + “기관 관리자 로그인”을 중심으로 구성한다.
- “기관에서 발급받은 관리자 계정을 사용하세요.” 안내와 비밀번호 찾기 제공.
- MVP에서는 신규 기관 가입 버튼과 Google 로그인 버튼을 제공하지 않는다.
- 기관 Google 로그인은 서버의 기존 계정·역할 검증을 보완한 이후 확장한다. 현재 요청에 `org_admin`을 추가하는 것만으로는 구현할 수 없다.

### 상태와 접근성

- 탭 전환 시 이메일 입력은 유지하고 비밀번호·오류 메시지는 초기화한다.
- 인증 진행 중에는 탭·이메일 제출·Google 버튼의 중복 실행을 막는다. URL이 바뀌는 경우에도 인증 시작 당시의 역할을 고정하여 응답을 처리한다.
- Google 팝업 취소·실패 후에는 다시 조작할 수 있게 잠금을 해제한다.
- 선택 상태를 색상과 표시선으로 함께 전달한다. `tablist`, `tab`, `tabpanel`, `aria-selected`와 키보드 좌우 이동·포커스 처리를 설계한다.
- 모바일에서도 3탭 전체를 한 줄에 표시하고 각 폼 입력에 명시적인 레이블을 둔다.
- 공통 오류: 잘못된 자격 증명, 계정 잠김, 네트워크 오류를 구분하되 인증 전에 계정 존재 여부를 노출하지 않는다.
- 미지원 카카오 로그인은 MVP 주요 동선에서 제외한다. 새로운 인증 수단을 추가하지 않는다.

## 3. 플랫폼 관리자: 공개 4번째 탭과 별도 진입 비교

- 안 A — 공개 “플랫폼 관리자” 4번째 탭:
  - 장점: 모든 역할의 진입 방식을 통일하고 운영자가 쉽게 찾을 수 있다.
  - 단점: 일반 사용자에게 필요 없는 선택지를 추가하고 “기관”과 혼동하게 하며 관리자 진입 노출을 늘린다.
- 안 B — 공개 3탭, 기존 `?role=platform_admin` 유지 **(권고)**:
  - 장점: 사용자 요구와 일치하고 일반 화면을 단순하게 유지하며 기존 관리자 링크도 보존한다.
  - 단점: 운영자는 별도 링크·북마크를 알아야 한다.
- 관리자 모드에서는 공개 탭 대신 “플랫폼 관리자 로그인”과 기존 Google Workspace 인증을 표시한다. “일반 로그인으로 돌아가기”는 `/login?role=client`로 이동한다.
- 일반 로그인 화면에 관리자 링크나 숨겨진 4번째 탭을 추가하지 않는다.
- 숨김은 노출 최소화일 뿐 보안 통제가 아니다. **서버 인증·권한 검사가 1차 방어**이며 URL을 알아도 승인되지 않은 계정이 관리자 권한을 얻어서는 안 된다.

## 4. 경로와 탭 상태

- 단일 공개 로그인 경로: `/login`.
- 탭 상태는 URL 쿼리 `role`을 유일한 기준으로 사용한다. 별도 `tab` 파라미터와 영속 로컬 상태를 추가하지 않는다.
- 정규 주소:
  - 회원: `/login?role=client`.
  - 상담사: `/login?role=counselor`.
  - 기관: `/login?role=org_admin`.
  - 플랫폼 관리자: `/login?role=platform_admin`.
- `/login` 또는 누락·알 수 없는 `role`은 회원으로 처리한다. 역할은 허용 목록으로 해석한다.
- 탭 클릭은 히스토리에 반영해 뒤로 가기로 이전 탭을 복원한다. 새로고침·주소 공유 후에도 선택이 유지된다.
- `/login/client`는 `/login?role=client`로 `replace` 리다이렉트한다. 충돌하는 `role`은 회원으로 정규화한다.
- 관리자 기존 `role`·검증된 `next`는 유지한다. 일반 탭에서는 관리자 `next`를 제거하고 임의 목적지 이동을 지원하지 않는다.
- 상담사 대상 홈 링크·로그아웃·보호 경로 진입은 명시적으로 `role=counselor`를 지정하도록 점검한다. 기관 대상은 `role=org_admin`, 회원 대상은 `role=client`로 연결한다.
- 기존 `/login` 북마크는 계속 열리지만 기본 화면은 회원으로 바뀐다. 상담사 탭 한 번으로 전환 가능하며, 역할이 명시된 기존 링크는 그대로 목적에 맞게 동작한다.

## 5. 기술적 구현 방향

### 통합 방식 비교

- 안 A — 기존 두 페이지를 탭 컨테이너로 감싸기:
  - 초기 수정량이 적지만 전체 페이지 레이아웃·오류 처리·이동 분기가 중복된다.
  - 단기 시제품에는 가능하나 최종 MVP 구조로는 권고하지 않는다.
- 안 B — `LoginPage`를 공통 화면으로 통합 **(권고)**:
  - 공통 레이아웃·이메일 폼·Google 버튼·오류 처리를 재사용한다.
  - 탭별 설정으로 제목, 안내, 버튼 순서, 허용 인증 수단, 요청 역할을 결정한다.
  - `ClientLoginPage`의 동작을 옮긴 후 `/login/client`는 라우트 리다이렉트만 남긴다.
  - 관리자 모드는 같은 인증 구성요소를 사용하되 별도 화면 분기로 유지한다.
- `resolvePostLoginPath`를 공통 유틸리티로 추출하고 모든 인증 성공 지점에서 재사용한다. 상담사 온보딩 누락은 아래 정책으로 명시적으로 보완한다.
- 예상 변경 대상: `App.tsx`, `LoginPage.tsx`, `ClientLoginPage.tsx`, 인증 스토어/API 계약, 서버 인증 엔드포인트. 이 문서는 변경 방향만 제안한다.

### 역할 고정과 서버 계약

- 탭별 `requestedRole`은 회원=`client`, 상담사=`counselor`, 기관=`org_admin`으로 고정한다.
- 선택 역할은 **로그인 의도**이며 권한 부여 근거가 아니다. 실제 역할은 서버가 계정·승인 정보로 결정한다.
- 권고 동작: 선택 역할과 인증된 역할이 다르면 해당 탭의 로그인은 완료하지 않고 “선택한 로그인 유형과 계정 유형이 다릅니다. 올바른 탭에서 다시 로그인해 주세요.”를 표시한다.
- 이메일 API는 현재 역할 인자가 없으므로 선택 역할을 선택적 필드로 추가하는 호환 계약을 설계한다. 기존 호출은 기존 동작을 유지하고 새 통합 화면은 반드시 전달한다.
- 서버는 새 요청의 역할 일치를 **토큰 발급 전에** 검사한다. 클라이언트에서는 검사 완료 전에 인증 상태를 저장하지 않는다.
- 현재 `authStore.login`과 `loginGoogle`은 응답 즉시 토큰·사용자를 저장한다. 화면에서 사후 검사만 덧붙여 로그인된 상태가 남지 않도록 저장 경계를 함께 검토한다.
- Google 신규 회원만 기존 회원 가입 정책을 적용한다. 상담사·기관 요청은 사전 등록된 해당 역할 계정만 허용하고 자동 생성·승격하지 않는다.
- 현재 Google 서버 코드는 신규 `counselor`만 차단하고, 신규 `org_admin` 요청은 `client`로 생성할 수 있다. 기관 Google 버튼의 출시는 이 분기 보완과 검증 이후로 제한한다.
- 현재 관리자 Google 인증에는 회사 이메일 도메인 확인 후 기존 계정을 `platform_admin`으로 승격하는 로직이 있다. 관리자 승인 근거로 도메인을 사용하는 현 정책을 별도로 확인하고, 쿼리만으로 권한이 고정·보호된다고 설명하지 않는다.
- 일반 역할 요청에서 관리자 승격 경로로 들어가지 않도록 분리한다. 관리자 자격 정책을 변경하려면 별도 승인·회귀 검증이 필요하다.
- 모든 보호 API는 로그인 화면을 거치지 않은 직접 요청에도 서버 역할·기관 소속 범위를 검사해야 한다. 탭 검사와 프런트 라우트 가드는 이를 대체하지 않는다.

### Google OAuth(외부 계정 인증) 클라이언트 ID

- 현행: `main.tsx`의 단일 `GoogleOAuthProvider`와 `VITE_GOOGLE_CLIENT_ID`를 공통 사용한다. 역할별 ID 분기는 아직 없다.
- MVP 권고: 공통 ID를 유지하고 탭별 인증 요청 역할만 명시한다. ID 분리가 역할 검증을 대신하지 않으므로 불필요한 설정을 늘리지 않는다.
- 확장 시 역할별 설정 후보: `VITE_GOOGLE_CLIENT_ID_CLIENT`, `VITE_GOOGLE_CLIENT_ID_COUNSELOR`, `VITE_GOOGLE_CLIENT_ID_ORG_ADMIN`, `VITE_GOOGLE_CLIENT_ID_PLATFORM_ADMIN`.
- 분리 도입 시 선택 역할에 맞는 Provider 경계와 인증 시작 시점의 ID를 고정하고, 해당 ID 미설정 시 Google 버튼을 비활성화한다. 관리자 ID가 없을 때 일반 ID로 조용히 대체하지 않는다.
- 백엔드도 인증 토큰의 대상 클라이언트·발급자 등 선택한 OAuth 흐름에 맞는 검증을 지원해야 한다. 현행은 Google `userinfo` 조회 중심이며 역할별 대상 클라이언트 검증이 구현돼 있다고 가정하지 않는다.
- 프런트 환경 변수에는 공개 클라이언트 ID만 둔다. 클라이언트 비밀키는 브라우저에 배포하지 않는다.

## 6. 로그인 성공·온보딩 이동 정책

- 공통 순서: 서버 인증 → 선택 역할 일치 확인 → 인증 상태 저장 → 공통 `resolvePostLoginPath` → 이동.
- 회원 `client`:
  - `onboarding_completed === true` → `/app`.
  - 미완료 → `/onboarding/client`.
- 상담사 `counselor`:
  - 완료 → `/dashboard`.
  - 미완료 → `/onboarding/counselor`.
  - 이는 현행 `LoginPage`에 없는 분기를 추가하는 제안이며, `ClientLoginPage`에 존재하는 정책과 통일한다.
- 기관 관리자 `org_admin`:
  - 현재 계약 유지: `/dashboard/org`.
  - 기관 전용 온보딩 라우트는 현재 확인되지 않는다. 미온보딩 값을 이유로 상담사 온보딩으로 보내거나 존재하지 않는 경로를 만들지 않는다.
  - 기관 전용 초기 설정은 확장 단계에서 별도로 설계한다.
- 플랫폼 관리자 `platform_admin`:
  - 온보딩 분기 없이 `/admin/orgs` 또는 안전성이 확인된 관리자 `next`.
  - 현재 `next.startsWith('/admin')`보다 명확한 `/admin` 또는 `/admin/` 경로 경계 검증을 제안한다. 외부 URL·프로토콜 상대 URL·비관리자 경로는 거부한다.
- 알 수 없는 역할이나 레거시 `admin`은 기관·플랫폼 관리자로 추정하지 않는다. 현재 공통 함수의 `/` 폴백을 유지하고 보호 화면 권한은 별도로 검사한다.
- 인증 응답이 없거나 필수 역할 정보가 없으면 성공 이동하지 않고 오류로 처리한다.

## 7. 단계와 완료 기준

### 우선순위 0 — 구현 전 확인

- 서비스 기획 검토: 기본 회원 탭, 관리자 별도 진입, 역할 불일치 시 재로그인, 기관 이메일 우선 정책.
- 디자인 단계: 기존 스타일 안에서 `TabMenu` 아래 콘텐츠 교체 방식의 목업 검토.
- 구현 단계: SDD의 `plan.md`·구현 전 `verify.md`에서 서버 계약과 회귀 시나리오를 확정하고 승인 후 구현한다.
- 이 기획 문서만으로 SDD 완료나 구현 승인을 갈음하지 않는다.

### 우선순위 1 — MVP(최소 기능 제품)

- 공개 3탭, `/login` 통합, URL 탭 유지, `/login/client` 호환 리다이렉트.
- 회원 Google 강조, 상담사·기관 이메일 중심, 관리자 Google 전용 별도 모드 보존.
- 공통 이동 함수와 상담사 온보딩 정책 통일.
- 역할 의도와 실제 권한 구분, 서버의 역할 일치 검사, 인증 상태 저장 순서 정리.
- 기존 가입·비밀번호 찾기·로그아웃·보호 경로의 진입 링크 점검.
- 개발 역할 시뮬레이션은 기존 플래그 조건과 서버 게이트를 유지하며 일반 사용자의 역할 선택 기능과 분리한다.

### 우선순위 2 — 확장

- 기관 초기 설정·관리자 초대·기관별 계정 안내 심화.
- 기관 Google 인증: 사전 등록 계정 확인 및 잘못된 자동 가입 차단을 먼저 구현한 후 노출.
- 운영상 분리 필요가 확인된 경우에만 역할별 Google 클라이언트 ID 도입.
- 다중 역할 계정 전환은 별도 요구사항으로 다룬다. 이번 탭이 기존 계정 역할을 변경하지 않는다.

### 구현 시 검증할 인수 조건

- 첫 방문 `/login`은 회원 탭이고, 각 역할 URL은 지정한 탭/관리자 화면을 연다.
- 탭 클릭·새로고침·뒤로 가기에서 선택 상태가 일치하고 기존 회원·관리자 링크가 동작한다.
- 각 공개 역할의 정상 이메일 인증, 허용한 Google 인증, 회원·상담사 온보딩 완료/미완료 이동을 확인한다.
- 기관 계정은 `/dashboard/org`, 관리자는 허용된 `next` 또는 `/admin/orgs`로 이동한다.
- 다른 역할의 계정을 사용하면 토큰 발급·저장 전에 차단하고 올바른 탭 사용을 안내한다.
- URL·요청 역할을 조작하거나 보호 API를 직접 호출해도 계정 권한과 기관 접근 범위가 확대되지 않는다.
- 신규 상담사·기관 Google 요청으로 계정이 잘못 생성되지 않으며 일반 계정의 관리자 모드 접근이 서버 정책에 따라 거부된다.
- 인증 중 탭 전환·중복 클릭·Google 취소·계정 잠김·네트워크 실패 뒤 상태가 일관된다.
- 모바일 화면, 키보드 탭 조작, 스크린리더 레이블을 점검한다.
- 본 작업에서는 코드 실행·브라우저 검증을 수행하지 않았다. 위 항목은 향후 구현 검증 기준이다.
