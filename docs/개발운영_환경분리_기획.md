### 2-1. 환경 구성

| 항목 | dev (현 서버 유지) | staging (임시 검증) | prod (신설) |
|---|---|---|---|
| 용도 | 개발·에이전트 실험·SDD 검증 | 릴리스 후보 최종 검증(필요 시 생성→검증→삭제) | 실사용자 서비스 |
| 데이터 | **비식별 + 합성 데이터만**(실데이터 이관 후 폐기) | 합성 데이터 | 실데이터 |
| 주소 | `dev.` / `dev-api.`(**당분간 존속**: 구 앱 빌드가 고정) | 임시 서브도메인 | `mindbreeze.` / `api.mindbreeze.` (같은 상위 도메인 유지 — 쿠키 SameSite) |

### 2-2. 브랜치·병렬 개발 규칙 `[제안]`
| 브랜치 | 규칙 |
|---|---|
| `feature/NNN-*`·`fix/NNN-*` | 에이전트/개발자별 독립 브랜치(작업 폴더 분리). **develop 직접 push 금지**, PR로 병합 |
| `develop` | 통합 기준. 필수 검사 통과 후 병합. 병합 커밋의 **CI가 통과해야** dev 자동배포 |
| `release/x.y.z` | develop에서 분기, 기능 동결(수정만) |
| `main` | 운영 출시 기준(병합만으로 배포하지 않음). **현재 main은 6월 이후 방치·565커밋 차이 → 보존 태그 후 기준점 재설정**(강제 덮어쓰기·일괄 병합 금지) |

### 2-4. DB·마이그레이션 정책 `[제안]`
- **expand → migrate → contract**: ①컬럼·테이블 추가만 배포 → ②이중 쓰기·백필 → ③구 컬럼 제거는 **구 앱 지원 종료 후 1릴리스 뒤**.
- `drop_column`·`drop_table`·파괴적 UPDATE 포함 마이그레이션은 **Brian 승인 + 사전 스냅샷 의무**, 별도 릴리스로 분리.
- 자동 `alembic downgrade`를 운영 복구 수단으로 보지 않는다.
- 데이터 정정(수동 SQL)은 사전 승인 + 실행 이력 보관.

### 2-5. 주기 작업(cron 14개) `[제안]`

### 5-3. D5(뇌파 영구 보관) 영향 — 후속 조치
| 항목 | 내용 |
|---|---|
| 현재 설정과 충돌 | `EEG_RAW_RETENTION_DAYS = 90`(`eeg_raw_service.py:325`) + 매일 04:30 정리 cron이 동작 중 `[검증]`. 서버 로그상 **지금까지 만료 삭제는 0건**(`expired_deleted` 0) → 아직 유실 없음. 그러나 90일이 지나기 시작하면 뇌파 원본이 삭제되므로 **Phase 0에서 뇌파 원본 정리를 중지**해야 함(음성·영상은 90일 유지: `MEDIA_RETENTION_DAYS = 90`) |
| 저장 비용 | 250Hz·2채널·50분 원본은 비압축 약 6MB `[추정]`, 압축 시 그 이하. 영구 보관 비용은 낮음 → S3 수명주기(일정 기간 후 저비용 보관 등급 이동)로 관리. **로컬 디스크에 영구 보관은 비권장**(내구성) |
| 법·정책 | 개인정보(민감정보) 영구 보관은 **목적·보유기간 고지와 동의**가 필요하고 탈퇴·삭제 요청 대응이 필수. 권고: ①동의 문구에 "뇌파 데이터 영구 보관(연구·서비스 개선)" 명시 ②원본은 **가명처리 후 보관**(식별정보와 분리) ③탈퇴 시 삭제 또는 비식별 전환 정책 확정 ④법무 검토. 이 항목은 법률 자문이 필요해 본 문서에서 결론 내지 않음 |
| 기술 처리 | 보관 정책을 데이터 종류별 설정으로 분리(뇌파=무기한, 음성=90일, 전사·요약=3년 제안), 정리 cron은 설정에 따라 동작, 접근 감사 로그 신설(Phase 4) |

- `[검증]` 항목은 이번 조사에서 코드·서버·AWS·공개 주소로 직접 확인. 비용·일정·확장 임계는 모두 `[추정]`.
