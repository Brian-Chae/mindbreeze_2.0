# 회원가입 역할별 분리 기획안

- 작성일: 2026-09-17
- 단계: Phase 1 서비스 기획 / 검토안
- 범위: 회원·상담사·기관의 가입 화면과 신청·검토·활성화 절차 설계
- 산출물 범위: 기획 문서만 작성. 코드·DB·배포·실제 메일 발송은 수행하지 않음.

## 1. 핵심 제안

- 가입 입구를 **회원 / 상담사 / 기관** 세 페이지로 분리한다.
- 회원은 개인정보와 초대한 상담사 코드를 입력하고 이메일 인증 후 가입한다.
- 상담사는 **기관 초대 수락 / 개인 상담사 신청** 중 자신의 상황에 맞는 절차로 진입한다.
- 개인 상담사 신청은 **개인 기관 1개 + 상담사 계정 1개 + 상담사 프로필**을 자동 생성한다. 신청 시점에는 이용 대기 상태이며, 관리자 승인과 본인의 초대 수락을 모두 마친 뒤 이용한다.
- 기관 가입은 **기업 가입 상담 신청**이다. 접수만으로 기관이나 담당자 계정을 만들지 않으며, 영업 상담 이후 플랫폼 관리자가 기존 기관 등록 절차로 생성한다.
- 기관·개인 상담사 신청 모두 `brian.chae@looxidlabs.com`으로 알린다. 신청 DB가 원본이고 이메일은 운영 알림이다.
- 최소 기능 제품(MVP)은 기존 단일 `User.role`을 유지한다. 개인 상담사는 `role="counselor"`로 상담 업무를 수행하고 자신의 개인 기관 설정만 제한적으로 관리한다.

## 2. 현재 구조와 변경 지점

### 2.1 회원 가입·온보딩

- `frontend/src/pages/RegisterPage.tsx`
  - `/register?role=client`: 이메일 + 일회용 인증번호(OTP) → 약관 동의 → 비밀번호 + 이름의 3단계.
  - 가입 후 `/onboarding/client`로 이동한다.
  - `invite_token` 기반 기존 초대 가입 경로가 있으며, 초대한 상담사에 연결하는 흐름을 유지해야 한다.
- `frontend/src/pages/onboarding/ClientOnboardingPage.tsx`
  - 현재 이름·전화번호, 성별·생년월일 등 추가 정보를 받는다.
  - SDD-062 기준 성별은 `male/female/other`, 생년월일은 `YYYY-MM-DD`이며 게스트/회원 수집 흐름이 있다.
  - 상담사 코드 입력·매칭 및 초대 가입의 연결 확인 화면이 있다.
- 변경: 회원 필수 개인정보와 상담사 연결을 가입 시점에 완료한다. 온보딩에서는 저장된 값을 재사용하고 이미 완료한 개인정보·코드 입력을 반복시키지 않는다. 게스트 흐름은 별도로 유지한다.

### 2.2 기관 소속 상담사

- `/register?role=counselor`는 직접 가입 폼을 숨기고 “상담사는 기관 담당자의 초대로 가입합니다”를 표시한다(SDD-017).
- 백엔드 `POST /auth/register/counselor`에는 `org_code` 검증 가입이 남아 있다. 화면이 숨겨져 있다는 사실만으로 서버 접근이 차단된 것은 아니다.
- `org_service.invite_counselor`
  - 기관 담당자가 이름·이메일로 초대한다.
  - `User(role="counselor", status="pending")`와 `CounselorProfile`을 생성한다.
  - 유일한 6자리 `counselor_code`, 초대 토큰, 초대 메일을 발급한다.
  - 초대 수락 전에는 알 수 없는 난수의 비밀번호 해시를 사용해 로그인할 수 없다.
  - 기관별 초대 요청 빈도 제한과 이메일 중복 검사가 있다.
- 변경: 기존 초대 절차는 유지하면서 개인 상담사 신청을 별도 경로로 추가한다.

### 2.3 기관 등록

- 플랫폼 관리자 `OrgManagementPage`와 `org_service.create_org_with_admin`이 기준 운영 경로다.
- 기관명 등을 입력해 기관 및 6자리 `org_code`를 만들고, 담당자 이름·이메일 등으로 `org_admin` 계정을 생성한 뒤 초대 메일을 보낸다.
- 담당자는 `pending` 상태와 난수 비밀번호 해시로 생성되어 초대 수락 전 로그인할 수 없다.
- 코드 확인 시 추가로 발견된 경로:
  - `/org/register`의 `OrgRegisterPage`에는 로그인한 상담사가 센터를 등록하는 기존 화면이 남아 있다.
  - `org_service.create_organization`에는 기관 생성 후 사용자를 `org_admin`으로 바꾸는 로직이 있다.
  - 이는 공개 기업 상담 신청과 다른 기존 경로다. 신규 공개 가입에 재사용하지 않으며, 구현 전 사용처를 확인해 플랫폼 관리자 등록 정책을 우회하지 않도록 화면과 서버 정책을 함께 정리한다.

### 2.4 이메일 운영

- 제공된 운영 전제: Celery의 `email_app` 작업 실행기(worker), systemd 서비스 `mindbreeze-email-worker`가 필요하다.
- 저장소에서 확인한 사항:
  - `backend/app/tasks/report_email_task.py`에 Redis 브로커를 사용하는 `email_app`이 있다.
  - `backend/app/tasks/email.py`는 Resend 발송 공통 함수와 메일 템플릿을 제공한다.
  - `org_invite_service` 등 일부 초대 흐름은 발송 함수를 직접 호출한다. 모든 기존 초대·승인 메일이 이미 `email_app`을 경유한다고 단정할 수 없다.
- 신규 신청 알림·승인 초대는 `email_app` 경유를 명시적으로 설계한다. 운영 서버의 실제 worker 실행 상태와 작업 등록 여부는 구현·배포 단계에서 확인한다.

## 3. 역할별 가입 화면과 절차

### 3.1 공통 진입

- `/register`: 역할 선택 화면.
  - **회원 가입** — “상담사와 연결해 상담·명상 서비스를 이용해요.”
  - **상담사 가입** — “기관 초대를 받았거나 개인 상담사로 시작해요.”
  - **기관 가입 상담** — “우리 기관의 도입을 상담해요.”
- 신규 경로 제안: `/register/client`, `/register/counselor`, `/register/organization`.
- 기존 `?role=client|counselor` 주소는 대응 페이지로 연결하고 `invite_token`, `code` 등 기존 유효한 초대 정보를 보존한다.
- 화면 상단에 역할 전환 링크, 하단에 로그인 링크를 제공한다. 역할을 바꿔도 다른 역할 폼으로 개인정보를 무조건 전달하지 않는다.

### 3.2 회원 가입

- 필수 필드:
  - 이름: 앞뒤 공백 제거, 기존 사용자 이름 길이 제한 적용.
  - 성별: 남성 / 여성 / 기타 → `male/female/other`.
  - 생년월일: `YYYY-MM-DD`, 실제 존재하는 날짜이며 미래 날짜 불가.
  - 전화번호: 연락 가능한 번호, 형식 정규화 및 검증. 문자 인증은 이번 MVP에 추가하지 않으므로 전화번호 소유 확인 완료로 표시하지 않는다.
  - 이메일: 기존 OTP로 소유 확인.
  - 비밀번호·비밀번호 확인: 기존 비밀번호 정책 유지.
  - 초대한 상담사 코드: 기존 6자리 `counselor_code` 사용.
  - 서비스 이용약관·개인정보 처리 관련 필수 동의. 마케팅 동의는 선택·미선택 기본값.
- 3단계 구성:
  1. 이메일 입력 및 OTP 인증.
  2. 약관 동의, 개인정보 수집 목적 확인.
  3. 이름·성별·생년월일·전화번호·비밀번호·상담사 코드 입력 → 연결 대상 확인 → 가입 완료.
- 코드 확인 후 상담사 표시명과 소속 기관명만 보여주고 “이 상담사와 연결하여 가입”을 명시한다.
- 일반 가입은 코드 필수로 제안한다. 코드가 없으면 “초대한 상담사에게 코드를 요청해 주세요”로 안내하며 임의 상담사나 공용 기관에 연결하지 않는다.
- 유효한 기존 `invite_token`이 있으면 서버가 초대한 상담사를 확정하고 코드 입력을 대신한다. 사용자가 동일 코드를 다시 타이핑하지 않도록 연결 대상을 표시한다.
- 코드와 토큰이 서로 다른 상담사를 가리키면 자동으로 어느 쪽도 선택하지 않고 오류를 표시한다.
- 가입 후 미완료 온보딩 항목만 진행한다. 가입 정보와 `ClientProfile`, `User.phone`, 온보딩 진행 상태가 일치해야 한다.
- 생년월일을 받는다고 미성년자 가입 동의가 해결되는 것은 아니다. 서비스 대상 연령·보호자 절차는 출시 전 기존 운영 정책과 맞춰 확정할 항목이다.

### 3.3 상담사 가입 — 기관 초대

- 상담사 페이지에 두 선택지를 제시한다: **기관 소속 상담사 / 개인 상담사**.
- 기관 소속 선택 시 안내:
  1. 기관 담당자에게 초대를 요청한다.
  2. 담당자가 기관 관리 화면에서 상담사 이름·이메일을 입력한다.
  3. 상담사는 초대 메일 링크에서 유효성·소속 기관을 확인한다.
  4. 기존 초대 수락 절차로 비밀번호 설정·계정 활성화 후 상담사 온보딩을 진행한다.
- 초대 미수신·만료 시 기관 담당자에게 재발송을 요청하도록 안내한다. 기관 코드 입력만으로 초대 승인을 대체하지 않는다.
- 초대 재발송 빈도 제한과 기존 계정 중복 처리 규칙을 유지한다.

### 3.4 상담사 가입 — 개인 신청

- 필수 필드: 이름, 이메일 + OTP, 전화번호, 개인정보 수집·이용 동의.
- 선택 필드: 활동명/상담소명, 전문 분야, 경력·자격 요약, 문의 내용.
- 활동명 미입력 시 기관 표시명은 “{이름} 개인 상담실”로 자동 제안한다.
- 첫 신청에는 사업자등록번호·자격증 파일·주소·내담자 사례를 요구하지 않는다. 검토상 필요한 증빙은 이후 별도 절차로 요청한다.
- 제출 버튼: **개인 상담사 이용 신청**.
- 신청 직후:
  - 신청 기록과 개인용 `Organization`, 대기 `User`, `CounselorProfile`을 자동 생성한다.
  - Brian에게 신청 알림을 발송한다.
  - “신청이 접수되었습니다. 검토 후 등록한 이메일로 이용 안내를 보내드립니다.”를 표시한다.
- 관리자 승인 후 기존 초대 수락 방식을 활용한 활성화 메일을 신청자에게 보낸다. 비밀번호는 이 단계에서 본인이 설정한다.
- 활성화 후 본인 기관 소속 상담사로 상담·내담자 초대·리포트 기능을 이용한다. 조직원 추가 등 기업용 운영 기능은 MVP 범위에서 제외한다.
- **검토안의 정책 선택**: 요구사항의 ‘제출 시 개인이 기관이자 상담사로 설정’을 즉시 데이터 생성으로 반영하고, 실제 이용은 승인 후 허용한다. 즉시 활성화가 필요한 경우 별도 제품 결정과 권한 검토가 필요하다.

### 3.5 기관 가입 상담 신청

- 필수 필드: 기업/기관명, 담당자 이름, 연락처(전화번호), 업무 이메일, 개인정보 수집·이용 동의.
- 선택 필드: 부서·직책, 예상 이용 인원, 도입 희망 시기, 상담 요청 내용.
- 제출 버튼: **기관 가입 상담 신청**.
- 개인정보를 담을 필요가 없는 상담 사례·건강정보는 입력하지 않도록 도움말을 제공한다.
- 제출 → 신청 저장 → `brian.chae@looxidlabs.com` 알림 → 접수 번호와 완료 안내 표시.
- 영업 담당자가 연락하여 도입 조건을 확인한 뒤 플랫폼 관리자에게 기관 등록을 요청한다.
- 플랫폼 관리자가 기존 등록 기능으로 기관과 `org_admin`을 생성하고 담당자 초대 메일을 발송한다.
- 신청 폼에서는 비밀번호·기관 코드·사업자 증빙 파일을 받지 않는다. 접수 완료 화면에 계정 생성 또는 이용 승인 완료로 표시하지 않는다.

## 4. 기술 구현 방향

### 4.1 신청 저장과 이메일 파이프라인

- 신규 모델 제안: `SignupApplication` 하나로 `organization`과 `individual_counselor` 신청을 관리한다.
- 주요 필드 제안:
  - `id`, `application_type`, `organization_name`, `contact_name`, `email`, `phone`, 선택 문의 정보.
  - `status`, `reviewed_by`, `reviewed_at`, `review_note`, `created_at`, `updated_at`.
  - `organization_id`, `user_id`: 실제 생성한 객체 참조, 생성 전에는 `null`.
  - 동의 문서 버전·동의 시각, 중복 요청 방지용 `idempotency_key`.
- 신규 API(응용 프로그램 인터페이스) 제안:
  - `POST /signup-applications/organization`: 기관 상담 접수.
  - `POST /signup-applications/individual-counselor`: 이메일 인증을 확인한 개인 상담사 접수·대기 객체 생성.
  - 관리자용 목록·상세·검토 상태 변경·알림 재발송. 플랫폼 관리자만 접근한다.
- 저장 트랜잭션에 신청 및 발송 대기 레코드를 함께 기록하는 소규모 아웃박스(outbox, 발송 대기함)를 둔다.
- 저장 완료 후 `email_app` 작업에 신청 ID/발송 ID를 전달한다. 브로커 장애로 큐에 넣지 못한 항목은 대기함에서 복구한다.
- `mindbreeze-email-worker`가 해당 작업을 등록·소비하도록 모듈 import와 큐 구성을 확인한다. 단순히 새 함수를 작성하는 것만으로 worker가 실행하지 않는다.
- 수신 주소는 서버 설정으로 고정하며 초기값은 **`brian.chae@looxidlabs.com`**이다. 클라이언트가 수신자를 바꿀 수 없게 한다.
- 기존 Resend 전송 함수를 재사용하되 실패 반환값을 작업 실패로 전환해 제한된 횟수의 지수 지연 재시도를 적용한다.
- 신청 상태와 발송 상태를 분리한다. 발송 상태 예: `pending / queued / sent / failed`.
- `sent`는 발송 제공자의 요청 수락 의미다. 실제 수신함 도착 확인과 구분하며, 전달 결과 웹훅은 후속 범위로 둘 수 있다.
- 신청 저장 성공·메일 실패 시 신청은 접수된 상태로 남기고 운영자가 재발송한다. 사용자가 새 신청을 반복하게 하지 않는다.
- 같은 발송 건은 멱등 처리한다. 제공자 수락 직후 worker가 중단되는 경우 중복 알림 가능성이 있으므로 지원되는 멱등 키를 활용하고 신청 ID를 제목에 포함한다.

### 4.2 신청 알림 메일 구조

- 기관 제목: `[MIND BREEZE][기관 가입 상담] 신청 {application_id}`.
- 개인 상담사 제목: `[MIND BREEZE][개인 상담사 신청] 신청 {application_id}`.
- 공통 본문:
  - 접수 일시, 신청 유형, 기관명 또는 활동명, 담당자/신청자 이름.
  - 회신 이메일, 마스킹한 전화번호, 문의 요약.
  - 현재 상태, 관리자 검토 화면 링크, 다음 처리 안내.
- 전체 전화번호와 신청 원문은 인증된 관리자 상세 화면에서 확인한다. 메일 제목·로그에는 전화번호를 넣지 않는다.
- 발신자는 서비스 인증 주소를 사용한다. `Reply-To`를 지원하도록 확장할 경우 검증된 신청자 이메일만 지정한다.
- 비밀번호·OTP·인증 토큰·건강정보는 Brian 수신 신청 알림에 포함하지 않는다. 활성화 토큰은 해당 신청자에게 보내는 초대 메일에만 포함한다.
- HTML 및 일반 텍스트 본문을 함께 제공하고 사용자 입력을 이스케이프한다.

### 4.3 개인 상담사의 기관·계정·권한

- 선택지 비교:
  - **권고: `counselor` 계정 1개 + 개인 기관 소유 관계**. 상담사 기존 진입 경로를 유지하고 개인 기관 설정만 제한적으로 허용한다.
  - `org_admin` 계정 1개 + `CounselorProfile`: 기존 기관 관리 권한은 사용하기 쉽지만 상담사 로그인·라우팅·역할 검사 수정 범위가 넓다.
  - 기관 담당자/상담사 계정 2개 또는 전면 다중 역할: 중복 로그인·이메일 관리 또는 권한 체계 개편이 필요하므로 MVP에서 제외한다.
- 권고 모델 확장:
  - `Organization.kind`: `institution / individual`, 기존 기관은 `institution`으로 유지.
  - `Organization.owner_user_id`: 개인 기관의 소유 상담사 참조. 기존 `primary_admin_id`의 `org_admin` 의미를 바꾸지 않는다.
  - `User.role="counselor"`, `User.org_id=개인 기관 ID`, `User.status="pending"`.
  - `CounselorProfile.user_id=해당 User.id`, 기존 생성기로 유일한 `counselor_code` 발급.
  - 미검토 개인 기관은 `verified=False`; 신청 심사 승인 시 기관 이용 검토 결과에 맞게 처리한다. 이것이 상담사 자격 인증 `verified_tier`의 자동 승격을 뜻하지는 않는다.
- 생성 단위: 신청 + 개인 기관 + 대기 사용자 + 프로필 + 소유 관계를 하나의 트랜잭션으로 저장한다. 순환 참조는 기관·사용자 순서로 `flush`한 뒤 소유 관계를 설정한다.
- 기존 `create_org_with_admin`은 `org_admin` 생성 및 내부 `commit`을 포함하므로 개인 신청에 그대로 호출한 뒤 역할만 바꾸지 않는다. 코드 발급·초대·비밀번호 처리 규칙을 재사용할 수 있는 서비스 경계를 설계한다.
- 권한 범위:
  - 상담 업무: 기존 상담사 권한과 본인 내담자 관계 검사 사용.
  - 개인 기관 표시명·대표 연락처 수정: `kind="individual"`이고 `owner_user_id`가 본인이며 소속이 일치할 때만 허용.
  - 기관 구성원 초대·역할 변경·타 기관 조회·플랫폼 관리: 허용하지 않는다.
  - 기존 `org_admin` 전용 검사에 모든 상담사를 일괄 추가하지 않는다.
- 로그인은 기존 상담사 경로를 유지한다. 가입 승인 전, 초대 미수락, 반려 상태에는 로그인과 코드 연결을 허용하지 않는다.
- 기존 이메일 계정은 자동 병합·기관 이동·역할 승격하지 않는다. 신청자가 본인임을 확인하고 운영자가 별도 처리하도록 안내한다.

### 4.4 회원의 상담사 코드 검증·연결

- 저장 위치: `CounselorProfile.counselor_code`. `Organization.org_code`와 목적이 다르며 혼용하지 않는다.
- 서버에서 형식·길이·정규화 규칙을 기존 코드 생성 규칙과 일치시킨다.
- 코드 존재뿐 아니라 연결 대상의 상담 가능 역할, `User.status="active"`, 유효한 기관 소속과 개인 신청 승인 상태를 검사한다.
- OTP 검증 이후 코드 확인을 허용하고 요청 빈도를 제한한다. 이메일·전화번호·내담자 정보는 코드 조회 응답에 포함하지 않는다.
- 입력 중 조회 결과를 신뢰해 끝내지 않고 최종 가입 시 다시 검증한다.
- `User`, `ClientProfile`, 동의 기록, `ClientCounselorLink`가 일관되게 생성된 뒤 가입 성공과 인증 토큰을 반환한다.
- 연결은 기존 `client_service.assign_counselor`의 중복 방지·재활성화·채팅방 생성 규칙을 재사용한다.
- 주의: 현재 사용자 생성·연결·채팅방 헬퍼에는 내부 `commit`이 있으므로 단순 연속 호출만으로 원자성이 확보되지 않는다. 구현 계획에서 가입 트랜잭션 경계를 조정하고 중간 실패 시 불완전 가입을 남기지 않는 복구 방식을 검증한다.
- 기존 `invite_token` 경로의 이메일 일치·만료 검증을 유지한다. 유효한 토큰에서 얻은 상담사를 코드와 같은 검증·연결 정책에 적용한다.
- 로그인된 기존 회원의 상담사 추가와 게스트 이용에는 이번 신규 가입의 코드 필수 정책을 소급 적용하지 않는다.

## 5. 신청 상태와 관리자 검토

- 신청 상태 제안: `submitted → reviewing → approved / rejected`; 철회는 `withdrawn`.
- `approved`는 이용 심사 통과를 뜻하며 계정 활성화와 구분한다.
- 개인 상담사:
  - `submitted`: 대기 객체 생성, 로그인 불가, 코드 사용 불가.
  - `reviewing`: 연락처·활동 내용 확인, 필요 시 추가 자료 요청.
  - `approved`: 승인 이력 저장 → 활성화 초대 발송 → 본인이 수락한 뒤 계정 `active`.
  - `rejected/withdrawn`: 초대 토큰 무효화, 대기 계정·개인 기관 이용 불가 유지, 보유 정책에 따라 정리.
- 기관:
  - 신청 검토·상담 → `approved` → 기존 관리자 기관 등록 → 담당자 초대 수락.
  - 기관 생성 결과의 ID를 신청에 연결한다. 승인 재시도로 기관이나 담당자가 중복 생성되지 않게 한다.
- 관리자 최소 화면: 신청 유형·상태·접수일 목록, 상세 연락처·문의, 검토 메모, 승인/반려, 발송 상태·재발송.
- 승인·반려 작업은 플랫폼 관리자만 실행하고 담당자·시각·이전/이후 상태를 기록한다. 영업 담당자는 초기에는 Brian을 통해 처리하고 별도의 광범위한 관리자 권한을 만들지 않는다.
- 같은 신청의 동시 승인과 메일 재시도는 동일 객체·동일 상태를 유지하도록 잠금 또는 조건부 갱신으로 처리한다.

## 6. 개인정보·운영 원칙

- 전화번호는 회원 연락 또는 가입 상담 목적을 명시하고 필수 여부·수집 항목·보유 기간·동의 거부 시 영향을 폼에서 안내한다. 마케팅 활용은 별도 선택 동의로 분리한다.
- 성별·생년월일은 회원 가입 목적과 기존 프로필 사용 목적을 설명하고 상담 신청 메일로 전달하지 않는다.
- 전송 암호화, 저장 데이터 접근 제한, 관리자 연락처 열람 기록, 로그 마스킹을 적용한다. 공개 신청 상세 조회 API는 만들지 않는다.
- 신청 데이터 보유안: 미전환·반려·철회 신청의 연락처와 문의 원문은 접수 후 90일 이내 삭제 또는 비식별 처리한다. 이는 제품 운영 제안이며 출시 전 담당자가 보유 정책을 확정한다.
- 승인·계정 전환 후 필요한 계정 정보만 계정 보유 정책으로 관리하고 신청서 복제본·메일 보관함에도 정리 정책을 적용한다.
- 신청 중복 제출은 버튼 비활성화와 서버 멱등성으로 막는다. 개인 신청은 이메일 OTP, 공개 기관 신청은 IP·이메일 기반 요청 빈도 제한과 숨김 스팸 필드 등으로 남용을 완화한다.
- 브라우저 새로고침·시간 초과 후 재시도에도 하나의 신청만 남아야 한다. 전화번호 형식 검증을 본인 인증으로 표시하지 않는다.

## 7. 우선순위와 추진 단계

### P0 — 정책·기획 승인

- 역할별 페이지, 회원 코드 필수 및 초대 토큰 예외, 개인 상담사 대기 생성·승인 후 활성화 정책을 확정한다.
- 개인 상담사의 최소 기관 관리 범위, 전화번호 수집 목적, 대상 연령과 보유 기간을 확정한다.
- 기존 `/org/register`와 `/auth/register/counselor`를 포함한 우회 경로의 사용처 및 서버 정책 정리 범위를 결정한다.
- 현재 문서가 Phase 1 산출물이며, 이후 디자인 기획과 구현은 프로젝트 승인 절차에 따라 별도로 진행한다.

### P1 — 역할 분리·기관 상담 접수

- 세 가입 페이지와 기존 주소 호환 연결을 제공한다.
- 기관 신청 저장·Brian 알림·관리자 최소 신청 목록/상세·발송 실패 재시도를 구현한다.
- 실제 `email_app` 작업 등록과 `mindbreeze-email-worker` 운영을 확인한다.
- 이 단계는 부분 출시이며 개인 상담사 신청까지 완료된 것으로 안내하지 않는다.

### P2 — 회원 가입 정보·코드 통합

- 개인정보 필드 이동, 서버 검증, 상담사 연결, 기존 초대 호환, 온보딩 중복 제거를 구현한다.
- 가입 도중 실패·동시 요청·기존 회원 및 게스트 회귀를 검증한다.

### P3 — 개인 상담사 자동 설정

- 개인 기관·상담사·프로필 원자적 생성, 심사·활성화·소유자 권한을 구현한다.
- 자동 생성 실패 복구와 승인 중복 방지, 코드 노출·로그인 차단을 검증한다.
- 기관 규모 확장·다중 역할·사업자 자동 심사·파일 증빙 업로드는 후속 범위다.
- 구현 전 SDD의 spec·plan·verify 승인, 구현 후 테스트·summary·최종 리뷰를 진행한다. 이 문서는 구현 승인이나 사후 verify를 대신하지 않는다.

## 8. 구현 시 수용 기준

- 세 역할 페이지가 분리되고 기존 초대 URL로 접근해도 정보가 손실되지 않는다.
- 기관 신청 1건은 신청 DB 1건과 Brian 수신 알림으로 처리되고, 기관·사용자는 접수만으로 생성되지 않는다.
- 개인 신청 1건은 개인 기관·대기 상담사·프로필 각 1개를 만들고 Brian에게 알린다.
- 승인 전/초대 미수락 개인 상담사는 로그인하거나 회원을 코드로 연결할 수 없다.
- 활성화된 개인 상담사는 상담 업무와 본인 개인 기관의 허용된 설정만 사용할 수 있다.
- 잘못된 코드·비활성 상담사·토큰 불일치로 가입이 실패하면 불완전한 회원·연결을 남기지 않는다.
- 회원 가입에서 받은 정보가 온보딩에 반영되고, 게스트 및 기존 초대 가입이 유지된다.
- 메일 worker 중단·브로커 오류·Resend 실패에도 신청이 유실되지 않고 중복 생성 없이 재처리된다.
- 개발 모드의 발송 성공 반환값과 큐 적재만으로 실제 메일 수신을 통과 처리하지 않는다. 운영 수신함 확인은 별도 배포 검증 항목이다.
