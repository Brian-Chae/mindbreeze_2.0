# Mind Breeze 채팅방 회원 초대 — 프론트엔드 UX 기획

작성일: 2026-09-25  
대상: 현재 `mindbreeze_2.0` 저장소의 Mind Breeze 채팅 기능  
입력: `docs/chat-invite-member/00-research-brief.md`  
상태: 검토용 기획안. 구현·API 추가·DB 변경은 수행하지 않는다.

## 1. 배경과 기획 원칙

상담사가 그룹 명상 대화를 위해 다른 상담사와 내담자를 초대할 때, 기존 대화를 공유할지 새 대화를 시작할지 명시적으로 선택하도록 한다. 여기서 ‘초대’는 채팅 참여자 추가이며, 신규 가입 초대·기관 소속 초대·상담사와 내담자의 연결 생성이 아니다.

이 문서의 **현재 사실**은 확인한 코드에 파일:라인을 붙인다. **제안**은 앞으로 만들 UX와 API 계약이며 현재 지원되는 기능으로 해석하지 않는다. 백엔드 합의가 필요한 항목은 별도로 표시한다. 다른 프로젝트의 지식·메모리는 사용하지 않는다.

### 1.1 현재 코드에서 확인한 범위

- `RoomActionsMenu`의 ⋯ 메뉴에는 현재 ‘채팅방 설정’만 있다. 상담사와 내담자 페이지 모두 이 컴포넌트를 사용한다. 근거: `frontend/src/components/chat/RoomActionsMenu.tsx:38`, `frontend/src/components/chat/RoomActionsMenu.tsx:42`, `frontend/src/pages/chat/ChatPage.tsx:169`, `frontend/src/pages/client/ClientChatPage.tsx:210`.
- 설정의 참여자 관리는 `group && host_id === userId`로 노출하고, `listClients()`로 내담자를 검색한 뒤 바로 추가한다. 역할 자체를 검사하는 조건은 해당 `canManage`에 없다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:82`, `frontend/src/components/chat/RoomSettingsModal.tsx:141`, `frontend/src/components/chat/RoomSettingsModal.tsx:180`, `frontend/src/components/chat/RoomSettingsModal.tsx:232`.
- 참여자 추가·조회 API는 그룹방 호스트 전용이다. `_ensure_group_host()`는 방 유형과 호스트 ID를 검사하며, 이 함수 자체에는 상담사 역할 검사가 없다. 후보 검증은 Link 또는 내담자용 공유 기관 검사다. 근거: `backend/app/services/chat_service.py:573`, `backend/app/services/chat_service.py:587`, `backend/app/services/chat_service.py:636`, `backend/app/services/chat_service.py:26`. 따라서 ‘상담사 역할과 상담사 간 멤버십 검증이 이미 완비됐다’고 간주하지 않는다.
- `listClients({ q, page, size })`는 재사용 가능하다. 실제 서버 검색 범위는 요청 상담사와 `ClientCounselorLink`로 연결된 사용자이며 이름·이메일 검색을 지원한다. 공유 기관의 모든 내담자를 반환하는 조회가 아니다. 근거: `frontend/src/lib/api/clients.ts:45`, `backend/app/services/client_service.py:94`.
- 기관 관리용 `listCounselors(orgId)`는 존재하지만 OrgAdmin 전용이고, 서버 목록에 `active`와 `invited`, `counselor`와 `org_admin`이 포함된다. **일반 상담사의 채팅 초대 후보 검색으로 그대로 재사용할 수 없다.** 근거: `frontend/src/lib/api/org.ts:106`, `backend/app/api/v1/org.py:206`, `backend/app/services/org_service.py:295`. 브리프의 ‘상담사 후보 조회 API 없음’은 채팅 초대에 적합한 API가 없다는 의미로 구체화한다.
- 현재 메시지 조회는 방 참여 권한 확인 후 해당 방 메시지를 조회하며, 참여 시각 이후로 제한하지 않는다. 기존 방에 추가하면 초대 전 대화도 조회할 수 있는 구조다. 근거: `backend/app/services/chat_service.py:133`, `backend/app/services/chat_service.py:656`.
- 신규 그룹방 생성은 호스트를 `host_id`에, 나머지 참여자를 `ChatRoomParticipant`에 저장한다. 참여자 명단 응답에 호스트가 자동 포함된다고 가정하면 안 된다. 근거: `backend/app/services/chat_service.py:236`, `backend/app/services/chat_service.py:245`, `backend/app/services/chat_service.py:636`.

## 2. 요구사항과 범위 제안

1. 초대 실행자는 **현재 방의 호스트이면서 `user.role === 'counselor'`인 사용자**로 제한한다. 초대받은 상담사에게 공동 호스트 권한을 자동 부여하지 않는다.
2. 상담사와 내담자를 같은 초대 흐름에서 함께 선택할 수 있게 한다.
3. 그룹방에서는 ‘기존 대화 유지하고 추가’와 ‘새 방으로 만들기’를 모두 제공한다.
4. 새 방은 기존 참여자와 신규 선택자를 포함하는 새로운 `group`이며, 기존 방과 기존 메시지를 그대로 남긴다. 메시지·파일·읽음 상태를 복사하지 않는다.
5. 내담자에게 초대 메뉴·검색·선택·실행 버튼을 표시하지 않는다. 초대된 내담자가 자신의 새 방을 목록에서 보는 것은 허용한다.
6. UI는 한국어, 순수 Tailwind 클래스, 보라 `#5F0080` 테마를 사용한다. 인라인 `style`, CSS-in-JS, 별도 스타일시트 추가를 사용하지 않는다.

### 2.1 방 유형별 정책 제안

- **group:** 상담사 호스트가 두 방식을 선택한다. 이번 기능의 핵심 범위다.
- **direct:** 상담사 호스트에게 초대 진입점을 제공하되 ‘새 방으로 만들기’만 실행 가능하게 한다. 기존 호스트·상대방·신규 선택자를 새 그룹방에 포함한다. ‘기존 대화 유지하고 추가’는 비활성화하고 ‘1:1 채팅은 새 그룹방으로만 초대할 수 있습니다.’를 표시한다. 기존 direct를 group으로 변환하는 것은 이번 기획에서 제외한다.
- **session:** 이번 초대 진입점을 표시하지 않는다. 현재 타입에는 `session`이 남아 있으므로 명시적으로 분기한다. 근거: `frontend/src/lib/api/chat.ts:6`.

현재 참여자 API는 direct를 거부한다(`backend/app/services/chat_service.py:579`). direct의 새 방 흐름은 **신규 서버 계약이 필요한 제안**이며 기존 API로 지원된다고 안내하지 않는다. 새 계약 배포 전에는 direct 초대 진입점을 활성화하지 않는다.

## 3. 초대 진입점

### 3.1 권장안: ⋯ 메뉴 + 설정 모달의 공통 흐름

- 대화 목록의 기존 ⋯ 메뉴에 권한이 있을 때만 **‘회원 초대’**를 ‘채팅방 설정’ 위에 추가한다.
- `RoomSettingsModal`의 기존 ‘참여자 추가’를 **‘회원 초대’**로 바꿔 같은 초대 흐름을 연다. 기존의 즉시 추가 폼은 공통 흐름으로 대체하고 이름 변경·내보내기는 유지한다.
- direct 설정에서는 신규 계약이 준비된 경우 ‘새 그룹방에 회원 초대’ 설명과 함께 같은 진입점을 제공한다.
- 모바일에서 방을 연 상태에도 사용할 수 있도록 채팅 상세 상단에 동일한 `RoomActionsMenu`를 배치한다. 현재 모바일에서는 방 선택 시 목록이 숨겨지고 상세 상단에는 목록 복귀 버튼만 있다. 근거: `frontend/src/pages/chat/ChatPage.tsx:110`, `frontend/src/pages/chat/ChatPage.tsx:185`.
- 상단에 별도의 상시 ‘+ 초대’ 버튼은 만들지 않는다. 메뉴·설정·별도 버튼에 같은 기능이 중복되는 것을 피한다.

대안 검토: 설정 모달만 사용하면 기존 구조 재사용은 쉽지만 초대까지 탐색 단계가 늘어난다. 별도 버튼은 발견하기 쉽지만 대화 화면의 상시 조작이 늘어난다. 메뉴를 주 진입점, 설정을 보조 진입점으로 둔다.

### 3.2 모달 전환

새 `InviteMemberModal` 한 개에서 **대상 선택 → 방식 선택 → 처리 결과**를 전환한다. 데스크톱은 중앙 모달, 모바일은 하단 시트 형태로 같은 상태를 사용한다. 설정 위에 모달을 중첩하지 않는다.

설정에서 진입할 때 이름 변경이 남아 있으면 해당 설정 화면 안에서 ‘이름 변경을 저장하거나 취소한 뒤 초대해 주세요.’와 ‘이름 저장 / 변경 취소’를 제공한다. 변경이 해소되면 설정을 닫고 초대를 연다. 초대를 취소하면 원래 설정으로 돌아가고, 메뉴에서 진입했으면 메뉴 트리거로 포커스를 돌린다. 기존 설정에는 저장되지 않은 이름의 닫기 확인과 포커스 복귀가 있다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:84`, `frontend/src/components/chat/RoomSettingsModal.tsx:92`.

## 4. 초대 대상 검색·선택 UX

### 4.1 화면 구성

- 제목: **‘채팅방에 회원 초대’**
- 설명: ‘초대할 상담사 또는 내담자를 선택해 주세요.’
- 현재 방 표시: 사용자용 방 이름. direct의 내부 `name`을 표시 이름으로 사용하지 않는다. 기존 `chatRoomDisplayName()` 재사용 근거: `frontend/src/lib/chat-sort.ts:19`.
- 탭: **‘상담사’ / ‘내담자’**. 핵심 시나리오에 맞춰 상담사 탭을 기본으로 한다. 통합 검색은 이번 범위에 넣지 않아 서로 다른 조회 범위를 분명히 한다.
- 검색 입력: label ‘이름 또는 이메일 검색’, placeholder ‘이름 또는 이메일을 입력하세요’.
- 후보 행: 이름, ‘상담사’ 또는 ‘내담자’ 역할 배지, 식별용 이메일, 체크박스. 상담사 행은 서버가 제공한 **공유 기관명만** 보조 정보로 표시한다.
- 선택 영역: ‘선택한 회원 N명’, 이름·역할 칩, 개별 제거 버튼. 이름이 같아도 `user_id`로 구분한다. 건강 정보·상담 주제는 표시하지 않는다.
- 하단: ‘취소’, **‘다음 · N명’**. 유효한 신규 선택자가 1명 이상이고 방 정보·기존 참여자 확인을 마쳤을 때 다음 활성화.

### 4.2 내담자 조회: `listClients()` 재사용

- `listClients({ q: trimmedQuery || undefined, page, size: 50 })` 사용. 입력 후 250ms 지연 검색은 기존 설정과 맞춘다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:146`, `frontend/src/lib/api/clients.ts:51`.
- 안내 문구: **‘나와 연결된 내담자를 검색합니다.’** 공유 기관 전체를 검색한다고 표시하지 않는다.
- 응답의 `total`, `page`로 ‘더 보기’를 제공한다. 첫 50명만으로 목록이 끝났다고 판단하지 않는다. 근거: `frontend/src/lib/api/clients.ts:13`.
- 탭·검색어별 조회 상태와 페이지를 분리한다. 검색어 변경 시 페이지는 초기화하되 선택 칩은 유지한다. 늦게 도착한 이전 검색 응답은 무시한다.
- 선택 ID와 이름·역할 등 표시 스냅샷을 별도로 유지해, 현재 검색 결과에서 사라져도 선택자를 확인·제거할 수 있게 한다.
- 백엔드 추가 권한인 Link OR 공유 기관은 유지한다. 다만 공유 기관만 있고 Link가 없는 내담자의 **검색 범위 확장**은 별도 계약이 필요하다. 이번 기본 검색은 연결 내담자로 한정한다. 근거: `backend/app/services/chat_service.py:600`, `backend/app/services/client_service.py:104`.

### 4.3 상담사 조회: 신규 API 제안

아래 경로·필드명은 **프론트엔드 요구 계약 초안**이며 현재 API가 아니다.

- 클라이언트 함수 제안: `listChatInviteCounselors(roomId, { q, page, size })`.
- 경로 제안: `GET /chat/rooms/{roomId}/invite-candidates/counselors?q=...&page=1&size=50`.
- 응답 요구: `counselors` 배열, `total`, `page`. 후보는 `user_id`, `name`, `role: 'counselor'`, `email`, `shared_orgs: [{ id, name }]`를 제공한다. 이메일은 서버가 해당 호스트에게 공개 가능한 범위에서만 제공하고, 제공되지 않으면 기관명으로 식별한다.
- 서버가 요청자의 상담사 역할·방 호스트 권한을 검증하고, **양쪽 모두 active인 기관 멤버십이 하나 이상 겹치는 상담사**만 반환하도록 제안한다. 다중 기관에 겹쳐도 사용자별 한 행으로 중복 제거한다.
- 프론트엔드가 `User.org_id` 하나로 상담사 간 공유 기관을 계산하지 않는다. 멤버십 모델은 다중 기관과 `active/invited/left`를 구분한다. 근거: `backend/app/models/user_org_membership.py:17`, `backend/app/models/user_org_membership.py:27`.
- `org_admin`을 상담사와 동일하게 포함하지 않는다. 관리자 초대·관리자의 초대 실행 권한은 이번 기본안에서 제외하고 정책 확장 시 별도 합의한다.
- 후보 검색이 성공해도 제출 때 서버가 권한·멤버십을 재검증한다. 선택 후 탈퇴·소속 변경에 대응하기 위해서다.

### 4.4 상태와 제한

- 초기/검색 로딩: ‘상담사를 불러오는 중…’ 또는 ‘내담자를 불러오는 중…’. 다른 탭의 정상 결과·선택은 유지한다.
- 검색 결과 없음: ‘검색 결과가 없습니다. 이름 또는 이메일을 확인해 주세요.’
- 빈 검색어에서 상담사 없음: ‘초대 가능한 상담사가 없습니다. 같은 기관에 소속된 상담사만 초대할 수 있습니다.’
- 내담자 없음: ‘초대 가능한 연결 내담자가 없습니다.’
- 조회 실패: ‘목록을 불러오지 못했습니다.’와 해당 탭의 ‘다시 시도’. 실패를 0건으로 표현하지 않는다.
- 자기 자신과 기존 참여자는 선택할 수 없다. 후보 응답에 포함되면 각각 ‘나’, ‘이미 참여 중’ 배지를 붙인 비활성 행으로 표시한다. 서버에서 제외되었으면 이를 표시하려고 추가 개인정보 조회를 하지 않는다.
- 최대 신규 선택자는 두 탭 합계 100명으로 제안한다. 현재 추가 API의 요청 제한과 맞춘 값이며 방의 최대 인원이라는 의미는 아니다. 근거: `backend/app/schemas/chat.py:39`. 새 방 최종 총원 제한은 서버 계약에서 별도로 정해야 한다.

## 5. ‘기존 대화 유지 vs 새 방’ 선택 다이얼로그

### 5.1 형태와 공통 정보

대상 선택 모달의 두 번째 단계로 전환한다. 중첩 모달·브라우저 `confirm()`은 사용하지 않는다. 제목은 **‘어떻게 초대할까요?’**, 설명은 ‘선택한 N명을 초대할 방을 선택해 주세요.’로 한다. 선택자 이름·역할과 기존 참여자 수, 초대 후 총인원을 함께 보여 준다. 총인원은 호스트를 포함한 사용자 ID 집합으로 계산하되 저장 후에는 서버 값을 사용한다.

그룹방에서는 두 라디오 카드 중 **초기 선택을 비워 둔다**. 대화 공개 여부를 사용자가 직접 선택해야 실행할 수 있다. direct는 새 방 카드만 선택 가능하며, 기존 방 카드에는 비활성 사유를 표시한다.

### 5.2 카드 A — 기존 대화 유지하고 추가

- 제목: **‘기존 대화 유지하고 추가’**
- 본문: ‘현재 채팅방에 선택한 회원을 추가합니다.’
- 강조 안내: **‘새로 참여한 회원도 이전 메시지와 대화에 공유된 파일을 볼 수 있습니다.’**
- 보조 설명: ‘채팅방과 기존 참여자는 그대로 유지됩니다.’
- 추가 확인 체크박스: **‘선택한 회원에게 기존 대화가 공개됨을 확인했습니다.’**
- 실행 버튼: **‘N명 초대’**. 카드 선택과 확인 체크가 모두 완료돼야 활성화한다.

현재 메시지 조회에 참여 시각 필터가 없다는 사실을 바탕으로 명확하게 알린다(`backend/app/services/chat_service.py:656`). 이전 첨부파일의 실제 다운로드 권한도 같은 의미로 동작하는지 백엔드에서 검증해야 하며, ‘초대 이후 대화만 공개’ 기능이 있다고 안내하지 않는다.

### 5.3 카드 B — 새 방으로 만들기

- 제목: **‘새 방으로 만들기’**
- 본문: ‘기존 참여자와 선택한 회원이 함께하는 새 그룹 채팅방을 만듭니다.’
- 강조 안내: **‘이전 메시지와 파일은 새 방으로 옮겨지지 않습니다.’**
- 보조 설명: **‘기존 채팅방은 그대로 남습니다.’**
- 방 이름 입력: ‘새 채팅방 이름’. 기본값은 ‘새 그룹 대화’, 사용자가 변경 가능. 기존 direct의 내부 `name`은 복사하지 않는다.
- 이름 검증 제안: 앞뒤 공백 제거, 1~120자, 줄바꿈·제어문자 금지. 기존 설정 UX와 맞추되 새 API에도 같은 검증 계약을 요구한다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:76`, `frontend/src/components/chat/RoomSettingsModal.tsx:228`.
- 실행 버튼: **‘새 방 만들고 초대’**.

하단 ‘이전’은 대상 선택으로 돌아가 검색·선택을 보존한다. 방식 변경 또는 대상 변경 후에는 대화 공개 확인 체크를 초기화한다. 취소하면 아무 요청도 보내지 않는다. 실행 중에는 ‘초대 중…’/‘새 방 만드는 중…’으로 바꾸고 중복 실행·이전·닫기를 잠근다. 요청 종료 또는 결과 확인 상태로 전환되면 조작 가능하게 한다.

## 6. 프론트엔드가 요구하는 API 의미

### 6.1 기존 방 유지

현재 `addChatRoomParticipants(roomId, participantIds)`의 `POST /chat/rooms/{id}/participants`와 `ChatRoom` 응답을 유지한다. 근거: `frontend/src/lib/api/chat.ts:108`. 신규 선택자의 ID만 보내며 호스트·기존 참여자를 반복 전송하지 않는다.

상담사를 포함하는 요청에는 서버의 상담사 후보 검증 확장이 선행돼야 한다. 기존 내담자 요청의 형식·권한 정책은 하위 호환한다. 두 역할을 선택했을 때 요청을 역할별로 나누지 말고 한 요청으로 처리하고, 권한 오류가 있으면 전체 미반영을 요구한다. 부분 성공을 프론트엔드가 추정하지 않는다.

### 6.2 새 방 생성

신규 계약 제안: `POST /chat/rooms/{sourceRoomId}/invite-new-room`. 요청은 신규 `participant_ids`, `name`, 중복 방 생성을 막기 위한 `request_id`를 포함하고 응답은 생성된 `ChatRoom`과 요청 식별자를 반환한다.

- 서버가 원본 방의 최신 호스트·참여자와 신규 선택자를 합집합으로 구성한다. direct의 기존 상대방도 서버에서 확인한다.
- 호스트는 요청한 기존 호스트를 유지한다. 새로 초대한 상담사는 일반 참여자다.
- 기존 참여자까지 현재 정책에 따라 재검증한다. 부적격자가 있으면 새 방을 만들지 않고 재확인을 요청한다. 조용히 일부를 제외하지 않는다.
- 생성은 참여자 등록까지 하나의 성공으로 완료돼야 한다. 메시지·파일·읽음 기록은 복사하지 않고 원본 방을 삭제·보관 처리하지 않는다.
- 같은 `request_id`의 재요청은 같은 결과를 반환하도록 요구한다. 결과가 불명확할 때 같은 키로 확인·재시도할 수 있어야 한다.

현재 `createGroupRoom()`은 `participant_ids`, `room_type`, `name`만 받으며 원본 방·멱등 키 계약이 없다(`frontend/src/lib/api/chat.ts:70`, `frontend/src/lib/api/chat.ts:82`). 단순히 기존 생성 모달을 열거나 브라우저에서 읽은 명단을 복사해 현재 API를 호출하는 것으로 이 요구가 충족됐다고 보지 않는다. 현재 그룹 생성은 방 생성과 참여자 등록의 commit도 나뉜다(`backend/app/services/chat_service.py:242`, `backend/app/services/chat_service.py:247`).

### 6.3 추가 데이터와 합의 항목

- `ChatRoom`에 서버 계산 `can_invite`, `invite_disabled_reason`, `allowed_invite_modes` 추가를 제안한다. `can_rename`을 초대 권한으로 재사용하지 않는다. 현재 DTO에는 이름 변경 권한만 있다. 근거: `frontend/src/lib/api/chat.ts:24`.
- 후보의 통합 프론트엔드 모델은 `userId`, `name`, `role`, 선택적 `email`, `sharedOrgs`로 제안한다. 기존 내담자 응답의 `id`는 어댑터에서 `userId`로 정규화한다.
- 참여자 응답에 `role`을 추가해 명단에서도 상담사·내담자 배지를 표시하도록 요청한다. 현재 참여자 DTO는 `user_id`, `name`, `joined_at`뿐이다. 근거: `frontend/src/lib/api/chat.ts:92`.
- 역할은 `User.role`을 조회해 응답하는 방식을 제안한다. 프론트엔드 배지를 위해 참여자 테이블에 역할을 중복 저장할 필요는 없다. 현재 참여자 모델에는 역할 컬럼이 없다. 근거: `backend/app/models/chat.py:55`.
- 호스트 포함 명단은 서버 `host_id`와 참여자 ID를 합쳐 중복 제거한다. 현재 인원 집계도 참여자 행 수에 호스트 1명을 더한다. 근거: `backend/app/services/chat_service.py:416`.
- 구현 전 백엔드 기획과 합의할 항목: 상담사·관리자 역할 범위, 공유 기관만 있는 내담자의 검색 확대 여부, direct 새 방 지원, 최종 총원 제한, 혼합 대상 요청의 원자성, 멱등 처리, 이력·첨부 공개 범위, 이벤트 계약. 이 문서의 경로·필드는 제안이며 합의 전 확정 API로 사용하지 않는다.

## 7. 초대 완료 후 목록·상태 반영

### 7.1 기존 방에 추가한 경우

1. 성공 응답 후 ‘회원을 초대했습니다.’를 표시한다. 응답에 실제 추가 인원이 없으면 선택 수로 ‘N명 추가 완료’를 단정하지 않는다. 기존 서버는 이미 참여한 ID를 건너뛴다. 근거: `backend/app/services/chat_service.py:598`.
2. 같은 방·같은 화면에 머물고 기존 메시지·입력 중인 메시지·스크롤을 유지한다.
3. 참여자 명단을 다시 조회하고, 응답의 `participant_count` 및 이름·권한 관련 메타데이터만 갱신한다. 설정에서 진입했다면 갱신된 설정 명단으로 돌아간다.
4. 오래된 전체 `ChatRoom` 응답으로 최신 메시지와 읽지 않은 수를 덮어쓰지 않는다. 기존 설정의 메타데이터 한정 갱신 원칙을 따른다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:41`, `frontend/src/stores/chatStore.ts:30`.
5. 초대만으로 메시지 전송 시각·읽음 수를 프론트엔드에서 바꾸지 않는다. 시스템 메시지가 필요하면 서버가 실제 메시지를 저장·전달하는 별도 계약으로 처리한다.

### 7.2 새 방인 경우

1. 성공한 새 `room.id`를 저장소 목록에 중복 없이 삽입한 뒤 `/chat/{newRoomId}`로 이동한다. 현재 `updateRoom()`은 기존 ID만 수정하므로 새 방 삽입 동작이 별도로 필요하다. 근거: `frontend/src/stores/chatStore.ts:29`.
2. 목록 반영을 이동보다 먼저 수행한다. 현재 상세 선택은 URL의 ID를 `rooms`에서 찾으므로 이동만 하면 ‘채팅방을 찾을 수 없습니다.’가 나타날 수 있다. 근거: `frontend/src/pages/chat/ChatPage.tsx:82`, `frontend/src/pages/chat/ChatPage.tsx:198`.
3. ‘새 그룹 채팅방을 만들었습니다. 기존 방은 그대로 유지됩니다.’를 표시한다. 새 방에는 ‘첫 메시지를 보내 보세요.’ 빈 상태를 제공한다.
4. 원본 방의 메시지 캐시·읽음 상태·목록 항목은 유지한다. 새 방은 새 ID로 메시지를 조회하고 연결한다. 현재 활성 방과 소켓 입퇴장은 `roomId` 변화에 반응한다. 근거: `frontend/src/components/chat/ChatRoom.tsx:108`, `frontend/src/components/chat/ChatRoom.tsx:124`.
5. 기존 정렬 설정을 유지한다. 현재 정렬은 선택적으로 미읽음 우선 후 최근 메시지/생성 시각 순이다. 새 방을 무조건 목록 최상단으로 고정하지 않는다. 근거: `frontend/src/lib/chat-sort.ts:9`.

### 7.3 다른 참여자·초대 대상에게 반영

현재 상담사·내담자 목록은 최초 표시와 window focus 시 재조회한다. 참여 중 방의 소켓에는 메시지·프로필·읽음 이벤트 처리가 있지만 초대에 따른 방 목록 갱신 처리는 이 코드에 없다. 근거: `frontend/src/pages/chat/ChatPage.tsx:58`, `frontend/src/pages/client/ClientChatPage.tsx:71`, `frontend/src/components/chat/ChatRoom.tsx:124`.

**제안:** 서버가 영향받은 각 사용자에게 방 목록 변경 이벤트를 보내고, 공통 구독에서 목록·열린 참여자 명단을 재조회한다. 새 참여자는 아직 방 채널에 들어가지 않았으므로 기존 방 채널에만 보내지 않는다. 사용자별 채널 기반은 존재한다(`backend/app/ws/chat_namespace.py:18`). 이벤트 이름·페이로드는 신규 계약이다. 초대받은 사용자를 강제로 새 방으로 이동시키지 않는다. 현재 대화를 유지하고 목록·안내만 갱신한다.

재접속·focus 재조회는 누락 복구 수단으로 유지한다. 이벤트 계약 전에는 다른 사용자 화면의 ‘즉시 반영’을 완료 기준으로 주장할 수 없다.

## 8. 상담사 전용 노출·권한

- 공통 진입 조건: 인증 사용자 있음 + `user.role === 'counselor'` + `room.host_id === user.id` + 지원 방 유형 + 해당 기능 계약 준비. 인증 사용자 역할 필드는 `frontend/src/lib/api/auth.ts:8`에 있다.
- 서버 권한 응답이 추가되면 `can_invite === true`와 허용 방식까지 확인한다. 권한 조회 중·실패·필드 미지원 상태에서는 초대 실행을 허용하지 않는다.
- 내담자 및 `admin/org_admin/platform_admin`에게 초대 메뉴·설정 내 초대 버튼을 렌더링하지 않는다. 상담사여도 호스트가 아니면 숨긴다.
- 내담자 페이지에서 공유 `RoomActionsMenu`와 `RoomSettingsModal`을 쓴다는 점 때문에 상담사 페이지에서만 숨기는 방식으로 끝내지 않는다. 공통 컴포넌트·열기 핸들러·제출 핸들러에 같은 정책을 적용한다.
- 내담자에게 기존 설정 조회 자체를 불필요하게 제거하지 않는다. 이번에 제한하는 것은 초대 흐름이다.
- 서버가 매 요청마다 권한을 검증한다. UI 숨김은 보안 검증을 대체하지 않는다. 기관·역할을 클라이언트가 임의 지정해 검색 범위를 넓힐 수 없어야 한다.

## 9. 엣지케이스와 오류 복구

- **이미 참여 중 / 자기 자신:** 선택 불가. 제출 직전 최신 명단과 대조해 빠진 선택을 알리고 최종 인원·공개 확인을 다시 받는다. 전원이 기존 참여자라면 ‘선택한 회원은 이미 참여 중입니다.’로 실행을 막는다.
- **동명이인 / 중복 기관:** 이름 대신 ID로 중복 제거. 이메일 또는 공유 기관 정보로 구분하고 역할 배지는 항상 표시한다.
- **검색 응답 역전 / 탭 이동 / 방 변경:** 요청 세대별로 오래된 응답을 무시한다. 방 변경 시 초대 흐름을 종료해 다른 방으로 제출하지 않는다. 정상적으로 종료한 다음 다시 열면 이전 선택을 초기화한다.
- **참여자 명단 조회 실패:** 후보를 먼저 받았더라도 다음·실행을 막고 ‘기존 참여자를 확인하지 못했습니다.’와 재조회를 제공한다. 호스트가 명단에 없다고 탈퇴로 판단하지 않는다.
- **권한 없는 대상 / 기관 탈퇴 / 계정 사용 불가:** 서버가 거부하면 ‘초대할 수 없는 회원이 포함되어 있습니다. 목록을 새로 확인해 주세요.’를 표시한다. 공개 가능한 실패 ID가 반환될 때만 해당 선택자를 표시한다. 나머지 선택은 보존하고 몰래 일부만 초대하지 않는다.
- **호스트 권한 상실(403):** ‘이 채팅방에 회원을 초대할 권한이 없습니다.’를 표시하고 실행 비활성화, 방 권한 재조회. 대상 부적격과 구분 가능한 오류 코드를 신규 계약에 요청한다.
- **삭제된 방·접근 불가(404/403):** 결과를 안내하고 목록으로 복귀한다. 기존 UI에 남은 초대 진입점도 제거한다.
- **기존 참여자 변동:** 확인 단계 재조회와 서버 최종 재검증을 모두 수행한다. 새 방 포함 인원이 바뀌면 최신 명단·인원으로 재확인한다. 원본에서 내보낸 사용자를 오래된 프론트엔드 스냅샷으로 다시 초대하지 않는다.
- **중복 클릭:** 요청 잠금과 버튼 비활성화를 함께 적용한다. 새 방은 서버 `request_id`로 중복 생성도 방지한다.
- **응답 유실·타임아웃:** ‘처리 결과를 확인하지 못했습니다.’를 표시한다. 기존 방은 명단을 재조회해 반영 여부를 확인하고, 새 방은 동일 `request_id`로 결과 확인/재요청한다. 새 키로 자동 재생성하지 않는다.
- **변경 성공 후 재조회만 실패:** ‘초대는 완료됐지만 최신 목록을 불러오지 못했습니다.’와 ‘목록 다시 조회’를 표시한다. 성공한 mutation을 다시 실행하는 버튼은 제공하지 않는다.
- **인원 제한·이름 오류(422):** 서버와 합의한 제한에 맞는 필드 오류를 보여주고 입력을 유지한다. 기존 `CreateRoomModal`의 ‘2명 이상 선택’은 신규 초대에 적용하지 않는다. 기존 방에 신규 1명만 초대할 수 있어야 한다. 근거: `frontend/src/components/chat/CreateRoomModal.tsx:89`.
- **상담사 검색 API 장애:** 내담자 탭 사용은 계속 가능하다. 상담사 후보를 관리자 API로 우회 조회하거나 빈 결과로 가장하지 않는다.

## 10. Tailwind·반응형·접근성

- 중앙 모달/모바일 시트: `fixed inset-0`, `items-end sm:items-center`, `w-full sm:max-w-lg`, `rounded-t-2xl sm:rounded-2xl`, `max-h-[90dvh]`, `overflow-y-auto` 등의 정적 Tailwind 클래스로 구성한다.
- 핵심 버튼: `bg-[#5F0080] text-white hover:bg-[#4B0066]`; 선택 카드: `border-[#5F0080] bg-[#F5EDFC]`; 포커스: `focus-visible:ring-2 focus-visible:ring-[#5F0080]`; 체크·라디오: `accent-[#5F0080]`. 현재 설정에서도 같은 보라 계열을 사용한다. 근거: `frontend/src/components/chat/RoomSettingsModal.tsx:227`, `frontend/src/components/chat/RoomSettingsModal.tsx:230`.
- DOM은 한 dialog만 유지한다. `role="dialog"`, `aria-modal`, 제목·설명 연결, 포커스 가두기, 배경 조작 차단, 종료 후 트리거 포커스 복귀를 제공한다. 단계 변경 시 새 단계 제목으로 포커스를 이동한다.
- 대상 행은 label과 실제 checkbox, 방식 선택은 fieldset/legend와 실제 radio를 사용한다. 키보드 탭·화살표·Space로 조작 가능해야 한다. 두 항목으로 늘어난 ⋯ 메뉴도 항목 간 키보드 이동을 지원한다.
- 공개 확인·오류는 색상만으로 구별하지 않는다. 오류는 `role="alert"`, 검색·선택 수·성공 안내는 `role="status"`로 전달한다.
- 긴 이름·이메일·기관명은 줄바꿈/말줄임과 접근 가능한 전체 이름을 제공한다. 칩 제거 버튼의 이름은 ‘홍길동 상담사 선택 취소’처럼 대상과 동작을 포함한다.
- 모바일 키보드가 열려도 검색 결과와 하단 실행 버튼에 접근할 수 있게 본문 스크롤과 하단 영역을 분리한다. 창 크기를 JS로 계산해 인라인 스타일로 주입하지 않는다.
