# 리포트 워치독 해결 방안

## 문제

세션 종료 후 리포트 생성 파이프라인은 Celery 체인(녹음 저장 → STT → 화자분리 → AI 요약 → 리포트 생성)으로 수 분간 실행된다. 진행 상태는 `Report.generation_status`(pending/processing/ready/partial)로 파생한다.

**현재 한계:** 파이프라인이 Celery 워커에서 중간에 죽으면(워커 크래시·재시작·OOM·브로커 장애), `generation_status`가 `processing`에 **영구히 머문다**. 진행 상태를 DB 파생으로 계산하기 때문에 "더 이상 진행되지 않는데도 진행 중"으로 표시되어, 회원·상담사가 리포트가 언제까지 기다려도 안 나오는 상태로 남는다.

근본 원인은 두 가지다.
1. 상태가 **푸시 기반**(각 태스크가 성공 경로에서만 다음 상태로 전이)이라, 실패·중단 경로에서 최종 상태로 마감되는 보장이 없다.
2. "언제부터 processing 인지"를 추적하는 **타임스탬프/하트비트**가 없다 → "먹통"을 감지할 근거가 없다.

## 해결 방안

### ① (핵심) 타임아웃 워치독 — Celery beat 주기 스캔

`processing` 상태의 리포트 중 **시작 시각이 일정 시간(예: 30분)을 초과한 것**을 `failed`(또는 `partial`)로 마감한다.

- **시작 시각 추적**: `Report`에 `generation_started_at` 컬럼 추가(파이프라인 최초 진입 시 기록). 또는 `generation_status`를 `processing`으로 바꿀 때 `updated_at`을 갱신하고 이를 기준으로 삼는다(스키마 변경 최소화).
- **주기 태스크**: `sweep_stale_reports`(Celery beat, 300초)가 `generation_status == processing AND generation_started_at < now - 30분`인 행을 찾아 `failed` + `reason = report_timeout`으로 갱신하고 `report:progress`를 재브로드캐스트.
- **타임아웃 기준은 단계별 상한의 합**: save(~1분) + STT(음성 길이×실시간 비율, 보통 5~15분) + 요약(~2분) + 리포트 생성(~1분) → 안전 상한 30분, 짧게는 20분. 운영 지표로 튜닝.

장점: 가장 단순하고 신뢰성 높음. 워커가 죽어도 beat 워커가 살아있으면 반드시 수습된다. DB만 읽고 쓰므로 파이프라인과 완전히 분리.

### ② (방어) 태스크 실패 시 즉시 마감 — soft_time_limit + on_failure

각 Celery 태스크에 `soft_time_limit`/`time_limit`을 걸고, `on_failure`/`after_return` 콜백에서 해당 세션의 `generation_status`를 `failed`로 마감한다.

- STT·요약·리포트 태스크별로 시간 상한을 설정(예: STT 20분, 요약 5분).
- 실패 시 `report_progress_service`를 호출해 `failed` + 사유(`stt_failed`/`summary_failed`/`report_failed`) 반영.

장점: 정상적인 "실패"(예외·타임아웃)는 즉시 마감되어 사용자 대기 시간이 짧다. 단, 워커 프로세스 자체가 SIGKILL 되면 콜백이 안 돈다 → ①이 안전망.

### ③ (보완) 하트비트/리스(lease) — 장기 실행 태스크 추적

STT처럼 오래 도는 태스크가 주기적으로 `generation_heartbeat_at`을 갱신. 워치독은 "started_at은 오래됐지만 heartbeat_at은 최근"이면 계속 진행 중으로 보고, heartbeat마저 멈췄으면 먹통으로 판정.

- 장점: 길게 도는 정상 작업을 오탐 없이 허용하면서 진짜 먹통만 잡는다.
- 단점: 구현 복잡도가 ①보다 높다. STT가 수 분 단위로 갱신하기 어려운 외부 호출(단일 Gemini 요청)이면 heartbeat 효과가 제한적.

### ④ (UX 완충) 프론트 타임아웃 폴백

백엔드가 아무 것도 못 하더라도, 프론트 `useReportProgress`가 `processing` 상태를 N분(예: 30분) 넘게 보면 "처리 지연 중 — 자동으로 계속 시도됩니다" 문구로 전환한다.

- 장점: 서버 장애 시에도 사용자에게 무한 대기라는 느낌을 주지 않는다.
- 한계: 상태 자체는 여전히 processing → ①의 DB 정합이 본질 해결이다.

## 권장 조합

| 우선순위 | 조치 | 효과 |
|---|---|---|
| P0 | ① 타임아웃 워치독(beat 스캔) | 본질 해결 — 먹통을 자동 수습 |
| P1 | ② soft_time_limit + on_failure | 정상 실패를 즉시 마감 |
| P2 | ④ 프론트 지연 문구 | 서버 장애 시 UX 완충 |
| P3 | ③ 하트비트 | 장기 정상 작업 오탐 방지(필요 시) |

P0+P1만으로도 "영구히 processing" 문제가 해소된다. ③은 STT가 장시간(15분+) 걸리는 대형 클래스에서 오탐이 관찰되면 그때 도입한다.

## 구현 시 주의

- **멱등성**: 워치독 마감은 이미 `ready`/`partial`/`failed`인 행은 건드리지 않는다(멱등).
- **재시도**: STT/요약은 일시 장애(네트워크)일 수 있으므로 1회 자동 재시도 후에도 실패 시 `failed`로 마감한다(무한 재시도 금지).
- **상태머신 정합**: `Report.status`(승인 게이트)와 `generation_status`(생성 진행)는 독립 축 — 워치독은 `generation_status`만 건드린다. `failed`로 마감해도 승인 게이트 상태는 유지된다.
- **브로드캐스트**: 마감 시 `report:progress`를 한 번 더 보내 프론트 스텝퍼를 즉시 갱신한다.
