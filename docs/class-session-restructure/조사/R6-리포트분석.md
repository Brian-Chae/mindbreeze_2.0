### 2.2 생성 흐름

1. 회차 종료(`transition_status end`) → `audio_service` 가 `[영상 병합] → STT → 요약 → generate_reports_for_session` 체인을 큐에 적재, 발행 보장은 `PipelineOutbox`(R2 §7.1).
2. `generate_reports_for_session`(`report_task.py:709-734`)이 **회차 호스트 기준**으로 `generate_report(..., s.host_id, "counselor")` 후 `generate_client_reports_for_session` 호출.
3. 상담사 리포트(`type=counselor`) = 회차당 1건. `user_id`=**생성 시점의 `s.host_id`**, `participant_id`=가장 먼저 입장한 참여자(결정적 정렬) (`report_service.py:305-331`). 반영 동의한 참가자 전원의 EEG 집계(`report_task.py:517-537`).
4. 회원 리포트(`type=client`) = **대기열 밖 참여자마다 1건**, `report_included=False`(기본 제외)인 참여자는 **행 자체를 만들지 않음**(`report_service.py:400-402`). 그룹 회차의 client 리포트는 공통 녹음 요약(`ai_record`)을 넣지 않음(`report_task.py:556`).
5. 생성 결과 `status=pending_review` (승인 게이트). 호스트가 `User.auto_approve_report=True`(상담사 개인 설정) 이면 AI 코멘트 생성 후 즉시 `approve_report`(`report_service.py:343-353, 427-436`).
6. 실패 시 `status=error`, `generation_error`(50자), 알림 `report_generation_failed`(**`report.user_id` 에게**) (`report_task.py:570-615`).
7. 재생성: `generate_report_inline` 은 호출될 때마다 본문을 다시 만든다. **이미 승인(completed)된 리포트는 재생성해도 승인 상태 유지**, 재생성 실패 시 기존 내용 보존(`report_task.py:490-504, 576-582`). 상담사 코멘트(`content.counselor_comment`)는 이월(`report_task.py:617-628`).

### 2.5 점수·서사·정규화 (콘텐츠 계약)

- `content.eeg` = `status` · `loss_reason` · `coverage_ratio` · `reliability` · `drowsiness_flag` · **`score`(`meditation_total_score`, 주석 "종합점수 — null 보존")** · `metrics`(7지표) · `timeline`(≤300점) · **`narrative`** · `normalization_source/version` (`report_task.py:342-358`).
- **종합점수는 데이터로는 아직 저장**된다. SDD-054 가 화면 표시만 제거(`specs/054-report-score-removal/spec.md:14-15` "score 데이터 자체는 유지 (하위호환), 표시만 제거"). → **클래스 추이·집계는 `eeg.score` 를 입력으로 쓰면 안 된다**(§8).
- 서사 입력 `build_metrics_summary`(`report_narrative.py:73-125`): 한 회차를 중간점으로 **전반/후반**으로 나눠 6지표(몸 3·마음 3)의 `early/late/delta/percent_change/direction(up|down|stable)` 산출. 혼합 참가자 집계에서는 방향을 산출하지 않음(`:73-77`).
- 정규화: 활성 `NormalizationModel`(전역 sigmoid 표준 모델) 우선, 없으면 최신 모델, 그것도 없으면 코호트 상수 폴백 (`report_task.py:261-271`).
- `group_aggregate.py`(실시간 그룹 지표)는 **리포트 본문에 들어가지 않는 별도 경로**. 참가자 첫 120초를 **그 회차 내 개인 기준선**으로 삼고(`group_aggregate.py:34-37`) 착용자 3명 미만이면 평균 비노출(`MIN_WEARERS=3`, `group_aggregate.py:46-49`).

## 4. 리포트 소유·승인 모델 제안 (클래스 도입 시)

### 4.1 기본값 (기술)

1. **리포트 행 키 불변**(`session_id`·`participant_id`·`type`). 클래스는 `sessions.class_id` 를 통해 조인으로 묶는다 — 리포트 테이블에 `class_id` 를 중복 저장하지 않음(정합성 이중화 방지). 목록 성능이 문제가 되면 후속에 파생 인덱스.
2. **승인자·승인 시각 컬럼 추가(추가형, nullable)**: `reports.approved_by_user_id`, `reports.approved_at`. 기존 `sent_at` 은 호환 유지(= 앱 노출 시각). 기존 completed 행은 백필 시 `approved_by = sessions.host_id`(추정치임을 `approved_at IS NULL` 로 구분) 또는 NULL 유지(권장 NULL — 사실을 지어내지 않음).
3. **코멘트 작성자**: `content.counselor_comment_by`(JSONB 내부 키, 마이그레이션 없음). 코멘트는 `pending_review` 에서만 저장되는 현행 규칙 유지.
4. **"진행 강사" = `sessions.host_id` 의미 유지**(R2·R1 와 동일 전제). `approve_report` 의 `host_id` 일치 규칙을 **"클래스 강사 집합 안에서 승인 가능"** 으로 넓힐지는 정책(R6-D1).
5. **counselor 리포트 `user_id` 는 승인/열람 판정에 쓰지 않는다**(현행도 `session.host_id` 로 판정). 알림 수신자만 `user_id` 대신 "현재 진행 강사(`sessions.host_id`)"로 바꾼다 — 강사 교체 후 실패 알림이 구 강사에게 가는 것을 방지.
6. **자동 승인 설정 위치**: 현행 호스트 개인 설정 유지(호환). 클래스 단위 설정은 후속(R6-D2).

### 4.2 강사 교체 시 영향 (표)

| 상황 | 현행 코드 동작 | 영향·제안 |
|---|---|---|
| 완료 **전** 회차의 진행 강사 교체 | 리포트는 종료 시 생성 → `s.host_id`(= 새 강사) 로 생성·자동승인 판정 | 정상. 자동 승인 여부가 **새 진행 강사 개인 설정**을 따름 → 표에 표시 필요 |

### 5.2 API 제안 (기본값 — R2 §3.3 의 `/classes/*` 와 결합)

| # | 메서드 경로 | 설명 | 비고 |
|---|---|---|---|

- 구현 원칙: 일괄 처리는 **새 서비스 함수가 기존 `approve_report`·`generate_report`·`enqueue_report_email` 을 건별로 호출**하는 얇은 오케스트레이터. 기존 단건 API(`/reports/{id}/approve` 등) **호환 유지**.
- 현행 `POST /reports/approve-all` 은 **호환 유지** + 내부를 클래스/회차 필터를 받는 공통 함수로 리팩터(범위 미지정=현행 동작).
- 승인 주체 검사: 기존 `approve_report` 의 `session.host_id == 호출자` 를 "호출자가 해당 클래스 강사이며 정책 R6-D1 이 허용하는 경우"로 확장(요구: 클래스 상세에서 **여러 회차 일괄** 승인 → 진행 강사가 서로 다른 회차가 섞여 있으면 현행 규칙만으로는 한 강사가 타 강사 회차를 승인 불가 → **정책 결정 필수**).
- 일괄 승인이 사용자에게 보이는 부작용을 사전 안내: 승인 = 회원 앱 노출 + `report_ready` 알림 + 신청자 메일 + AI 비서 대화 시작 훅(`report_service.py:930-976`). 확인 모달에 대상 건수·메일 발송 예정 수 표시.
- 코멘트가 필요한 회원 리포트(`pending_review` + 코멘트 없음)를 일괄 승인하면 코멘트 없이 나감(`approve-all` 도 동일, `reports.py:101` docstring). 클래스 일괄 승인 모달에 "코멘트 없는 N건" 경고 표시(신규 UX).

### 5.3 상태·전이 (리포트 단위, 현행 유지 + 보강)

```
pending_analysis ──생성 성공──▶ pending_review ──승인──▶ completed
        │                         │  ▲                    │
        └──생성 실패/타임아웃──▶ error ◀─ 재생성 ─────────┘(재생성해도 completed 유지)
```
- 승인된 건 재생성 시 상태 유지는 현행 규칙(`report_task.py:490-504`) — 클래스 일괄 재생성에서도 동일하게 "승인 취소 없음"을 UI 문구에 명시.
- 금지 전이(현행 코드 기준): `pending_analysis`/`error` → 승인 불가(`report_service.py:919-920`), completed → pending_review 되돌림 없음.

## 6. 클래스 단위 추이·회차 비교·출석 요약 — 범위 제안

### 6.1 현행으로 가능한 것과 없는 것

- 가능: 회차 1개 안의 전반→후반 변화량(6지표 방향·%/±), 타임라인, 서사.
- **없음**: 회차 간 비교 기준. 개인 기준선은 **그 회차 첫 120초**(`group_aggregate.py:37`)뿐이고, `normalization_baselines` 는 관리자가 올린 표준 모델 재료(§7). 즉 "1회차 대비 8회차에서 이완이 올랐다"를 만들 수 있는 **회원 개인 장기 기준선이 존재하지 않는다**.
- 따라서 회차 간 비교를 **절대 수준(정규화 점수 0~100)** 으로 만들면 사실상 종합점수·성적표화(원칙 위반)가 되고 타당도 근거도 없음 → 기본값에서 제외.

### 6.2 제안 범위 (MVP / 후속)

| 구분 | 항목 | 설명 | 원칙 정합 |
|---|---|---|---|
| **MVP** | 회차별 변화 방향 띠 | 회원 개인: 회차마다 6지표 각각 `↑ / → / ↓` (그 회차 전반→후반). 출석한 회차만 표시, 결석·미착용은 빈칸("측정 안 됨") | 방향 + 변화량, 점수 없음 |
| MVP | 첫·마지막 비교 문구 | "1회차에서는 이완이 오른 흐름이 많았고 8회차에서는 안정적으로 유지됐어요" 식 **서사**(규칙 기반 템플릿, 결정론적). 수치는 ±% 카드로만 | 서사 + 변화량 |
| MVP | 출석 요약 | 클래스: 회차별 출석·결석·보강 인원 / 회원: `3/8 참석`, 결석 회차, 보강 완료/대기 | 점수 아님. 결석≠0 |
| MVP | 착용 회차 수 | "뇌파 측정 회차 5/8" (미착용은 정상 미측정 — 감점·표시 강조 없음) | 미측정≠0 |
| MVP | 상담사용 클래스 요약 | 회차별 **방향 분포 인원수**(이완 ↑ n명·→ n명·↓ n명), 착용자 3명 미만이면 비노출 | 개인 식별·순위 없음. `group_aggregate` 익명성 게이트(`MIN_WEARERS=3`) 재사용 |
| 후속 | 클래스 평균 흐름 그래프 | 회차별 집단 평균 변화 곡선(상담사만) | 정규화 수준값 노출 여부는 결정 후보 R6-D5 |
| 후속 | 개인 장기 기준선(1회차 첫 N분 기준 상대값) | 회차 간 "수준" 비교 가능해짐. 데이터 모델 신설 필요 | 별도 SDD, 점수 환원 방지 검증 선행 |
| **제외** | 강사별 통계·강사 간 클래스 비교·회원 순위·종합점수·타인 대비 | §9 | 원칙 위반/위험 |

### 6.3 데이터 구현 기본값 (기술)

1. **기존 리포트 `content` 에서 파생**: 회차 리포트 생성 시 `build_metrics_summary(...)` 결과(6지표 early/late/delta/%/direction)를 `content.eeg.change` 로 **가산 저장**(스키마 변경 없음, 하위호환 — SDD-022 "content 하위호환" 원칙과 정합). 클래스 추이는 해당 클래스 회차의 **승인(completed) 된 client 리포트**의 `content.eeg.change` 를 읽어 조립. 이점: ① `report_included=False` 참여자는 애초에 행이 없어 자동 제외 ② 승인 후에만 회원에게 노출 ③ 제외 선택 변경 시 `refresh_reports_after_choice_change` 가 재생성하며 함께 갱신 ④ 신규 테이블 없음.
2. 기존 회차 리포트(이미 생성된 것)는 `content.eeg.change` 가 없음 → **백필 태스크**(Celery, `tasks/upgrade_narrative_cache.py` 와 같은 방식, 윈도우에서 재계산) 또는 "과거 회차는 추이에서 제외" 중 택일. 기본값: 백필(결정론적 재계산, 서사 LLM 호출 없음).
3. 클래스 추이 갱신은 **요청 시 조립(캐시 없음)** 에서 시작 — 회차 ≤ 수십, 회원 ≤ 수십 규모. 느려지면 `class_report_snapshots` 파생 테이블(후속). 회차 리포트 완료 훅 + 비동기 태스크는 이때 도입(R2 §7.1).
4. **제외·결석 처리**: 추이 입력은 "client 리포트가 존재하고 `report_scope.excluded` 가 아닌 건"만. 결석 = 리포트 행 없음(= 빈칸). 중간 합류자는 합류 이후 회차만 채워짐(합류 전 회차는 "참여 전"으로 구분 표기).
5. **대기열·정원·보강**: 보강 회차에 참석한 회원은 그 회차 리포트가 생기므로 추이에서 "보강" 표식으로 원 회차 위치에 연결(원 회차 연결 키는 R4/R5 결정에 따라 `makeup_for_session_id` 등 — 미정).

### 6.4 회원용 / 상담사용 구분 (유지)

| 항목 | 회원용(client) | 상담사용(counselor) |
|---|---|---|
| 현행 | `type=client`, 본인 것만(IDOR 방어 `report_service.py:741-749`), 그룹 회차에서는 공통 녹음 요약 제외(`report_task.py:556`) | `type=counselor`, 반영 동의 참가자 집계 + 기록·영상·STT, 회원 403(`:732-733`) |

## 9. 강사별 통계 — 기본값 "만들지 않음"

근거(코드·문서):

1. **원칙 충돌**: 점수 환원·순위·비교 배제(§3). 강사별 통계는 결국 "강사 A 클래스의 회원 변화량이 B보다 크다" 형태 → 성적표/순위화. 회원 화면에서 이미 "평균·순위·델타·종합점수" 금지(`member-player-case.ts:4`).
2. **타당도 근거 없음**: 지표 변화량은 그 회차 전반/후반 비교이고 방향 판정 임계는 "안정 여부 판정용"(`report_narrative.py:119-123`)이지 효과 크기 척도가 아님. 개인 기준선 없음(§6.1), 정규화는 전역 모델(§7), 회원·회차·시간대·밴드 착용 여부가 강사와 교락(confound).
3. **동의 범위 밖 2차 이용**: 뇌파는 개인 건강 정보로 "본인 세션 + 담당 상담사만 접근"(`.claude/rules/data-privacy.md` 접근 제어). 리포트 반영·연구 동의는 본인 리포트·연구 DB 비식별 목적(`policy-revision-r4.md:10, 63`)이며 **강사 평가용 이용 동의는 없음**.
4. **기존 설계와 정합**: 기관 관리자 대시보드·강사 활동 화면은 활동량·메타데이터만이고 "상담 내용은 노출하지 않는다"(`org_service.py:457-461`), 리포트는 메타데이터 수준 건수만 집계(`dashboard_service.py:81-92` `report_count`).
5. **측정 불가 영역 오해 위험**: 결석·미측정이 많은 클래스가 "낮은 성과"로 읽힘.

대안(허용 가능, 기본값은 클래스 단위만 노출):
- **업무 지표**: 클래스별 "승인 대기 건수·가장 오래된 대기 일수"(성과가 아니라 처리 현황). 센터 관리자에게 보일지는 결정 후보 R6-D6. 강사 **개인 순위/비교 화면은 만들지 않음**.
- 강사 본인에게만: 내가 진행한 회차 수·승인 대기(개인 업무 화면). 평가 용도 아님 명시.

## 11. 미확인

- R6-X1: **회원에게 `pending_review` 리포트가 승인 전에 노출되는지** — 서버 `list_reports`/`get_report` 에 승인 상태 필터가 없고 프론트 목록에서도 필터를 찾지 못함. 실제 호출 검증 미수행(코드 읽기 한정).
- R6-X2: `ORM 전역 필터(hidden_at/removed_at)` 가 `list_reports` 회원 분기의 `JOIN Session` 및 `get_report` 의 `SessionParticipant` 조회에 실제로 적용되는지 — `with_loader_criteria` 의미상 적용된다고 해석했으나 실행 검증 안 함.
- R6-X3: 다기관 소속 강사(`user_org_membership`, SDD-079)가 `list_reports` org_admin 분기(`User.org_id == user.org_id`, `report_service.py:~548`)에서 어떻게 보이는지 — 코드는 `User.org_id` 단일 컬럼만 사용, 다기관 모델과의 정합 미확인.
- R6-X4: SDD-122(`specs/122-report-loss-policy/*`)·SDD-087(코멘트)·SDD-119 본문, `리포트_데이터유실_정책_기획.md` 80-214줄 — 미열람(본 조사는 코드와 기획서 앞부분으로 확인).
- R6-X5: 프론트의 회원/상담사 리포트 화면이 `content.eeg.score` 를 어디서든 읽는지(SDD-054 후 잔존) — 전수 grep 미수행. `content.eeg.change` 가산이 프론트 리포트 계약 타입에 영향 없는지도 미확인.
- R6-X6: `approve_all_reports` 대량 건수에서의 실제 응답 시간·메일 큐 부하 — 측정 안 함.
- R6-X7: 운영 DB의 리포트 건수·`pending_review` 적체량·자동 승인 사용 비율 — 조회 권한 없음.
- R6-X8: 보강 회차 ↔ 원 회차 연결 키(데이터 모델)는 R4/R5 결과에 의존 — 이번 조사 범위 밖.
- R6-X9: PDF(`report_pdf_*`)가 클래스 맥락(클래스명·회차 번호)을 표기하는 방법 — 미조사. 현행은 `session.title`·`scheduled_at` 사용(`report_task.py:360-362, 390-392`).
