### 2.3 권고 — 확장(A안) vs 신설(B안)

| | A. 기존 테이블 확장 (기본값) | B. `counseling_relations` 신설 후 링크는 회원 연결용으로 축소 |
|---|---|---|
| 방식 | 컬럼 추가·`client_id` nullable·XOR 체크·이력 테이블 신설 | 새 테이블, 링크 1:1 이전 후 소비 12곳 전환 |
| 장점 | 회원 경로(코드·초대·관리자·채팅·AI 비서·기관 차단) 무변경, 추가형(nullable) 마이그레이션 | 개념 깔끔, `ended` 의미 재정의 자유 |

### 2.5 상태 머신 초안 (상담 관계)

| 상태 | 뜻 | 새 상담 세션 예약 | 입장 | 메모 수정 | 목록 노출 |
|---|---|---|---|---|---|
| `pending` | 초대 발송, 내담자 첫 입장/수락 전 | 허용(첫 상담 동시 예약) | 첫 입장 시 `active` 전이 | 가능 | 상담사 목록 "초대 중" |
| `active` | 상담 진행 | 허용 | 허용 | 가능 | 기본 목록 |
| `ended` | 종결(재개 가능) | **불가**(재개 먼저) | 불가 | 가능(마무리) | "종결" 탭, 읽기 전용 열람 |
| `archived` | 보관(재개 불가, 새 관계로만) | 불가 | 불가 | 불가 | 기본 목록 숨김, 검색으로 열람 |

전이 표:

| # | 전이 | 조건·부수 동작 |
|---|---|---|
| T1 | ∅ → `pending` | 상담사가 비회원/미가입 내담자 초대. 이메일 필수(§6.2). 세션·PII 0건일 때만 취소(삭제) 가능 |
| T2 | ∅ → `active` | 회원 연결(코드·가입 초대·관리자 수동 = 현행 5경로) |
| T3 | `pending` → `active` | 내담자 첫 입장+동의 완료 또는 회원 수락 |
| T4 | `active` → `ended` | 상담사 종결(또는 내담자 종결 — D-C1). **진행 중(`in_progress`) 세션이 있으면 409**. 예정·대기(`ready/scheduled/open`) 세션은 확인 후 일괄 취소+내담자 알림. `ended_by`·`end_reason` 기록, 비회원 자격 폐기(`entry_ver` 증가 `entry_credential_service.py:96-100`), 직접 채팅방 읽기 전용 |
| T5 | `ended` → `active` | 재개(같은 관계). 규칙: `ended_by=client` 이면 내담자 단독 재개 가능(현행 코드 재연결과 동일 `client_portal.py:159-174`), `ended_by=counselor|admin|system` 이면 상담사(또는 관리자) 승인 필요. `ended_at` 은 지우지 않고 이벤트에 보존 |
| T6 | `ended` → `archived` | 종결 후 N일 자동(D-C4 기본 365) 또는 상담사 수동. 비회원 PII 스크럽 기준일(§8.3) |
| T7 | 교체 | `active` → `ended`(reason=`counselor_transfer`) + 새 상담사와 새 관계 `pending/active`, `predecessor_link_id` 연결(§9) |

금지 전이: `archived → active|ended`(재상담은 새 관계), `ended → pending`, `active → archived`(종결 없이 보관 불가), `pending → ended`(세션 없는 종결 무의미 → 삭제), `ended|archived` 에서 신규 세션 생성, 진행 중 세션 있는 종결.

### 2.6 불변식

- I1 관계의 내담자는 회원 xor 비회원, 정확히 1명(CHECK).
- I2 관계의 현재 상담사는 정확히 1명(`counselor_id` NOT NULL). 교체는 관계 변경이 아니라 종결+새 관계.
- I3 상담 세션은 정확히 한 관계에 속하고, 세션 진행 상담사(`host_id`) = 생성 시점 관계의 상담사. 이후 교체돼도 **과거 세션 host 불변**(리포트 승인자·작성자 귀속 보존, `report_service.py:914-916` 승인=host).
- I4 같은 쌍의 비-`archived` 관계는 최대 1개.
- I5 `ended|archived` 관계와 그 세션·리포트는 계정 삭제·상담사 삭제로 사라지지 않는다 → `_ACCOUNT_ACCESS_TABLES`(`admin_service.py:714`)에서 상담 관계 제외, 상담 세션은 상담사 삭제 시 `hidden_at` 숨김 제외(§8.2).
- I6 상담 세션 참여자는 관계의 내담자 1명(`participant_mode=one_on_one`, `max_participants=1`을 서버가 강제).
- I7 비회원 PII 스크럽 후에도 관계·세션·리포트 행은 유지(`pii_scrubbed_at` 기록, `models/session.py:161-162` 패턴).

| `clinical`, `hypnosis` | 상담 | **참여자 ≤ 1 이고 `participant_mode='one_on_one'`** 인 세션만. 그룹형(`group` 또는 참여자>1)은 **집단 상담** 으로 보아 기본값 = 명상 클래스 영역(프로그램 컨테이너)으로 이전하되 `type`·라벨 유지(상담 관계는 1:1 이므로 수용 불가) → D-X2 |
| `custom` | 규칙 기반 | ① `custom_type_name` 이 명상 계열 키워드(명상·마음챙김·호흡·요가·MBSR) → 명상 클래스 ② 상담 계열 키워드(상담·치료·코칭·심리·면담) → 상담(1:1 조건 동일) ③ 둘 다 아니면 `participant_mode`: group → 명상 클래스, one_on_one → 상담 ④ 키워드 충돌·키워드와 방식 불일치 → **"분류 확인 필요" 목록**(호스트에게 앱 내 1회 질문 또는 관리자 확인) |
| 템플릿(`is_template=true`) | 같은 규칙으로 영역만 지정(관계·클래스 생성 안 함) |

`type` 값은 변경하지 않고 유지(연구 번들·라벨 호환). 영역은 상위 FK(`class_id` / `counseling_link_id`)로 표현. 상담 관계 생성은 호스트별 `(host_id, 참여 user_id|guest)` 로 묶어 `matched_at = min(세션 created_at)`, 상태는 마지막 세션이 90일 이내이거나 예정 세션 존재 시 `active`, 아니면 `ended`(reason=`inactive`) 제안 — 구체 값은 R7 과 합산.

**dry-run SQL (미실행, 숨김 행 포함: raw SQL 은 ORM 의 `hidden_at` 필터를 타지 않음)**

```sql
-- Q1 type × 진행 방식 분포
SELECT type, participant_mode, (max_participants > 1) AS multi, count(*) AS n
FROM sessions WHERE is_template = false GROUP BY 1,2,3 ORDER BY 1,2,3;
-- Q2 상담 후보 중 그룹형(집단 상담) 규모
SELECT s.type, count(*) AS sessions
FROM sessions s
WHERE s.is_template = false AND s.type IN ('clinical','hypnosis')
  AND (s.participant_mode = 'group' OR s.max_participants > 1
       OR (SELECT count(*) FROM session_participants p WHERE p.session_id = s.id AND p.removed_at IS NULL) > 1)
GROUP BY 1;
-- Q3 custom 이름 분포(이름은 유형명 30자, 개인정보 아님)
SELECT custom_type_name, participant_mode, count(*) AS n
FROM sessions WHERE type = 'custom' AND is_template = false GROUP BY 1,2 ORDER BY n DESC;
-- Q4 상담 후보 (상담사, 회원 내담자) 쌍 수와 기존 링크 보유율
SELECT count(*) AS pairs, count(l.id) AS with_link
FROM (SELECT DISTINCT s.host_id, p.user_id
      FROM sessions s JOIN session_participants p ON p.session_id = s.id
      WHERE s.type IN ('clinical','hypnosis') AND s.is_template = false AND p.user_id IS NOT NULL) x
LEFT JOIN client_counselor_links l ON l.counselor_id = x.host_id AND l.client_id = x.user_id;
-- Q5 상담 후보 세션의 비회원 참여자 수(관계 생성 시 guest 프로필 필요 규모)
SELECT count(*) AS guest_participants
FROM session_participants p JOIN sessions s ON s.id = p.session_id
WHERE s.type IN ('clinical','hypnosis') AND p.user_id IS NULL;
```

실행 결과는 모두 `미확인`(운영 DB 접근 없음). 검증 쿼리 기대값: Q1 합계 = 비템플릿 세션 수, 이전 후 `class_id`/`counseling_link_id` 둘 다 NULL 인 비템플릿 세션 = 0(분류 확인 필요 목록 제외).

### 6.2 설계 — 입장·본인 확인·개인정보

**엔티티 (신설)** `counseling_guests`: id, `name`, `gender`, `birth_date`, `email`, `email_norm`, `pii_scrubbed_at`, `claimed_user_id` NULL, `claimed_at` NULL, created_at. (관계가 비회원 PII 의 단일 보유처 — 세션 참여자 행에는 복사하지 않고 `guest_id` 만 둔다. 한쪽만 스크럽하는 실수 방지, R4 §7.3 지적 반영.)

**흐름 (기본값)**
1. 상담사 "새 상담 관계 → 가입 없이 상담" : **이메일(필수, 재입력 확인 1회)** + 표시 이름(상담사 전용 별칭)만 입력. 관계 `pending` 생성, 관계 단위 4자리 코드 발급, 초대 메일 발송(코드는 본문에만, 링크에 싣지 않음 = SDD-209 R5-A 정합). 오프라인 대면 상담이면 메일 대신 상담사가 코드를 직접 안내해도 됨(이메일은 여전히 필수 — 리포트 전달에 필요, 확정).
2. 내담자 `/join` : 코드 → **입력 이메일이 상담사 사전 등록 이메일과 일치**해야 통과(OTP 아님, 사전 등록 값 대조 — D-1 의 "OTP 없음"과 양립; 코드가 메일에만 있으므로 선점 위험도 낮춤) → 이름·성별·생년월일 입력 → 입장 자격 발급 → 동의 단계(§5 #5·#6) → 관계 `active`.
3. 코드 범위: **관계 단위**(회차마다 새 코드가 아님). 활성 세션 코드와 **같은 4자리 공간·같은 유일 규칙**(`uq_sessions_active_access_code` `models/session.py:17-34`)을 공유해 `/join` 입구를 하나로 유지 → 관계 `ended` 시 코드 무효화(재개 시 재활성화 또는 재발급). 1:1 이므로 공간 소모는 상담 관계 수만큼.
4. 대안(코드를 세션 단위로 유지): 구현은 쉬우나 매 회차 새 코드·새 참여자·재식별 문제 → 비채택.

관계가 비회원을 **1명으로 고정**하므로 "누구인가"는 관계가 정하고, 문제는 "그 관계의 진짜 본인인가"다.

| 옵션 | 방식 | 장단 |
|---|---|---|
| **a. 관계 자격 + 재확인 (기본값)** | 첫 입장 시 관계 단위 자격(JWT 새 type `counseling_entry`, sub=guest id, `ver`) 발급, 기기에 저장, **마지막 사용 후 90일 슬라이딩 TTL**, 종결 시 `entry_ver` 증가로 즉시 폐기. 자격이 없거나 만료면 **코드 + 이메일 + 생년월일** 3요소를 사전 등록 값과 대조해 재발급(시도 제한 `class_code_attempt_service.py` 재사용) | 정책 위반 없음(자격 소지자만 복귀), 공용 기기용 로그아웃=`entry/revoke`(`api/v1/session.py:165`) 재사용 |
| b. 이메일 매직링크 복구 | 이메일로 일회용 링크 → 자격 재발급 | 편하나 **이메일 OTP 제외(R5 D-1)와 충돌** → 정책 재논의(D-G1) |
| c. 상담사 수동 재발급 | 상담사가 "자격 초기화" → 새 코드 | 분실 복구용 보조 수단으로 병행 |
| d. 회원가입 유도 | 2회차 이후 가입 제안 → §6.5 | 가장 안정적 |

기본값 = **a + c**, b 는 후보. 오프라인 상담에서 내담자 기기 없이 상담사 기기로만 진행하는 경우 `entered_at`/자격 없이도 세션 진행·기록은 가능(현행 오프라인 세션 동일, 참여자 행 없는 진행) — 이때 리포트는 관계의 이메일로 발송.

### 6.4 리포트 전달·개인정보·연구 동의

- **리포트 이메일 전달**: 현행 승인→자동 예약 경로(`report_service.py:874-905`)를 재사용하되 수신처를 `counseling_guests.email` 로(참여자 `report_email` 대신). 상담 리포트는 상담사 승인 필수(자동 승인 정책 D-R1). 링크 TTL 7일(`report_email_service.py:23-26`) — 만료 후 재열람은 ① 관계 자격 보유 기기의 "내 상담" 최소 화면(다음 일정·지난 리포트 목록, R4 §7.3 패턴) ② 상담사 재발송(`reports.py:171`). 링크 TTL 연장은 D-G5.
- **개인정보 보관·삭제**: 현행 비회원 PII 는 세션 종료 후 `RETENTION_GUEST_PII_DAYS=90` 에 스크럽(`config.py:101`, `retention_sweep_service.py:256-296`). 상담에서는 관계가 `active` 인 동안 스크럽하면 리포트 발송·재식별이 끊기므로 **기준일을 관계 종결일(없으면 마지막 세션 종료일)+90일**로(§8.3). 비회원은 계정이 없어 열람·정정·삭제 요청 창구가 없다 → 메일 하단 "내 정보 삭제 요청" 링크 → 운영 접수 → 플랫폼 관리자 처리(R5-B 와 정합).
- **연구 동의**: 현행 참여자 단위 `research_consents`(unique participant_id, `research.py`). 상담 비회원은 관계 첫 입장에서 1회, 이후 승계(§5 #6). 가명 ID 는 이름+생년월일 HMAC 이라 같은 사람이 회차·관계를 넘어 누적 매핑됨(C5) — 회원 가입 후 연결(§6.5) 후에도 동일 ID 유지.

### 6.5 회원 가입 시 기존 상담 기록 연결 (claim)

현행 코드 없음. 연결 시 갱신 대상: `counseling_guests.claimed_user_id`, 관계의 `client_id`(guest_id 는 보존), 해당 관계 세션의 `session_participants.user_id`, 그리고 게스트 소유 4개 테이블의 nullable `user_id` — `eeg_records`(`models/record.py:100`)·`eeg_raw_chunks`(`:150`)·`reports`(`:209`)·`eeg_feature_windows`(`eeg_feature.py:61`). 소유는 `participant_id` 로 식별되므로 데이터 이동은 없고 `user_id` 채움뿐. **회원 리포트 목록은 `Report.user_id` 필터**(`report_service.py` 목록/`mark_all_read` `:980-993`)이므로 `reports.user_id` 갱신은 필수.

| 옵션 | 방식 | 오연결 위험 |
|---|---|---|
| **a. 토큰+이메일 일치 (기본값 1)** | 초대 메일의 가입 링크(claim 토큰, `client_invites` 패턴 재사용)로 가입 + 가입 이메일 = 사전 등록 이메일 + 이메일 인증 완료(가입 시 `verified_tier='email'`, `auth.py:361`) | 낮음 — 가로챈 링크로 다른 이메일 가입 시 불일치로 거부(`link_invited_client` 원칙 `client_service.py:273-277`) |
| **b. 이메일 일치 + 생년월일 확인 (기본값 2)** | 링크 없이 가입한 회원에게 "이 이메일로 받은 상담 기록이 있어요" 확인 화면 → 상담 때 입력한 생년월일 일치 시 연결 | 중간 — 상담사 이메일 입력 오타로 **타인에게 기록 노출** 위험 → 생년월일 일치+명시 동의+상담사 알림으로 완화 |
| c. 자격 보유 기기에서 "계정 만들기" | 자격 소지로 소유 증명, 이메일 불일치 허용 | 공용 기기·분실 시 위험 → 이메일 불일치는 상담사 승인 요구 |

기본값 = **a 와 b 병행, 자동 연결 금지(확인 화면 필수)**, 연결 후 상담사 알림+`claimed` 이벤트 기록. 충돌: 회원이 이미 같은 상담사와 비-`archived` 관계를 갖고 있으면 **병합**(비회원 관계의 세션을 기존 관계로 이전, 비회원 관계는 `archived`+`merged` 이벤트) — 행 이전은 단일 트랜잭션. 연결 취소(오연결 되돌리기)는 플랫폼 관리자 경로 + 이벤트로 추적.

### 8.3 재개 · 보관 기간 정책과의 관계 (기본값)

- **재개**: 기본 = **같은 관계 재개**(T5, 현행 동작과 동일, 쌍 유일 제약 유지). 이력은 `counseling_link_events` 로 보존(현행의 `ended_at` 덮어쓰기 중단). `archived` 후 재상담 = **새 관계+`predecessor_link_id`**, 새 상담사 화면에는 "이전 상담 기록 N건"으로 연결 표시(열람은 같은 상담사일 때만, 다른 상담사면 §9 규칙).
- **원본(EEG raw·음성·영상·STT 원문)**: 종결과 무관하게 SDD-209 대로 **세션 종료 후 90일 기간 삭제** — 상담도 동일(D-C6: 별도 기간 필요 여부). 종결로 앞당기거나 미루지 않는다.
- **영구층(관계·세션 메타·리포트·기록지·메모)**: 삭제 대상 아님(N-2 유지). 보관 상한 기간 도입 여부는 법무 확인 사항(D-C5). 내담자 삭제 요청은 운영 접수→플랫폼 관리자 처리.
- **비회원 PII 스크럽 기준일**: 관계 단위로 `종결일(`ended_at`) + 90일`, 종결 없이 마지막 세션만 있으면 마지막 세션 종료일+90일. 현행 스윕은 `coalesce(ended_at, created_at)` 세션 단위 기준(`retention_sweep_service.py:68-85`)이라 상담 비회원 참여자를 대상에서 빼고(참여자 행에 PII 복사 안 함) `counseling_guests` 전용 단계를 추가. 스크럽 후 이메일이 사라져 **리포트 재발송·본인 재확인 불가** → 사전 고지 필요.
- **archived 자동 전환**: 종결 후 N일(기본 365, D-C4). `archived` 전환 자체는 데이터를 지우지 않고 UI·권한만 바꾼다.
- **계정 탈퇴·삭제**: 내담자 탈퇴 → 관계 `ended`(`ended_by=system`, reason=`account_deleted`), 링크 행·세션·리포트 유지(`client_id` 는 삭제 상태 계정 참조 유지). 상담사 삭제 → 관계 `ended`(reason=`counselor_left`) 후 이관 대상(§9). 둘 다 `_ACCOUNT_ACCESS_TABLES` 의 링크 DELETE 제거 필요.
- 최초 활성화 안전장치(dry-run 후 승인, `retention_sweep_enabled=false`)는 상담 단계 추가 시에도 동일 적용.

## 9. 항목 8 — 상담사 교체/이관 시나리오 초안

**모델 기본값**: 관계는 상담사에 귀속(I2) → 교체 = 기존 관계 `ended`(reason=`counselor_transfer`) + 새 상담사와 새 관계(`predecessor_link_id`). 과거 세션 `host_id` 불변(I3).

| 항목 | 기본값 |
|---|---|
| 트리거 | ① 상담사 요청 ② 센터 관리자 이관(퇴사·휴직·기관 소속 해제 — 현행 차단 문구가 이관을 요구하지만 기능 없음 `org_management_service.py:166,304`) ③ 내담자 요청 ④ 계정 정지·삭제(`admin_service.py:728-767`) |
| 과거 세션·리포트 귀속 | 세션 `host_id`·리포트 작성/승인자 = 이전 상담사 그대로. 내담자 열람은 참여자 행 기반이라 영향 없음. 이전 상담사는 종결 후에도 본인 세션 읽기 전용 유지(§8.2) |
| 새 상담사의 과거 열람 | 기본: **요약(AI 요약·리포트)만, 내담자 동의 필수**. 상담사 비공개 메모(`memo`)·녹취 원문·EEG raw 는 제외(D-T1). 회원=앱 내 동의 화면, 비회원=메일 링크 동의 |
| 예정 세션 | 이전 상담사의 `ready/scheduled/open` 세션은 취소+내담자 알림 후 새 상담사가 재예약(세션 host 변경은 I3 위반이라 비허용) |
| 승인 대기 리포트 | 승인은 host 만 가능(`report_service.py:914-916`) → 이전 상담사 부재 시 대리 승인 주체 필요(기본 org_admin/플랫폼 관리자, D-T2) |
| 채팅 | 새 상담사와 새 직접방. 이전 방은 읽기 전용 |
| 비회원 | 새 관계 코드 발급+새 상담사 안내 메일. 자격은 폐기(관계가 바뀌므로). 동일 `counseling_guests` 행을 새 관계가 참조(PII 재입력 불요, 동의 메일 포함) |
| 범위 | 기본: 같은 기관 내 이관. 기관 간은 내담자 동의 후 새 관계(이관 아님) |
| 감사 | `transferred_out`/`transferred_in` 이벤트(양쪽 관계에 기록), 수행자 기록 |
| 기관 비활성화 | active 관계가 이관·종결로 정리되면 차단 해제(현행 `org_management_service.py:156-166`) |
