### 1.3 현행 권한 판정 규칙 (요약)

- 규칙 A "호스트만": 세션 수정·상태전이(열기/시작/종료/취소)·삭제·복제·템플릿 저장·초대/제거/리마인드·마커·기록 수정·발언권·녹음/영상·리포트 승인·연구 동의 요약. 비교 대상은 항상 `Session.host_id` 한 컬럼 (`session_service.py:742-754`).
- 규칙 B "호스트 또는 참여자": 세션 조회·기록 조회·입장 (`_get_session_for_user` `session_service.py:724-739`). 참여자에게는 전사문·내부 메모·타 참여자 PII 비노출 (`record_service.py:190-215`, `session_service.py:719-721`).
- 규칙 C "호스트의 기관이 살아 있어야 함": `_get_session_as_host` 가 `require_active_user_org(host)`·`require_active_org(session.organization_id)` 를 호출 (`session_service.py:750-755`) → 기관 비활성 시 모든 호스트 조작 차단.
- 라우트 레벨 role 가드(`require_roles`)는 `reports.py`(counselor/org_admin), `dashboard.py:25`(org_admin/platform_admin), `onboarding.py`, `agent*.py` 에만 있다. `api/v1/session.py` 는 전 라우트가 `get_current_user` 만 쓴다 (`session.py:86-98` 포함). 세션 생성에 role 검사가 서비스 안에서도 없다 (`session_service.py:333-345`에서 확인한 범위) — **client 계정의 세션 생성 차단 여부는 미확인**(프론트 가드 의존 가능성).
- 세션 도중 역할: WS `joined` 시 `host`/`participant` (`ws/session_live_namespace.py:530,553-558`), 판정은 `s.host_id == uid` (`session_service.py:2731`).
- 공동 진행·대리 진행: **없음** (명령 ⑦). 세션 생성 후 호스트 이전: **없음** (명령 ⑧). 따라서 상담사 퇴사·교체 시 세션 소유 이전 수단이 현재 전무하다.

### 2.3 센터 간 강사 공유 — 현행 불가

- 한 상담사의 다중 소속 자체는 가능: `uq_membership_user_org_alive`(user×org 중복 방지), `uq_membership_primary_active`(주 소속 1개) (`models/user_org_membership.py:52-70`), 개인 상담소 자동 개설 (`personal_office_service.py:1-12`).
- 그러나 세션은 **주 소속 1개 기관에만 귀속**: `create_session` 이 `require_active_user_org(host)`(= `User.org_id` 미러) 로 기관을 정하고 `Session.organization_id` 에 스냅샷 (`session_service.py:339,379`). `SessionCreateRequest` 에는 organization 선택 필드가 없다 (`schemas/session.py:19-75`에서 확인한 범위).
- 기관 관리자 집계는 `User.org_id == org.id` 인 사용자의 세션만 (`dashboard_service.py:124-127,175`; `report_service.py:549-551`). 부 소속 기관의 관리자는 해당 상담사의 세션을 못 본다. 다기관 격리 계획(`docs/counselor-multi-org-기획.md:191-199`: 기관 컨텍스트 기준 집계, A기관 관리자는 B기관 활동 비열람)은 문서상 설계이며 **세션 생성·집계 코드에는 미반영**(위 인용 코드 기준).
- 결론: "한 클래스에 타 센터 강사 참여" 는 현행 데이터 모델·권한으로 표현 불가. 신규 설계는 `Session.organization_id`(=클래스 소속 센터) 와 강사의 membership 을 분리해야 한다 → 기본값은 §5 (c) 참조.

## 3. 충돌 검사 현행

### 3.1 시간 충돌 — 있음

| 항목 | 현행 | 근거 |
|---|---|---|
| 함수 | `detect_conflict(host_id, scheduled_at, duration_min, exclude_id, db)` → 겹치는 세션 1건 반환 | `session_service.py:300-325` |
| 단위 | **상담사(host) 단위**. 같은 `host_id` 의 `ACTIVE_STATUSES = (ready, scheduled, open, in_progress)` 세션과 시간 겹침(`s_start < new_end and new_start < s_end`) | `:30,310-324` |
| 범위 | 개인상담(1:1)·그룹 구분 없음, 기관 구분 없음(host 의 전 기관 합산), 템플릿 제외(일정 없음→skip `:319`) | `:317-324` |
| 일정 없는 즉석 클래스 | 검사 제외 | `:318-320` |
| 호출처 3곳 | 생성(`:354`), 복제(`:599`), 수정(`:787`) | grep `detect_conflict` |
| 강도 | **소프트**: `force=True` 이면 건너뜀 (`:352-356`, `:785-789`; 스키마 `schemas/session.py:40,95,221`). 충돌 시 409 "시간이 겹치는 세션이 있습니다" | |
| 구현 방식 | 해당 host 의 활성 세션을 전부 로드해 파이썬 루프 비교 (DB 제약·범위 인덱스 없음) | `:310-324` |
| 회원(참여자) 쪽 충돌 | 검사 없음 | detect_conflict 호출 3곳 모두 host 만 |
| 테스트 | 시간 충돌 전용 테스트는 확인 못 함(`tests` grep `detect_conflict` 0건, `conflict` 검색 결과는 다른 주제) → **미확인** | |

### 3.2 설계 시사점

- 회차(세션) 일괄 생성(예: 8회) 시 `detect_conflict` 를 N회 호출하면 호스트 세션 전량 로드가 N번 → 일괄 검사용 함수(구간 목록 일괄 비교, 같은 요청 안 신규 세션 간 자체 충돌 포함) 필요. 기본값: 앱 레벨 일괄 검사 + 경고 표시 (DB EXCLUDE 제약은 `force` 소프트 정책과 충돌하므로 비도입).
- 진행 강사가 바뀌면 새 강사 기준으로 재검사 필요(수정 경로 `:787` 은 `s.host_id` 기준이라 호스트 변경 시 새 호스트 기준 호출로 바뀌어야 함).

### 3.3 장소 필드·장소 충돌

- 필드: `location_type`(`online`/`offline`, `models/session.py:74`), `location_address`(String 300, 오프라인 방문 주소·온라인은 항상 null, `:75-80`) — SDD-188(D8).
- 룸·공간·자원 엔티티: **없음** (`grep -rniE "venue|classroom|room_name|resource_id|place_id" app/models` 0건). `webrtc_room_id` 는 온라인 영상 룸 id(장소 아님).
- 기본값 주소 채움: 기관 주소 → 상담사 프로필 주소 순 (`session_service.py:54-80`, `:382-388`).
- 결론: **장소 충돌 검사는 현행에 없고, 문자열 주소만으로는 신뢰할 수 있는 충돌 판정이 불가능**하다. 센터 룸(공간) 개념이 필요한지는 결정 후보 (D-R9-14). 기본값: 이번 구조 개편에서는 장소 충돌을 "같은 센터·같은 주소 문자열·시간 겹침" 시 **정보성 경고**로만 표시하고 차단하지 않음, 룸 관리는 후속 Phase.

설계 시사점: ① 계정 삭제 시 미래 세션 숨김은 회원 입장에서 "일정이 사라지는" 사고이므로 강사 모델에서는 삭제 전 미래 세션 재배정(또는 취소+알림)을 필수 단계로 둬야 한다. ② 정지 상태 호스트의 미래 세션은 현재 방치 → `needs_reassign` 감지 배치 필요. ③ 소속 해제의 "정리 선행(409)" 방식은 이미 코드 관례이며 정상 이탈의 기본값으로 재사용 가능.

## 6. 초안 — 강사 모델 (기본값 제안)

### 6.0 개체 초안

```
Class(클래스)  1 ──< ClassInstructor(클래스 강사: class_id, user_id, role{lead|assistant|guest}, status{active|removed}, scope_session_id? (guest 한정), added_by, added_at, removed_at)
Class          1 ──< Session(회차: class_id, seq, host_id [= 진행 강사, NOT NULL], host_state{assigned|needs_reassign|confirmed?}, ...)
제약:  UNIQUE(class_id, user_id) on ClassInstructor
       FK  sessions(class_id, host_id) → class_instructors(class_id, user_id)   -- 복합 FK
```

- `sessions.host_id` 는 **이름·NOT NULL·의미 유지**("이 회차의 진행 강사"). 이유: 코드 참조 89줄/23파일·테스트 72줄(§0)·구 앱 응답 필드 `host_id`(`schemas/session.py:161`)를 깨지 않는다. 단일 컬럼이라 "정확히 1명(0·2명 불가)"이 **구조적으로 보장**된다.
- 복합 FK 로 "진행자는 해당 클래스 강사 행에 존재" 를 DB 가 강제(PostgreSQL 지원). 단 `status=removed` 행도 FK 를 만족하므로 "active 여부"는 앱 검증+서비스 락으로 강제. 테스트 DB 가 SQLite 인 경우 FK 강제 여부가 달라질 수 있음 → 앱 레벨 검증을 1차 방어로 둔다(테스트 DB 종류는 `models/session.py:21` 의 `sqlite_where` 로 SQLite 병행 사용이 추정될 뿐 **미확인**).
- "클래스 강사 ≥ 1명, 주강사 ≥ 1명" 은 DB 로 간단히 강제 불가(지연 제약 트리거 필요) → 앱 레벨 + 클래스 행 잠금.
- `host_state` 로 "이탈·비활성으로 진행자가 유효하지 않음(needs_reassign)" 을 표현해 **NULL 없이** 불변식 유지. (대안: host_id NULL 허용 — 구 코드 NOT NULL 가정 다수·"정확히 1명" 위반이라 비권장.)

### 6.2 (b) 세션 진행 강사 상태 머신

상태 정의(세션 단위 `host_state` + 회차 `status` 조합):

| 상태 | 설명 | 보유 위치 |
|---|---|---|
| `unassigned` | 편성 초안에서 아직 강사 미선택. **세션 행으로는 존재하지 않음**(초안 표 UI 상태). 클래스 "공개/확정" 시 전 회차 배정 필수 | 편성 UI·초안 저장(`draft`) |
| `assigned` | `host_id` 지정됨(미래 회차). 해당 강사에게 배정 알림 발송 | `sessions.host_id` |
| `changed` | 배정 후 1회 이상 변경됨(이력 존재). 상태가 아니라 변경 이력 N회 플래그 | `session_host_history` |
| `needs_reassign` | 진행자가 이탈·정지·삭제 등으로 유효하지 않음. `host_id` 는 이전 값 유지(NOT NULL), 열기·시작 차단, 에스컬레이션 대상 | `host_state` |
| `locked` | `open`/`in_progress` — 변경 불가(인계 예외 경로만) | `sessions.status` 에서 파생 |
| `finalized` | `completed`/`cancelled` — 이력 확정, 귀속 정정만 별도 경로 | `sessions.status` 에서 파생 |

전이표:

| 전이 | 조건·행위자 | 부수 효과 |
|---|---|---|
| (초안) `unassigned` → `assigned` | 편성 시 주강사/센터 관리자가 지정. 지정 대상은 **active 클래스 강사**(대체 강사는 §6.3) | 충돌 검사 경고 표시, 확정(공개) 시 배정 알림 |
| `assigned` → `assigned`(변경) | 주강사·센터 관리자(즉시). 진행 강사 본인은 "양도 요청" | 이전·신규 강사 알림, 변경 이력, 회원 알림(§6.2-규칙), 새 강사 기준 시간 충돌 재검사, 채팅방 방장 동기화 |
| `assigned` → `needs_reassign` | 진행자 계정 정지/삭제/클래스 제거 강행(비자발적) 시 시스템 | 주강사·센터 관리자 알림, D-3/D-1 에스컬레이션 |
| `needs_reassign` → `assigned` | 주강사/센터 관리자 재배정 | 위와 동일 |
| `assigned` → `locked` | 세션 `open` 전이(진행 강사만 가능, `session_service.py:941-952` 규칙 그대로) | 이후 변경 불가 |
| `locked` → `finalized` | 종료/취소 | 리포트 생성 파이프라인(진행자 = host_id 로 리포트 소유자 확정) |
| **금지** | `unassigned` 세션의 열기·시작; `needs_reassign` 의 열기·시작; `in_progress`/`completed` 중 일반 변경; 진행자가 클래스 강사 아닌 사람(대체 규칙 §6.3 경유 없이); 진행자 2명 | 409 |

| 회차 상태·시점 | 변경 가능 | 승인자 | 조건·알림 |

| `ready`/`scheduled`, 시작 60분 초과 전 | O 즉시 | 주강사·센터 관리자 | 이전·신규 강사 알림, 회원 알림은 §D-R9-11 기준(기본: 7일 이내 변경만) |

완료 후 리포트 귀속 정정 (오기재 정정, 대강 미기록 등):
- 현행 근거: counselor 리포트의 `user_id` 는 `s.host_id` 로 확정되고(`report_service.py:305`) Report 에 작성자·승인자 컬럼이 없다(`models/record.py:205-232`).
- 옵션: A 불가(기록 보존) / B 리포트 **승인 전**에만 정정(owner 이전, 감사 로그) / C 언제든 정정(승인 후엔 "정정됨" 이력).
- **기본값 B**. 정정은 센터 관리자 또는 주강사가, 사유 필수, `session_host_history` 에 (이전, 이후, 사유, 실행자, 시각) 기록. 승인 후 리포트는 `host_id` 를 바꾸지 않고 "표시 진행 강사" 정정 메모만 허용. 결정 후보 D-R9-06.
- 신규 컬럼 제안: `reports.approved_by`, `reports.approved_at` (현행 `sent_at` 만 존재 `models/record.py:234`), 승인자 ≠ 진행 강사일 수 있음(대행 승인)을 기록.

### 6.3 (c) 대체 강사(클래스 강사가 아닌 사람) 처리

| 옵션 | 내용 | 장단 |
|---|---|---|
| A. 엄격 | 클래스 강사로 먼저 추가해야 진행자 지정 가능 | 불변식·복합 FK 단순. 급한 대강 시 2단계라 불편 |
| **B. 임시 강사 자동 등록 (기본값)** | 진행자 선택 시 같은 센터 active 강사 검색 → 선택하면 `ClassInstructor(role=guest, scope_session_id=해당 회차)` 자동 생성 후 진행자 지정 | 복합 FK 유지, 권한 범위가 해당 회차로 한정, 편함 |
| C. 클래스 밖 자유 지정(타 센터 포함) | 어떤 사용자든 지정 | 불변식 약화, 데이터 접근 경계(§2.3) 붕괴 → 비권장 |

B 의 세부 기본값:
- 자격: 같은 센터(`Session.organization_id` = 클래스 센터)의 active membership 이 있는 `counselor` 만. 개인 상담소 상담사는 해당 없음(단일 구성). 타 센터 강사는 후속 Phase(결정 후보 D-R9-04).
- guest 권한: 해당 회차 열기·시작·종료·그 회차 참가자 명단·기록·리포트 승인. 클래스 다른 회차·회원 전체 명단·클래스 편집은 불가.
- 만료: 해당 회차 리포트 전부 승인되거나 종료 후 14일 중 먼저 도래 시 guest 접근 종료(리포트는 본인 진행분 열람 유지). 14일은 기본값.
- 대체 강사 수락: 수락 필수(§6.2 임박 규칙) — 수락 전엔 `assigned(pending_ack)` 로 보류, 현 진행자 유지.
- 대체 강사 지정 권한: 주강사·센터 관리자. 보조·진행 강사는 요청만.

### 6.4 (d) 강사 이탈·비활성 시 미래 세션 처리

| 옵션 | 내용 | 적용 |
|---|---|---|
| A. 자동 미배정 + 알림 | 해당 강사 진행 미래 회차를 `needs_reassign` 으로 표시, 주강사·센터 관리자 알림, 열기 전 재배정 강제 | **비자발적 이탈(정지·삭제·강제 해제) 기본값** |
| B. 주강사 자동 인수 | 주강사에게 자동 이관 | 충돌·동의 없이 부담 전가 → 비권장(주강사 본인 충돌 시 자동 불가) |
| **C. 이탈 차단·재배정 마법사 (자발적·정상 이탈 기본값)** | 클래스 제거/소속 해제/계정 삭제 전에 담당 미래 회차 N건을 "누구에게?" 일괄 재배정(또는 취소)하도록 강제. 현행 소속 해제의 "먼저 정리" 409 와 같은 관례(`org_management_service.py:288-300`) | 정상 경로 |

세부:
- 에스컬레이션: 미배정 회차가 시작 72시간 전·24시간 전에 남아 있으면 주강사+센터 관리자 재알림, 24시간 전까지 미해결이면 해당 회차에 "진행자 필요" 배지 + 센터 관리자 대시보드 최상단. 회원 알림은 **재배정 확정 또는 취소 확정 시점**에만(미확정 상태의 불안 유발 알림 금지).
- `suspend_user`/`delete_user` 는 지금처럼 세션을 건드리지 않거나 전부 숨기므로(§5), 신규에서는 **정지·삭제 시 미래 회차를 자동으로 `needs_reassign` 으로 전환**하고 숨김 대신 보존(삭제 시 hidden 일괄 적용 중단). 기본값.
- 완료·진행 중 회차는 `host_id` 유지(이력·리포트 소유 보존). 숨김은 회원 앱의 일정 소실 사고를 낳으므로 미래 회차에 한해 폐기.
- 퇴사(소속 해제)로 강사가 센터를 떠나도 이미 진행한 회차의 리포트는 해당 센터 `Session.organization_id` 스냅샷에 귀속 유지(`docs/counselor-multi-org-기획.md:210`).

### 6.5 (e) 강사 한 명 제거 시 기존 세션 정합

| 대상 회차 | 규칙 |
|---|---|
| 미래(`ready`/`scheduled`) 진행 회차 | 제거 전 재배정 필수(일괄 재배정 UI). 재배정 없이 강제 제거 시에만 §6.4-A |
| `open`·`in_progress` 진행 회차 | 제거 **불가**(409) — 종료 후 가능 |
| 완료·취소 회차 | `host_id` 유지(이력). `class_instructors` 행은 삭제하지 않고 `status=removed`, `removed_at` 기록(복합 FK 유지) |
| 마지막 주강사 | 제거·강등 불가(409) — 다른 강사를 주강사로 먼저 지정 |
| 마지막 강사 | 제거 불가(강사 0명 금지) |
| 제거된 강사의 이후 권한 | 클래스 접근 종료. 단 본인이 진행한 회차의 리포트·기록 열람은 유지(귀속 권리, 현행 host 본인 열람과 동일) |
| 제거 알림 | 대상 강사(클래스에서 제외됨), 주강사 |
| 회원 노출 | 과거 회차 강사명은 그대로 표시(이력). 미래 회차는 재배정된 강사로 표시 |
| 재추가 | 동일 사용자를 다시 추가하면 새 행이 아니라 기존 행 `status=active` 복구(UNIQUE 유지) |

### 6.6 (f) 불변식 목록

I1. 모든 세션은 `class_id` 를 갖는다 (이전 후 NOT NULL).
I2. 모든 세션의 진행 강사(`host_id`)는 정확히 1명이다 (단일 NOT NULL 컬럼).
I3. 세션 진행 강사는 해당 클래스의 강사 행(`class_instructors`)에 존재한다 (복합 FK + 앱 검증). `status=removed` 강사는 신규 배정 불가, 과거 회차 이력으로만 남는다.
I4. 클래스의 active 강사는 1명 이상이고, 그중 주강사(lead)는 1명 이상이다 (앱 레벨 + 클래스 잠금).
I5. 같은 `(class_id, user_id)` 강사 행은 1개이다 (UNIQUE; 제거는 soft).
I6. `unassigned` 인 회차는 열기·시작할 수 없다. `needs_reassign` 인 회차도 마찬가지다.
I7. `open`·`in_progress` 회차의 진행 강사는 변경할 수 없다 (인계 경로 도입 전까지).
I8. 같은 강사는 같은 시각에 겹치는 두 회차의 진행자가 될 수 없다 — **경고 후 확인(소프트)** 이 기본값이며, 확인 없이는 저장 불가 (현행 `force` 정책 유지).
I9. 진행 강사가 아닌 클래스 강사는 열기·시작·종료·녹음·발언권 제어를 할 수 없다 (열람R 만).
I10. 센터 관리자는 회차를 직접 열기·시작·종료하지 못한다 (콘텐츠 진행·녹음 동의 책임은 강사). 편성·재배정 대행만 가능.
I11. 리포트 승인자는 해당 회차 진행 강사 또는 주강사이며 `approved_by` 가 기록된다. 승인된 리포트의 소유(`user_id`)는 변경하지 않는다.
I12. 완료된 회차의 `host_id` 변경은 귀속 정정 경로(사유·감사·리포트 승인 전 한정)로만 가능하고 이력이 남는다.
I13. 강사 제거는 해당 강사 진행의 미래 회차가 0건일 때만 정상 처리된다. 비정상(정지·삭제)은 `needs_reassign` 으로 전환된다.
I14. 대체(guest) 강사는 지정된 한 회차에만 권한을 가지며 회차 종료·리포트 승인 완료 후 만료된다.
I15. 모든 진행자 변경은 `session_host_history`(회차, 이전, 이후, 사유, 실행자, 시각)에 기록된다 (삭제 불가).
I16. 진행자 변경 시 채팅방 방장(`ChatRoom.host_id`)·충돌 검사·리마인더·AI 비서 접근 범위가 새 진행자 기준으로 갱신된다 (채팅 `chat_service.py:281`, AI `agent_policy.py:447`).
I17. 클래스·세션의 기관 귀속은 `organization_id` 스냅샷이며 강사가 소속을 옮겨도 불변이다. 접근 판정은 현재 `User.org_id` 가 아니라 이 스냅샷 기준이다.
I18. 강사 개인별 성과·평가·순위 지표는 생성하지 않는다 (기본값; 근거: 명상/웰니스 리포트 원칙 "점수 환원·순위 금지" 및 평가 압박으로 인한 진행 왜곡 위험. 클래스 회차 비교는 진행 강사와 무관하게 클래스 단위로 이어진다).
I19. 비활성·삭제 계정의 미래 회차는 숨기지 않고 `needs_reassign` 으로 보존한다 (현행 `delete_user` 일괄 숨김 `admin_service.py:761` 대체).
I20. 회원에게 보이는 진행 강사는 항상 확정(`assigned`, 수락 완료)된 1명이며, 미배정·보류 상태 강사명은 노출하지 않는다.
