1. **`sessions.id` 와 `session_participants.id` 는 절대 바꾸지 않는다.** S3 키(`video/{session_id}/…`, `eeg-raw/{sid}/{participant_id}/…`), 입장 자격 JWT(`sid`·`sub`), 리포트 토큰, 알림 딥링크, Celery 인자가 모두 이 값에 묶여 있다 (§2.3). 이전은 "부모 행을 추가하고 `sessions.class_id` 를 채우는" 추가형만 가능하다.
2. 상위가 둘이라 **`sessions` 한 테이블을 유지하고 부모 FK 두 개(`class_id`·`counseling_relationship_id`) 중 정확히 하나만 채우는 구조(A)** 를 권장한다. 엔진 13개 FK 테이블이 그대로 산다 (§7).
3. `sessions.host_id` 는 **이름·NOT NULL 을 유지한 채 "이 회차의 진행 강사"로 의미를 확정**한다(R9 §6.0 과 동일). `instructor_id` 별도 컬럼은 같은 사실의 이중 저장이라 만들지 않는다 (§13).
4. 상담 관계는 **`client_counselor_links` 와 별개의 새 테이블**이다. 링크는 회원 전용이고 `UNIQUE(client_id, counselor_id)`, 세션과 연결이 없으며 채팅방·AI 비서 권한을 좌우한다. 이전 때 링크를 자동 생성하면 권한이 생기는 부작용이 있다 (§9).
5. 비회원 내담자는 `counseling_guest_clients`(재방문 토큰 해시 · 검증 이메일 · `claimed_user_id`)로 식별하며, 회원 전환은 **이메일 OTP 검증 후 `claimed_user_id` 기록 + 참여자·리포트 `user_id` 이관** (§11).
6. SDD-209 삭제 스위프(전사·원본 기간 삭제, 비회원 개인정보 스크럽)가 **세션 단위**로 동작해 "상담 종결 시 데이터 보관"과 정면 충돌한다 (`services/retention_sweep_service.py:1-26`). 정책 값(숫자)은 결정 필요, 데이터 모델은 스위프가 읽을 보관 플래그를 준비한다 (§10.3).

### 4.1 `run_id` — 재실행 그룹 키. 사실상 미사용
- 정의: `models/session.py:36-42` ("반복 실행 회차 식별자(경량 SessionRun). 기본값 = session_id", "EEG/리포트는 여전히 session_id 기반이므로 조회·집계의 그룹핑 키로만").
- 기록 지점: 생성 시 `session.run_id = session.id` (`services/session_service.py:407-410`), 템플릿 (`:516-517`), 복제 (`:563-564`), **`start_new_run` 이 새 uuid 로 교체 (`:1127-1142`)**, 엔드포인트 `POST /sessions/{id}/new-run` (`api/v1/session.py:270-285`).
- 읽는 곳: 응답 직렬화 `"run_id": str(s.run_id) if s.run_id else str(s.id)` (`session_service.py:125`) + 스키마 `schemas/session.py:157`.
- 프론트: **선언만 3곳**(`lib/socket.ts:178,350`, `lib/api/session.ts:61`), `new-run` 호출 0건 (`grep -rn "run_id\|new-run\|startNewRun" frontend/src`).
- 결론: 집계·조회에서 `run_id` 로 묶는 코드가 없다(백엔드 grep 전수에서 위 지점뿐). 회차 개념이 클래스/세션으로 바뀌면 **폐기 후보**. 이전은 값 보존(=id), 신규는 쓰지 않음, `new-run` 은 호환 기간 유지 (R2 §11-2 와 동일).

### 4.2 `is_template` — "유형 설정 저장본". sessions 행인데 세션이 아니다
- 정의: `models/session.py:92-94`. 템플릿 행은 일정·참여코드·채팅방이 없고 일반 목록에서 제외, 복제 산출물은 항상 `is_template=False`.
- 템플릿 행 생성: `status="ready"`, `scheduled_at=None`, `access_code=None`, `webrtc_room_id=None` (`session_service.py:475-513`).
- 제외 필터가 걸린 곳(**14개 파일**, `grep -rn is_template app`): `tasks/reminder_task.py:47`, `services/agent_counselor_service.py:362`, `retention_sweep_service.py:78`, `agent_policy.py:111,528,560,627,759`, `reminder_service.py:344,449`, `dashboard_service.py:131,176`, `agent_checkin.py:411`, `class_code_service.py:54,98`, `class_code_reissue.py:30`, `org_public_service.py:76`, `agent_reminder.py:73,311`, `report_service.py:568`, `session_email_invite_service.py:105`, `session_service.py:676,709,1093,1930`.
- 결론: 템플릿은 **이전 대상(1+1)이 아니다**. 별도 `class_templates` 로 옮기되 contract 단계(R7 §5)까지 `sessions` 에 둔다. 그동안 CHECK 는 `is_template OR …` 로 예외를 둔다.

### 4.3 `access_code` / `legacy_access_code` — 로그인 없는 4자리 입장 코드
- 컬럼: `String(6)` index (`models/session.py:62`), 재발급 시 이전 6자리 보존 `legacy_access_code` (`:64`).
- 형식·유일성: 4자리 숫자 **문자열**(선행 0), **활성(입장 가능) 클래스 사이에서만 유일** — 부분 유니크 `uq_sessions_active_access_code` (`models/session.py:20-34`, `e036a0000044`), 활성 정의 = `access_code IS NOT NULL AND is_template=false AND hidden_at IS NULL AND status NOT IN ('completed','cancelled')`.
- 발급: `generate_class_code` (`services/class_code_service.py:62`), 충돌 재시도 `_add_session_with_code_retry` (`services/session_service.py:273-284`) — **모든 세션 생성 시 발급**(상담 유형 포함, `:382`).
- 입장: `find_enterable_session` (`class_code_service.py:89-99`) → `_get_session_by_code` (`session_service.py:1729-1735`, 없는/종료/취소/숨김 동일 404).
- 소비처: 이메일 초대 본문(`session_email_invite_service.py:214-243`, 링크에는 코드 미포함), 리마인더 문구(`reminder_service.py:56,145,281`), 대시보드(`dashboard_service.py:41`), 로그 마스킹(`core/log_redaction.py:16`), 재발급 스크립트(`class_code_reissue.py`, `scripts/reissue_class_codes.py`).
- 함의: 코드는 "세션 1건 = 클래스 1건"일 때만 성립하는 모델이다. 명상 클래스에서는 **클래스 단위로 올리고**(R4 §7.4 와 동일), 상담에서는 신규 발급을 없앤다(공용 코드가 1:1 상담에 부적합, §11). 활성 코드 수는 현재 소수(기준선: 코드 보유 79 / 비템플릿 102, `baseline.md` §4-1)라 10,000 공간 여유가 크다.

### 4.4 `host_id` — "진행자 = 소유자 = 권한 주체"가 한 컬럼에 합쳐져 있다
- 정의: `UUID NOT NULL FK users.id` (`models/session.py:49`), 최초 마이그레이션 `77cff497fbe0:68`.
- 규모: **245줄 / 33개 파일**(`grep -rn host_id app`), 그중 세션 컬럼 접근 약 89줄/23파일 + `ChatRoom.host_id`(방장, 별개 컬럼 `models/chat.py:21-23`) + 함수 인자명(요청자 id). 상세 분류는 R9 §1.
- 용도: ① 권한 판정 `s.host_id != 요청자 → 403 "host 상담사만 가능합니다"` (`session_service.py:742-755`, 리포트 `report_service.py:230`, 영상 `api/v1/video.py:81,108`) ② 시간 충돌 `Session.host_id == host_id` (`session_service.py:300-325`) ③ 알림 수신자 제외 (`:1175`) ④ 채팅방 방장 `host_id=session.host_id` (`chat_service.py:281`) ⑤ AI 비서 중계 대상 (`models/agent.py:108-110`) ⑥ 오픈 방치 자동 취소 `transition_status(str(s.host_id), "cancel")` ⑦ 파이프라인 `report_service.generate_report(str(s.id), str(s.host_id), "counselor")` (`tasks/report_task.py:725`).
- 생성 후 `host_id` 를 바꾸는 코드는 없다 (R9 §0 명령 ⑧ 인용).

### 4.5 `type` — 엔진 분기 없음
- 값: `clinical|hypnosis|meditation|custom` (`models/session.py:43`, `schemas/session.py:11`), `custom` 이면 `custom_type_name` 필수 (`schemas/session.py:58-61`).
- **사용처 전수(분기 로직 아님)**: ① 표시 라벨 `임상심리상담/최면심리상담/명상수업` (`agent_policy.py:46-62`, `reminder_service.py:99-105`, `report_comment_service.py:25-27,102-103`) ② 정원 정규화 `meditation` 만 입력 정원 허용, 그 외 최소 1 (`session_service.py:362-366,468-472`) ③ 리포트 content 에 `session_type` 기록 (`report_service.py:196,518`, `report_scope.py:119-123`) ④ 연구 내보내기 허용 값 (`research_export_service.py:57`).
- **`participant_mode`(one_on_one/group) 와 독립**이다 — 스키마가 type 과 mode 의 조합을 제한하지 않는다 (`schemas/session.py:16,33`). 즉 `clinical`+`group`, `meditation`+`one_on_one` 이 데이터로 존재할 수 있다 → 이전 분류에서 예외 처리 대상 (R7 §4).
- 결론: `grep -rnE "\.type (==|in|!=) |session_type|\"meditation\"|\"clinical\"|\"hypnosis\"" services api tasks core` 범위에서 EEG·녹음·STT·리포트 엔진이 type 으로 갈라지는 곳은 발견되지 않았다(위 4종뿐) → **"엔진 공유, 상위·마법사·리포트 화면만 분리"가 코드 구조와 맞는다.** (프론트의 type 분기는 R3 범위, 이 조사에서는 미확인.)

## 6. 컬럼 분류표

분류 기호: **U** = 상위(클래스/상담 관계)로 올림 — 원천은 상위, 세션 컬럼은 "유효값"으로 남긴다 / **S** = 세션 유지 / **H** = 판단 보류(이유 명시).

원칙(기술 기본값):
- **P1 세션은 유효값을 계속 보유한다.** 상위 설정은 "기본값", 세션 컬럼은 "생성 시 복사된 유효값"(회차별 override 가능). 엔진(입장·녹음·LINK BAND 게이팅 등)이 `sessions` 를 읽는 코드 89줄+를 건드리지 않기 위해서다.
- **P2 구 앱 응답 필드는 유지**한다(`SessionResponse` 필드 삭제 금지, R2 §11-2).
- **P3 FK·키에 쓰이는 id 는 S**.
- **P4 개인정보는 중복 저장을 최소화**하고 스크럽 대상은 양쪽에 둔다(§11.4).

## 7. 상위가 둘일 때의 구조 비교와 기본값

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 부모 테이블 2개 + `sessions` 의 FK 2개 중 하나만 채움 (CHECK)** | `classes`, `counseling_relationships` 각각 신설. `sessions.class_id` / `sessions.counseling_relationship_id` 둘 다 nullable, `CHECK (is_template OR (class_id IS NULL) <> (counseling_relationship_id IS NULL))` | ① 상담의 "내담자 1 + 상담사 1" 을 **컬럼 구조로 보장**(`client_user_id`/`client_guest_id`) ② 명상 전용 컬럼(정원·코드·강사 N명)이 상담 쪽에 NULL 로 퍼지지 않음 ③ 복합 FK 가 MATCH SIMPLE 이라 **NULL 인 쪽은 자동으로 검사 생략**(§12) ④ R2·R4·R9 가 이미 `classes`/`class_members`/`class_instructors` 로 전제 | ① "오늘 일정" 같은 합산 조회가 두 부모 LEFT JOIN 필요(단 일정 자체는 `sessions` 한 테이블이라 부모는 제목 표시용) ② 세 번째 제품이 생기면 FK 가 하나 더 늘어남 |
| B. 공통 `programs` 테이블(kind) + 확장 테이블 | `sessions.program_id` 하나. 강사·멤버도 `program_staff`/`program_members` 공통 | FK 하나, 합산 조회 단순, 제품 추가 쉬움 | ① 상담 1:1 보장이 **구조적으로 불가**(멤버 수 제약을 kind 에 따라 거는 CHECK 는 다른 테이블 참조라 불가 → kind 비정규화 필요) ② 클래스 전용 컬럼이 NULL 투성이 또는 1:1 확장 테이블 추가 ③ R2·R4·R9 명칭 전면 재작성 |

보완:
- 읽기 편의용 **SQL VIEW `v_session_parent`**(session_id, parent_kind, parent_id, title, organization_id)를 둘 수 있다(선택, 모델 변경 없음).

## 9. `client_counselor_links` 재사용 vs 신설

### 9.1 현행 사실
- 테이블 `client_counselor_links`: `client_id`·`counselor_id` 둘 다 **`users.id` FK NOT NULL**, `UNIQUE(client_id, counselor_id)`, `status active|ended`, `matched_at`, `ended_at`, `memo` (`models/client_counselor_link.py:15-27`).
- 생성 경로: 초대 가입(`api/v1/auth.py:903` → `client_service.link_invited_client`), 내담자 포털에서 상담사 코드로 연결(`api/v1/client_portal.py:140-185`), 상담사 지정(`client_service.assign_counselor` `:35-110`). **세션과 연결되지 않는다** — 목록의 `last_session_at` 은 `None  # 추후 세션 연동` (`client_service.py:154`).
- `ended` 로 바꾸는 코드는 **발견되지 않았다**(`grep 'status = "ended"'` 0건). 읽는 쪽(목록에서 제외 `client_service.py:128-130`)과 재활성화(`:90-92`, `client_portal.py:166-172`)만 있다 → "종결" 기능은 사실상 미구현.
- **권한 부작용**: 링크 생성 시 1:1 채팅방 자동 생성(`client_portal.py:176-185`, `client_service.py:105-108`), AI 비서는 `status='active'` 링크 **또는 세션의 active 참여자**로 담당 내담자를 판정(`agent_policy.py:444-450,495-504`, `agent_counselor_service.py:424-436`), 채팅 권한도 링크 의존(`chat_service.py:207-214,379-382,422-425,989-992`).

### 9.2 옵션 비교

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **R-1. 링크를 상담 관계의 뿌리로 재사용** | 링크에 컬럼 추가, 세션이 링크를 FK | 기존 `ended`·`memo`·재활성화 의미 재사용 | ① **회원 전용**(`client_id` NOT NULL FK) → 비회원 내담자 불가(확정 요구와 충돌) ② `UNIQUE(client_id,counselor_id)` → 같은 쌍의 "새 관계"·기관 간 중복 불가 ③ 링크 생성이 채팅·AI 권한을 부여하므로 이전 때 링크를 만들면 권한이 생김 |
| **R-2. 신설 + 약결합 (기본값)** | `counseling_relationships` 신설, 회원 관계이고 링크가 이미 있으면 `link_id` 로 연결만 | 비회원 지원, 상태(active/closed/archived)·이력 자유, 권한 부작용 없음 | 두 곳에 "연결" 개념이 공존 → 동기화 규칙 필요 |
| R-3. 링크를 관계로 대체(마이그레이션 후 링크 폐기) | | 단일 개념 | 링크 참조 코드 30여 곳(chat·agent·client) 수정, 위험 큼 |

**기본값: R-2.** 동기화 규칙(기본값 제안):
1. 이전·신규 어디서도 **링크를 자동 생성하지 않는다**(채팅방·AI 권한 부작용). 링크가 이미 있으면 `link_id` 만 기록.
2. 링크가 `ended` 면 이전 시 관계 `status='closed'`, `closed_at=link.ended_at` (유일한 종결 신호).
3. 관계 종결이 링크를 자동으로 `ended` 로 바꾸지 않는다(종결 내담자에게 AI 비서·채팅을 계속 열어 둘지는 **결정 후보 C-2**, 기본값 "유지, 상담사가 별도 해제").
4. `memo`: 링크가 있으면 링크 `memo` 를 계속 읽는다(복사하지 않음 — 이중화 방지).

### 9.3 조사 간 충돌: R10 은 "링크 확장(A안)"을 권고 — 통합 단계에서 한 줄 결정 필요

`조사/R10-상담분리.md` §2.3~2.4 는 이 문서와 반대로 **`client_counselor_links` 를 "상담 관계"로 확장**(`client_id` NULL 허용 + `guest_id` + XOR 체크, `status pending|active|ended|archived`, 부분 유일 제약, 이력 `counseling_link_events`, `sessions.counseling_link_id`, 관계 단위 4자리 코드, 비회원 `counseling_guests`)하자고 한다. 이 문서의 `counseling_relationships` ≈ R10 의 확장된 `client_counselor_links`, `counseling_guest_clients` ≈ `counseling_guests`, `sessions.counseling_relationship_id` ≈ `sessions.counseling_link_id` 이다. **나머지 골격(부모 FK 정확히 하나, 복합 FK 로 진행자 강제, 상태·종결·재개, 비회원 신원·회원 전환, 이전 규칙)은 이름만 다르고 동일**하다.

| 쟁점 | 이 문서(신설 + `link_id` 약결합) | R10(링크 확장) | 조정 시 필요한 것 |
|---|---|---|---|
| 개념 수 | 링크와 관계 2개 공존, 동기화 규칙 필요 | 1개 — "내담자 목록 = 상담 관계 목록"이 코드와 일치 | A 가 개념상 단순하다는 R10 지적은 타당 |
| 이전 때 권한 부작용 | 링크를 만들지 않음 → 부작용 없음 | 세션 쌍마다 링크 행을 만들면 `status='active'` 가 곧 **채팅 접근**(`chat_service.py:207-214`)과 **AI 비서 담당 내담자**(`agent_policy.py:444-450,495-504`)를 부여 | A 를 택하면 이전분은 `pending`/별도 상태로 만들고 소비처가 `active` 만 보게 하거나, 이전분 활성화를 상담사 확인 뒤로 미룬다 |
| 소비처 | 변경 없음 | `client_id` NULL 허용·`ended` 의미 변경 → 소비처 5~12곳 수정(R10 §2.3) | 수정 범위 vs 이중 개념 비용 |
| 데이터 보관 | 신규 테이블이라 계정 삭제 경로 영향 없음 | 계정 삭제 시 링크 행 DELETE(R10 §2.2 인용 `admin_service.py:714-716`) → **종결 후 보관 원칙과 충돌**, 제외 처리 필요(R10 I5) | 둘 다 삭제 경로 점검 필요 |
| 4자리 코드 | 상담은 **미발급**, 이메일 초대 링크 + 재방문 자격(§11.2) | **관계 단위 4자리 코드**(활성 세션 코드와 같은 공간, R10 §6) | 관계에 `access_code`·`legacy_access_code` 컬럼을 두고 유일 규칙을 `classes`·`sessions`·관계 3곳 합집합으로 확장하면 흡수 가능. 어느 쪽이든 비회원 본인 확인(이메일 일치 vs OTP)은 상담 기획에서 확정 |
| 종결 추정 | 이전 시 **추정하지 않음**(링크 `ended` 만 반영) | 마지막 세션 90일 초과면 `ended(inactive)` 로 제안 | 비즈니스 결정 → R7 C-15 |

판단: **이 문서의 기본값은 "신설"을 유지**하되(권한 부작용·종결 데이터 보관을 구조적으로 격리), "내담자 목록 = 상담 관계" 일치가 더 중요하면 R10 안으로 가도 §6~§8·§11·R7 의 규칙은 이름 치환만으로 재사용된다. **최종 선택은 통합(`기획.md`) 단계에서 한 줄로 확정**하고, 선택이 `link_id` 약결합을 쓰는지 링크 확장인지만 모델 이름에 반영한다. (기술 선택이므로 Brian 결정 항목 아님.)

## 10. 상담 관계 상태 · 종결 · 재개 · 보관 (데이터 모델 관점)

### 10.1 상태 (기본값 제안)

| 상태 | 의미 | 새 회차 생성 | 목록 노출 |
|---|---|---|---|
| `active` | 진행 중 | 가능 | 기본 |
| `closed` | 종결(데이터 보관, 읽기 전용 + 재개 가능) | **불가**(재개 후 가능) | "종결" 필터 |
| `archived` | 보관(기본 목록에서 숨김, 열람 가능) | 불가(재개 후 가능) | "보관함" |

전이: `active → closed`(종결, `closed_at/by/reason`) · `closed → active`(재개, `reopened_count+1`, 같은 관계 계속) · `closed → archived`(수동 또는 정책 기간 후) · `archived → active`(재상담, 재개). **금지**: 물리 삭제(예외 = SDD-209 B1 의 플랫폼 관리자 원본 삭제 경로뿐, 감사 `original_deletion_audits`), `active → archived` 직행.
불변식: ① `closed|archived` 관계에는 `ready|scheduled|open|in_progress` 세션이 없다(종결 시 예정 세션은 취소하고 안내 — 취소 알림은 R9 §4) ② 모든 전이는 `counseling_relationship_events` 에 남는다 ③ 재개 시 `seq` 는 이어서 증가.

### 10.2 열람 권한 (데이터 접근 규칙 초안)
- 상담사: 본인이 담당(현재 또는 과거 `counseling_relationship_counselors`)한 관계는 종결·보관 후에도 읽기 가능. 이관 후 이전 상담사의 열람 범위는 **결정 후보**(R9 와 함께).
- 회원 내담자: 본인 리포트 접근은 `session_participants` 행 존재 기반(`report_service.py:833-844`)이므로 **종결해도 유지**된다(출석 행을 숨기지 않는 원칙, R4 불변식 5).
- 비회원 내담자: 이메일로 받은 사본 + 재방문 자격 유효 기간 내 열람(§11).
- org_admin: 현행(리포트 열람·수정, 세션 조작 불가 — R9 §2.4)을 그대로.

### 10.3 보관 정책과의 충돌 (결정 필요)
- 스위프는 **세션 종료일 기준**으로 completed·cancelled 세션의 EEG raw·음성/영상·**STT 원문(transcript)** 을 `RETENTION_RAW_DAYS` 후 삭제하고 비회원 개인정보를 `RETENTION_GUEST_PII_DAYS` 후 스크럽한다. 리포트 본문·지표 요약·회원 계정은 대상 아님 (`services/retention_sweep_service.py:1-26,68-94`).
- "상담 종결해도 **데이터 보관(삭제 없음)**"(`브리프-추가2.md` 확정 추가)은 두 지점과 충돌한다: ① 전사·원본이 기간 후 삭제됨 ② 비회원 내담자 개인정보가 스크럽되면 **재방문 식별(§11)과 재개가 불가능**해짐.
- 모델 대응(기본값): `counseling_relationships.retention_hold`(기본 true)를 스위프가 읽어 상담 세션을 제외하거나 상담 전용 기간을 적용하도록 **훅을 준비**한다. 어느 쪽이든 숫자(기간)·범위(전사 포함 여부)는 비즈니스 결정 → **C-1**.

## 11. 비회원 내담자 식별 · 재방문 · 리포트 · 회원 전환

### 11.1 현행 비회원 모델 (사실)
- 비회원은 `session_participants` 행(`user_id NULL` + `guest_name/gender/birth_date/report_email`)이 전부이며 **세션 간 동일인 식별이 없다**. 정책: "같은 이름을 적었다는 이유로 기존 참여자를 인계하지 않는다" (`policy-revision-r4.md` 위임받은 기술 결정 4번째 불릿).
- 복귀 수단: 입장 자격 JWT(TTL 24시간 `settings.entry_credential_ttl_hours`, R4 §0-6 인용), 리포트 이메일 요청 토큰 7일(`report_email_service.py:23-31`).
- 리포트 전달: 종료 후 입력한 이메일로 자동 발송(`policy-revision-r4.md` 5번), 이메일 OTP 검증 토큰은 15분 JWT (`services/email_verify_service.py:10-12`).

### 11.2 설계 (기술 기본값 — 상담 관계의 비회원은 "관계 단위 신원"을 가진다)

| 단계 | 동작 | 저장 |
|---|---|---|
| ① 최초 초대 | 상담사가 관계 생성 시 비회원 내담자를 등록(이름·이메일 필수, 성별·생년월일 선택). **이메일 초대**에 일회용 서명 토큰 링크 포함(공용 4자리 코드 사용 안 함 — 1:1 에 공용 코드는 부적합) | `counseling_guest_clients` 행 |
| ② 본인 확인·첫 입장 | 링크 진입 → 개인정보 수집·보관 동의 → **이메일 OTP**(15분 토큰, 기존 `email_verify_service` 재사용) → 성공 시 `email_verified_at` 기록 | `privacy_consent_at/version`, `email_verified_at` |
| ③ 재방문 자격 발급 | 서버가 `counseling_entry` 자격(JWT, `sub=guest_client_id`, `ver=reentry_ver`, 슬라이딩 TTL 기본 90일)을 기기에 발급. 비밀 값 해시만 저장 | `reentry_secret_hash`, `reentry_issued_at` |
| ④ 같은 기기 재방문 | 자격 유효 → 회차 입장 시 해당 관계의 비회원 출석 행을 생성/재사용 | `session_participants.guest_client_id` |
| ⑤ 기기 분실·만료 | 등록 이메일로 OTP → 자격 재발급(`reentry_ver+1` 로 이전 자격 폐기). 이메일 불일치/없음이면 상담사가 "초대 재발송" | |
| ⑥ 리포트 | 회차 리포트 승인 후 `counseling_guest_clients.email` 로 발송(결과는 출석 행의 `report_email_status`) | 기존 컬럼 재사용 |
| ⑦ 회원 전환 | §11.3 | `claimed_user_id` 등 |

- **4자리 코드와의 정합**: SDD-209 R5 는 "코드 확인 뒤 개인정보 입력으로 입장"이지만 상담은 상담사가 내담자를 미리 아는 구조이므로 **코드를 쓰지 않고** 관계 초대 링크로 신원을 먼저 확정한다. 이미 존재하는 clinical 세션의 활성 코드는 호환 기간 그대로 동작(R7 §6).
- 상담사별 격리: 같은 사람이 두 상담사에게 상담받으면 `counseling_guest_clients` 행이 **둘**(§8.6 유니크가 상담사 단위).

### 11.3 회원 전환(가입 시 기존 기록 연결)
1. 가입(또는 로그인) 계정의 이메일 정규화 값 = `counseling_guest_clients.email_norm` 이고 `email_verified_at IS NOT NULL` 이면 후보. 가입 자체가 이메일 검증을 거친다(`email_verify_service.generate_email_verify_token`).
2. 계정 소유자에게 "○○ 상담사와의 기록을 연결할까요?" 확인(사용자 동의) 후 **한 트랜잭션**으로: `claimed_user_id/claimed_at/claim_method` 기록 → `counseling_relationships.client_user_id` 채움(`client_guest_id` 는 출처로 유지) → 해당 관계 세션의 `session_participants.user_id`, `reports.user_id`, `eeg_records.user_id`, `eeg_raw_chunks.user_id`, `eeg_feature_windows.user_id` 이관(리포트 접근이 `user_id` 와 행 존재로 판정되기 때문) → `guest_claim_events` 에 건수 기록.
3. 이메일이 미검증이거나 불일치면 자동 연결 금지 — 상담사 확인 경로(`claim_method='counselor_confirmed'`)는 **결정 후보**(기본값 "자동 연결은 검증된 이메일만").
4. 연결 후 비회원 재방문 자격은 폐기(`reentry_ver+1`)하고 회원 로그인으로 통일. `link_id` 는 필요 시 그때 생성(권한 부작용을 사용자 동의와 함께).
5. 역방향(연결 취소)은 지원하지 않는다 — 이력 보존만(`guest_claim_events`).

### 11.4 개인정보 보관·삭제·연구 동의
- 비회원 개인정보는 **세 곳에 존재할 수 있다**: `session_participants`(회차 사본), `counseling_guest_clients`(관계 신원), `session_email_invites`(이전 방식). 스위프(B12)는 앞의 것과 초대 행만 스크럽하므로 `counseling_guest_clients` 를 **스위프 대상에 추가해야 한다**(안 하면 보관 기간을 넘겨 남음, 하면 §10.3 충돌). 이 정책 값이 **C-1**.
- 연구 동의: 현행은 참여자 행 단위(`research_consents.participant_id` UNIQUE, `models/research.py:26`)로 가명 ID(이름+생년월일 해시)를 만든다. 관계 단위로 한 번 받을지는 R4 §8 의 동의 시점 결정에 종속. 모델은 변경 없이 호환.

## 12. "세션 진행자는 해당 클래스 강사여야 함" — PostgreSQL 강제 가능성

| 요구 | 강제 수단 | 가능 여부 | 비고 |
|---|---|---|---|
| 세션 진행자 정확히 1명 | `sessions.host_id` **단일 NOT NULL 컬럼** | ✅ 구조적 보장 | 0명·2명 표현 불가 |
| 진행자가 해당 클래스 강사 **행에 존재** | 복합 FK `FOREIGN KEY (class_id, host_id) REFERENCES class_instructors (class_id, user_id)` | ✅ | 참조 대상에 `UNIQUE(class_id, user_id)` 필수 |
| 진행자가 **활성(active)** 강사 | 위 FK 는 행 존재만 본다. 제거는 soft(`status='removed'`)이므로 FK 를 통과함 | ❌ 선언적 불가 | 앱 검증 1차 + (선택) `BEFORE INSERT/UPDATE OF host_id, class_id` 트리거. 저장소에 트리거 선례 없음(`grep -rli "create trigger"` 0건) → **앱 레벨 기본값** |
| 클래스 강사 ≥ 1명 | 선언적 불가(집계 제약) | ❌ | 앱 + 클래스 행 잠금 (R9 I4) |
| 상담: 진행자 = 관계 담당 상담사 | 복합 FK `(counseling_relationship_id, host_id) → counseling_relationship_counselors(relationship_id, counselor_id)` | ✅ | |
| `sessions` 한쪽 부모만 채움 | CHECK (§8.8) | ✅ | M6 에서 활성화 |

세부(PostgreSQL 동작):
1. **MATCH SIMPLE(기본)**: 참조 컬럼 중 하나라도 NULL 이면 제약을 **검사하지 않는다.** 상담 세션은 `class_id IS NULL` → 클래스 FK 가 자동으로 건너뛰고, 명상 세션은 `counseling_relationship_id IS NULL` → 상담 FK 가 건너뛴다. 별도 조건 분기가 필요 없다. (템플릿·이전 중 미채움 행도 안전하게 통과.)
2. **삭제/갱신**: 기본 NO ACTION(= RESTRICT 효과)이므로 세션이 참조하는 강사 행의 키를 지울 수 없다 → 강사 제거는 soft-remove 가 정답(과거 회차 이력 보존).
3. **잠금 경합**: 새 세션 INSERT 는 참조 행에 `FOR KEY SHARE` 를 건다. 키를 바꾸는 삭제/수정은 막히지만 `status` 같은 비키 컬럼 갱신은 막지 못한다 → "강사 제거 vs 동시 배정" 경합은 클래스 행 `SELECT … FOR UPDATE` 로 직렬화.
4. **도입 순서**: 참조 대상 행이 먼저 채워져야 한다. `ADD CONSTRAINT … NOT VALID`(새 행만 검사, 짧은 잠금) → 백필 후 `VALIDATE CONSTRAINT`(`SHARE UPDATE EXCLUSIVE`, 쓰기 안 막음). 이 저장소엔 `NOT VALID`·`DEFERRABLE` 선례가 없으므로 첫 사용이며 마이그레이션 PR 에 근거를 적는다.
5. **구 코드 호환**: 복합 FK 는 구 코드가 INSERT 하는 `class_id IS NULL` 행에는 작동하지 않으므로 **롤백(구 코드 복귀) 후에도 안전**하다. 반면 §8.8 의 one-parent CHECK 는 NOT VALID 라도 **새 INSERT 를 검사**하므로 구 코드가 깨진다 → M6 까지 미룸(R7 §2).
6. **SQLite 테스트**: FK 강제가 기본 꺼져 있어 테스트에서는 DB 제약이 동작하지 않는다(`tests/conftest.py` 가 SQLite 방언 shim 사용) → **앱 검증이 1차 방어**여야 하고 PostgreSQL 대상 제약 테스트는 별도(CI 에 PG 단계 없음, R7 §2 참고).
7. 인덱스: 참조하는 쪽에 `(class_id, host_id)` 인덱스(부모 키 변경/검증 성능).

기본값: **복합 FK(존재) + 앱 검증(활성·최소 1명) + 클래스 행 잠금.** 트리거는 앱 검증을 우회하는 경로(수동 SQL·스크립트)가 생길 때 후속 도입.

## 13. 현행 `host_id` 와의 의미 매핑

| 현행 `host_id` 용법 | 신규에서의 위치 | 이전 방법 |
|---|---|---|
| 세션 진행자 | `sessions.host_id` 그대로 = **진행 강사/진행 상담사** | 변경 없음 |
| 소유자·개설자 | 명상: `classes.created_by`, 상담: `counseling_relationships.counselor_id`(최초 담당) | `created_by` ← `host_id` |
| 클래스 강사(권한 주체) | `class_instructors(role='lead')` | 세션마다 1행 생성(중복은 `ON CONFLICT DO NOTHING`) |
| 알림 수신자 제외, 시간 충돌 검사 | 진행 강사(`sessions.host_id`) 기준 유지 | 변경 없음. 명상·상담이 한 테이블이라 **통합 충돌 검사가 이미 성립**(`session_service.py:300-325`) |
| 채팅방 방장(`ChatRoom.host_id`) | 진행자 변경 시 갱신 필요(R9 I16) | 변경 없음 |
| AI 비서 중계 대상(`agent_relay_events.target_user_id`) | 진행 강사 | 변경 없음 |
| 리포트 승인자 | 진행 강사 또는 주강사(R9 I11) | 변경 없음 |

**`instructor_id` 별도 컬럼 vs `host_id` 의미 확정**

| 안 | 내용 | 평가 |
|---|---|---|
| **H1 (기본값)** | `host_id` 이름·NOT NULL 유지, 의미만 "진행 강사"로 확정 | 코드 89줄+/23파일·테스트 72줄·구 앱 응답 `host_id`(`schemas/session.py:161`) 무변경. 이중 저장 없음 |
| H2 | `instructor_id` 신설, `host_id` 는 폐기 예정 | 이름은 깔끔하나 이중 저장(drift)·이중 쓰기 기간·89줄 수정. 얻는 것이 이름뿐 |

→ H1. 브리프의 "sessions.instructor_id" 는 **`host_id` 로 대체**한다(충돌 아님, 이름만 다름).
