## 0. 핵심 결론 (6줄)

1. **`session_participants` 행을 "회차 출석(attendance) 행"으로 유지하고, 그 위에 `class_members`(멤버십)를 신설**하는 확장형을 기본안으로 제안. 이유: `participant_id` 를 FK 로 거는 테이블이 4곳(`eeg_records`·`eeg_raw_chunks`·`reports`·`eeg_feature_windows`, §2.3)이고 모두 `ON DELETE CASCADE` — 출석 행 id 를 바꾸면 EEG·리포트 이전 비용이 크다.
2. 현행 "참여자 상태"는 **단일 enum 이 아니라 플래그·타임스탬프 조합**(`is_waitlisted`·`removed_at`·`waitlist_cancelled_at`·`entered_at`)이다. 상태 enum 컬럼이 없다 (`app/models/session.py:142-165`). 클래스 도입 시 멤버십·출석에 각각 **명시적 status 컬럼을 신설**하고 기존 플래그는 출석 쪽에서 호환 유지.
3. 이름 충돌 주의: `app/services/membership_service.py` 는 **상담사의 기관 소속**(`user_org_memberships`, 상태 invited/active/left)이며 클래스 멤버십과 무관하다 (`app/models/user_org_membership.py:30`, 활성 중복만 부분 유니크 `:53-64`). 단 상태 전이 패턴(left 는 이력 보존, 활성 중복만 부분 유니크)은 참고 가능.
4. **`removed_at` 은 이탈 표현에 쓰면 안 된다.** `removed_at`/`waitlist_cancelled_at` 이 있는 행은 모든 ORM SELECT 에서 숨겨지고 (`app/core/database.py:16-44`), 회원의 리포트 접근도 "SessionParticipant 행 존재" 로 판정한다 (`app/services/report_service.py:833-844`). 이탈한 회원의 **지난 회차 출석·리포트가 사라지는** 문제를 막으려면 이탈은 멤버십 status 로만 표현하고 과거 출석 행은 가시 상태로 둔다.
5. 4자리 코드는 현재 **회차(sessions) 단위**로 발급·유일(`app/models/session.py:17-34`, `app/services/class_code_service.py:49-80`)이다. 클래스 도입 시 **코드를 클래스 단위로 올리는 안**을 기본으로 제안 — 회차마다 새 코드를 쓰면 정기형에서 활성 코드 수가 폭증하고 비회원이 매 회차 코드를 다시 받아야 한다 (§7).
6. **비회원 장기 참가**가 가장 큰 설계 공백: 입장 자격(JWT) TTL 이 24시간 (`app/config.py:44`)이고 "이름이 같다고 기존 참여자를 인계하지 않는다" 가 확정 정책 (`specs/sdd-209-class-flow-redesign/policy-revision-r4.md:20`). 주 1회 클래스에서는 매주 새 참가자가 될 위험 → §7 에서 옵션 제시, 결정 후보 D4-5.

## 3. 설계안

### 3.1 옵션 비교 — 멤버십과 출석을 어떻게 나눌까

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|

### 3.3 불변식 (invariant)

1. `class_members.status='active'` 이고 클래스가 `active` 면, 예정(시작 전) 모든 정규 회차에 대해 출석 행이 존재한다 (없으면 시스템이 생성). 합류 시점 이전 회차에는 행을 **만들지 않는다**(합류 전을 결석으로 세지 않음).
2. 한 `(session_id, member_id)` 는 출석 행이 최대 1개. (현행 `uq_session_participant_user` 는 비회원을 못 막으므로 `UNIQUE (session_id, member_id)` 를 신설 — 멤버십 id 는 비회원도 NOT NULL.)
3. `attendance_kind='makeup'` ⇒ `makeup_for_session_id` NOT NULL 이고 그 회차는 같은 클래스의 `absent`/`excused` 출석을 가진 같은 멤버의 것이어야 한다 (앱 검증 + CHECK 복합 FK 로 같은 `class_id` 강제 — 복합 FK `(class_id, id)` 사용은 기술 선택, 기본값 제안).
4. `entered_at IS NOT NULL` ⇒ `attendance_status ∈ {attended}`. `attended` 는 `absent`/`excused`/`withdrawn` 으로 되돌릴 수 없다 (호스트 정정 이벤트만 예외, §9.2).
5. 멤버가 `left`/`removed`/`completed` 여도 **과거 출석 행·EEG·리포트는 가시 상태 유지** (리포트 접근 판정 `report_service.py:833-844` 가 행 존재에 의존하므로, 멤버십 status 로만 이탈을 표현하고 과거 출석 행에 `removed_at` 을 쓰지 않는다).
6. 클래스 정원 계산에 쓰는 인원 = `status='active'` 멤버 수 (§6).
7. 회원이 다른 클래스의 같은 시각 회차에 동시에 `expected` 여도 막지 않는다(경고만, R5 §5 참조).

## 5. 출석 확정 시점·집계 (기술 기본값 제안)

- 결석 확정은 **회차 `end` 전이 후 훅**에서 실행 (`transition_status` 의 `action=="end"` 블록 `session_service.py:1013-1033` 에 연결). 이유: 입장 데이터(`entered_at`)가 종료 시점에 확정됨, 별도 cron 불필요, 이미 `research_export_service.on_session_completed` 같은 종료 훅이 있음.
- 회차가 `in_progress` 에서 호스트가 `cancel` 로 끝내면(`TRANSITIONS['cancel']`에 `in_progress` 포함, `session_service.py:39`) 입장한 사람은 `attended` 유지, 나머지는 결석으로 확정하지 않음(데이터 없는 취소 처리 규칙 필요 → D4-2 의 하위 항목: "진행 중 취소 회차의 출석 인정").
- 클래스 출석 요약(R6와 연계): 분자 = `attended`(정규+보강), 분모 = 합류 이후의 `cancelled` 아닌 정규 회차 수. 점수 환원·순위 금지 원칙(`브리프.md` R6)에 따라 **회원 화면은 "3/8 참석" 같은 사실 표기만**, 출석률(%) 등급·정렬 금지.

## 6. 정원·대기열 — 클래스 단위 vs 회차 단위

현행: 정원 `sessions.max_participants`(`session.py:72`), 대기열은 같은 세션 안에서 `is_waitlisted`·`waitlist_position`, 판정은 `_has_capacity`·`_can_join_active`·`_promote_waitlist_all` (`session_service.py:1321-1397`), 행 잠금 `_lock_session_for_capacity` (`:1344`). 온라인 그룹 상한 50, 오프라인 100 (`schemas/session.py:63-71,111-119`, `policy-revision-r4.md:154`).

| 옵션 | 정원 의미 | 대기열 | 적합한 클래스 | 위험 |
|---|---|---|---|---|
| A. 클래스 단위 | 활성 멤버 수 ≤ 정원 | 클래스 대기열(`class_members.status='waitlisted'`) | 고정형 코호트(8회 MBSR) | 보강 참석자는 정원 밖 추가 인원이 되어 장소 초과 가능 → 회차 상한 필요 |
| B. 회차 단위 | 회차별 출석 `expected+attended` ≤ 정원 | 회차 대기열(현행) | 드롭인형 정기 클래스 | 코호트에서 "내 자리"가 보장되지 않음 |
| **C. 혼합 (기본값 제안)** | 멤버 정원(클래스) + 회차 상한(`sessions.max_participants`, 기본=클래스 정원) | 멤버 모집·승격은 클래스 대기열, 회차 상한 초과는 보강/드롭인에만 적용되는 회차 대기열(현행 로직 재사용) | 두 유형 모두 | 로직이 두 겹 — 단 회차 쪽은 현행 코드 그대로 |

**기본값 제안: C.**
- 회차 정원 카운트 = `attendance_status ∈ {expected, attended}` 인 행(`excused`·`absent`·`withdrawn` 은 제외 → 사전 결석이 자리를 비워 보강자가 들어올 수 있음). 현행 `_active_participant_count` (`:1321-1331`)의 `is_waitlisted=false` 조건에 상태 조건 추가.
- 정기형(상시 모집) 기본: 멤버 정원을 두되 비워 둘 수 있고(제한 없음, 현행 `max_participants` 0/None 은 무제한 `:1339`), 그때 정원은 회차 상한이 담당.
- 대기열 승격은 기존 규칙 유지: 순번 순, 취소자 제외, 새치기 방지(`_can_join_active :1375`), 승격은 행 잠금 하에서 (`policy-revision-r4.md:41` RV5).
- 주의: 승격 알림 `session_waitlist_promoted` (`session_service.py:1413`)는 클래스 대기열용 `class_waitlist_promoted` 신규 필요 (R2 신규 이벤트 후보 목록에 추가 제안).
- 정원 감소(클래스 정원 < 활성 멤버)는 현행처럼 막지 않고 **신규 입장만 대기로** 보낸다 (현행 `update_session` 은 정원 증가 때 승격만 처리 `:806-811`, 감소 때 기존 인원 강등 없음 — 확인).

| 입장 자격 | JWT(`sub`=참여자 id, `sid`=세션 id, `ver`=`entry_ver`), TTL 24h (`entry_credential_service.py:33-47`, `config.py:44`) | 이중: **멤버십 자격**(`mid`, 긴 TTL) + 회차 자격(현행 형식 유지, 단명). §7.2 |
| 멤버십 생성 | 없음 | 코드 입장 성공 시 `class_members(kind='guest', joined_via='code', status=active\|waitlisted)` + 현재 입장 가능 회차의 출석 행 |
| 대기 | 회차 대기열 | 클래스 정원이 찼으면 `waitlisted`(클래스 대기열) |

### 7.2 문제와 옵션 — 비회원의 회차 간 연속성

- 사실: TTL 24시간 (`config.py:44`). 새 브라우저에서 같은 이름을 적어도 기존 참여자를 인계하지 않는다는 정책이 확정 (`policy-revision-r4.md:20`, 코드 `session_service.py:1862-1873`). → 주 1회 클래스에서 자격이 만료되면 **매 회차 새 비회원(중복 멤버)** 이 만들어진다. 출석·변화 추이·리포트가 사람 단위로 이어지지 않음.
- 옵션:

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **a. 클래스 단위 장기 자격 (기본값 제안)** | 멤버십 자격 TTL = 클래스 종료일+N일 또는 마지막 사용 후 슬라이딩 N일. 기기 저장소에 보관. 만료 전이면 회차 입장은 코드 재입력 없이 자동 출석 | 정책 위반 없음(자격 소지자만 복귀) | 기기 분실·브라우저 정리 시 끊김. 공용 기기 위험 → `entry/revoke` 로그아웃 경로 필요(현행 `session.py:165`) |
| b. 호스트 "같은 사람 합치기" | 중복 비회원 멤버를 호스트가 수동 병합(`class_member_events` 에 merge 기록, 출석 행 `member_id` 이전) | 분실 복구 | 호스트 부담, 개인정보 노출 범위(이름·생년월일 대조) |
| c. 이메일 확인 링크 복구 | 입력 이메일로 일회용 복구 링크 → 같은 멤버십 자격 재발급 | 자동 복구 | D-1에서 이메일 OTP 제외 확정 (`policy-revision-r4.md:61,72`) — 정책 재논의 필요 |
| d. 회원가입 유도 | 2회차 이후 가입 제안, 가입 시 `class_members.user_id` 연결 | 가장 안정 | 가입 연동 시 소유 증명 방법 필요(미결) |

→ 기본값: **a + b**, c 는 정책 재논의 필요하므로 후보로만 둔다. 비즈니스 결정 D4-5.

### 7.3 비회원 개인정보 보관 (정합)

- 현행: 비회원 PII 는 `RETENTION_GUEST_PII_DAYS=90` 일 후 스크럽 (`app/config.py:101`, `retention_sweep_service.py` 헤더 2항), 기준일은 세션 종료일.
- 클래스 멤버십에 PII 가 올라가면 **기준일 정의가 필요**: 제안 기본값 = "멤버가 마지막으로 출석한 회차의 종료일 또는 멤버십 종료일 중 늦은 날 + 90일". 정기형(끝 없음)에서도 마지막 출석 기준이라 무한 보관이 되지 않는다. 출석 행 쪽 PII 사본과 같은 스위프 실행 단위에서 함께 스크럽해야 한다 (한쪽만 스크럽하는 실수 방지 — §3.1 단점 A 의 완화책).
- 비회원은 `user_id` 가 없으므로 리마인더·"내 클래스" 노출 범위가 제한된다: 회원 대상 리마인더는 `user_id` 보유 & 비대기자만 (`reminder_service.py:196-218`). 비회원에게 회차 리마인더 메일을 보내려면 수집 목적(리포트 발송) 확장 고지가 필요 → D4-6.
- 비회원 "내 클래스" 노출 범위(`브리프-추가1.md:13`) 제안: 계정이 없으므로 앱 홈이 없고, **입장 자격 보유 기기의 `/class/{id}` 한 화면**(다음 회차 일시·내 출석 요약·본인 리포트 링크)에 한정. 타 멤버 정보는 어떤 경우에도 비노출 (현행 EntryStateResponse 원칙 `schemas/session.py:633-646`, `session_service.py:2008-2012`).

### 7.4 4자리 코드를 클래스 단위로 올릴 때의 쟁점

- 현행 유일성: 활성(미종료·미취소·미숨김·비템플릿) **세션** 사이에서만 유일 — 부분 유니크 인덱스 `uq_sessions_active_access_code` (`session.py:17-34`). 코드 공간 10,000 (`class_code_service.py:27`), 소진 시 503 (`:82-86`).
- 회차마다 코드를 두면: 정기형에서 미래 회차를 미리 만들수록 "활성 세션" 수가 늘어 공간을 소모. 예) 주 1회·4회차 선생성 클래스 100개 → 400개 활성 코드. 클래스 코드 1개/클래스로 올리면 100개. (수치는 예시 산식이며 실제 운영 규모는 `미확인`.)
- 클래스 코드의 수명: 코드는 클래스가 `completed`/`archived`(종료) 되면 무효화 — 현행 "종료·취소 클래스 코드 무효화"(`policy-revision-r4.md:19`)와 같은 규칙을 클래스 status 에 적용. **회차 사이(다음 회차 전)에 코드를 입력하면** 입장 불가가 아니라 "다음 회차 N월 N일 N시에 입장할 수 있어요" 대기 화면 + 멤버십 생성(미리 가입)으로 처리 제안.
- 코드 노출 위험은 D-4로 수용(`policy-revision-r4.md:64`)했지만 **정기형은 노출 기간이 훨씬 길어진다** → 코드 재발급 기능(후속 SDD로 미룬 항목)의 우선순위가 올라간다. 현행 재발급 스크립트 `class_code_reissue.py` 는 일회성 이전용이며 호스트 UI 재발급은 없음(`class_code_reissue.py:1-14`). 결정 후보 D4-8.
- 입장 시도 제한은 현행 `class_code_attempt_service.py`(코드/IP/전체) 재사용 가능 — 내용 `미확인`(이번 조사에서 파일 본문을 읽지 않음, 줄 수 91).

## 8. 동의 — 클래스 가입 1회 vs 회차마다 확인

### 8.1 현행 동의 구성 (분리된 3종 + 레거시)

| 종류 | 저장 | 단위 | 변경 | 근거 |
|---|---|---|---|---|
| ① 수집 고지 확인 (녹음·AI 기록·뇌파·영상, 기록은 N일 후 삭제) | `report_notice_ack_at`/`report_notice_version` | 참여자 행(=회차) | 종료 전 | `session.py:154-155`, `spec.md:23` |
| ② 리포트 반영 선택 (기본 제외) | `report_included` + `report_choice_events` | 참여자 행(=회차) | 종료 전, 변경 시 산출물 재생성 | `session.py:152`, `policy-revision-r4.md:10,21,23` |
| ③ 연구 목적 데이터 활용 동의 (기본 미동의) | `research_consents`(`participant_id UNIQUE`) + `research_consent_events` | 참여자 행(=회차) | 종료 전 본인, 종료 후 플랫폼 관리자 철회만 | `research.py:21-46`, `policy-revision-r4.md:107-111,142` |
| (레거시) `consent_audio`/`consent_eeg` | 불리언 | 참여자 행 | 입장 시 `consent_eeg=True` 고정 | `session_service.py:1828,1886` |

- 정책 제약: ①②③은 **서로 분리 저장**, 어느 선택도 입장·수집을 막지 않는다 (`policy-revision-r4.md:10,111`, `spec.md:23`). 연구 동의는 "삭제 기한 없는 보관"이라 **명시적·별도 체크**여야 하며 가명 ID(이름+생년월일 HMAC)는 세션·클래스를 넘어 같은 사람에게 같은 값 (`policy-revision-r4.md:121`).
- 오래된 프로젝트 규칙: 녹음·밴드는 "세션 시작 전" 동의/opt-in (`.claude/rules/data-privacy.md:11-12`). SDD-209 R4 는 이를 "거부해도 막지 않음 + 리포트 제외"로 개정했다.
- 메모가 명시한 후속 결정: "동의 시점(클래스 가입 vs 회차)" (`docs/클래스-세션-개념-재정의_메모.md:18`).

### 8.3 SDD-209 R4/R5 정책과의 정합 체크 (O3 기준)

| 정책 (근거) | O3 의 처리 |
|---|---|
| 리포트 제외 선택은 기본 제외에서 시작, 명시 선택 시에만 포함 (`policy-revision-r4.md:20`) | `class_members.report_included_default=false` 기본, 가입 화면에서 명시 선택. 출석 행 생성 시 복사 |

| 수집 고지와 리포트 선택 분리, 거부해도 입장·수집 안 막음 (`:10`) | 회차 입장 시 고지 확인은 비차단 |
| 연구 동의는 별도 블록·별도 체크, 기본 미동의, 종료 전 본인 변경·종료 후 관리자 철회 (`:108-110`) | 클래스 단위로 올릴 때 "종료"를 **회차 종료**로 유지(회차 종료 후 그 회차 데이터의 동의는 확정) + 이후 회차 동의 변경은 허용. 즉 효력은 **회차별 스냅샷**(`research_consents` 행은 회차 단위 유지), 입력 UI 만 클래스 가입에서 1회 받아 미래 회차 행에 복사 |
| 가명 ID 는 같은 사람에게 같은 값 (`:121`) | 이미 회차를 넘어 동일 — 클래스 도입으로 변경 없음 |
| 비회원 PII 90일 스크럽 (`policy-revision-r4.md:157`) | §7.3 기준일 재정의 필요 |

→ O3 에서는 **`research_consents`·`report_scope`·내보내기 배치(`research_export_service`)가 모두 회차 단위 그대로**여서 검증이 끝난 SDD-209 코드를 건드리지 않는다. 변경은 "입력 시점·기본값 복사"에 국한. 이것이 기술적으로 가장 안전한 기본값이다.
- 비즈니스 쟁점(D4-1): 연구 동의를 가입 1회로 받아 미래 회차에 자동 적용하는 것이 "명시적 동의" 요건에 맞는지(개인정보보호법상 해석)는 `미확인` — 법무 검토 필요. 안전 대안은 연구 동의만 **회차마다 재확인(기본값=가입 시 선택)** 하는 변형(O3-s).

## 9. 상태 머신 초안

### 9.1 멤버십 (`class_members.status`)

값: `invited`(회원 초대 후 수락 전) / `waitlisted` / `active` / `completed` / `left` / `removed` / `declined`(초대 거절·만료). (정지·휴회 `paused` 는 후속, 이번 범위 제외 — 결정 후보 D4-9)

| 전이 | 조건·트리거 | 주체 | 부수 효과 |
|---|---|---|---|
| (없음) → `invited` | 호스트가 회원 초대 | 호스트 | 알림 `class_invited`; 현행 `invite_participant` 는 **수락 단계 없이 즉시 참여자 등록**(`session_service.py:1527-1535`)이므로 수락 도입은 동작 변경 → D4-10 |
| (없음) → `active` | 코드 입장(정원 여유) / 호스트 직접 추가(수락 생략 정책 시) / 이전(migration) | 본인·호스트·시스템 | 미래 회차 출석 `expected` 생성 |
| (없음) → `waitlisted` | 코드 입장 또는 초대 시 정원 가득, 또는 앞선 대기자 존재 | 본인·호스트 | `waitlist_position` 부여(끝 순번) |
| `invited` → `active` / `declined` | 수락/거절/만료 | 본인·시스템 | |
| `waitlisted` → `active` | 정원 여유 + 순번 | 시스템(잠금 하) | `class_waitlist_promoted` 알림 |
| `waitlisted` → `left` | 대기 취소 | 본인 | 현행 `cancel_waitlist` 와 동치. 행 삭제 금지, 재대기 시 같은 행 복구·끝 순번 (`policy-revision-r4.md:14`) |
| `active` → `left` | 본인 이탈 | 본인 | 미래 출석 `withdrawn`, 정원 반환·대기자 승격 |
| `active` → `removed` | 호스트 제외 | 호스트 | 위와 동일 + 사유 이력 |
| `active` → `completed` | 고정형 마지막 회차 종료 / 클래스 종료 | 시스템 | |
| `left` → `active`(또는 `waitlisted`) | 재가입(코드 재입장/초대) | 본인·호스트 | 같은 행 되살림, 이력 기록 |
| `removed` → `active` | **호스트 복구만** | 호스트 | 코드 자가 재입장은 차단(기본값, D4-7) |
| `completed` → `active` | 정기형으로 이어서 재등록 등 | 호스트 | 별도 정책 — 기본값 금지(새 기수로 재가입) |

**금지 전이**: `removed → (코드로) active`; `completed → left/removed`(종료된 멤버십 이력 불변); `declined → active`(새 초대 필요); `waitlisted → completed`; 클래스가 `archived/ended` 일 때의 모든 신규 전이; `active → invited`; 이력 삭제(append-only).

### 9.2 회차 출석 (`session_participants.attendance_status`)

값: `expected` / `attended` / `absent` / `excused` / `withdrawn` (+ 회차 자체 취소는 세션 status `cancelled` 에서 파생, 별도 값 없음)

| 전이 | 조건·트리거 | 주체 |
|---|---|---|
| (없음) → `expected` | 멤버 활성화 시 미래 회차 생성 / 회차 생성 시 활성 멤버 전원 / 보강 추가 | 시스템·호스트 |
| `expected` → `attended` | 회차 입장 성공(`entered_at` 최초 기록) | 본인 |
| `expected` → `excused` | 사전 결석 통보 (회차 시작 전까지) | 본인·호스트 |
| `excused` → `expected` | 취소 통보 + 회차 정원 여유 확인 | 본인·호스트 |
| `expected` → `absent` | 회차 `completed` 후 `entered_at IS NULL` 확정 | 시스템 |
| `expected`/`excused` → `withdrawn` | 멤버가 `left`/`removed` | 시스템 |
| `absent` ↔ `excused` | 사후 정정(사유 인정) | 호스트만 |
| `absent` → `attended` | 사후 정정(오기록) | 호스트만 + `class_member_events` 성 감사 기록 |

**금지 전이**: `attended` → `absent`/`excused`/`withdrawn`(호스트 정정 이벤트 제외); `withdrawn` → 어떤 값(재가입 시 새 `expected` 행이 아니라 기존 미래 행 복구는 재가입 로직이 담당); 종료(`completed`)된 회차의 `expected` 잔존(확정 훅이 반드시 해소); 회원 본인이 `absent` 로 직접 설정; 취소(`cancelled`) 회차에서 `absent` 확정.
- 현행 `ParticipantLogState`(READY/STARTED/COMPLETED)는 **세션 상태 파생**이며 출석 상태가 아니다 (`session_service.py:2517-2526`). 혼동 방지를 위해 출석 상태는 별도 필드명(`attendance_status`)으로 노출.

## 10. 마이그레이션 개요 (R7 와의 접점만)

1. 기존 `sessions` 1행 → `classes` 1 + 세션 id 유지 (R2 제안 1, `R2-API서비스.md:340`).
2. 기존 `session_participants` 행마다 `class_members` 1행 생성 후 `member_id` 연결. 상태 백필 규칙(제안):

| 기존 플래그 | `class_members.status` | `attendance_status` |
|---|---|---|
| `removed_at` 있음 | `removed` | `withdrawn` |
| `waitlist_cancelled_at` 있음 | `left` | `withdrawn` |
| `is_waitlisted=true` | `waitlisted` | `expected`(회차 대기, 이전 단회 클래스는 회차=클래스이므로 멤버십 대기와 동일) |
| `entered_at` 있음 | 세션 `completed` 면 `completed` 아니면 `active` | `attended` |
| `entered_at` 없음 & 세션 `completed` | `completed` | `absent`(미입장 확정). 단 `entered_at` 도입 전 데이터는 입장 여부를 알 수 없음 (`session.py:164` 주석) → **`absent` 로 단정하지 않고 `expected` 유지 + 마이그레이션 표시** 권장 |
| 그 외 | `active` | `expected` |

3. 입장 자격 JWT(`sub`=참여자 id, `sid`=세션 id)는 출석 행 id·세션 id 가 불변이므로 **기존 발급분이 그대로 유효** (구 앱 호환, 강제 업데이트 없음).
4. 비회원 이메일 초대 행(`session_email_invites`)은 이전 후에도 세션 FK 유지, 신규부터 클래스 단위 테이블 사용(두 경로 공존 기간 필요) — 세부는 R7.
