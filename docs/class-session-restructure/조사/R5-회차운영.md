### 2.4 `is_template` · `run_id` 실제 용도와 복제 재사용 가능성

**`is_template`** (`models/session.py:92-94`)
- 용도: SDD-095 "유형 설정 저장본". 일정·참여코드·WebRTC 룸·채팅방이 없고 일반 클래스 목록에서 제외, `ready` 상태로만 저장. (`:92` 주석, `session_service.py:475-517` `_create_template`, `:623-648` `save_as_template`, `:667-676` `list_templates`)
- 복사 항목(`_COPYABLE_CONFIG_FIELDS` `:447-467`, 13개): `type, custom_type_name, duration_min, max_participants, location_type, location_address, participant_mode, linkband_mode, sfu_enabled, record_audio, record_video, chat_enabled, reminder_offsets`. **복사 안 함**: 일정·상태·코드·룸·`run_id`·참여자.
- 제외 필터: `is_template.is_(False)` 조건이 backend/app **20곳**(파일별: agent_policy 5, session_service 3, class_code_service 2, dashboard_service 2, reminder_task·agent_checkin·agent_counselor_service·agent_reminder·class_code_reissue·org_public_service·report_service·retention_sweep_service 각 1; `grep -rn is_template backend/app | grep 'is_(False)'`) + `if …is_template` 분기 4곳(`reminder_service.py:344,449`, `agent_reminder.py:73`, `session_email_invite_service.py:105`) → 클래스/상위 개념을 도입해도 **템플릿 행은 "회차가 아닌 세션 행"으로 남아 필터를 계속 요구**한다.
- API: `GET /sessions/templates`(`api/v1/session.py:179`), `POST /{id}/duplicate`(`:288`), `POST /{id}/save-as-template`(`:314`).
- 프론트: 호출 래퍼는 `lib/api/session.ts:254-271`에 있으나 **"템플릿으로 시작" 입구는 만들기 마법사에 없음**(`listSessionTemplates`·`createSessionFromTemplate` 사용처 grep 0건). 실제 사용은 ① 생성 완료 화면 "템플릿 저장"(`CreateWizardContainer.tsx:149`) ② 상세의 복제·템플릿 저장(`SessionDetailPage.tsx:243,258`) ③ 플레이어의 복제(`ClassPlayerPage.tsx:1414`).

**`run_id`** (`models/session.py:38-42`)
- 용도: SDD-028 "경량 SessionRun". 생성 시 `run_id = 자기 id`(`session_service.py:407-410`, 복제 `:563-564`), `POST /{id}/new-run`(`api/v1/session.py:272`, `start_new_run :1126-1146`)이 **같은 행의** `run_id`만 새 UUID로 교체. 완료·취소 세션은 400.
- 소비처: 직렬화 필드(`:125`, `schemas/session.py:157`)뿐. 조회·집계·그룹핑에 쓰는 코드 없음(`run_id` grep 결과는 정의·생성·직렬화·`retention_sweep`의 무관한 `run.id`뿐). 프론트 호출 **0건**(`grep new-run|startNewRun frontend/src`).
- 결론: 회차(여러 행)가 아니라 "한 행의 재실행 표식". **회차는 `sessions` 행 자체**이고 `seq`를 새로 둬야 한다. `new-run` 은 구 앱 호환을 위해 응답만 유지하고 의미를 새로 부여하지 않는 것을 기본값으로 제안(폐기 여부는 기획.md).

| `_COPYABLE_CONFIG_FIELDS` 13개 | O | 클래스 설정(방식·정원·밴드·녹음·채팅·리마인더)과 동일 항목. 클래스 단위 복사 대상으로 그대로 승계 |
| `_clone_session_config` (코드·룸 신규 발급, `_add_session_with_code_retry`) | △ | 세션 1행 복제. 클래스 복제에서는 "클래스 행 1개 + 회차 N행" 생성기가 필요 |

| 템플릿 목록·저장 API | △ | 템플릿은 세션 행이라 클래스 템플릿이 필요하면 `classes.is_template` 류 새 플래그가 필요(또는 템플릿 개념을 "종료된 클래스 복제"로 대체) |

## 3. 데이터 초안 (R4·R9 와 맞춘 R5 관점 최소 항목)

```
classes            : id, host_org_id, title, kind('meditation'), schedule_kind('fixed'|'ongoing'),
                     planned_sessions(int NULL; fixed 만), recurrence_rule(JSONB), assignment_rule(JSONB),
                     rolling_window_weeks(int default 4; ongoing 만), ongoing_ends_on(date NULL),
                     status('draft'|'active'|'completed'|'archived'), access_code(4자리, R4), 클래스 설정(정원·밴드·녹음 …)
sessions (회차)    : (기존 컬럼 유지) + class_id FK, seq int, session_kind('regular'|'makeup'),
                     makeup_for_session_id FK NULL, host_id(=진행 강사, R9 유지)
                     UNIQUE(class_id, seq) ; 같은 class_id 안 (scheduled_at) 중복은 허용(보강 동시간 가능성 낮음 → 앱 검증)
```
`recurrence_rule` 예: `{ "weekdays": [1,3], "time": "19:00", "duration_min": 60, "start_date": "2026-11-03", "interval_weeks": 1, "tz": "Asia/Seoul", "skip_dates": ["2026-12-25"] }`
`assignment_rule` 예: `{ "mode": "rotate", "instructors": ["uidA","uidB"], "weekday_map": null }` (`mode` ∈ `all_one | rotate | by_weekday | per_session`)
- 규칙은 **저장**한다(정기형 롤링 생성·"지난 기수 그대로"가 재사용). 이미 생성된 회차에는 규칙을 소급하지 않는다(기본값; 변경 화면에서 "이후 회차에만 적용" 선택).
- `seq` 는 취소돼도 재사용하지 않는다(알림 딥링크·리포트 참조 안정). 화면의 `N회차` 는 `seq` 를 그대로 쓰고, 진행률 `3/8` 의 분모는 "취소가 아닌 정규 회차 수"로 계산한다(기본값).
- 상담 쪽 상위 개체와의 관계는 §7.5(`sessions` 가 `class_id` XOR `relationship_id` 를 가진다는 R5 관점 제안).

## 4. 고정형 · 정기형 생성 UX·데이터 초안

### 4.1 고정형 (총 N회)
- 입력: 시작 날짜, 요일(복수), 시작 시각(5분 단위), 소요(5분 단위), 총 횟수 N, 건너뛸 날짜(선택), 리마인더.
- 서버: `POST /classes`(클래스+회차 N행을 **한 트랜잭션**) — 사전 확인용 `POST /classes/preview-schedule`(저장 없음, 회차 목록+충돌 반환)을 같은 규칙 함수로 호출한다. R2 §3.3 의 `POST /classes/{id}/sessions/bulk` 는 "생성 후 회차 추가" 용으로 유지.
- 알고리즘(제안): 시작일부터 날짜를 하루씩 전진, `weekday ∈ weekdays` 이고 `skip_dates` 가 아니면 후보. `interval_weeks>1` 이면 기준 주 시작(월요일)에서 `(주 차이 % interval_weeks == 0)` 만 채택. 후보가 N개 차면 중단. 모두 `Asia/Seoul` 벽시계 시각으로 만든 뒤 UTC 로 저장(`scheduled_at` 은 aware datetime).
- 상한(기본값): N ≤ 52, 시작일 ≤ 오늘+365일, 시작 시각 07:00~22:00(현행 `class-wizard.ts:81-82` 유지). 근거: 현행 한도 문서·코드에 N 상한이 없어 임의 기본값이며 결정 아님.
- 공휴일: 한국 공휴일 데이터 소스가 코드에 **없음**(`미확인`). 기본값은 자동 건너뛰기 없음 + 표에서 해당 회차를 직접 이동/제외, "건너뛸 날짜" 입력 제공.
- 코드 공간: 회차마다 코드를 발급하면 8회 = 8코드 점유. **클래스 단위 코드 1개**로 올리는 것이 전제(R4 §7.4). 회차 행의 `access_code` 는 이전 호환용으로만 유지.

### 4.2 정기형 (끝 없음) — 롤링 생성
- 이유: 리마인더 ETA 예약(`schedule_session_reminders`), 충돌 검사, 회원 일정/홈 노출, 4자리 코드 공간이 모두 "회차 행이 이미 있음"을 전제 → 무한 생성 불가.
- 기본값: 항상 **앞으로 4주(`rolling_window_weeks=4`)** 분 회차를 유지한다. 방법 2중: ① 클래스 상세 진입 시 부족하면 on-demand 보충 ② 일 1회 cron `generate_class_sessions_cron.py`(기존 `*_cron.py` 패턴, `sweep_session_reminders_cron.py` 와 같은 등록 방식). 멱등: `UNIQUE(class_id, seq)` + "마지막 seq+1부터 규칙 투영" 계산.
- 생성 시 강사 배정: 저장된 `assignment_rule` 적용(`rotate` 는 `(seq-1) % 명수`), 규칙에 비활성 강사가 포함돼 있으면 해당 회차는 **미배정(`needs_reassign`, R9 §6.0)** 으로 만들고 클래스 소유 강사에게 알림.
- 롤링 생성 중 충돌: 충돌 회차도 만들되 충돌 표시(소프트). 상담사 홈에 "이번 주 겹치는 일정 N건" 배너 후보.
- 종료: 기본값은 상담사가 "이번 회차를 마지막으로 마쳐요" 또는 종료일 지정(`ongoing_ends_on`). 종료 시 미래 `scheduled` 회차는 취소(회원 알림), 이후 생성 중단. (정기형 종료 조건은 결정 후보 R5-D2)
- 리마인더: 회차가 생성되는 시점에 ETA 예약. 일정 변경은 기존 revoke→재예약 경로(`session_service.py:869-881`) 재사용.

### 4.3 일괄 생성과 리마인더·알림 폭주 방지
- 8회 일괄 생성 알림은 **회차마다가 아니라 클래스 단위 1통**("MBSR 봄 클래스에 초대됐어요 · 11/3부터 8회"). 현행 `session_invited` 알림은 세션 단위이므로(`session_service.py:1512,1545`) 클래스 단위 새 이벤트가 필요(R2 §6.1).
- ETA 태스크 수 = 오프셋 수 × 회차 수(고정형 8회×2 = 16, 브로커 부담 작음). 일정 일괄 이동 시 revoke 도 회차 수만큼 필요 → 일괄 이동 API 는 서버가 루프를 돈다(클라이언트 N회 호출 금지).

## 6. 시간 충돌 검사 — 클래스·상담 통합 제안

### 6.1 제안 (기술 기본값)
| 항목 | 제안 |
|---|---|
| 단위 | **(진행 강사 `host_id`, 시간 구간)**. 명상 회차·상담 회차가 같은 `sessions` 테이블을 쓰는 한 현행 쿼리가 이미 통합 검사다. 상담이 별도 테이블로 가더라도 "진행 강사 시간표"는 `sessions` 한 곳에서 읽는다 |
| 대상 상태 | 현행 `ACTIVE_STATUSES` 유지(`ready` 는 일정 없음이면 제외) |
| 일괄 | `detect_conflicts_bulk(host_id, intervals[], exclude_session_ids)` — **한 번의 범위 쿼리**(`min(start)-1일 ~ max(end)+1일`)로 호스트 활성 회차를 로드해 메모리에서 비교 + 요청 안 신규 회차끼리도 비교. 반환 항목에 `index`, `kind`(`class`/`counseling`), `parent_title`(클래스명/내담자명), `session_seq`, `scheduled_at`, `duration_min` |
| 쿼리 | 파이썬 전량 루프(`session_service.py:315-324`) → SQL 범위 조건 `scheduled_at < :end AND scheduled_at + duration_min * interval '1 minute' > :start`, 인덱스 `(host_id, scheduled_at)` 추가 |
| 강도 | 현행 소프트(`force`) 유지 + **열기/시작 시점 보조 검사 신규**: 같은 진행 강사의 다른 회차가 `open/in_progress` 이면 `다른 일정을 진행 중이에요. 그 일정을 먼저 마쳐 주세요.` 경고(차단 여부는 결정 R5-D4). "한 사람이 동시 진행 불가"는 이 두 지점으로 구현 |
| 프론트 | 프론트 자체 계산(`findScheduleConflict`)을 폐기하고 서버 `preview-schedule` 응답을 표시(권위 단일화). 현행은 서버와 프론트가 따로 계산해 어긋날 수 있음 |
| 수정 시 | 진행 강사 변경 → 새 강사 기준 재검사(현행 `:787` 은 `s.host_id` 고정이라 수정 필요, R9 §3.2) |
| 장소 충돌 | 정보성 경고(같은 기관·같은 주소 문자열·시간 겹침), 차단 안 함. 룸 엔티티는 후속(R9 D-R9-14) |
| 내담자(회원) 충돌 | 상담 마법사에서 **같은 상담사의 다른 회차**와 겹치는 경우만(=진행 강사 충돌과 동일). 타 상담사·타 클래스와의 겹침은 노출하지 않음(개인정보·타 상담 존재 노출 위험). 회원 충돌 일반 검사는 후속 |
| 버퍼(회차 사이 이동·정리 시간) | 기본값 0분(검사는 실제 구간만). 필요 여부는 결정 R5-D5 |

### 6.2 화면 표시 (해요체)

### 7.2 회차 일괄 편집 표 (S3 및 클래스 상세 "회차" 탭 공용)

| 열 | 입력 방식(드래그 없음) |
|---|---|
| 선택 | 체크박스(헤더 전체 선택) |
| 회차 | `1회차 … 8회차`, 보강은 `보강`, 취소는 `취소` 칩 |
| 날짜 | 날짜 입력 + `−1일/+1일` 버튼 |
| 시작·소요 | 5분 스텝퍼 |
| 방식·장소 | 온라인/오프라인 토글, 오프라인 주소(클래스 기본값 상속) |
| 진행 강사 | 셀렉트(클래스 강사만) |
| 충돌 | `겹쳐요` 칩(탭하면 사유 시트) |
- 일괄 동작 바(선택 시 노출): `시각 한꺼번에 바꾸기` · `강사 한꺼번에 바꾸기` · `한 주 밀기` · `선택 회차 취소`. 각 동작은 미리보기(변경 전→후)를 보여 준 뒤 `적용` 으로 저장.
- 행 편집 범위 선택: `이 회차만` / `이 회차부터 모두`(기본 `이 회차만`).
- **모바일**: 표 대신 회차 카드 목록 + `회차 편집` 바텀 시트(같은 필드, 같은 검증 함수). 일괄 동작은 상단 `선택` 모드. 근거: R3 §10 기본값(카드+시트), 몰입형 마법사의 390×844 스크롤 0 기준(`designs/class-flow-redesign/기획.md:163-166`)은 **이 단계만 회차 목록 영역 내부 스크롤 허용**으로 정의해야 한다(셸형 목록 영역 내부 스크롤 선례 `specs/sdd-209-class-flow-redesign/spec.md` 범위 절) — 기술 기본값.
- 모바일 상담사 사용: 현행 상담사 셸·마법사는 모바일 합격 기준 있음(`AppShell.tsx:96,243`, `host-flow-create.css`, `e2e/class-flow/fit.mjs`), 실기기 검증은 **미확인**(`specs/sdd-209-class-flow-redesign/summary.md:37`). 회차 표·일괄 편집은 신규라 모바일 합격 기준에 포함해야 한다.

### 7.3 지난 기수 그대로
- S0 에서 클래스 선택 → S1 값 채움(이름 뒤에 `(복사)` 붙이지 않고 이름 입력란 포커스), S2 는 **원본 `recurrence_rule` 투영**: 시작 날짜만 새로 입력, 요일·시각·횟수·소요 유지. S3 강사는 원본 `assignment_rule` 승계, 비활성 강사는 `미정`으로 표시.
- 멤버·초대 복사는 기본 꺼짐(`지난 회원을 함께 초대해요` 토글, 기본 해제; R5-D7). 4자리 코드는 새로 발급.
- 오류: 원본 강사가 이미 퇴사/비활성이면 `{이름} 강사는 더 이상 이 기관에 없어요. 다른 강사를 정해 주세요`.

## 8. 새 상담 세션 마법사 UX 초안

전제(브리프-추가2): 상담 = 내담자 1명 + 상담사 1명인 **상담 관계** 아래의 상담 세션(회차). 정원·대기열·강사 번갈아·비회원 4자리 코드 입장 스텝퍼 UI 없음. 엔진(진행 화면 SDD-208, 입장 전 SDD-209)은 공유.

### 8.1 설계 원칙
- **3단계 + 완료**: ① 누구와 만나요? → ② 언제, 어떻게 만나요? → ③ 확인. (명상 4단계보다 짧음)
- 이미 관계가 있는 내담자에게서 시작하면(내담자 상세·상담 상세의 `다음 상담 잡기`) ①을 건너뛴다 → 2단계.
- 현행 마법사의 항목 중 제외: 유형 4종 선택 화면(상담 유형은 ②의 칩 하나), 인원(1:1 고정), 정원, 대기열, LINK BAND·영상은 `고급 설정` 접이식(기본값 적용), 이메일 CSV 초대(해당 없음).
- 진행 중 이력: 같은 내담자의 지난 회차 `일시·방식·소요`를 ②에 prefill(요일·시각·방식·소요 그대로 +1주).

### 8.2 화면별 입력·검증·오류 문구

### 8.4 비회원 내담자 (브리프-추가2 확정 추가 반영, R4 §7 과 정합)
- **식별**: 상담사가 이름+이메일로 관계를 만든다. 비회원 정보는 `counseling_relationships.guest_*`(개인정보 스위프 대상, `RETENTION_GUEST_PII_DAYS=90` 기준일은 마지막 상담 종료일 — R4 §7.3 규칙 적용)에 두고 회차 참여 행(`session_participants`)에는 FK만 둔다.
- **입장·본인 확인**(기본값 제안): **관계 단위 4자리 코드** + 상담사 대기실 승인. 근거: 1:1 상담은 대기실에서 상담사가 사람을 직접 확인할 수 있고(비용 낮음), SDD-209 R5 의 "코드 소지만으로 입장"(`policy-revision-r4.md` 정책 5)은 그룹용 가정이라 1:1 상담에는 코드 노출 위험(D-4 수용 범위)보다 민감도가 높다. 승인 UX 는 SDD-209 가 "후속"으로 남긴 항목이므로 **신규 작업**.
- **재방문**: 같은 관계 코드를 쓰면 매 회차 같은 관계로 이어진다(회차마다 새 비회원 행이 생기는 R4 §7.2 문제가 상담에서는 관계 단위 코드로 해결). 코드 분실·재발급은 상담사 화면에서 `코드 다시 만들기`(기존 코드 즉시 무효).
- **코드 공간**: 4자리 코드는 현재 활성 세션 사이 부분 유니크 인덱스(`models/session.py:17-34`)로 유일 — 관계 코드가 별도 테이블이면 `/join` 입력 한 곳에서 **클래스 코드와 관계 코드를 구분 없이 조회**하므로 통합 유일성 보장이 필요(공간 10,000 공유, `class_code_service.py:27`). 기술 기본값: 코드 발급을 단일 서비스로 모으고 "활성 클래스 코드 ∪ 활성 관계 코드" 집합에서 중복 제외.
- **리포트 전달**: 입력 이메일로 자동 발송(`policy-revision-r4.md` R5-A 정합, 승인 후 발송 정책 유지). 오발송 가능성은 SDD-209 가 수용한 잔여 위험.
- **회원 가입 시 연결**: 가입 이메일이 관계의 `guest_email` 과 일치하면 가입 직후 `이전 상담을 내 계정에 연결할까요?` 확인 → 승인 시 `client_user_id` 채움. 이메일 일치만으로 자동 연결하지 않고 사용자 확인 + 가입 이메일 인증 완료(`auth.py:287,341,547` 이메일 인증 흐름 존재) 상태에서만 허용(기본값).

### 8.5 마법사 진입점
`/counseling/new`(상담 메뉴 `새 상담 시작`), `/counseling/:relationshipId` 의 `다음 상담 잡기`(A 건너뜀), 홈 빠른 액션. 현행 `/sessions/new` 는 명상 마법사 별칭으로 유지(R3 §11).

## 9. 상담 관계 흐름 — 세션 계속 추가·종결·재개

### 9.1 현행에서 쓸 수 있는 것
- `client_counselor_links`(`client_id`·`counselor_id` 둘 다 NOT NULL, UNIQUE(`client_id,counselor_id`), `status` `active/ended`, `matched_at`, `ended_at`, `memo`) — `models/client_counselor_link.py:13-24`.
- `ended` → `active` 재활성 코드가 이미 있다: 상담사 코드로 다시 연결하면 `status='active'`, `ended_at=None`, 채팅방 재보장(`client_portal.py:160-172`). **종결·재개의 선례는 있으나 이력(몇 번 종결/재개)은 `ended_at` 한 컬럼뿐.**
- 한계: `client_id` NOT NULL → **비회원 상담 관계를 표현할 수 없음**, 한 쌍당 1행이라 "종결 후 새 관계로 시작"을 같은 쌍에서 표현할 수 없음(UNIQUE). 링크는 "채팅·권한 연결"이고 상담 세션이 하나도 없어도 존재 가능(`client_portal.py:150-188`).
- 기본값 제안(R5 관점, 모델 확정은 기획.md): **링크는 그대로 두고 상담 관계(`counseling_relationships`)를 새 상위 개체로 둔다.** 회원 내담자면 관계 생성 시 링크(active)를 보장(채팅·기존 권한 재사용), 비회원이면 링크 없이 관계만. 장점: 비회원 허용, 종결/재개 이력 분리, 링크 의미(연결) 보존. 단점: 개체 1개 추가, 링크↔관계 동기화 규칙 필요. 대안(링크 확장: `client_id` NULL 허용 + UNIQUE 완화)은 기존 사용처(`chat_service.py` 3곳, `client_portal.py`, `agent_*`, `auth.py`)에 영향이 퍼져 비권장.

```
counseling_relationships : id, counselor_id, client_user_id(NULL=비회원), guest_name, guest_email(스위프 대상),
                           title(표시명, 기본 "{내담자} 상담"), status('active'|'ended'), started_at, ended_at, ended_by,
                           access_code(4자리, 활성 시), organization_id, record_consent_state/version/at(§8.2 C)
relationship_events      : relationship_id, from_status, to_status, actor_user_id, reason, created_at   -- 종결·재개 이력 append-only
sessions.relationship_id : FK NULL ; CHECK (num_nonnulls(class_id, relationship_id) = 1)
```
