# 기획 상세 — 리포트 (클래스 단위 관리 · 추이 · 상담 리포트)

> 2026-10-17 · Phase 1(서비스 기획) 초안 · 승인 대기. 본문 `기획.md` §8 Phase 5 의 상세 편.
> 근거: `조사/R6-리포트분석.md`(현행 구조·API·권한·원칙 인용·`narrative_cache`·강사별 통계), `조사/R2-API서비스.md` §7(생성 체인), `조사/R10-상담분리.md` §5·§7(상담 리포트 정책·자동 승인), `조사/R4-회원참여모델.md` §8(동의).
> 확정(브리프-추가1 §B-3): **리포트는 클래스 단위로 관리** — 클래스 상세에서 회차별 리포트 목록·승인 상태·발송 상태를 한눈에 보고 일괄 처리(승인/발송/재생성), 클래스 단위 추이·출석 요약. 회원별 리포트 열람 권한은 강사가 교체돼도 유지, 작성자/승인자는 세션 진행 강사와 연결. 리포트 원칙(점수 환원·종합점수·순위 금지, 서사 + 변화량만, 회원용/상담사용 구분)은 유지.

## 1. 한 장 요약

1. 리포트 행 키는 **회차(`session_id`) × 참여자(`participant_id`) × 유형(`counselor`/`client`)** 이다. 이 키를 바꾸지 않고 **클래스는 "묶음 뷰"로만 얹는다**(`sessions.class_id` 조인; 리포트 테이블에 `class_id` 를 중복 저장하지 않음).
2. 현행 리포트에는 **작성자·승인자 컬럼이 없고** 승인은 암묵적으로 `sessions.host_id == 호출자` 일 때만 가능하다. "세션 진행 강사 = `host_id`" 매핑이면 현행 규칙이 그대로 "진행 강사가 승인"이 된다. 승인 기록을 위해 `reports.approved_by_user_id`·`approved_at`(nullable, 추가형)을 더한다.
3. 승인은 현재 **호스트 소유 전체 일괄**(`POST /reports/approve-all`)만 있고 회차·클래스 범위를 지정할 수 없다. 재생성·메일 재발송은 **단건**뿐이다. 클래스 단위 일괄 처리는 **신규**이며, 기존 단건 함수를 건별로 호출하는 얇은 오케스트레이터로 만든다.
4. 회원 열람은 강사와 무관(참여자 행 + 소유자 본인) → **강사가 교체돼도 유지**된다. 단 참여자 행이 제거·숨김되면 사라지므로(코드 해석) 이탈은 멤버십 status 로만 표현한다.
5. 클래스 추이는 **회차마다의 세션 내 변화 방향·변화량을 나열**한다. 회차 간 비교용 개인 기준선이 현재 없고, 수준값(정규화 점수)을 쓰면 종합점수화이므로 MVP 에서 제외한다.
6. `narrative_cache`(전역 6자 패턴 캐시)와 정규화 베이스라인은 **클래스와 연결할 것이 없다**. 클래스 서사는 캐시를 쓰지 않는 결정론 템플릿이다.
7. 강사별 통계는 **만들지 않는다**.
8. 상담 리포트는 별도 정책을 가진다: 상담사 승인 필수(자동 승인 영역별 분리, 상담 기본 off), 기본 **포함**(고지 확인), 센터 관리자는 메타만.

## 2. 현행 구조 (사실)

### 2.1 코드 지도·생성 흐름

회차 종료(`end`) → 영상/오디오 finalize → STT → 요약 → 리포트 생성 Celery chain(`PipelineOutbox` 로 발행 보장). 태스크는 모두 `session_id` 한 개를 받아 `SessionRecord` 1건과 `Report` 를 만든다 → **회차 단위로 정확히 맞아 체인 자체는 변경 없음**(`R2 §7.1`). 추가로 필요한 것은 회차 리포트 완료 후 클래스 추이 갱신 훅(신규, 비동기).

### 2.2 `reports` 상태·작성자·승인자 (`R6 §2.4`)

| 질문 | 현행 답 |
|---|---|
| 상태 | 승인축 4값(`pending_analysis`/`pending_review`/`completed`/`error`) × 생성축 4값(`pending`/`processing`/`ready`/`partial`) |
| "초안" | 별도 값 없음 — `pending_review` 가 검토 대기(초안 단계), 코멘트는 이 상태에서만 저장 |
| "발송" | 값 없음 — 승인 시 `sent_at`(최초 1회) 설정 + `report_ready` 인앱 알림 + (신청 시) 메일 큐. 참여자 메일 상태(`report_email_status`)와 조합 |
| 작성자 | AI 가 생성(컬럼 없음). 코멘트 작성자도 컬럼 없음(`content.counselor_comment` 문자열만) |
| 승인자 | 컬럼 없음. `approve_report` 는 `session.host_id == 호출자` 일 때만 허용(센터 관리자도 403) |
| 승인 시각 | `sent_at` 이 사실상 승인 시각 |
| 승인 알림 | `report.user_id` 에게. **counselor 리포트를 승인하면 호스트 본인에게 "리포트가 도착했습니다"가 간다**(노이즈 가능) |
| 자동 승인 | **호스트 개인 설정**(`users.auto_approve_report`) — 회차 호스트가 바뀌면 같은 클래스 안에서 회차마다 동작이 달라짐 |

### 2.3 API (리포트 15개)와 일괄 한계

| 경로 | 권한 | 일괄 |
|---|---|---|
| `GET /reports/view`, `view/pdf` | 공개(토큰) | — |
| `GET·PATCH /reports/auto-approve` | counselor·org_admin | — |
| `POST /reports/generate/{session_id}` | 서비스에서 host 일치 | **단건**(재생성) |
| `GET /reports` | 로그인(상담사 = 호스트 회차 전체 + 미생성 합성 행, 센터 관리자 = 기관 호스트 전체, 회원 = 본인) | 페이지네이션 |
| `POST /reports/approve-all` | counselor | **호스트 전체 범위, 지정 불가** |
| `GET·PUT /reports/{id}`, `/pdf`, `PATCH …/comment`, `POST …/comment-draft` | counselor·org_admin | — |
| `POST /reports/{id}/approve` | 서비스에서 host 일치 | **단건** |
| `POST /reports/{id}/resend-email` | counselor·org_admin(소속 기관) | **단건** |

- `approve_all_reports` 는 요청 안에서 건별 `approve_report` 를 순차 호출한다(각 건 커밋 + 메일 예약 + AI 비서 훅). 8회 × 10명 = 90건 규모면 HTTP 시간이 선형 증가해 "HTTP 200ms 이내" 원칙과 충돌 가능(미측정, `R6-X6`). 응답은 `{approved: n}` 뿐이라 **실패·건너뜀 내역을 알 수 없다**.
- 상담사 목록은 이미 **회차 단위 합성 행**(리포트 없는 완료/진행 중 회차를 "생성 실패/생성 중"으로 표시)을 지원하므로 클래스 리포트 표의 "미생성 회차" 행에 재사용한다.

### 2.4 열람 권한 (현행)

| 대상 | 판정 |
|---|---|
| 상담사(호스트) | `session.host_id == 사용자` |
| 센터 관리자 | 호스트의 `org_id == 본인 org_id` — 조회·수정·메일 재발송 가능, **승인·생성 불가** |
| 회원 | 그 회차 **참여자 행 존재**(ORM 전역 필터로 `removed_at`·`waitlist_cancelled_at` 행은 제외) + client 리포트는 소유자 본인만(IDOR 방어). counselor 리포트는 회원 403 |
| 비회원 | 메일 토큰(`report_view`, 7일)으로만, 승인(completed) 후에만 발송 |

**미확인(위험)**: 회원 `list_reports`·`get_report` 모두 `status` 필터가 없다. `pending_review` 회원 리포트가 승인 전에 회원에게 보일 수 있는지 코드만으로는 단정할 수 없다 → 클래스 리포트 관리(승인 게이트가 핵심)의 전제이므로 **Phase 0 에서 실제 호출로 검증하고 필요 시 수정**한다(`R6-X1`).

## 3. 클래스 단위 리포트 관리 (신규)

### 3.1 클래스 상세 → `리포트` 탭

표 1행 = 회차 1개.

| 열 | 내용 | 출처 |
|---|---|---|
| 회차 | `3회차` · 일시 · 진행 강사 | `sessions` |
| 회차 상태 | 완료/진행 중/예정/취소 | `sessions.status` |
| 대상 | 리포트 반영 N명 / 출석 M명 (제외 K명) | `report_included` · 출석 |
| 생성 | 준비됨 a · 만드는 중 b · 일부만 c · 실패 d | `generation_status` / `status=error` |
| 승인 | 검토 대기 x · 승인 y (+ 상담사용 승인 여부) | `reports.status` |
| 발송 | 앱 노출 y건(`sent_at`) · 메일 성공 s / 실패 f / 대기 w | `sent_at`, `report_email_status` |
| 작업 | 보기 · 승인 · 재생성 · 메일 재발송 | |

- 행 펼침 = 회원별 client 리포트(이름·상태·메일 상태·열람 여부) + 상담사용 리포트 1건. 결석 회원은 "결석"으로 **리포트 없음 표기**(0점·빈 리포트를 만들지 않음).
- 상단 일괄 동작: `대기 중인 리포트 모두 승인` · `실패한 리포트 다시 만들기` · `메일 다시 보내기`. 승인은 회원 앱 노출 + `report_ready` 알림 + 신청자 메일 + AI 비서 대화 시작 훅을 일으키므로 확인 모달에 **대상 건수·메일 발송 예정 수**를 보여준다.
- 확인 모달 경고: 코멘트가 필요한 회원 리포트(`pending_review` + 코멘트 없음)를 일괄 승인하면 코멘트 없이 나간다 → `코멘트가 없는 리포트가 4건 있어요. 그대로 보낼까요?`. 재생성 문구: `다시 만들어도 이미 승인한 리포트는 승인 상태가 유지돼요`(승인 취소 없음).
- 승인 상태 점검 화면의 센터 관리자 노출은 **클래스 단위 건수만**(성과가 아니라 처리 현황 — `D-41`).

### 3.2 API (기본값, `/classes/*` 와 결합)

| # | 메서드 경로 | 설명 | 비고 |
|---|---|---|---|
| A1 | `GET /classes/{id}/reports` | 위 표의 데이터(회차별 집계, 건별 목록은 `?session_id=` 지연 로딩) | 읽기. 클래스 강사. 회원 호출 불가 |
| A2 | `POST /classes/{id}/reports/approve` | body `{session_ids?, report_ids?, only:"pending_review"}`, 미지정이면 클래스 전체 | 응답 `{approved, skipped[], failed[{id,reason}]}`. **건별 멱등**(이미 `completed` 는 skipped) |
| A3 | `POST /classes/{id}/reports/regenerate` | body 동일 + `scope: counselor/client/all` | **Celery 큐 적재 후 202**(LLM 호출 포함 → 동기 호출 금지 규칙). 진행은 기존 `report:progress` WS 이벤트 재사용 |
| A4 | `POST /classes/{id}/reports/resend-email` | 메일 신청자 중 `failed`/NULL 대상 일괄 재발송 | 기존 `enqueue_report_email` 재사용, 큐 적재 후 202 |
| A5 | `GET /classes/{id}/reports/summary` | 클래스 추이·출석 요약(상담사용, §5) | |
| A6 | `GET /me/classes/{id}/progress` | 회원용: 내 출석 + 내 회차별 변화 흐름 + 내 리포트 링크 | 본인 데이터만 |

- 구현 원칙: 새 서비스 함수가 기존 `approve_report`·`generate_report`·`enqueue_report_email` 을 **건별로 호출**하는 오케스트레이터. 기존 단건 API 와 `POST /reports/approve-all` 은 **호환 유지**(범위 미지정 = 현행 동작)하되 내부를 클래스/회차 필터를 받는 공통 함수로 리팩터.
- 승인 주체 검사: 현행 `session.host_id == 호출자` 를 "호출자가 해당 회차 진행 강사이거나 클래스 **주강사**(대행)"로 넓힌다. 이유: 여러 회차를 한 번에 처리하려는 요구(B-3)와 맞고, 서로 다른 강사의 회차가 섞인 클래스에서 한 강사가 타 강사 회차를 승인하는 길이 열리지만 `approved_by` 로 책임이 기록된다. R6 은 "클래스 강사 누구나"를 제안했으나 보조 강사가 승인하면 책임 소재가 흐려지므로 R9 의 "진행 강사 + 주강사"를 채택한다(`D-36`, `기획.md` §5 충돌 정리).
- 센터 관리자는 승인 불가를 유지한다(현행과 동일).

## 4. 소유·승인 모델과 강사 교체 (`R6 §4`)

### 4.1 기본값

1. 리포트 행 키 불변. 클래스는 조인으로만 묶는다.
2. `reports.approved_by_user_id`, `reports.approved_at` 추가(nullable). 기존 `sent_at` 은 호환 유지(= 앱 노출 시각). 기존 `completed` 행의 승인자는 **NULL 유지**(사실을 지어내지 않음).
3. 코멘트 작성자: `content.counselor_comment_by`(JSONB 내부 키, 마이그레이션 없음). 코멘트는 `pending_review` 에서만 저장되는 현행 규칙 유지.
4. counselor 리포트 `user_id` 는 승인/열람 판정에 쓰지 않는다(현행도 `session.host_id` 로 판정). 알림 수신자만 `user_id` → **현재 진행 강사**로 바꾼다.
5. 자동 승인: 강사 개인 설정 유지 + **영역별 분리**(명상/상담), 상담 기본 off. 클래스 상세에 "이 클래스는 자동 승인 켜짐" 표시(`D-37`).

### 4.2 강사 교체 시 영향

| 상황 | 현행 코드 동작 | 영향·제안 |
|---|---|---|
| 완료 **전** 회차의 진행 강사 교체 | 리포트는 종료 시 `s.host_id`(= 새 강사)로 생성·자동 승인 판정 | 정상. 자동 승인 여부가 새 진행 강사의 개인 설정을 따름 → 표에 표시 |
| 완료 **후** 진행 강사 정정 | 목록(`Session.host_id` 기준)은 새 강사에게 이동, 승인·수정·생성도 새 강사만 가능. 구 강사는 403 | 승인 대기 건의 소유 이동은 자연스러움. **이미 승인된 리포트의 "승인자 귀속"은 `approved_by` 로 보존**해야 정정 후에도 이력이 남음. 정정은 승인 전에만(`D-24`) |
| 클래스 강사 추가/제거 | 개념 없음 | 제거된 강사가 과거 회차 호스트였다면 그 회차 리포트는 새 진행 강사 지정 전까지 승인 주체가 없음 → "진행 강사 정확히 1명" 불변식이 승인 가능성을 보장 |
| 강사 계정 비활성/퇴사 | 호스트 비활성이면 세션 조작 경로가 막히지만 리포트 서비스의 호스트 검사에는 활성 검사가 없음 | 승인 대기가 있는 회차의 진행 강사 변경 경로 필요 — 승인권 자동 이관 + 새 진행 강사에게 "승인 대기 N건" 알림(`D-38`) |
| **회원 열람** | 강사와 무관 | **강사 교체와 무관하게 유지** — 요구(B-3) 충족 |
| 참여자 행 제거/숨김 | ORM 전역 필터로 참여자 행이 사라져 보임 → 회원 상세 403, 목록 제외 가능 | 이탈 회원의 과거 리포트 유지: 회원 본인 client 리포트는 `Report.user_id` 기준으로 열람 유지, 제거는 `removed_at` 대신 멤버십 상태로만 표현(`D-12`) |

## 5. 클래스 단위 추이·회차 비교·출석 요약 — 범위

### 5.1 현행으로 가능한 것과 없는 것

- 가능: 회차 1개 안의 전반→후반 변화량(6지표 방향·%/±), 타임라인, 서사.
- **없음**: 회차 간 비교 기준. 개인 기준선은 그 회차 첫 120초(`group_aggregate`)뿐이고 `normalization_baselines` 는 관리자가 올린 표준 모델 재료다. "1회차 대비 8회차에서 이완이 올랐다"를 만들 **회원 개인 장기 기준선이 존재하지 않는다**.

### 5.2 제안 범위 (MVP / 후속 / 제외)

| 구분 | 항목 | 설명 | 원칙 정합 |
|---|---|---|---|
| MVP | 회차별 변화 방향 띠 | 회원 개인: 회차마다 6지표 `↑/→/↓`(그 회차 전반→후반). 출석한 회차만, 결석·미착용은 빈칸(`측정 안 됨`) | 방향 + 변화량, 점수 없음 |
| MVP | 첫·마지막 비교 서사 | 규칙 기반 템플릿(결정론적, LLM·전역 캐시 비사용), 수치는 ±% 카드 | 서사 + 변화량 |
| MVP | 출석 요약 | 클래스: 회차별 출석·결석·보강 인원 / 회원: `3/8 참석`, 결석 회차, 보강 완료/대기 | 점수 아님, 결석≠0 |
| MVP | 착용 회차 수 | `뇌파 측정 회차 5/8`(미착용은 정상 미측정 — 감점·강조 없음) | 미측정≠0 |
| MVP | 상담사용 클래스 요약 | 회차별 **방향 분포 인원수**(이완 ↑ n명 · → n명 · ↓ n명), 착용자 3명 미만이면 비노출 | 개인 식별·순위 없음, `MIN_WEARERS=3` 재사용 |
| 후속 | 클래스 평균 흐름 그래프(상담사만) | 정규화 수준값 노출 여부 `D-40` | |
| 후속 | 개인 장기 기준선(1회차 첫 N분 기준 상대값) | 데이터 모델 신설, 점수 환원 방지 검증 선행 | 별도 SDD |
| 후속 | 클래스 마무리 리포트(회원용 요약 1건) | 새 리포트 유형 필요, MVP 제외(`D-39`) | |
| 제외 | 강사별 통계·강사 간 클래스 비교·회원 순위·종합점수·타인 대비 | §8 | 원칙 위반/위험 |

### 5.3 데이터 구현 기본값

1. **기존 리포트 `content` 에서 파생**: 회차 리포트 생성 시 `build_metrics_summary(...)` 결과(6지표 early/late/delta/%/direction)를 `content.eeg.change` 로 가산 저장(스키마 변경 없음, 하위호환). 클래스 추이는 해당 클래스 회차의 승인(`completed`)된 client 리포트의 `content.eeg.change` 를 읽어 조립한다. 이점: ① `report_included=False` 참여자는 애초에 행이 없어 자동 제외 ② 승인 후에만 노출 ③ 제외 선택 변경 시 `refresh_reports_after_choice_change` 가 재생성하며 함께 갱신 ④ 신규 테이블 없음.
2. 기존 회차 리포트에는 `content.eeg.change` 가 없다 → **백필 태스크**(Celery, 윈도우에서 결정론적 재계산, 서사 LLM 호출 없음)를 기본값으로 한다(대안: 과거 회차는 추이에서 제외).
3. 갱신은 **요청 시 조립(캐시 없음)** 에서 시작(회차 ≤ 수십, 회원 ≤ 수십). 느려지면 파생 테이블(후속). 회차 리포트 완료 훅 + 비동기 태스크는 그때 도입.
4. 제외·결석 처리: 추이 입력은 "client 리포트가 존재하고 `report_scope.excluded` 가 아닌 건"만. 결석 = 행 없음 = 빈칸. 중간 합류자는 합류 이후 회차만 채워지고 합류 전 회차는 `참여 전`으로 구분 표기.
5. 보강 회차에 참석한 회원은 그 회차 리포트가 생기므로 추이에서 `보강` 표식으로 원 회차 위치에 연결(`makeup_for_session_id`).

## 6. 회원용 / 상담사용 구분 (유지)

| 항목 | 회원용(client) | 상담사용(counselor) |
|---|---|---|
| 현행 | `type=client`, 본인 것만(IDOR 방어), 그룹 회차에서는 공통 녹음 요약 제외 | `type=counselor`, 반영 동의 참가자 집계 + 기록·영상·STT, 회원 403 |
| 클래스 추이 | **본인** 회차별 방향 띠 + 서사 + 출석(3/8). 그룹 평균·순위·±델타·종합점수·타인 대비 **금지**(SDD-208 합의 #5) | 클래스 방향 분포(익명, ≥3명) + 회차별 출석 + 개인별 흐름(담당 회원 개인 리포트는 이미 열람) |
| 제외 선택한 회원 | 본인 화면 `리포트에 반영되지 않아요` | 집계·분포에서 제외(인원수에도 미포함) |
| 비회원 | 메일 토큰 열람은 회차 단위. 클래스 추이는 **제공하지 않음**(계정 없음) | 회차 단위 표시(이름은 게스트 입력값) |

## 7. 상담 리포트 (분리 영역)

상담의 핵심 산출물은 리포트·기록지이므로 명상과 정책이 다르다(`R10 §5`).

| 항목 | 상담 기본값 | 근거·결정 |
|---|---|---|
| 승인 | **상담사 승인 필수**. 자동 승인은 영역별로 분리하고 상담 기본 off — 현행 `users.auto_approve_report` 는 계정 단일 불린이라 명상에서 켜면 상담 리포트도 자동 발송되는 위험 | `D-37` |
| 리포트 반영 | 기본 **포함**(`report_included=true` 시드) + 동의 단계에서 "상담 기록·리포트 작성" 고지 1회 확인. 리포트 제외 토글은 상담 UI 에서 숨김 | SDD-209 의 "기본 제외" 와 반대 → `D-03` |
| 녹음 동의 거부 | 수동 기록 모드(기본값) | SDD-209(`거부해도 녹음을 막지 않음`)와 프로젝트 규칙(`별도 동의, 거부 시 수동 기록`)이 충돌 → `D-02` |
| 연구 동의 | 관계 최초 입장 시 1회, 이후 마지막 선택 승계. 음성·STT 원문은 연구 DB 비적재 | `D-04` |
| 센터 관리자 | **메타만**(건수·일정), 본문·리포트·기록지 비공개 | `D-28` |
| 종결 후 열람 | 상담사 읽기 전용, 내담자 지난 리포트 열람 유지 | `기획-상세-상담.md` §5 |
| 비회원 내담자 | 승인 후 등록 이메일로 발송(메일 링크 7일). 재열람은 자격 보유 기기의 "내 상담" 최소 화면 또는 상담사 재발송 | `D-51` |
| 상담사 부재 | 승인 대기 리포트는 센터 관리자가 대리 승인 | `D-59` |
| 이관 | 과거 세션 `host_id`·리포트 작성/승인 귀속은 이전 상담사로 불변, 새 상담사는 요약·리포트만(내담자 동의) | `D-58` |
| 영역 필터 | `/reports` 목록에 영역 칩(`전체·클래스·상담`), 상세 화면은 영역별 | |

## 8. 점수·순위 금지 원칙 적용 체크리스트 (클래스 기능용)

| # | 금지/요구 | 클래스 기능에서의 적용 |
|---|---|---|
| 1 | 종합점수(`eeg.score`) 사용 금지 | 추이·출석·요약 어디에도 `eeg.score`·`metrics` 수준값 합산을 쓰지 않는다(저장값이 남아 있어 구현 실수 가능 → **테스트로 고정**) |
| 2 | 회원 화면 그룹 평균·순위·±델타·타인 대비 금지 | "내 클래스" 추이는 본인 데이터만. 분포(인원수)는 상담사 전용 |
| 3 | 개인 식별 가능한 소표본 집계 금지 | 분포는 착용자 ≥3명일 때만 |
| 4 | 미측정 ≠ 0, 유실 ≠ 미측정 | 결석·미착용은 빈칸. 유실은 "측정 시도됨·유실"로 구분 표기 |
| 5 | 제외 참여자 전 경로 제외 | 추이·분포·일괄 발송·메일 재발송에서 `report_included=False` 제외 |
| 6 | 서사 + 변화량 | 클래스 서사는 결정론 규칙 템플릿(LLM·전역 캐시 비사용), 수치는 ±카드 |
| 7 | 의료 오인 방지 | "진단/치료 목적 아님" 고지 유지. 클래스 서사에 개선/악화 단정·평가 표현 금지(현행은 LLM 프롬프트 지시 수준이고 의미 검증기가 없다) |

원칙 문서 근거: 몸마음리포트 기획("점수 없음 — 명상을 성적처럼 환원하지 않는다", 서사 중심, 변화량 표현), 리포트 데이터유실 정책("점수 환원 금지", 미측정/유실 구분), SDD-054(내담자 화면 종합점수 표시 제거 — 데이터는 하위호환으로 유지), SDD-208 합의 #5, `group_aggregate` 의 "개인 점수·순위는 어떤 형태로도 담지 않는다", SDD-209 정책 2(제외 참여자는 모든 파생물에서 제외). "순위 금지"를 명시한 문서는 코드·스펙에서 `group_aggregate` 와 SDD-208 합의 #5 수준이며 별도 신규 원칙 문서는 없다(`grep` 확인) — 클래스 기능에도 같은 기준을 적용한다.

## 9. `narrative_cache` · 정규화 — 클래스 연결 불필요

| 대상 | 실제 키 | 클래스 도입 시 |
|---|---|---|
| `narrative_cache` | PK `signature` String(6) = 6지표 방향 패턴. `session_id`·`user_id` 컬럼 **없음**. 전역 패턴 캐시 | **변경 없음**. 클래스 서사는 이 캐시를 쓰지 않는다 — 개인 맞춤 서사를 전역 캐시에 섞으면 개인 정보가 캐시로 새는 구조가 되므로 결정론 템플릿이 기본값 |
| `normalization_baselines` | PK `id`(int), `user_id`(String) = **기준 데이터를 올린 관리자 id**, 전역 `is_active` 1건 | **리포트 경로에서 쓰이지 않음**(사용처 = 정규화 API·분포 계산뿐). 연결 불필요 |
| `normalization_models` | `version`, `params`, 전역 `is_active` 1건 | 변경 없음. 리포트에 `normalization_version` 이 기록되므로 클래스 안에서 버전이 회차마다 다를 수 있으나 추이는 방향·변화량만 쓰므로 영향이 적다. **수준 비교를 후속에 도입할 때 버전 고정이 필요** |
| 회원 개인 기준선 | **없음** | 후속 |

결론: "narrative_cache·정규화 베이스라인을 클래스에 연결"해야 할 항목은 없다. 클래스 단위로 필요한 신규 데이터는 회차 리포트 안의 `content.eeg.change` 하나뿐이다.

## 10. 강사별 통계 — 기본값 "만들지 않음"

근거 5가지는 `기획-상세-강사모델.md` §9. 허용 대안(기본값): 클래스별 승인 대기 건수·가장 오래된 대기 일수(업무 지표), 강사 본인 개인 업무 화면. 강사 개인 순위/비교 화면은 만들지 않는다. 현행 `org_dashboard` 의 상담사별 `class_count`/`participant_count`/`completed_count` 유지 여부는 `D-35` 하위.
