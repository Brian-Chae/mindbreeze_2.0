# 기획 상세 — 강사 모델 (클래스 강사 ≥1 · 세션 진행 강사 정확히 1)

> 2026-10-17 · Phase 1(서비스 기획) 초안 · 승인 대기. 본문 `기획.md` §4 의 상세 편.
> 근거: `조사/R9-강사모델권한.md`(현행 `host_id`·역할·충돌·알림·계정 처리), `조사/R1-데이터모델.md` §8·§12·§13(제약·매핑), `조사/R7-이전계획.md` §4.5(자동 매핑), `조사/R6-리포트분석.md` §4·§9(리포트 연결·통계).
> 확정(브리프-추가1 §B-1, 뒤집지 않음): 한 클래스에 강사 1명 이상 · 한 세션의 진행 강사는 정확히 1명 · 세션별 배정은 **편성 단계에서 만들고** 중간에 수정 가능.
> 적용 범위: **명상 클래스**. 상담은 "관계의 상담사 1명 = 진행자"라 클래스 강사 모델이 없다(교체/이관만 `기획-상세-상담.md` §6).

## 1. 한 장 요약

1. `sessions.host_id` 는 **이름·NOT NULL 을 유지**하고 의미만 "그 회차의 진행 강사"로 확정한다. 단일 컬럼이라 "0명·2명 불가"가 구조적으로 보장되며, `instructor_id` 별도 컬럼은 같은 사실의 이중 저장이라 만들지 않는다(`R1 §13` H1).
2. 클래스 강사는 신설 `class_instructors` 에 둔다(역할 `lead`/`assistant`/`guest`, 제거는 soft). **복합 FK** `(class_id, host_id) → class_instructors(class_id, user_id)` 로 "진행자는 그 클래스의 강사 행에 존재"를 DB 가 강제한다. "활성 여부"·"강사 ≥1명"은 앱 검증 + 클래스 행 잠금.
3. 편성 때 배정 방식은 4종(모두 한 명 · 번갈아 · 요일별 · 회차별 개별). 규칙은 클래스에 **저장**해 정기형 롤링 생성과 "지난 기수 그대로"가 재사용한다.
4. 미정(진행 강사 없음)은 **편성 초안(`draft`)에서만** 존재할 수 있다. 세션 행은 항상 진행자가 있다.
5. 진행자 변경은 시점별 규칙(미래 즉시 / 임박 수락 / 대기실 이후 불가 / 완료 후 승인 전만 정정), 이탈은 "먼저 정리"(재배정 마법사)가 정상 경로.
6. 현행 권한은 사실상 `host_id == 요청자` 한 줄이 **9곳**에 복제돼 있다. 강사 모델 도입의 최대 공사는 이 판정의 단일화(`authorize_session`)다.
7. 강사별 통계는 **만들지 않는다**(평가·순위화 위험, §9).

## 2. 개체와 속성

### 2.1 `class_instructors` (신규)

| 컬럼 | 타입 | 제약·의미 |
|---|---|---|
| `id` | uuid PK | |
| `class_id` | uuid FK `classes` RESTRICT | |
| `user_id` | uuid FK `users` | **`UNIQUE (class_id, user_id)`** — 복합 FK 의 참조 대상. 재추가 시 새 행이 아니라 기존 행 `status=active` 복구 |
| `role` | `lead` / `assistant` / `guest` | `lead` 주강사(≥1), `assistant` 보조, `guest` 임시(대강, `scope_session_id` 한정) |
| `status` | `active` / `removed` | **행 삭제 금지**(soft). 과거 회차 이력과 복합 FK 유지를 위해 |
| `scope_session_id` | uuid FK `sessions` NULL | `guest` 한정 회차 |
| `added_by`, `added_at`, `removed_at` | | 감사 |

- 역할 의미: **세션 진행자는 항상 1명**이다. 역할(주강사/보조)은 **진행 권한이 아니라 클래스 관리 권한**의 차이다(주강사 = 편집·강사 관리·일괄 승인, 보조 = 열람·참관). 번갈아 진행하는 두 강사는 둘 다 `lead` 여도 되고 한 명이 `assistant` 여도 되며, 진행 가능 여부는 역할이 아니라 "active 클래스 강사인가"로 정한다.
- 개설자는 생성 시 자동으로 `lead` 에 등록된다. 이후 `lead` 에서 빠지면 일반 타 강사와 같은 취급이다(개설자 영구 권한 없음 — `D-34`).

### 2.2 `sessions` 변경

| 컬럼 | 의미 |
|---|---|
| `host_id` (기존) | **진행 강사**. NOT NULL FK `users` 유지 |
| `class_id` (신규, nullable → 백필) | 명상 회차의 부모 |
| 복합 FK `(class_id, host_id)` → `class_instructors(class_id, user_id)` | MATCH SIMPLE: `class_id` 가 NULL 이면(상담 세션·미이전 행) 검사 생략. `NOT VALID` → 백필 → `VALIDATE` 순서(구 코드 롤백 안전, `R1 §12`) |
| `host_state` (신규) | `assigned` / `pending_ack` / `needs_reassign` (`기획-상세-상태머신권한.md` §1.3) |
| `seq`, `session_kind` | 회차 번호, `regular`/`makeup` |

### 2.3 `session_host_history` (신규, append-only)

`(session_id, 이전 host_id, 이후 host_id, 사유, 실행자, 시각)`. 모든 진행자 변경(편성 변경·긴급 변경·대강·이탈 재배정·귀속 정정)이 남는다. 삭제·수정 불가.

### 2.4 DB 제약 vs 앱 검증 (`R1 §12`)

| 요구 | 수단 | 가능 |
|---|---|---|
| 진행자 정확히 1명 | `sessions.host_id` 단일 NOT NULL | 구조적 O |
| 진행자가 해당 클래스 강사 행에 존재 | 복합 FK | DB 강제 O |
| 진행자가 **active** 강사 | 앱 검증 + 클래스 행 `SELECT … FOR UPDATE`(제거는 soft 라 FK 를 통과하므로) | 선언적 X → 앱 |
| 클래스 강사 ≥ 1, 주강사 ≥ 1 | 앱 검증 + 클래스 행 잠금 | 선언적 X → 앱 |
| 강사 제거 vs 동시 배정 경합 | 클래스 행 잠금으로 직렬화 | 앱 |

- 저장소에 DB 트리거 선례가 없다(`grep` 0건). 수동 SQL·스크립트로 앱 검증을 우회하는 경로가 생기면 후속에 트리거를 도입한다.
- 테스트 DB 는 SQLite 를 병용한다(`tests/conftest.py` 의 방언 shim) → FK 가 기본 꺼져 있어 **앱 검증이 1차 방어**여야 하고, PostgreSQL 제약 테스트는 별도 CI 단계가 필요하다(CI 에 PG 단계 없음 — Phase 0 의 선행 작업).

## 3. 현행 `host_id` 이전 (`R7 §4.5`)

| 대상 | 규칙 |
|---|---|
| `sessions.host_id` | **변경 없음**. 의미만 "진행 강사"로 확정 |
| `class_instructors` | 클래스마다 `(class_id, host_id, 'lead', 'active', added_by=host_id, added_at=세션 created_at)` 1행. 복합 FK 의 참조 대상이므로 **세션의 `class_id` 를 채우기 전에** INSERT |
| 개설자 | `classes.created_by` ← `host_id` |
| 비활성 호스트(`users.status ≠ active`) | 그대로 `lead` 로 등록(이력 충실). 미래 회차(`ready`/`scheduled`/`open`)면 `needs_reassign` **후보로 보고만**(상태 변경은 Phase 3 규칙 도입 후) |
| 기관 | `organization_id`·`organization_attribution_known` 값 복사 — 추정으로 채우지 않는다 |
| 검증 쿼리 | `class_id IS NOT NULL` 세션 중 `class_instructors` 에 `(class_id, host_id)` 가 없는 행 = 0건 |

현행 코드에 공동·대리 진행 개념과 "세션 생성 후 `host_id` 를 바꾸는" 코드가 **없다**(`R9 §0`). 즉 변경 기능은 전부 신규다.

## 4. 편성: 회차별 진행 강사 배정

### 4.1 배정 방식 4종 (`R5 §3`, `assignment_rule` JSONB 에 저장)

| 방식 | 규칙 | 예 |
|---|---|---|
| `all_one` 모두 한 분이 맡아요 | 전 회차 한 명 | 8회 모두 김지수 |
| `rotate` 번갈아 맡아요 | 강사 순서 `[A,B]` → 회차 `seq` 의 `(seq-1) % 명수` | A,B,A,B… |
| `by_weekday` 요일마다 달라요 | 요일 → 강사 매핑 | 월=A, 목=B |
| `per_session` 회차마다 직접 정해요 | 회차 표에서 개별 셀렉트 | 3회차만 C |

- 규칙은 **생성 시점에 회차 값으로 펼쳐지고**, 이미 생성된 회차에는 소급하지 않는다(규칙 변경 화면에서 "이후 회차에만 적용" 선택). 개별 수정은 항상 `per_session` 으로 덮는다.
- 정기형 롤링 생성(4주 앞)은 저장된 규칙을 투영한다. 규칙에 **비활성/제거된 강사**가 포함돼 있으면 해당 회차는 `needs_reassign` 로 만들고 주강사에게 알린다(`R5 §4.2`).
- "지난 기수 그대로": 원본 `assignment_rule` 승계. 비활성 강사는 `미정` 으로 표시(`R5 §7.3`).

### 4.2 미정 허용 범위

- **편성 중(`draft`)만 허용**: 회차 표에 `미정` 셀을 두고 `draft_schedule` 에 저장할 수 있다(`D-19`).
- **공개(`draft` → `active`, 또는 마법사 완료) 시 전 회차 진행 강사 필수**. 그래서 세션 행의 `host_id NOT NULL` 이 항상 성립한다.
- 열기·시작 시점 검증은 `host_state = needs_reassign` 차단으로 대체한다(미정 상태 자체가 세션 행에 없으므로).

### 4.3 배정 규칙 시안 (표 UI 개념, 상세 흐름은 `기획-상세-편성UX.md`)

```
강사     [김지수 주강사] [박서연 강사] [+ 강사 추가]
배정     (•) 번갈아 맡아요   ( ) 모두 한 분이 맡아요   ( ) 요일마다 달라요   ( ) 회차마다 직접 정해요
순서     1. 김지수  [↑][↓]    2. 박서연  [↑][↓]

회차   날짜          시간   방식    진행 강사       충돌
1회차  11/3(월)     19:00  온라인  김지수 ▾        
2회차  11/10(월)    19:00  온라인  박서연 ▾        겹쳐요
3회차  11/17(월)    19:00  온라인  김지수 ▾
```

- 드래그 없이 셀렉트·버튼·스텝퍼로만 편집(`R3 §8.2`). 모바일은 회차 카드 + 편집 시트로 같은 필드·같은 검증 함수를 쓴다.
- 일괄 동작: `강사 한꺼번에 바꾸기`(선택 회차) · `시각 한꺼번에 바꾸기` · `한 주 밀기` · `선택 회차 취소`. 각 동작은 변경 전→후 미리 보기 후 `적용`.

## 5. 불변식 (강사 모델)

| ID | 불변식 |
|---|---|
| I1 | 모든 명상 세션은 `class_id` 를 갖는다(이전 후 contract 에서 NOT NULL) |
| I2 | 모든 세션의 진행 강사(`host_id`)는 정확히 1명이다(단일 NOT NULL 컬럼) |
| I3 | 진행 강사는 해당 클래스의 강사 행(`class_instructors`)에 존재한다(복합 FK + 앱 검증). `removed` 강사는 신규 배정 불가, 과거 회차 이력으로만 남는다 |
| I4 | 클래스의 active 강사는 1명 이상, 그중 `lead` 는 1명 이상이다(앱 + 클래스 잠금) |
| I5 | 같은 `(class_id, user_id)` 강사 행은 1개다(UNIQUE, 제거는 soft) |
| I6 | 미정(초안)·`needs_reassign` 회차는 열기·시작할 수 없다 |
| I7 | `open`/`in_progress` 회차의 진행 강사는 변경할 수 없다(인계 도입 전까지, `D-23`) |
| I8 | 같은 강사는 같은 시각에 겹치는 두 회차의 진행자가 될 수 없다 — 기본값은 **경고 후 확인(소프트)**(`D-33`) |
| I9 | 진행 강사가 아닌 클래스 강사는 열기·시작·종료·녹음·발언권 제어를 할 수 없다(참관·열람 R 만) |
| I10 | 센터 관리자는 회차를 직접 열기·시작·종료하지 못한다(녹음 동의 책임은 강사). 편성·재배정 **대행**만 가능(`D-25`) |
| I11 | 리포트 승인자는 해당 회차 진행 강사 또는 주강사이며 `approved_by` 가 기록된다. 승인된 리포트의 소유(`user_id`)는 바꾸지 않는다 |
| I12 | 완료된 회차의 `host_id` 변경은 귀속 정정 경로(사유·감사·**리포트 승인 전** 한정)로만 가능하고 이력이 남는다 |
| I13 | 강사 제거는 해당 강사 진행의 미래 회차가 0건일 때만 정상 처리된다. 비정상(정지·삭제)은 `needs_reassign` 로 전환된다 |
| I14 | 대체(guest) 강사는 지정된 한 회차에만 권한을 가지며 회차 종료·리포트 승인 완료 후 만료된다 |
| I15 | 모든 진행자 변경은 `session_host_history` 에 기록된다(삭제 불가) |
| I16 | 진행자 변경 시 채팅방 방장(`ChatRoom.host_id`)·충돌 검사·리마인더·AI 비서 접근 범위가 새 진행자 기준으로 갱신된다 |
| I17 | 클래스·세션의 기관 귀속은 `organization_id` 스냅샷이며 강사가 소속을 옮겨도 불변이다. 접근 판정은 현재 `User.org_id` 가 아니라 이 스냅샷 기준이다 |
| I18 | 강사 개인별 성과·평가·순위 지표는 생성하지 않는다(§9) |
| I19 | 비활성·삭제 계정의 미래 회차는 숨기지 않고 `needs_reassign` 로 보존한다(현행 `delete_user` 의 일괄 숨김 폐지) |
| I20 | 회원에게 보이는 진행 강사는 항상 확정(`assigned`, 수락 완료)된 1명이며, 미정·`pending_ack` 상태의 강사명은 노출하지 않는다 |

## 6. 수정 규칙

### 6.1 시점별 진행자 변경

| 회차 상태·시점 | 변경 | 승인 주체 | 조건·알림 |
|---|---|---|---|
| `ready`/`scheduled`, 시작 60분 초과 전 | O 즉시 | 주강사·센터 관리자 | 이전·신규 강사 알림, 회원 알림은 `D-29`(기본: 시작 7일 이내 변경만 + 임박 시 푸시) |
| `scheduled`, 시작 60분 이내(임박) | △ 긴급 변경 | 주강사·센터 관리자 | 새 강사 **수락 필수**(`pending_ack`, 현 진행자 유지), 회원 즉시 알림은 수락 확정 뒤. 60분은 리마인더 기본 시점(`[1440, 60]`)에 맞춘 기본값(`D-20`) |
| `open`(대기실) | X (기본) | — | 녹음·영상·발언권이 host 단일 판정이라 중간 교체는 데이터 소유 분리 위험. 인계는 후속(`D-23`) |
| `in_progress` | X | — | 장애 시 진행자 재접속, 불가피하면 종료 후 보강 회차 |
| `completed` | 귀속 정정만 | 주강사·센터 관리자 | **리포트 승인 전**에만(`D-24`). 승인 후엔 표시 메모만 |
| `cancelled` | X | — | |

- 진행 강사 본인은 자기 회차를 **양도 요청**할 수 있고(즉시 양도 아님), 주강사/센터 관리자가 확인한다(`D-21`).
- 진행자 변경이 일어나면 새 강사 기준으로 **충돌을 재검사**한다(현행 수정 경로는 `s.host_id` 고정이라 새 호스트 기준 호출로 바뀌어야 함, `R9 §3.2`).

### 6.2 대체 강사(대강)

| 옵션 | 내용 | 평가 |
|---|---|---|
| A 엄격 | 클래스 강사로 먼저 추가해야 진행자 지정 가능 | 불변식 단순, 급한 대강에 불편 |
| **B 임시 등록 (기본값)** | 진행자 선택 시 같은 센터 active 강사를 검색 → 선택하면 `guest` 행을 **자동 생성**하고 지정 | 복합 FK 유지, 권한이 해당 회차로 한정, 편함 |
| C 자유 지정(타 센터 포함) | 어떤 사용자든 | 데이터 접근 경계 붕괴 — 비권장 |

B 의 세부: 자격 = 같은 센터(`Session.organization_id`)의 active membership 이 있는 `counselor`(개인 상담소 상담사는 해당 없음). guest 권한과 만료는 `기획-상세-상태머신권한.md` §2.1. 지정 권한 = 주강사·센터 관리자(보조·진행 강사는 요청만). 타 센터 강사는 후속(`D-22`).

### 6.3 강사 이탈·비활성

| 경우 | 기본 동작 |
|---|---|
| 자발적·정상 이탈(클래스 제거, 소속 해제, 계정 삭제 전) | **이탈 차단 + 재배정 마법사**: 담당 미래 회차 N건을 "누구에게?" 일괄 재배정(또는 취소)하도록 강제. 현행 소속 해제의 "먼저 정리"(409) 관례와 같다 |
| 비자발적(정지·삭제·강제 해제) | 미래 회차를 **`needs_reassign`** 로 전환, 숨기지 않음, 주강사·센터 관리자 알림, 시작 72h/24h 전 재알림, 24h 전까지 미해결이면 "진행자 필요" 배지 + 센터 관리자 대시보드 최상단(`D-30`) |
| 회원 알림 | **재배정 확정 또는 취소 확정 시점**에만(미확정 상태의 불안 유발 금지) |
| 완료·진행 중 회차 | `host_id` 유지(이력·리포트 소유 보존) |
| 퇴사(소속 해제) | 이미 진행한 회차의 리포트는 해당 센터 `organization_id` 스냅샷에 귀속 유지 |

현행의 정지는 세션을 건드리지 않고(호스트가 토큰이 있어도 매 요청 403 → 열기·시작 불가인데 참여자 알림은 없음), 삭제는 호스트의 **모든 세션을 일괄 숨김**(참여자 알림·예약 리마인더 취소 없음)이다(`R9 §5`). 회원 앱에서 일정이 조용히 사라지는 사고이므로 Phase 3 에서 이 둘을 위 규칙으로 바꾼다.

### 6.4 클래스 강사 추가·제거 시 기존 세션 정합

| 대상 회차 | 규칙 |
|---|---|
| 미래(`ready`/`scheduled`) 진행 회차 | 제거 전 재배정 필수(일괄 재배정 UI). 강제 제거만 `needs_reassign` |
| `open`·`in_progress` 진행 회차 | 제거 **불가**(409) |
| 완료·취소 회차 | `host_id` 유지, 강사 행은 `status=removed` + `removed_at` |
| 마지막 주강사 / 마지막 강사 | 제거·강등 불가(409). 다른 강사를 주강사로 먼저 지정 (`D-31`) |
| 제거된 강사의 이후 권한 | 클래스 접근 종료. 본인이 진행한 회차의 리포트·기록 열람은 유지(귀속 권리) |
| 회원 노출 | 과거 회차 강사명은 그대로(이력), 미래 회차는 재배정된 강사로 표시 |
| 재추가 | 같은 사용자를 다시 추가하면 기존 행 `active` 복구 |

## 7. 충돌

| 항목 | 현행 | 새 구조의 기본값 |
|---|---|---|
| 강사 시간 충돌 | `detect_conflict(host_id, …)` — 같은 `host_id` 의 활성 세션(`ready`/`scheduled`/`open`/`in_progress`)과 시간 겹침, **type·참여 방식·기관 무관**. 호출 3곳(생성·복제·수정). 소프트(`force=true` 면 건너뜀). 파이썬 전량 로드 루프 | 단위 = (`host_id`, 시간 구간)을 유지하면 **명상+상담이 같은 `sessions` 테이블이라 통합 검사가 그대로 성립**. 보강: ① 일괄 검사 `detect_conflicts_bulk`(요청 안 신규 회차끼리 포함, 한 번의 범위 쿼리) ② SQL 범위 조건 + `(host_id, scheduled_at)` 인덱스 ③ 응답에 `kind`(class/counseling)·`parent_title`·`seq`·시각 ④ 프론트 자체 계산 폐기, 서버 `preview-schedule` 응답을 권위로 |
| 열기·시작 시 동시 진행 | 검사 없음 | **경고 후 확인**(`D-33`): `다른 일정을 진행 중이에요. 그 일정을 먼저 마쳐 주세요` |
| 장소 충돌 | 룸·자원 엔티티 없음(주소 문자열만) → 신뢰할 수 있는 판정 불가 | 정보성 경고만(같은 센터·같은 주소 문자열·시간 겹침), 차단 안 함. 룸 관리는 후속(`D-32`) |
| 회원(참여자) 충돌 | 없음 | 정보성 경고(차단 안 함). 상담에서는 같은 상담사의 다른 회차와 겹칠 때만 표시(타 상담 존재 노출 금지) |
| 버퍼(이동·정리 시간) | 없음 | 0분 |
| DB EXCLUDE 제약 | — | **비도입**(`force` 소프트 정책과 충돌) |

센터(기관) 간 강사 공유: 현행 **불가**(세션은 호스트의 주 소속 1개 기관에 귀속, `R9 §2.3`). 이번 구조에서도 같은 센터 강사만 지정한다. 다기관 소속 강사(`user_org_membership`)의 리포트 노출 범위는 `미확인`(`R6-X3`).

## 8. 알림

배정·변경·취소·이탈 알림의 이벤트·수신자·시점·문구는 `기획-상세-상태머신권한.md` §3. 요점: 강사에게는 항상, 회원에게는 **확정된 변경만**(`D-29`), 미정·`pending_ack` 는 회원에게 알리지 않는다.

## 9. 리포트·분석과의 연결

- 리포트 행 키(`session_id`·`participant_id`·`type`)는 바뀌지 않는다. 현행에는 작성자·승인자 컬럼이 **없고**, 승인은 암묵적으로 `session.host_id == 호출자` 일 때만 허용된다. 따라서 "진행 강사 = `host_id`" 매핑이면 현행 규칙이 그대로 "진행 강사가 승인"이 된다.
- 신규: `reports.approved_by_user_id`, `reports.approved_at`(nullable, 추가형). 승인 알림 수신자는 `report.user_id` 가 아니라 **현재 진행 강사**로(강사 교체 후 알림이 구 강사에게 가는 것을 방지).
- 클래스 단위 일괄 승인의 권한(`D-36`): 기본값 = **진행 강사 + 주강사**(대행 승인 시 `approved_by` 기록). 보조 강사는 승인 불가. 조사 간 이견: R6 은 "클래스 강사 누구나"를 기본으로, R9 는 "진행 강사 + 주강사"를 기본으로 제안 → 책임 소재가 흐려지지 않는 후자를 채택(`기획.md` §5 충돌 정리).
- 자동 승인(`users.auto_approve_report`)은 **강사 개인 설정**이라 회차 진행자가 바뀌면 같은 클래스 안에서 회차마다 동작이 달라진다. 기본값: 개인 설정 유지 + 클래스 상세에 "이 회차는 자동 승인 켜짐" 표시, 영역별(명상/상담) 2개로 분리(`D-37`).
- 회차 비교는 진행 강사가 달라도 **클래스 단위로 이어진다**(추이는 회차 리포트의 방향·변화량을 조립하므로 진행자와 무관).
- **강사별 통계는 만들지 않는다**(`D-35`). 근거 5가지(`R6 §9`): ① 점수 환원·순위·비교 배제 원칙과 충돌 ② 변화량은 그 회차 전반/후반 비교일 뿐 효과 크기 척도가 아니고 개인 기준선·회원·시간대·착용 여부가 강사와 교락 ③ 뇌파는 "본인 세션 + 담당 상담사"까지만이며 리포트 반영·연구 동의에 강사 평가용 2차 이용 동의가 없음 ④ 센터 관리자 화면은 활동량 메타만이고 "상담 내용 비노출" 원칙 ⑤ 결석·미측정이 많은 클래스가 낮은 성과로 읽힘. 허용되는 대안은 **업무 지표**(클래스별 승인 대기 건수·가장 오래된 대기 일수)와 강사 본인에게만 보이는 개인 업무 화면. 현행 `org_dashboard` 의 상담사별 `class_count`/`participant_count`/`completed_count` 는 신규 지표 추가 금지 의미로 두고, 유지/제거는 `D-35` 하위 결정.

## 10. 구현 영향 메모

- 호스트 판정 단일화: 5개 서비스 파일에 복제된 9개 헬퍼를 `authorize_session(user, session, action)` 하나로 통합하고 action 별 허용 역할표(`기획-상세-상태머신권한.md` §2)를 데이터화한다. `host_id` 관련 backend 33파일(245줄)·`Session.host_id` 접근 23파일(89줄)·테스트 33파일(72줄)·프론트 10파일 중 세션 관련 6파일이 영향권이다.
- 센터 접근 판정을 `User.org_id`(미러) → `Session.organization_id` 스냅샷 + membership 으로 전환(I17): `_can_access_report`·`dashboard_service`·`report_service` 의 기관 분기가 대상.
- 신규 알림 이벤트는 카탈로그와 선호 기본값 2곳에 동시 추가.
- 채팅방: 진행자 변경 시 `ChatRoom.host_id` 동기화(세션 방은 `Session.host_id` 로 판정하는 현행 규칙 유지 여부 확인).
- 미확인: 세션 생성 API 의 역할 검사 부재(client 토큰으로 호출 가능 — Phase 0 에서 역할 가드 추가), 시간 충돌 전용 테스트 존재 여부, 계정 삭제 후 예약된 ETA 리마인더가 숨김 세션에 발송되는지, 프론트 세션 생성·편집 화면의 role 가드 세부.
