# 기획 상세 — 상담 영역 (상담 관계 · 비회원 내담자 · 종결/보관 · 이관 · 두 영역 사용)

> 2026-10-17 · Phase 1(서비스 기획) 초안 · 승인 대기. 본문 `기획.md` §4·§8 Phase 6~7 의 상세 편.
> 근거: `조사/R10-상담분리.md`(관계 후보·게이트·type 분기·SDD-209 단순화·비회원·종결·이관), `조사/R1-데이터모델.md` §8~§11, `조사/R5-회차운영.md` §8~§9, `조사/R7-이전계획.md` §4.
> 확정(브리프-추가2, 뒤집지 않음): 명상 클래스와 상담은 **별도 제품·메뉴** · 상담의 상위 = 상담 관계(내담자 1 + 상담사 1), 하위 = 상담 세션 · 모든 사용자에게 두 메뉴 오픈, 기관 단위 on/off 없음, 한 계정이 두 영역 모두 사용 · 상담 세션 마법사 신규, 엔진 공유 · **비회원 내담자 상담 허용**(식별·재방문·리포트 전달·개인정보·회원 전환 시 기록 연결을 기획) · **상담 종결 + 데이터 보관**(종결 후 상태·열람 권한·재개·보관 기간 정책을 기획, 보관 기간 숫자만 결정 필요).

## 1. 한 장 요약

1. 상담 관계는 **`client_counselor_links` 를 확장하지 않고 신설**한다(`counseling_relationships`). 현행 링크는 회원 전용이고 `ended` 로 바꾸는 코드가 앱 전체에 0건이며, `ended` 가 "상담사 접근 차단"이라는 반대 의미로 쓰이고, 링크 생성이 채팅방·AI 비서 접근을 자동 부여하고, 계정 삭제 시 링크 행을 DELETE 하기 때문이다. 회원 관계에 링크가 이미 있으면 `link_id` 로 약결합만 하고 **이전 때 링크를 자동 생성하지 않는다**.
2. `sessions` 한 테이블을 유지하고 부모 FK 두 개(`class_id` / `counseling_relationship_id`) 중 **정확히 하나만** 채운다. 진행 화면·입장·뇌파·녹음/STT/요약·리포트 엔진·알림은 그대로 공유한다.
3. 상담 관계 상태는 `pending → active → closed → archived`. 종결·보관은 **데이터를 지우지 않는다**(영구층 보존). 같은 관계 재개가 기본, 보관 후에는 새 관계.
4. 비회원 내담자: 상담사가 이름 + 이메일(필수)로 등록 → **관계 단위 4자리 코드 + 등록 이메일 일치 + 상담사 대기실 승인**으로 입장 → 관계 단위 재방문 자격(90일 슬라이딩) → 리포트는 등록 이메일로 발송 → 회원 가입 시 확인 화면 + 생년월일 일치로 기록 연결(자동 연결 금지).
5. 현행에서는 비회원이 type 무관하게 4자리 코드로 clinical/hypnosis 세션에도 입장하고, 정원 1 이면 **코드를 아는 아무나 먼저 들어가 내담자 행세**를 할 수 있다 — 상담에서는 막아야 하는 틈이다.
6. 역할·자격·온보딩·기관 플래그 중 "두 메뉴 모두 오픈"을 막는 것은 **현재 없다**(제거할 on/off 플래그도 없음). 필요한 최소 변경은 메뉴 노출·라우트 신설·**세션 생성 API 역할 가드(현재 로그인만 확인)** 등 6개(§3).
7. 한 계정이 두 영역을 쓰면 권한은 상위 개체 소유로 판정(교차 접근 없음), 통계·알림 payload·자동 승인은 영역별로 분리하고, 시간 충돌은 이미 `host_id` 기준 통합 검사다.

## 2. 상담 관계 모델

### 2.1 `client_counselor_links` 재사용 평가 (`R10 §2`, `R1 §9`)

| 요건 | 현행 링크 | 판정 |
|---|---|---|
| (내담자, 상담사) 쌍 | `UNIQUE(client_id, counselor_id)` | 맞음 — 단 "종결 후 새 관계"를 같은 쌍에서 표현할 수 없음 |
| 비회원 내담자 | `client_id` NOT NULL FK | **불가** (확정 요구와 충돌) |
| 세션과 연결 | 없음 (`last_session_at` 은 `None  # 추후 세션 연동`) | **불가** |
| 종결 | `status` `active`/`ended`. `ended` 로 바꾸는 코드 **0건**(생성·재활성화만) | 사실상 미구현 |
| 종결의 의미 | 현행 `ended` = 목록·프로필·메모·AI 비서 모두 차단 | "종결 후 열람"과 **반대 의미** |
| 이력 | `ended_at` 한 컬럼 | 몇 번 종결·재개됐는지 모름 |
| 계정 삭제 | 접근 테이블 DELETE 에 링크 포함 | "종결해도 보관"과 충돌 |
| 권한 부작용 | 링크 생성 시 1:1 채팅방 자동 생성, AI 비서가 `active` 링크로 담당 내담자 판정, 채팅 권한도 링크 의존 | 이전 때 링크를 만들면 권한이 생김 |

옵션 비교 (`R1 §9.2`): ① 링크를 뿌리로 확장(회원 경로 무변경이 장점이나 `client_id` nullable·`ended` 의미 변경으로 소비처 5~12곳 수정, 계정 삭제 DELETE 경로 수정 필요) ② **신설 + 약결합 `link_id`**(채택) ③ 링크 폐기 후 관계로 대체(참조 30여 곳 수정, 위험 큼).

**조사 간 이견(`기획.md` §5)**: R10 은 ①을 권고했다(개념 하나, "내담자 목록 = 상담 관계 목록"과 코드가 일치). R1·R5 는 ②를 권고했다(권한 부작용 격리). 채택 이유 — 이전·신규 어디서도 링크를 자동 생성하지 않아야 하고(채팅·AI 비서 접근이 곧 권한), 종결·보관 데이터가 계정 삭제 경로에서 구조적으로 격리되며, `ended` 의미 충돌을 피한다. 개념이 둘이라는 비용은 **동기화 규칙**(아래 §2.3)으로 흡수한다. 선택 번복 시 R1 §6~§11·R7 규칙은 이름 치환만으로 재사용된다.

### 2.2 `counseling_relationships` (신규, 요약 — 컬럼 전체는 `R1 §8.4`)

| 그룹 | 컬럼 |
|---|---|
| 식별 | `id` · `organization_id`(+`organization_attribution_known`) · `counselor_id`(현재 담당 상담사, NOT NULL) · `client_user_id`(회원) · `client_guest_id`(비회원 FK `counseling_guests`) · `is_placeholder`(이전 시 "내담자 미상" 세션 보관용, 상담사당 1개) · `link_id`(약결합, ON DELETE SET NULL) |
| 표시 | `title`(기본 `{내담자} 상담`, 상담사가 변경 가능) · `modality_default`(`clinical`/`hypnosis`) |
| 상태 | `status`(`pending`/`active`/`closed`/`archived`) · `started_at` · `closed_at`·`closed_by`·`close_reason`(`completed`·`client_request`·`counselor_transfer`·`counselor_left`·`account_deleted`·`inactive`) · `archived_at` · `reopened_count` · `predecessor_relationship_id`(새 관계의 이전 관계) |
| 기본값 | `default_duration_min` · `location_type`·`location_address` · `linkband_mode` · `record_audio`·`record_video` · `reminder_offsets` |
| 코드 | `access_code`·`legacy_access_code`(비회원 입장용, §4) |
| 보관 | `retention_hold`(기본 true — 스위프가 읽는 훅, 판단 보류) · `hidden_at` |

- 제약: CHECK `ck_rel_client`(placeholder 이거나 회원/비회원 중 하나 이상 — 회원 전환 후엔 출처 보존을 위해 둘 다 채워질 수 있어 XOR 가 아니라 OR) · 부분 유니크 `uq_rel_active_pair(counselor_id, client_user_id) WHERE status<>'archived'` · `uq_rel_guest(client_guest_id)` · `uq_rel_placeholder(counselor_id) WHERE is_placeholder`.
- **담당 상담사 이력**: `counseling_relationship_counselors`(`(relationship_id, counselor_id)` UNIQUE, `status`, `from_at`/`to_at`)를 복합 FK 의 참조 대상으로 **처음부터** 둔다. `counseling_relationships.counselor_id` 를 직접 참조하면 이관 시 과거 세션의 `host_id` 가 FK 를 위반하기 때문이다(행 1개로 시작).
- 진행자 제약: `sessions` 에 복합 FK `(counseling_relationship_id, host_id) → counseling_relationship_counselors(relationship_id, counselor_id)` — MATCH SIMPLE 이라 명상 세션(관계 NULL)은 자동 생략.
- 이벤트: `counseling_relationship_events`(append-only: 상태 전이·주체·사유).
- 상담 세션은 정원·대기열이 없으므로 서버가 `participant_mode=one_on_one`, `max_participants=1` 을 강제한다(현행 정원 기본값이 10 이라 정원으로는 1:1 판정 불가).

### 2.3 링크와의 동기화 규칙

1. 이전·신규 어디서도 **링크를 자동 생성하지 않는다**(채팅방·AI 비서 권한 부작용). 링크가 이미 있으면 `link_id` 만 기록한다. 이를 테스트로 고정한다(`X16`).
2. 링크가 `ended` 면 이전 시 관계 `closed`, `closed_at = link.ended_at`(유일한 종결 신호). 마지막 세션이 오래됐다는 이유로 종결을 **추정하지 않는다**(현행 원칙 "추정하여 보완하지 않는다"; R10 의 "마지막 세션 90일 초과면 종결 추정" 제안은 기본값에서 제외 — `D-57`).
3. 관계 종결이 링크를 자동으로 `ended` 로 바꾸지 않는다. 종결 내담자에게 AI 비서·채팅을 계속 열어 둘지는 기본값 "유지, 상담사가 별도 해제"(`D-44` 하위).
4. 링크 `memo` 는 링크가 있으면 링크를 계속 읽는다(복사하지 않음 — 이중화 방지).
5. 회원 내담자와 새 관계를 만들 때 링크가 없으면, 채팅·AI 비서 담당 판정이 필요한 시점(회원이 수락한 이후)에 링크를 보장한다(사용자 동의와 함께).

## 3. 역할·자격 게이트와 두 메뉴 오픈 (`R10 §3`)

현행: `users.role` 4값(`counselor`·`client`·`org_admin`·`platform_admin`), 지도사/명상 전용 역할 없음. **세션 생성 API 는 로그인만 확인**하고 서비스도 역할·`verified_tier`·온보딩을 보지 않는다(이론상 `client` 토큰도 호출 가능 — 보안 틈). 프론트는 라우트 가드(`/sessions*` = `counselor`+`org_admin`)뿐이다. `RoleGuard.requireFullyVerified` 는 정의만 있고 사용처 0건. `qualifications` 는 프로필 입력 데이터일 뿐 기능 게이트가 아니고, `onboarding_progress` 는 로그인 후 1회 이동과 대시보드 배너뿐이다. 유일한 실게이트는 **내담자가 상담사 코드로 연결할 때 상담사 `verified_tier != unverified`·계정 active·기관 active** 이다. 기관 단위 on/off 플래그는 **없다**(`organizations` 컬럼 전수 확인).

→ "모든 사용자에게 두 메뉴 모두 오픈"을 막는 게이트가 없고 제거할 플래그도 없다. 최소 변경:

| # | 변경 | 비고 |
|---|---|---|
| M1 | 상담사/기관관리자 사이드바에 **명상 클래스**·**상담** 두 항목 노출(현행 `클래스` 1개 → 2개), 하단 탭 구성 | 항상 노출, 역할·자격·기관 조건 추가 금지 |
| M2 | `/counseling*` 라우트 신설, 가드는 `/sessions*` 와 동일 | |
| M3 | 세션 생성·수정 API 에 `require_roles("counselor","org_admin")` 추가 | **현재 없는 틈 보완**, Phase 0 |
| M4 | 상담 코드 연결의 `verified_tier != unverified` 검사 처리 | `D-53`. 기본값: 검사 제거 + 상담사 프로필에 "인증 배지" 표기로 대체 |
| M5 | 상담 세션 생성은 상담 전용 엔드포인트(`/counseling/{id}/sessions`)에서 관계 소유·상태 검사 | `participant_ids` 임의 user_id 허용 금지 |
| M6 | 상담사 가입·로그인 문구의 "상담사" 단일 표기를 "상담사·지도사" 공용 표현으로 | 호칭은 `D-62` |

불필요: 역할 신설, `qualification`/`credential` 로직 변경, 기관 플래그 제거, 온보딩 게이트 추가. 한 계정이 두 영역을 쓰는 것 자체는 권한 문제가 아니다.

## 4. 비회원 내담자 상담 (확정 반영)

### 4.1 현행 (`R10 §6.1`)

| 질문 | 답 |
|---|---|
| 비회원이 clinical/hypnosis 세션에 참여? | **가능** — 코드 조회가 type 을 보지 않는다 |
| 4자리 코드로 상담 입장? | **가능**. 코드 확인 → 개인정보(이름·성별·생년월일·이메일 모두 필수) → 입장 자격 발급 |
| 1:1 정원과 선점 | 정원 1 이면 먼저 입장한 사람이 차지하고 이후는 대기열. 코드를 아는 아무나 내담자 행세 가능 |
| 비회원 재방문 | 입장 자격(JWT, TTL 24h)이 가리키는 같은 세션의 본인 참여자만. **세션이 달라지면 매번 새 참여자**, 같은 이름은 인계하지 않음(확정 정책) |
| 비회원 리포트 | 참여자 `report_email` 로 승인 시 자동 메일 예약, `report_view` 링크 7일. 수동 요청 경로는 비계정 이메일에 OTP 요구(SDD-209 D-1 "OTP 없음"과 불일치 가능, 프론트 사용 여부 미확인) |
| 비회원→회원 전환 | **코드 없음** |
| 비회원 리마인더 | 제외(회원·비대기자만) |

### 4.2 신원 엔티티 `counseling_guests` (신규, `R1 §8.6`·`R10 §6.2` 통합)

`id` · `organization_id` · `created_by_counselor_id`(프라이버시 격리 단위) · `display_name` · `email`·`email_norm`(가입 이메일과 같은 정규화 규칙) · `email_verified_at` · `gender`·`birth_date` · `reentry_secret_hash`(SHA-256, 평문 저장 금지)·`reentry_ver`·`reentry_issued_at`·`reentry_last_used_at` · `privacy_consent_at`·`privacy_notice_version` · `claimed_user_id`·`claimed_at`·`claim_method` · `pii_scrubbed_at` · `origin`(`created`/`migrated`).

- **관계가 비회원 개인정보의 단일 보유처**다. 회차 참여자 행에는 복사하지 않고 `guest_client_id` 만 둔다(한쪽만 스크럽하는 실수 방지).
- 같은 이메일이 서로 다른 상담사에게는 **별개 행**이다(상담사 간 기록 격리, 부분 유니크는 상담사 단위).

### 4.3 입장·본인 확인·재방문 (기본값)

| 단계 | 동작 | 저장 |
|---|---|---|
| ① 등록 | 상담사 "새 상담 → 가입 없이 상담": **이메일(필수, 재입력 확인 1회)** + 표시 이름. 관계 `pending` 생성, **관계 단위 4자리 코드** 발급, 초대 메일(코드는 본문에만, URL 에 싣지 않음 — SDD-209 R5-A 정합). 오프라인 대면이면 상담사가 코드를 직접 안내해도 되며 이메일은 여전히 필수(리포트 전달) | `counseling_guests`, 관계 코드 |
| ② 첫 입장 | `/join` 에서 코드 입력 → 코드가 가리키는 대상이 관계임을 해석 → **입력 이메일이 사전 등록 이메일과 일치**해야 통과(OTP 아님 — 이메일 OTP 제외 확정과 양립, 코드가 메일에만 있어 선점 위험도 낮춤) → 이름·성별·생년월일 입력 → 개인정보 수집·보관 동의 → 입장 자격 발급 → **상담사 대기실 승인**(1:1 이므로 상담사가 사람을 직접 확인, 비용이 낮음) → 관계 `active` | `privacy_consent_at/version` |
| ③ 재방문 자격 | 서버가 `counseling_entry` 자격(JWT, `sub=guest id`, `ver=reentry_ver`, 마지막 사용 후 **90일 슬라이딩**)을 기기에 발급. 종결 시 `reentry_ver` 증가로 즉시 폐기 | `reentry_*` |
| ④ 같은 기기 재방문 | 자격 유효 → 회차 입장 시 해당 관계의 비회원 출석 행을 생성/재사용 | `session_participants.guest_client_id` |
| ⑤ 기기 분실·만료 | **코드 + 이메일 + 생년월일** 3요소를 사전 등록 값과 대조해 재발급(시도 제한 재사용), `reentry_ver`+1 로 이전 자격 폐기. 상담사 화면의 `코드 다시 만들기`(기존 코드 즉시 무효)는 보조 수단 | |
| ⑥ 이메일 링크 복구 | **채택하지 않음** — SDD-209 D-1(이메일 OTP 제외 확정)과 충돌, 정책 재논의가 필요한 후보 | `D-54` |
| ⑦ 리포트 | 회차 리포트 **승인 후** 등록 이메일로 발송(결과는 출석 행의 `report_email_status`). 오발송 가능성은 SDD-209 가 수용한 잔여 위험 | |

- **코드 공간**: 4자리(10,000)를 클래스 코드·관계 코드·(호환 기간) 세션 코드가 공유한다. 발급을 **단일 서비스**로 모으고 "활성 클래스 코드 ∪ 활성 관계 코드 ∪ 활성 세션 코드" 집합에서 중복을 피한다. `/join` 의 해석 순서는 클래스 → 관계 → 세션(폴백).
- **정원·대기열 없음**: 이미 입장한 관계에 다른 기기가 같은 코드로 들어오면 대기열이 아니라 **409 + 상담사 알림**(`이미 진행 중인 상담이에요`).
- **회원 내담자**는 로그인 + 관계 기반 입장이라 코드가 필요 없다(현행 `enter_session_as_invited` 패턴).
- 오프라인 대면에서 내담자 기기 없이 상담사 기기로만 진행하는 경우: 세션 진행·기록은 가능(현행 오프라인 세션과 동일)하고 리포트는 관계의 이메일로 발송한다. 이때의 동의·녹음 고지 방식은 제품 UX 결정 필요(`미확인`).

### 4.4 개인정보 보관·삭제·연구 동의

- 비회원 개인정보는 세 곳에 존재할 수 있다: `session_participants`(회차 사본, 이전분), `counseling_guests`(관계 신원), `session_email_invites`(이전 방식). 스위프(B12)는 앞의 것과 초대 행만 스크럽하므로 **`counseling_guests` 를 스위프 대상에 추가**해야 한다(안 하면 보관 기간을 넘겨 남고, 하면 §6 의 "종결 후 보관"과 충돌).
- 스크럽 기준일(기본값): **종결일(`closed_at`) + 90일**, 종결 없이 마지막 세션만 있으면 마지막 세션 종료일 + 90일(`D-50`). 관계가 `active` 인 동안 스크럽하면 리포트 발송·재식별이 끊기므로 기준일을 세션 종료일이 아니라 관계 단위로 옮긴다. 스크럽 후 **이메일이 사라져 리포트 재발송·본인 재확인이 불가** → 사전 고지: `개인정보 보관 기간이 지나 다시 보낼 수 없어요`.
- 계정이 없어 열람·정정·삭제 요청 창구가 없다 → 리포트 메일 하단 "내 정보 삭제 요청" 링크 → 운영 접수 → 플랫폼 관리자 처리.
- 연구 동의: 상담에서도 받을지 `D-04`(기본: 받음, 선택, 기본 미동의, 고지 강화). 받는 경우 관계 첫 입장에서 1회, 이후 회차는 마지막 선택 승계. 음성·STT 원문은 연구 DB 에 싣지 않는다(현행 C4 유지). 가명 ID(이름 + 생년월일 HMAC)는 회차·관계를 넘어 동일하므로 회원 전환 후에도 같은 ID 가 유지된다.

### 4.5 회원 가입 시 기존 상담 기록 연결 (claim)

연결 시 갱신 대상: `counseling_guests.claimed_user_id` · 관계의 `client_user_id`(`client_guest_id` 는 출처로 보존) · 해당 관계 세션의 `session_participants.user_id` · 비회원 소유 4개 테이블의 nullable `user_id`(`eeg_records`·`eeg_raw_chunks`·`reports`·`eeg_feature_windows`). 데이터 이동은 없고 `user_id` 채움뿐이다. **회원 리포트 목록은 `Report.user_id` 필터이므로 `reports.user_id` 갱신은 필수**다.

| 방식 | 내용 | 오연결 위험 |
|---|---|---|
| **a. 토큰 + 이메일 일치 (기본값 1)** | 초대 메일의 가입 링크(claim 토큰, `client_invites` 패턴 재사용)로 가입 + 가입 이메일 = 사전 등록 이메일 + 이메일 인증 완료 | 낮음 — 가로챈 링크로 다른 이메일 가입 시 불일치로 거부 |
| **b. 이메일 일치 + 생년월일 확인 (기본값 2)** | 링크 없이 가입한 회원에게 "이 이메일로 받은 상담 기록이 있어요" 확인 화면 → 상담 때 입력한 생년월일 일치 시 연결 | 중간 — 상담사 이메일 오타로 **타인에게 기록 노출**될 위험 → 생년월일 일치 + 명시 동의 + 상담사 알림으로 완화 |
| c. 자격 보유 기기에서 "계정 만들기" | 자격 소지로 소유 증명 | 공용 기기·분실 시 위험 → 이메일 불일치는 상담사 승인 요구 |

기본값 = **a 와 b 병행, 자동 연결 금지(확인 화면 필수)**, 연결 후 상담사 알림 + `guest_claim_events` 기록(건수). 충돌: 회원이 이미 같은 상담사와 비-`archived` 관계를 갖고 있으면 **병합**(비회원 관계의 세션을 기존 관계로 이전, 비회원 관계는 `archived` + `merged` 이벤트, 한 트랜잭션). 연결 취소는 지원하지 않는다(이력 보존만, 오연결 정정은 플랫폼 관리자 경로). 연결 후 비회원 재방문 자격은 폐기하고 회원 로그인으로 통일한다. 연결 방식의 강도는 `D-52`.

## 6. 종결 · 보관 · 재개 (확정 반영)

### 6.1 현행 보관 3층 구조와의 관계 (`R10 §8.1`)

**"종결 후 데이터 보관"은 현행 보관 3층과 직교한다.** ① 영구층(관계·세션 메타·리포트·기록지 요약·상담사 메모·계정) ② 기간 삭제층(원본: EEG raw·음성·영상·STT 원문, 종료 후 90일) ③ 개인정보 스크럽층(비회원 PII, 90일). 종결은 ①을 지우지 않고, ②③의 기준일에도 영향을 주지 않는다(③만 관계 단위로 기준일 조정). 즉 "보관"의 기본 해석은 **영구층 보존**이며, 원본까지 영구 보관하려면 SDD-209 R5 에서 확정된 삭제 스위프(90일)의 예외를 두어야 하므로 비즈니스 결정이다(`D-49`).

### 6.2 종결 후 열람 권한 (기본값)

| 대상 | `closed` | `archived` | 현행 대비 변경 |
|---|---|---|---|
| 담당 상담사 | 기록·리포트·메모 **읽기**, 신규 세션 불가, 메모 마무리 수정 가능, 목록은 "마무리한 상담" | 읽기 전용, 기본 목록 숨김·검색 가능 | 현행 `ended` 는 목록·프로필·메모 모두 차단 → **변경 필요** |
| 내담자(회원) | 지난 세션·리포트 열람 유지(참여자 행 기반이라 가능) | 동일 | 상담사 계정 삭제 시 세션 `hidden_at` 로 열람 불가해지는 문제 → **상담 세션은 상담사 삭제 시 숨김 제외** |
| 내담자(비회원) | 종결 시 자격 폐기, 지난 리포트는 메일 링크/상담사 재발송 | 동일 | |
| AI 비서(상담사 채널) | 현행 유지: 담당 = `active` 만 조회. 종결 열람은 일반 UI 로 | 동일 | 재개 시 복귀 |
| 직접 채팅방 | 읽기 전용(전송 불가) | 읽기 전용 | 현행 `_ensure_member` 는 `status` 무시 → 전송 시 `active|pending` 확인 추가 |
| 센터 관리자 | 메타만 | 메타만 | |
| 플랫폼 관리자 | 감사 하 접근, 원본 기간 전 삭제 권한 | 동일 | SDD-209 R5-B 유지 |
| 기관 비활성화·소속 해제 차단 | `pending|active` 관계로 확장 | | "이관하거나 종료"가 실제로 가능해짐(현행 차단 문구가 요구하는 기능이 없음) |

### 6.3 재개 · 보관 기간

- **재개**: 기본 = **같은 관계 재개**(쌍 유일 제약 유지). 이력은 `counseling_relationship_events` 로 보존(현행의 `ended_at` 덮어쓰기 중단). 상담사가 종결한 건은 내담자 단독 재개 불가·승인 필요, 내담자가 종결한 건은 단독 재개 가능(`D-46`). `archived` 후 재상담 = **새 관계** + `predecessor_relationship_id`, 같은 상담사 화면에는 "이전 상담 기록 N건" 표시(다른 상담사면 §7 규칙).
- **보관 전환**: 종결 후 N일 자동(기본 365일, `D-47`) 또는 수동. `archived` 전환은 데이터를 지우지 않고 UI·권한만 바꾼다.
- **원본**: 종결과 무관하게 SDD-209 대로 세션 종료 후 90일 기간 삭제. 상담만 다르게 할지 `D-49`. 영구층 보관 상한은 법무 확인 사항(`D-48`).
- **계정 탈퇴·삭제**: 내담자 탈퇴 → 관계 `closed`(reason=`account_deleted`), 세션·리포트 유지. 상담사 삭제 → 관계 `closed`(reason=`counselor_left`) 후 이관 대상. 둘 다 계정 접근 테이블 DELETE 대상에서 **상담 관계를 제외**한다.
- 최초 활성화 안전장치(dry-run 후 승인, `RETENTION_SWEEP_ENABLED=false`)는 상담 단계 추가 시에도 동일하게 적용한다.
- 상태 머신 전이·금지는 `기획-상세-상태머신권한.md` §1.6.

## 7. 상담사 교체 / 이관 (초안)

모델: 관계는 상담사에 귀속 → **교체 = 기존 관계 `closed`(reason=`counselor_transfer`) + 새 상담사와 새 관계**(`predecessor_relationship_id` 연결). 과거 세션 `host_id` 불변.

| 항목 | 기본값 |
|---|---|
| 트리거 | ① 상담사 요청 ② 센터 관리자 이관(퇴사·휴직·소속 해제) ③ 내담자 요청 ④ 계정 정지·삭제 |
| 과거 세션·리포트 귀속 | `host_id`·리포트 작성/승인자 = 이전 상담사 그대로. 내담자 열람은 참여자 행 기반이라 영향 없음. 이전 상담사는 종결 후에도 본인 세션 읽기 전용 |
| 새 상담사의 과거 열람 | **요약(AI 요약·리포트)만, 내담자 동의 필수**. 비공개 메모·녹취 원문·EEG raw 는 제외. 회원 = 앱 내 동의 화면, 비회원 = 메일 링크 동의 (`D-58`) |
| 예정 세션 | 이전 상담사의 `ready`/`scheduled`/`open` 세션은 취소 + 내담자 알림 후 새 상담사가 재예약(세션 `host_id` 변경 비허용) |
| 승인 대기 리포트 | 승인은 host 만 가능 → 이전 상담사 부재 시 대리 승인 주체 필요(센터 관리자, 없으면 플랫폼 관리자 — `D-59`) |
| 채팅 | 새 상담사와 새 직접방, 이전 방은 읽기 전용 |
| 비회원 | 새 관계 코드 + 새 상담사 안내 메일. 자격 폐기. 같은 `counseling_guests` 행을 새 관계가 참조(PII 재입력 불요, 동의 메일 포함) |
| 범위 | 같은 센터 내 이관. 기관 간은 내담자 동의 후 새 관계(이관 아님) |
| 감사 | `transferred_out`/`transferred_in` 이벤트(양쪽 관계) |
| 기관 비활성화 | active 관계가 이관·종결로 정리되면 차단 해제 |

이관 UI·API 는 Phase 8 범위(현재 기능 자체가 없음).

## 8. 한 계정 두 영역 — 권한·통계·알림·충돌 (`R10 §7`)

| 영역 | 현행 | 규칙 |
|---|---|---|
| 권한(소유) | 모두 `host_id` 기준, type 무관 | 접근 판정은 **상위 개체 소유**로 통일, 영역 간 교차 접근 없음 |
| 센터 관리자 | 리포트 본문 열람·수정 허용(활동 조회는 "상담 내용 비노출"로 불일치) | **상담 영역은 메타(건수·일정)만**, 본문·리포트·기록지 비공개. 명상 영역은 `D-28` |
| 통계 | 대시보드 합산이 type 무시(`total_classes` 등), 내담자 홈 "다음 세션"·"오늘 세션 수"도 type 무시 | 응답에 `by_area: {meditation:{…}, counseling:{…}}` 추가(**기존 합계 필드는 호환 유지**). 상담 = 활성 관계 수·세션 수·승인 대기, 명상 = 클래스 수·참가자 수. **참가자 수를 합산하지 않음**(1:1 과 그룹 인원이 섞임). 홈 "오늘 일정"은 두 영역 통합 목록 + 영역 칩 |
| 알림 | 설정은 이벤트 키 단일 사전, 문구 하드코딩("새 세션 예약" 등) | 이벤트 키 불변·설정 UI 영역별 분리 없음. payload 에 `area` 필드, 제목·본문 영역별 템플릿("새 상담 예약" vs "새 클래스 회차"), 딥링크 영역별(`/counseling/{id}` vs `/classes/{id}`) |
| 자동 승인 | `users.auto_approve_report` **계정 단일 불린** — 명상에서 켜면 상담 리포트도 자동 발송 | **영역별 2개로 분리**, 상담 기본 off (`D-37`) |
| 리포트 목록 | `/reports` 단일 | 영역 탭/필터 |
| 채팅 | 직접방 = (상담사, 내담자) 쌍 | 상담 관계와 1:1 대응. 명상 클래스 회원과의 직접방은 별개로 존속 |
| 시간 충돌 | `detect_conflict` 는 host 단위·type 무관·단일 `sessions` 테이블 | **이미 통합 검사**. 상담 전용 엔드포인트(M5)도 반드시 이 함수를 공유(영역별 필터 금지). 반복 상담 예약 N회는 일괄 검사. 내담자 쪽 충돌은 정보성 경고(비차단) |
| 호칭 | 두 영역 모두 `상담사` | 호칭은 **그 화면의 영역**을 따른다(계정 칭호가 아니라 화면 기준): 명상 화면 `지도사`, 상담 화면 `상담사`, 데이터·권한 문서 `강사` (`D-62`) |

## 9. 기존 `sessions.type` 의 이전 매핑 (`R7 §4.1`, `R10 §4.4`)

`sessions.type` 값은 **변경하지 않고 유지**한다(연구 번들·라벨 호환). 영역은 부모 FK 로 표현한다. type 으로 **엔진이 갈라지는 곳은 3종뿐**(STT 화자 프롬프트, 요약 템플릿, 신규 입력에서 사실상 무효인 정원 정규화)이라 엔진 무변경이 가능하다.

| 순서 | 조건 | 상위 | 규칙 코드 |
|---|---|---|---|
| 0 | `is_template` | 이전 안 함(contract 단계에서 `class_templates` 로) | — |
| 1 | `type='meditation'` | 명상 클래스 | C1 |
| 2 | `clinical`/`hypnosis` 이고 활성 참여자 ≥ 2 | 명상 클래스(유형 불일치 표시, 라벨 유지) | C3 — `D-55` |
| 3 | `clinical`/`hypnosis` 이고 활성 참여자 = 1(회원) | 상담 관계(회원) | R1 |
| 4 | 〃 활성 참여자 = 1(비회원) | 상담 관계(비회원, 세션당 관계 1) | R2 |
| 5 | 〃 활성 참여자 = 0 | 상담 관계(내담자 미상 placeholder, 상담사당 1개, 삭제 금지) | R3 — `D-57` |
| 6 | `custom` 이고 (`participant_mode='group'` 또는 참여자 ≥ 2) | 명상 클래스 | C2 — `D-56` |
| 7 | `custom` 그 외 | 상담 관계 | R1/R2/R3 |

- 정원(`max_participants`)으로 그룹/1:1 을 판정하지 않는다(기본 정원이 10 이라 상담도 10 일 수 있음). `participant_mode` 도 type 과 독립이므로 type 규칙이 우선하고 `custom` 에서만 보조 지표로 쓴다.
- **조사 간 이견**: R10 은 상담 유형이라도 `participant_mode='group'` 이면 집단 상담으로 보아 클래스로 보내자고 하고, R7 은 Brian 규칙("clinical·hypnosis → 상담")을 우선해 **참여자 수만** 본다. 기본값은 R7(참여자 수). (clinical/hypnosis, `group`, 활성 참여자 ≤ 1) 건수를 사전 조회(R7 §3.2 D-1·D-2)로 확인한 뒤 갈리면 `D-55` 에서 함께 결정한다.
- 회원 1명짜리 상담 세션은 `(host_id, 회원 user_id)` 쌍으로 **한 관계에 묶는다**(`seq` = `coalesce(scheduled_at, started_at, created_at)` 순). 비회원은 세션 간 동일인 증거가 없고 정책상 이름 일치로 인계하지 않으므로 세션당 관계 1개(`D-57`).
- `custom` 은 `custom_type_name` 키워드(명상·마음챙김·호흡·요가·MBSR → 명상 / 상담·치료·코칭·심리·면담 → 상담)로 초안을 만들고 충돌·모호건은 "분류 확인 필요" 목록으로 호스트에게 1회 질문한다(`D-56`).
- 이전된 활성 상담 세션의 4자리 코드는 호환 기간 동안 그대로 동작한다(신규 발급은 관계 단위로만).
- 이전된 비회원 상담 관계는 재방문 신원(`reentry_secret_hash`)이 없어 **재방문 불가 → 다음 상담 때 초대 재발송 안내**(`D-63`).
- 이전 후 새 코드는 `POST /sessions` shim 으로 구 앱이 부모 없이 생성해도 같은 분류 함수로 부모를 자동 생성한다.

## 11. 미확인

1. DB 의 type 분포·`custom_type_name` 분포·집단 상담(clinical/hypnosis + group) 건수·상담 후보 (상담사, 회원) 쌍 수·비회원 상담 참여자 수 — 분포 조회 SQL(R7 §3.2, R10 §4.4 Q1~Q5)은 **미실행**.
2. 1:1 세션에서 발언권/`can_publish` 가 항상 허용되는지.
3. 상담사 삭제 시 세션 `hidden_at` 숨김이 내담자(회원) 화면의 세션·리포트 열람을 실제로 막는지(ORM 필터 동작은 코드 해석, 실행 미검증).
4. `request_report_email` 의 OTP 요구 경로를 프론트가 아직 쓰는지.
5. 상담사 대기실에 "입장 승인" 기능을 얹을 수 있는지(SDD-209 가 후속으로 남긴 항목, FH06 로비 구조) — 코드 미확인. 불가하면 Phase 7 의 신규 작업 규모가 커진다.
6. 시도 제한(`class_code_attempt_service`)이 관계 코드에도 그대로 쓰일 수 있는지 — 본문 미열람.
7. 개인정보보호법상 상담 기록·리포트 보유 상한(`D-48`) — 법무 확인.
8. 직접 채팅방 유일 제약(DB 레벨) 및 `name=str(client_id)` 저장 방식의 마이그레이션 영향.
9. 기관 간(타 센터) 상담사 이관 시 내담자 `users.org_id`/membership 영향.
10. 오프라인 대면 비회원 상담에서 내담자 기기 없이 진행할 때의 동의·녹음 고지 방식.
11. 내담자 앱에서 상담사 목록·"내 상담" 화면의 현행 구성(`ClientSessionListPage`·`ClientHomePage` 본문 미읽음).
