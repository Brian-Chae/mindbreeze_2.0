# 워커 브리프 — 클래스·세션 구조 재설계 기획 (Phase 1: 문서만, 코드·시안 수정 금지, 커밋·푸시 금지)

## 배경 (Brian 확정, 먼저 읽을 것: `docs/클래스-세션-개념-재정의_메모.md`)
- **클래스 = 프로그램(상위)**, **세션 = 클래스의 회차(하위)**. 예: "MBSR 봄 클래스"의 3번째 세션. 상담은 "채용욱 상담"의 4번째 세션.
- 현재는 `sessions` 테이블 1개가 단회차 단위이고, 화면에서는 이것을 "클래스"라고 부른다(SDD-208/209 에서 "세션→클래스" 치환). 상위 개념 없음.
- 확정: 회원은 **결석·보강·중간 합류·이탈** 가능 / 주 고객은 명상 센터 → 화면 용어는 **"클래스"** (상담센터 고객이 늘면 "상담 세션" 유형을 별도로 연다) / 명상 클래스는 **회차 고정형**(예 8회) + **정기형**(회차 계속 이어짐) 둘 다 / 기존 단회차 데이터 → **클래스 1개 + 세션 1개**로 이전.
- 사용자: Brian(CEO·CTO). 비즈니스 결정만 묻는다. 기술 선택은 기본값을 제안하라. 문서는 개조식, 한글, 해요체 UI 문구.

## 조사 과제 (근거는 파일:줄·실행 결과, 확인 못 하면 `미확인`)
- **R1 데이터 모델**: `backend/app/models/{session,record,chat,notification,...}.py` 에서 `sessions.id`/`session_id` 를 FK·참조하는 모든 테이블·컬럼, `run_id`·`is_template`·`access_code` 의 실제 용도, SDD-209 에서 추가된 컬럼(`0042`~`0051` 마이그레이션 요약), 클래스 단위로 올릴 것(정원·초대·동의·4자리 코드·참여 방식·LINK BAND 모드·녹음 설정)과 세션에 남길 것(일정·상태·입장·기록·리포트·EEG)을 컬럼 단위로 분류한 표.
- **R2 API·서비스 영향**: `backend/app/api/v1/*`, `services/session_service.py` 등에서 세션 중심 엔드포인트·함수 목록과 호출 수(grep), 클래스 개념 도입 시 신규/변경/호환 유지 분류. WebSocket 룸·알림·리마인더·리포트 생성·STT 파이프라인·권한(회원이 볼 수 있는 범위)·org_admin 영향.
- **R3 프론트 영향**: `frontend/src/` 의 세션 목록·상세·만들기·홈·플레이어·입장 전 흐름(SDD-209)에서 "클래스 = 세션 1건" 가정이 박힌 곳(타입 `SessionResponse` 사용 파일 수, 라우트 `/sessions/:id`·`/class/:id/enter` 등), 새 정보 구조(클래스 목록 → 클래스 상세(회차 타임라인) → 세션 입장)로 바꿀 때 화면별 재사용/재설계/신규 분류. 시안 자산 `designs/class-flow-redesign/`, `designs/class-player-redesign/` 중 그대로 쓸 수 있는 것.
- **R4 회원·참여 모델**: 현재 `session_participants`(회원/비회원 4자리 코드/초대/대기열/동의/리포트 반영 선택/연구 동의)를 **클래스 멤버십 + 회차별 출석**으로 분리하는 안. 결석·보강·중간 합류·이탈 각각이 데이터로 어떻게 표현되는지, 정원·대기열이 클래스 단위인지 회차 단위인지, 비회원(4자리 코드)이 클래스 멤버가 되는 경로, 동의(리포트 반영·연구)를 클래스 가입 시 1회 vs 세션마다 확인하는 옵션별 장단(SDD-209 R4/R5 정책 `specs/sdd-209-class-flow-redesign/policy-revision-r4.md` 와 정합).
- **R5 회차 운영**: 고정형(총 N회·일괄 예약·요일 반복)과 정기형(끝 없음·다음 회차 자동 생성) 생성 UX·데이터, 회차 변경/취소/보강 회차 추가, 시간 충돌 검사 단위, 리마인더, 상담(1:1 클래스 = 회원 1명 + 상담사, 회차 계속 추가)과의 통합.
- **R6 리포트·분석**: 세션 리포트(현행)와 **클래스 단위 추이·회차 비교·출석**(새 가치)의 범위 제안. 명상/웰니스 리포트 원칙(점수 환원·종합점수·순위 금지, 서사+변화량만)과 회원용/상담사용 구분 유지. 기존 `narrative_cache`·정규화 베이스라인이 클래스 단위로 어떻게 연결되는지.
- **R7 이전(마이그레이션)**: 기존 `sessions` 행마다 클래스 1개 + 세션 1개 생성(제목·유형·호스트·기관·참여자 이전), 이미 만들어진 4자리 코드·초대 링크·알림 딥링크·구 앱(Capacitor 번들, 강제 업데이트 없음) 호환, 추가형(nullable)·롤백 트랩(DB 되돌림 없음, `deploy-dev.yml`) 전제 단계 계획, 이전 dry-run·검증 쿼리 설계.
- **R8 용어·IA**: "클래스(프로그램)/세션(회차)" 확정 후 SDD-209 가 치환한 "세션→클래스" 문구·라벨·알림 문구·E2E 단언에서 되돌릴/유지할 범위 목록(대략 건수), 회원 홈 "다음 일정" 표기(`MBSR 봄 · 3회차`), 상담사 목록·상세 정보 구조.
