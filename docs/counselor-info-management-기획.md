# 상담사 정보 관리 기획안

- 작성일: 2026-09-17
- 단계: Phase 1 서비스 기획 / 검토용 제안. 구현·마이그레이션·배포를 수행하지 않는다.
- 목표: 플랫폼 관리자, 기관 관리자, 상담사 본인이 필요한 범위에서 상담사 정보를 조회·수정하고, 기관 주 담당자의 계정 정보를 정정한다.
- 권장 방향: 기존 `User` + `CounselorProfile` + `Career` + `Qualification`을 재사용한다. 일반 정보 수정은 간단히 제공하고, 개인정보 정정과 이메일 변경에는 별도 조건을 둔다.

## 1. 현재 구조와 브리프 정정

- **현재 체크아웃 확인 결과, “상담사에는 성별·생년월일이 없다”는 브리프의 전제가 실제 코드와 다르다.** 아래는 소스 확인 결과이며 운영 DB 적용 상태를 의미하지 않는다.
- `User` (`users`): `name`, 고유 `email`, `phone`, `role`, `status`, `org_id`, `profile_image`, `bio`, `verified_tier`, `auth_provider`, 초대 시각 등이 존재한다. `gender`, `birth_date`, 개인 주소는 없다.
- `CounselorProfile` (`counselor_profiles`): `user_id`, `counselor_code`, `specialties` 외에 **`gender`, `birth_date`, `years_of_experience`, `affiliation_type`, `profile_image_url`, `bio`도 이미 존재**한다. 주소는 없다.
- `ClientProfile`에도 성별·생년월일이 있지만 별도 회원 정보다. 상담사 정보를 이 테이블에서 가져오거나 자동 복제하지 않는다.
- `Career` (`careers`), `Qualification` (`qualifications`)이 이미 `user_id`로 연결된다. 경력·자격 테이블을 새로 만들 필요가 없다.
- 상담사 초대는 `org_service.invite_counselor`가 `User(role=counselor, status=pending)`와 상담사 코드를 가진 `CounselorProfile`을 생성한다. 개인정보 누락을 이유로 초대를 막지 않는다.
- 상담사 온보딩은 성별·생년월일·경력 연수·전문분야를 입력받고, 백엔드 `counselor_step2`가 상담사 프로필에 저장한다.
  - 프런트엔드가 `experience_years`, 백엔드가 `years_of_experience`를 사용하는 계약 차이가 보인다. 구현 시 실제 요청·스키마 회귀 검증이 필요하다.
- 본인 설정에 `AccountSection`, `ProfileSection`과 `GET/PATCH /api/v1/auth/counselors/me/profile`이 이미 있다. 현재 상담사 프로필 응답·수정 스키마에는 성별·생년월일·주소가 없다.
- `PATCH /api/v1/auth/users/me`의 성별·생년월일은 `ClientProfile` 경로다. 상담사 정정 기능으로 재사용하지 않는다.
- 기관 상세 모달은 주 담당자 조회와 상담사 목록을 제공한다. SDD-076은 플랫폼 관리자의 역할 변경·소속 해제이며, 개인정보 수정 기능과 구분한다.
- 기관 주 담당자는 `Organization.primary_admin_id → User`다. 이름·이메일·전화번호의 원본은 `User`이며 기관 테이블에 복제하지 않는다.
- `kind=individual`의 `owner_user_id`는 개인 기관 소유 상담사다. 주 담당자(`primary_admin_id`)와 같은 의미로 취급하지 않는다.

## 2. 저장 구조와 필드 정의

### 2.1 대안 비교와 권장안

- **권장: `CounselorProfile` 확장 + 기존 경력·자격 테이블 재사용.** 계정 공통 정보는 `User`, 상담사 인적사항·전문 정보는 상담사 프로필에 둔다. 신규 개인 주소와 수정 충돌 방지 필드만 추가하여 변경 범위를 줄인다.
- 대안: `User`에 성별·생년월일·주소를 통합한다. 역할 간 공통화는 가능하지만 회원 프로필 이관, 중복 값 충돌, 기존 응답 계약 변경이 필요하므로 이번 범위에서는 제외한다.
- 대안: 별도 공통 개인정보 테이블을 만든다. 접근 통제를 분리하기 좋으나 현재 목적에는 조회·이관 구조가 과해 후속 다중 역할 요구가 생길 때 검토한다.
- 경력·자격을 자유 텍스트 하나나 신규 JSON 필드로 합치지 않는다. 기존 구조화된 항목을 유지한다.

### 2.2 계정 기본 정보 — `User` 유지

- `name`: 이름, 필수 문자열 1~100자. 공백만 입력 불가. 상담 화면·채팅 등에서 사용되는 공통 이름이며 관리자 수정 시 영향 안내.
- `email`: 로그인·알림 이메일, 필수·고유. 일반 프로필 저장에서 변경 금지. 6절의 별도 재인증 흐름만 허용.
- `phone`: 연락처, 선택 문자열 최대 20자. 국제 번호를 허용하며 형식 검증·정규화. 입력 여부와 번호 소유 인증 여부를 혼동하지 않는다.
- `profile_image`, `bio`: 기존 본인 설정의 계정 사진·소개 원본을 유지한다. 상담사 프로필의 레거시 값은 현재 조회의 대체값 처리와 호환하되 신규 중복 쓰기를 만들지 않는다.
- `role`, `status`, `org_id`, `verified_tier`, `auth_provider`: 정보 수정 요청에 포함하지 않는다. 기존 역할·소속·계정 관리 흐름으로 분리한다.

### 2.3 상담사 인적사항 — `CounselorProfile`

- `gender`: **기존 필드 활용**. `male` / `female` / `other` / `null`. UI는 남성/여성/기타/응답하지 않음. `null`을 특정 성별로 추정하지 않는다.
- `birth_date`: **기존 필드 활용**, 선택 `DATE`, `YYYY-MM-DD`. 실제 날짜·미래 날짜 여부 검증. 연령을 별도 저장하거나 임의의 기본 생일을 채우지 않는다.
- `postal_code`: 신규 제안, 선택 문자열 최대 20자. 숫자형 사용 금지.
- `address_line1`: 신규 제안, 선택 문자열 최대 300자. 도로명·기본 주소.
- `address_line2`: 신규 제안, 선택 문자열 최대 200자. 상세 주소. 우편 발송 등 사용 목적이 없으면 수집을 요청하지 않는다.
- 주소는 상담사 **개인 연락·우편 주소**이며 기관 주소(`Organization.address`)와 구분한다. 기관 주소를 기본값으로 복사하지 않는다.
- `version`: 신규 제안, 정수 기본 1. 계정 기본 정보·상담사 프로필·경력·자격을 묶은 편집 충돌 검사에 사용한다. 기존 모든 관련 쓰기 경로도 같은 버전을 갱신해야 한다.
- 기존 데이터는 보존하고 신규 선택 필드는 `null`로 시작한다. `ClientProfile`에서 자동 이관하지 않는다.

### 2.4 이력 — 기존 구조 활용

- 전문분야: `CounselorProfile.specialties`, 문자열 목록. 선택지와 기타 항목을 유지하고 중복 제거·최대 10개 제안.
- 경력 연수: `CounselorProfile.years_of_experience`, 선택 0 이상의 정수. 자기 기재 값이며 경력 기간의 중복을 단순 합산하여 덮어쓰지 않는다. 미입력과 0년은 구분한다.
- 경력: `Career.organization`(기관명, 필수), `role`(직무), `started_at`, `ended_at`, `is_current`를 재사용한다. 종료일은 시작일 이전 불가, 재직 중이면 종료일 없음.
- 자격: `Qualification.name`(필수), `issuer`, `issued_at`를 재사용한다. 미래 취득일은 허용하지 않는다.
- `affiliation_type`: 기존 전문 활동 형태 값이다. 실제 기관 소속은 `User.org_id`만을 기준으로 검사하며 이 필드 수정으로 소속이 바뀌지 않는다.
- `Career.id`, `Qualification.id`를 유지하는 항목별 수정 방향을 권장한다. 현재 전체 삭제 후 재삽입 방식은 이력 추적에 불리하므로 구현 계획에서 변경 범위를 명시한다.
- 자격 텍스트 입력과 증빙 심사는 분리한다. 정보 수정으로 `verified_tier`를 승격하지 않는다. 증빙과 연계된 자격이 바뀌면 후속 심사 대상으로 표시하고 기존 인증을 새 내용에 자동 승계하지 않는다.
- 신규 자격증 번호·증빙 파일·학력 항목은 MVP에서 추가 수집하지 않는다.

## 3. 권한 매트릭스

- 아래 매트릭스는 각 필드의 **수정 권한**이다. 기관 관리자는 현재 소속 상담사에 한정하고, 상담사는 본인만 수정한다.
- 표기: **가능**=일반 수정 / **조건부**=아래 조건 충족 / **불가**=해당 정보 수정 기능에서 차단.

| 필드 | 플랫폼 관리자 | 기관 관리자 | 상담사 본인 |
|---|---|---|---|
| 이름 | 가능, 사유 필수 | 가능, 사유 필수 | 가능 |
| 전화번호 | 가능, 사유 필수 | 가능, 사유 필수 | 가능 |
| 사진·소개 | 가능, 사유 필수 | 가능, 사유 필수 | 가능 |
| 경력·경력 연수·전문분야·활동 형태 | 가능, 사유 필수 | 가능, 사유 필수 | 가능 |
| 자격 기재 내용 | 가능, 사유 필수 | 가능, 사유 필수 | 가능, 인증 등급 변경 불가 |
| 성별 | 조건부, 정정 사유·최근 재인증 | 불가 | 조건부, 최근 재인증 |
| 생년월일 | 조건부, 정정 사유·최근 재인증 | 불가 | 조건부, 최근 재인증·정정 사유 |
| 개인 주소 | 조건부, 정정 사유·최근 재인증 | 불가 | 가능 |
| 이메일 | 조건부, 변경 요청 시작만 | 조건부, 변경 요청 시작만 | 조건부, 재인증·새 주소 인증 |
| 상담사 코드 | 불가 | 불가 | 불가 |
| 역할·소속·상태·인증 등급 | 불가, 별도 관리 기능 이용 | 불가, 별도 관리 기능 이용 | 불가 |

### 3.1 조회 범위와 공통 조건

- 플랫폼 관리자: 전체 상담사 일반 정보를 조회한다. 성별·생년월일·주소는 기본 응답에서 제외하고, 업무 사유 입력 및 최근 재인증 후 별도 개인정보 보기에서 조회·정정한다. 조회도 감사 대상이다.
- 기관 관리자: 동일 기관 상담사의 이름·이메일·전화·전문 이력을 조회한다. 성별·생년월일·개인 주소는 응답에서 제외하고 검색·내보내기에도 포함하지 않는다.
- 상담사 본인: 자신의 정보를 모두 조회한다. `org_id=null`인 상담사도 본인 설정을 이용할 수 있다.
- `org_admin`으로 승격된 기존 상담사는 `CounselorProfile` 보유 여부로 본인 상담사 설정 접근을 유지한다. `role=org_admin`이라는 이유만으로 상담사 프로필을 자동 생성하지 않는다.
- 기관 관리자가 다른 기관 관리자의 계정 정보를 일반 상담사 편집 경로로 수정하지 못하게 한다. 기관 관리자 대상은 본인 수정 또는 플랫폼 관리자 수정만 허용한다.
- 관리자에 의한 수정은 변경 사유 필수이며 대상자에게 변경 항목·행위자 구분을 알린다. 알림에 생년월일·주소 원문을 넣지 않는다.
- 정지된 행위자, 미인증 초대 계정의 쓰기를 차단한다. 초대 대기 대상의 이름·전화는 관리자가 정정할 수 있지만 자격 인증이나 초대 수락 상태를 변경하지 않는다.
- 비활성 기관에서는 기관 관리자 대리 수정을 차단한다. 플랫폼의 정정과 활성 상담사의 본인 정보 정정은 별도 허용한다.

### 3.2 성별·생년월일 정책

- 선택 입력을 기본으로 하고 미입력 상태로 상담 업무를 이용할 수 있게 한다. 기존 온보딩도 같은 정책에 맞추는 작업을 구현 범위에 포함한다.
- 본인은 최근 10분 이내 재인증 후 등록·정정·삭제할 수 있다. 생년월일 변경은 짧은 사유를 남기고 반복 변경을 제한한다.
- 플랫폼 관리자는 업무상 정정 사유가 있을 때만 수정한다. 기관 관리자에게는 수정 요청을 본인에게 안내하는 경로를 제공한다.
- 잠금 해제나 나이 조작 방지를 이유로 영구 수정 금지하지 않는다. 오입력 정정 경로를 유지하고 최초값→새값 감사 기록은 제한된 저장소에서 보호한다.
- 성별·생년월일·주소를 업무상 보호가 필요한 개인정보로 취급하는 제품 정책이다. 법률상 민감정보 분류에 대한 단정은 하지 않는다.

## 4. 역할별 화면 기획

### 4.1 플랫폼 관리자 — 기관 관리

- `admin/OrgManagementPage` → 기관 상세 모달 → 상담사 탭의 기존 테이블 유지.
- 열: 이름, 이메일, 상담사 코드, 역할, 상태, 작업. 검색은 이름·이메일·코드, 필터는 역할·상태. 개인정보를 목록 열에 추가하지 않는다.
- 행 작업에 `정보 수정` 추가. 기존 `역할 변경`, `소속 해제`와 저장 동작을 분리한다.
- 편집은 기존 모달 내부의 상세 패널로 전환한다. 기본 정보 / 전문 이력 / 개인정보를 구분하고 한 화면에서 저장·취소한다.
- 개인정보 영역은 닫힌 상태로 시작하며 별도 조회 조건을 통과한 경우에만 값을 가져온다.
- 소속 없는 상담사가 누락되지 않도록 기관 관리에 `미소속 상담사` 진입점 추가. 동일 테이블·편집 패널을 재사용하고 기관을 임의 생성하지 않는다.
- 개인 기관 소유 상담사는 주 담당자 편집 대신 상담사 편집으로 연결한다.

### 4.2 기관 관리자 — 소속 상담사 목록

- `pages/org/OrgManagementPage`의 소속 상담사 목록에 테이블·검색·상태 필터·정보 수정 버튼을 제공한다.
- 허용 범위인 이름·전화·사진·소개·전문 이력을 편집한다. 이메일 옆에는 일반 입력 대신 `변경 요청`을 둔다.
- 성별·생년월일·주소 영역 자체를 노출하지 않는다. API가 제공하지 않는 값을 프런트에서 숨기기만 하는 방식은 금지한다.
- 다른 기관 관리자 행은 조회만, 본인 행은 본인 설정으로 이동한다. 소속 해제 직후 열린 편집 화면은 저장 실패 안내 후 재조회한다.
- 조회 오류를 빈 목록으로 표시하지 않는다. 불러오기 실패·권한 없음·실제 0명 상태를 구분한다.

### 4.3 상담사 본인 — 설정

- 기존 `SettingsPage`의 계정 정보·프로필 섹션을 확장한다. 별도 프로필 관리 앱이나 복잡한 승인함을 만들지 않는다.
- 기본 정보: 이름·전화·사진·소개. 개인정보: 성별·생년월일·주소, 수집 목적·선택 입력 안내.
- 전문 이력: 경력·자격 항목 추가/수정/삭제, 전문분야 다중 선택, 경력 연수 입력.
- 이메일: 현재 주소는 읽기 전용, `이메일 변경` 버튼으로 별도 절차 시작. 인증 대기 상태와 취소 동작 표시.
- 저장 시 변경된 필드만 전송하고 성공 후 서버 응답을 반영한다. 미저장 닫기 확인, 처리 중 중복 저장 차단, 실패 시 입력 보존.
- 좁은 화면에서도 입력·저장 버튼이 잘리지 않게 배치하고 모든 입력에 레이블·오류 설명·키보드 접근을 제공한다.

### 4.4 기관 주 담당자 수정

- 기관 상세 모달의 주 담당자 카드에 `담당자 정보 수정` 버튼을 추가한다.
- 대상은 저장 직전 `Organization.primary_admin_id`로 다시 조회한 `User`다. 이름·전화 수정 및 이메일 변경 요청을 제공한다.
- 플랫폼 관리자: 모든 기관 주 담당자를 수정할 수 있다. 기관 관리자: 자신이 주 담당자인 경우 본인 정보만 수정한다. 다른 기관 관리자가 주 담당자 계정을 수정하는 것은 차단한다.
- 주 담당자에 상담사 프로필이 없어도 이름·전화·이메일 업무는 가능해야 한다. 성별·생년월일·주소·이력을 입력받기 위해 프로필을 생성하지 않는다.
- `Organization.phone/address`는 기관 연락처이며 주 담당자 전화·개인 주소와 별개다. 저장 시 기관 연락처를 덮어쓰지 않는다.
- 주 담당자 미지정은 `담당자 미지정`, 삭제·참조 오류는 `담당자 정보를 확인할 수 없음`으로 구분한다.
- 담당자의 신원 정보 정정과 **담당자 교체**는 다르다. 이번 수정 API는 `primary_admin_id`를 바꾸지 않는다. 교체는 별도 후속 기능이다.
- 저장 성공 후 담당자 카드·상담사 목록·기관 목록을 함께 갱신한다. 변경 중 담당자가 교체되었다면 충돌로 중단한다.

## 5. API(응용 프로그램 인터페이스) 설계 방향

- 아래 경로는 공통 `/api/v1` 기준이며, 기존 경로와 신규 제안을 구분한다.
- 기존 본인 `GET/PATCH /auth/counselors/me/profile` 확장: 일반 정보·전문 이력·주소와 `version` 제공. 성별·생년월일 수정에는 재인증 조건 적용. 이메일과 권한 필드는 일반 PATCH에서 거부.
- 신규 플랫폼 `GET/PATCH /admin/counselors/{user_id}/profile`: 전체·미소속 상담사까지 처리. `GET /admin/counselors?org_id=...&unassigned=...&q=...&status=...`로 목록 보완. 기존 기관별 목록 반환 형식은 유지.
- 신규 플랫폼 `POST /admin/counselors/{user_id}/private-access`: 사유·재인증을 검사하여 개인정보 조회. 응답은 캐시 금지. 개인정보 수정은 별도 `PATCH /admin/counselors/{user_id}/private-profile`에서 같은 조건 검사.
- 신규 기관 `GET/PATCH /org/{org_id}/counselors/{user_id}/profile`: 동일 기관의 허용 대상만, 기관 관리자용 응답 스키마 사용.
- 신규 주 담당자 `PATCH /admin/orgs/{org_id}/primary-admin/profile`: 이름·전화·수정 사유·기대 담당자 ID·버전 전달. 이메일은 별도 변경 요청.
- 신규 본인 기관 관리자 `GET/PATCH /auth/users/me/contact`: 이름·전화·이메일 조회 및 이름·전화 수정, 상담사 프로필 없는 계정도 지원. 범위가 다른 기존 `/auth/users/me`의 회원 인적사항 기능은 유지.
- 신규 이메일 `POST /auth/users/me/email-change-requests`, `POST /auth/email-change-requests/{request_id}/confirm`, `DELETE /auth/users/me/email-change-requests/{request_id}` 제안.
- 관리자 시작 경로: `POST /admin/users/{user_id}/email-change-requests`, `POST /org/{org_id}/counselors/{user_id}/email-change-requests`. 주 담당자 요청도 플랫폼 경로를 이용하며 기관 소속·담당자 일치 검사를 추가한다.

### 서버 검사·동시 수정·호환성

- 공통 서비스에서 행위자의 최신 DB 역할·상태, 대상 유형, 현재 소속, 필드별 허용 목록을 검사한다. 화면·토큰의 과거 역할값만 믿지 않는다.
- 기관 URL의 `org_id`, 행위자의 `org_id`, 대상의 `org_id`가 모두 일치해야 한다. 타 기관 대상은 404, 권한 없는 필드 요청은 403, 유효하지 않은 값은 422.
- 허용하지 않은 필드를 조용히 무시하지 않고 전체 요청을 거부한다. `role`, `org_id`, `verified_tier` 등 대량 할당 우회 차단.
- PATCH 의미: 미전송은 유지, 허용된 `null`은 삭제, 빈 배열은 전체 항목 제거. 필수 이름에 `null`·공백 불가. 선택 전화·주소 삭제도 명시적으로 지원한다.
- 경력·자격 항목 ID는 대상 사용자 소유인지 검사한다. 없는 프로필은 임의 코드로 생성하지 않고 기존 생성 정책·고유 코드 서비스를 통하도록 구현 계획에 명시한다.
- 상담사 프로필 묶음은 `version` 기반 낙관적 잠금(동시 수정 충돌 검사)을 적용한다. 주 담당자 연락처에는 신규 `User.contact_version`을 제안한다. 상담사 연락처 수정 시 두 버전을 함께 증가시킨다.
- 다른 경로의 이름·전화·온보딩·경력 변경도 관련 버전을 증가시켜 우회 덮어쓰기를 막는다. 이전 버전이면 409와 재조회 안내, 입력값은 화면에서 보존한다.
- 기관 관리 경로는 SDD-076과 일관된 기관→사용자→프로필 잠금 순서 및 잠금 후 소속 재검사를 적용한다. 정보 수정 중 역할 변경·소속 해제가 일어날 때 권한을 다시 판단한다.
- 변경 내용과 감사 기록은 한 DB 트랜잭션으로 저장한다. 알림은 커밋 후 실패 재시도 대상으로 분리하며 저장 성공을 알림 실패로 되돌리지 않는다.
- 기존 이름 변경 시 채팅 프로필 갱신 등 부수 효과를 재사용한다. 상담 기록·과거 보고서의 이름 스냅샷을 일괄 재작성하지 않는다.
- 일반 목록은 최소 필드와 페이지 단위 조회를 사용한다. 경력·자격·개인정보는 상세에서 가져오고 일괄 선조회로 N+1 쿼리를 피한다.
- 새 제한을 기존 온보딩·본인 프로필 API에도 적용한다. 새 API만 안전하게 만들고 과거 쓰기 경로로 우회 가능한 상태로 출시하지 않는다.

## 6. 이메일 변경·개인정보 보호·감사 기록

### 6.1 이메일 변경

- 이메일은 계정 식별자다. 플랫폼 관리자도 일반 저장으로 즉시 덮어쓸 수 없다.
- 본인: 최근 재인증 → 새 주소 입력 → 인증 메일 발송 → 새 주소 소유 확인 → 고유성 재검사 → 원자적 변경.
- 관리자: 변경 사유와 새 주소로 요청 시작 → 대상자 본인의 로그인·최근 재인증 및 명시적 승인 → 새 주소 인증. 새 메일 수신만으로 기존 계정 소유권을 이전하지 않는다.
- 대기 중에는 기존 `User.email`과 로그인 수단을 유지한다. 새 주소는 별도 `EmailChangeRequest` 제안 저장소에서 관리한다.
- 제안 필드: `user_id`, `requested_by`, `new_email`, `token_hash`, `expires_at`, `status`, `reason`, `created_at`, `confirmed_at`. 토큰 원문은 저장하지 않는다.
- 인증 유효시간 30분, 재발송 간격 60초, 계정당 진행 요청 1개를 초기 정책으로 제안한다. 재발급 시 이전 토큰 무효화, 토큰 용도·대상 결합, 일회성 소비, 시도 횟수 제한.
- 요청·완료 시 모두 중복 이메일을 검사하고 DB 고유 제약을 최종 기준으로 삼는다. 완료 충돌은 409이며 기존 이메일을 보존한다.
- 변경 완료 후 기존·신규 주소에 변경 사실을 알리고 기존 세션·갱신 토큰을 무효화한다. 실제 접근 토큰 폐기 방식은 기존 인증 구조에 맞춰 구현·검증한다.
- 메일 발송 실패는 `발송 실패`로 표시하고 재시도한다. 요청 생성 성공을 이메일 변경 성공으로 표시하지 않는다.
- 초대 대기 계정은 일반 변경 흐름을 이용하지 않는다. 잘못된 주소는 기존 초대를 취소·토큰 무효화한 뒤 재초대하는 별도 지원 절차를 설계하며 수락 완료 상태를 대신 만들어 주지 않는다.
- `auth_provider=google`은 초기 일반 변경을 차단한다. Google 주체 식별자 연결과 재로그인 시 계정 매핑을 확인한 뒤 전용 경로를 별도 제공한다. 이메일 문자열만 변경해 로그인 계정이 분리되는 것을 방지한다.
- 기존 계정에 접근할 수 없는 사용자의 계정 복구는 별도 본인 확인 지원 절차다. 관리자 변경 요청이 복구 절차를 우회하지 않는다.

### 6.2 개인정보 및 감사

- 성별·생년월일·주소는 기본 비공개. 상담사 공개 프로필, 내담자 화면, 일반 로그, 검색 인덱스, 분석 이벤트에 원문을 넣지 않는다.
- 선택 수집 항목에는 목적·열람 주체·보관 기준을 안내한다. 목적 없는 주소 수집을 강제하지 않는다.
- 감사 항목: 행위자·대상 사용자·기관·행위·변경 필드명·서버 시각·사유·요청 식별자·성공/거부 결과. 관리자의 개인정보 열람도 기록한다.
- 변경 전후 값은 필드별 마스킹을 기본으로 한다. 실제 원문 정정 추적이 필요한 값은 암호화된 제한 접근 저장소로 분리하고 일반 관리자 활동 목록에는 노출하지 않는다.
- 기존 `VerificationAudit` 활용 가능성을 먼저 검토하되, 개인정보 원문을 기존 JSON 감사 필드에 무분별하게 저장하지 않는다. 조회 감사와 본인 수정까지 표현 가능한지 구현 설계에서 확인한다.
- 기관 관리자는 자기 기관 일반 변경 내역만, 상담사는 자신의 변경 사실만, 플랫폼의 지정 권한 담당자는 감사 원문 접근 사유를 남기고 조회한다.
- 프로필 정보는 목적 소멸·탈퇴 시 삭제·비식별 처리 정책에 연결한다. 감사 로그의 기간·삭제 예외·암호화 키 관리는 운영 정책 검토 후 출시 전에 확정한다. 무기한 보관을 기본값으로 두지 않는다.

## 7. 우선순위와 단계

- **P0 — 정보 수정 MVP**
  - 실제 스키마·마이그레이션 현황 확인, 상담사/회원 프로필 구분, 온보딩 필드 계약 정합.
  - 기존 본인 설정 확장과 플랫폼·기관 관리자 정보 수정, 미소속 상담사 접근.
  - 선택 주소 필드, 성별·생년월일 조건부 정정, 경력·자격 재사용, 주 담당자 이름·전화 수정.
  - 서버 권한·조회 필드 분리·감사·동시 수정 방지·관리자 수정 알림은 기능과 함께 구현.
  - 이메일은 읽기 전용. 변경 기능이 없는데 수정 가능한 일반 입력창을 제공하지 않는다.
- **P1 — 이메일 변경과 인증 운영**
  - 본인·관리자 요청, 대상자 승인, 새 주소 인증, 취소·만료·재시도·세션 폐기.
  - 주 담당자 이메일도 같은 서비스 사용. P1까지 완료해야 이번 요구사항의 이메일 수정 범위를 충족한다.
- **P2 — 후속 고도화**
  - 자격 증빙 재심사 연계, Google 계정 이메일 변경·복구, 담당자 교체, 필요 시 경력·자격 항목별 API 분리.
  - 일괄 업로드·대량 수정·주소 자동완성·전면 개인정보 모델 통합은 후순위.
- 다음 진행: 본 기획의 저장 구조·권한·단계 승인 → Phase 2 디자인 기획 → 승인 → Phase 3 SDD의 `spec`·`plan`·구현 전 `verify` 승인 후 구현.

## 8. 구현 단계 수용 기준

- 플랫폼은 소속·미소속 상담사 일반 정보를, 기관 관리자는 현재 소속 상담사 허용 필드만, 상담사는 자신의 정보를 수정할 수 있다.
- 타 기관 ID 교체, 숨긴 필드 직접 전송, 다른 사용자 경력 ID 전송, 기존 온보딩 API 우회를 모두 차단한다.
- 기관 관리자 응답·브라우저 네트워크 데이터에 생년월일·성별·개인 주소가 포함되지 않는다.
- 선택 정보의 미입력·삭제·0년 경력이 구분되고, 회원 인적사항은 변경되지 않는다.
- 주 담당자 정보 수정으로 기관 연락처·담당자 지정·역할·소속이 바뀌지 않는다. 프로필 없는 기관 관리자도 수정 가능하다.
- 두 사용자의 동시 편집, 저장 직전 소속 해제·담당자 교체는 덮어쓰기 없이 충돌 처리한다.
- 경력·자격 수정으로 인증 등급이 자동 상승하지 않는다. 저장과 감사 기록은 함께 성공하거나 함께 취소된다.
- 이메일 미인증·중복·만료·재사용·발송 실패·관리자 단독 완료 시도에서 기존 로그인 이메일을 보존한다.
- 역할별 UI, 좁은 화면, 키보드, 실패 입력 보존, 목록·상세 갱신과 이름 변경 알림을 검증한다.
- 기획 승인 시 결정할 정책: 개인정보 선택 수집 목적, 플랫폼 열람 담당 범위, 감사 보관 기간, 최근 재인증 수단. 권장안은 본문에 제시했으며 운영 정책 확정·실제 동작 검증은 후속 단계다.
