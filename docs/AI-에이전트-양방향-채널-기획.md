## 1. 개요

### 1.1 한 줄 정의

**하나의 AI 에이전트가 내담자와 상담사 각각과 따로 대화하며, 둘 사이의 정보를 동의 범위 안에서 중계하는 서비스.**

```text
  내담자 ⇄ [내담자:AI 채널]        [상담사:AI 채널] ⇄ 상담사
                    ╲                  ╱
                  AI 에이전트 (중계 · 요약 · 정책 계층)
```

- 내담자와 상담사는 **같은 채널에 들어가지 않는다.** 각자 AI와 1:1로만 대화한다.
- AI는 한쪽에서 들은 것을 **요약·정제**해 다른 쪽에 전달한다 (원문 그대로 전달하지 않음).
- 기존 1:1 채팅(내담자↔상담사 직접 대화)은 그대로 유지한다. AI 채널은 그와 별개의 추가 채널이다.

### 1.2 확정된 방향 (Brian 결정)

| # | 결정 | 의미 |
|---|---|---|
| 1 | 셀프 트레이닝 제외 | 호흡·명상 콘텐츠 제작, 처방 스케줄 설계는 범위에서 뺀다 |
| 2 | 마음 돌봄 팁 제외 | AI는 **조언·처방을 하지 않는다**. 듣고, 곁에 있고, 정리해 전달하는 역할만 한다 |
| 3 | 프로파일은 상담사 전용 | 내담자에게는 노출하지 않는다 |
| 4 | AI가 먼저 말을 건다 | 고정 시각 알림이 아니라 "먼저 연락하는" 느낌 |
| 5 | **내담자 비서 역할 (내담자 전용)** | 예약 **2~3시간 전·1시간 전** 사전 노티 + CTA(길찾기·입장·상담사 문의 등), 리포트 생성 시 링크 전달 + 리포트 기반 대화로 사후 피드백 유도 |
| 6 | **상담사는 하루 2회 브리핑** | 건별 알림 없음. **아침 1회**(기본 08:00): 하루 일정을 시작 전에 한 번에 / **저녁 1회**(기본 21:00): 오늘 상담한 내용을 정리. 시간은 상담사가 지정. **상담사에게 길찾기·장소 안내는 제공하지 않음** |
| 7 | **채널 분리 + 에이전트 중계** | 내담자:AI / 상담사:AI 별도 채널. 하나의 에이전트가 양쪽을 중계 |
| 8 | 앱 + 웹, **알림은 앱 푸시만** | 앱은 Capacitor 하이브리드(BLE·푸시). AI의 먼저 말 걸기 알림은 **앱 푸시만** 사용(이메일 알림 없음). 웹에서는 접속했을 때 AI 대화창에서 확인 |
| 9 | 앱 MVP1과 동시 출시 | Capacitor 앱 셸·푸시·BLE가 MVP1 범위에 포함 (§5.4, 일정 재산정 필요) |

### 1.3 문제 정의

| 대상 | 문제 |
|---|---|
| 내담자 | ① 예약을 잊거나 장소·입장 방법을 찾아 헤맨다 ② 상담과 상담 사이에 마음을 털어놓을 곳이 없다 ③ 리포트를 받아도 열어보고 끝난다 — 이해·피드백으로 이어지지 않는다 |
| 상담사 | ① 하루 일정·준비물을 여러 화면에서 모아 봐야 한다 ② 세션 사이 내담자 상태와 리포트에 대한 반응을 알 수 없다 ③ 건별 알림이 잦으면 오히려 업무 방해 |

### 1.4 목표 / 비목표

**목표**
- 내담자가 **예약을 놓치지 않고**, 알림에서 바로 행동(확인·입장·길찾기·문의)한다
- 내담자가 리포트를 **링크로 받고 대화로 이해하며**, 상담에 대한 소감을 자연스럽게 남긴다
- 내담자가 부담 없이 메신저처럼 짧은 안부 대화를 나눈다 (2차)
- 상담사가 **하루 두 번의 브리핑으로** 일정·내담자 변화·리포트 반응을 파악한다
- 기존 파이프라인(리마인더·리포트·알림·LLM 요약·동의)을 재사용한다

**비목표**
- AI의 상담·진단·조언·위기 개입 대행 (절대 하지 않음)
- 호흡·명상 콘텐츠, 처방, 과제 스케줄 관리
- 내담자에게 프로파일/점수/등급 노출
- AI가 **상담사 대신 내담자에게 메시지를 임의 발송**하거나 일정을 변경하는 것
- 상담사 대상 건별 알림·길찾기·장소 안내 (상담사는 아침/저녁 2회 브리핑만, §3.5)
- 그룹(명상 수업) 대상 — 1:1 상담 우선

## 2. 사용자 시나리오

### 2.1 내담자 ↔ AI

**(a) 예약 사전 노티 + CTA** — AI가 먼저 말을 건다
> **2~3시간 전:** "오늘 오후 3시에 ○○ 상담사님과 3회차 상담이 있어요. 장소는 ○○상담센터(대전 유성구 …)예요."
> [확인했어요] [길찾기] [일정 변경 문의] [상담사에게 메시지]
> **1시간 전:** "1시간 뒤 상담이에요. 이동 시간을 확인해 주세요." [길찾기] (오프라인) / "준비되면 입장해 주세요." [입장하기] (온라인) / [상담사에게 메시지]
- "일정 변경 문의"를 누르면 AI가 사유를 한두 문장으로 정리해 **상담사에게 중계**한다 (일정 변경은 상담사가 결정)
- LINK BAND 사용 세션이면 "기기 충전/착용 준비" 안내 추가 (밴드 선택 사용자에 한함)

**(b) 리포트 링크 + 리포트 기반 대화** — 리포트가 승인·발송되면 AI가 먼저 말을 건다
> "오늘 상담 리포트가 도착했어요. [리포트 보기]
> 리포트에서 '이완이 더 빨리 돌아왔다'는 부분이 눈에 띄었는데, 상담 중에 그런 느낌이 있으셨나요?"
- 리포트 **본문 범위 안에서만** 대화한다 (새로운 해석·진단 추가 금지)
- 질문은 열린 질문으로: "어떤 부분이 마음에 남으셨어요?" "이해하기 어려운 부분이 있었나요?"
- 대화 말미에 자연스럽게 사후 피드백을 유도: "오늘 상담에서 좋았던 점이나 아쉬웠던 점을 한 줄만 남겨주실래요?" — 필수 아님, 건너뛰기 가능
- 피드백은 **요약해서 상담사 AI 채널로 중계** (내담자 동의 후)

**(c) 안부 대화 (2차)** — 하루 한 번, 짧은 감정 대화. 상세 §3.3

### 2.2 상담사 ↔ AI

**아침 브리핑 (기본 08:00, 상담사가 시간 지정)** — 하루 일정을 시작 전에 한 번에
> "좋은 아침이에요. 오늘은 상담 3건이에요.
> ① 10:00 김○○ 님 (3회차) — 지난번 직장 이야기 중심, 어제 안부 대화에서 수면 부족 언급
> ② 14:00 이○○ 님 (첫 상담, 온라인)
> ③ 16:30 박○○ 님 (5회차) — 지난 리포트에 '도움이 됐다'는 소감이 있었어요.
> 승인 대기 중인 리포트가 2건 있어요."
> [오늘 일정 보기] [김○○ 님 지난 요약] [대기 리포트 승인]
- 장소·길찾기·연락 안내는 넣지 않는다 (상담사는 필요 없음). 온라인/오프라인 구분만 표시

**저녁 정리 (기본 21:00, 상담사가 시간 지정)** — 오늘 상담한 내용을 정리
> "오늘 상담 3건을 정리했어요.
> - 김○○ 님 (3회차): 직장 상사와의 갈등이 중심이었고, 후반부에 수면 이야기가 나왔어요. 다음 상담에서 이어볼 만한 주제로 '수면 패턴'이 남았어요. 리포트는 승인 대기예요.
> - 이○○ 님 (첫 상담): 주호소는 …, 상담 후 안부 대화에서 '생각보다 편했다'고 했어요.
> - 박○○ 님: 불참이었어요.
> 내일은 상담 2건이에요."
> [리포트 승인하기] [기록지 보기] [내일 일정 보기]
- 정리 내용은 세션 AI 요약(`SessionRecord`)을 기반으로 하고, "후보/남은 주제" 표현만 쓴다 (진단·치료 지시 금지)
- 마이크 오프/기록 없음 세션은 "기록 없음"으로 표시

**대화로 추가 요청 (예)**
- "김○○ 님 지난번에 뭐라고 했지?" → 요약 제공 (근거 링크)
- "내일 아침 브리핑 7시로 바꿔줘" → 설정 변경
- "이○○ 님한테 일정 확인 부탁한다고 전해줘" → **전달 문구 초안** 작성 → 상담사 확인 후 중계 (§3.6)

## 3. 기능 상세

### 3.1 F1. 에이전트 공통 구조 (채널 분리 + 중계)

| 구성 | 설명 |
|---|---|
| 채널 | 사용자별 AI 대화방. `client:AI`, `counselor:AI` 두 종류. 서로의 대화방을 볼 수 없음 |
| 컨텍스트 정책 | 채널별로 **AI가 볼 수 있는 데이터 범위를 정책 계층에서 고정**. 프롬프트 지시가 아니라 코드로 조회 범위를 제한 |
| 중계 | 한쪽 채널에서 발생한 정보를 **요약·정제한 이벤트**로 만들어 다른 쪽 채널에 전달. 원문 직접 노출 없음 |
| 동의 | 내담자는 **가입 후 첫 대화 시 한 번** 동의한다 (D1): ①AI가 먼저 연락 ②대화는 **요약**으로 상담사에게 전달 ③피드백은 상담사에게 그대로 전달 ④상담 대체 아님. 이후 대화마다 재동의하지 않음. 상담사에게는 원문이 아닌 요약만 전달 |
| 행동 제한 | AI는 허용 도구 목록 안에서만 동작 (조회·초안 작성·딥링크). 발송·일정 변경·삭제는 사람 확인 후 |

**내담자:AI가 볼 수 있는 것**
- 본인 예약 일정, 본인 **승인·발송된** 리포트 본문, 본인의 AI 대화 이력
- 볼 수 없는 것: 상담사 리포트·상담사 비공개 메모(`ClientCounselorLink.memo`)·타 참여자 정보·상담사 프로파일 작업 내용

**상담사:AI가 볼 수 있는 것**
- 본인 일정, 담당(`ClientCounselorLink` active) 내담자의 기록지 요약·리포트 상태·**공유 동의된** 안부 대화 요약·피드백 요약
- 볼 수 없는 것: 내담자가 "전달하지 않기"로 제외한 대화, 담당하지 않는 내담자, 타 상담사 데이터

### 3.2 F2. 내담자 비서 — 예약 사전 노티 + CTA

**발화 시점 (기본값, 설정 가능)**
| 시점 | 내용 |
|---|---|
| 상담 2~3시간 전 (기본 3시간) | 일정·회차·상담사·장소/입장 방법·준비 안내 + CTA |
| 상담 1시간 전 | 이동/입장 최종 안내 + CTA (오프라인=길찾기, 온라인=입장하기) |
| (옵션) 전날 | 사용자가 켠 경우에만. 기존 24시간 전 리마인더를 대체 |

- **이 기능과 길찾기는 내담자 전용이다.** 상담사에게는 건별 알림·장소 안내를 보내지 않는다 (§3.5)
- 기존 SDD-097 `reminder_offsets`(예 `[1440, 60]`) 리마인더(참여코드·준비물 안내, 인앱+이메일)는 **그대로 유지**한다 (D7: 병행, 용도가 다름). AI 알림은 대화형 CTA용 푸시. 단 기본 오프셋 60분이 겹치면 같은 시각에 두 번 울리므로 **발송 시점이 같으면 한 번으로 합치는 처리**를 plan에서 설계 (`session_reminder_logs` 중복 방지 패턴 참고)
- 취소·변경된 일정은 발송하지 않고, 이미 안내 후 변경되면 정정 안내
- 방해금지 시간 22:00~08:00 (단, 당일 임박 알림은 예외 없이 이 시간대에 몰리지 않도록 일정 생성 시 확인)

**CTA 목록**
| CTA | 동작 | 비고 |
|---|---|---|
| 확인했어요 | 확인 상태 기록 → 상담사 저녁 리뷰에 "확인" 반영 | 미확인 시 1회 재안내 |
| 입장하기 | 온라인 세션 대기실로 이동 | 기존 입장 흐름 |
| 길찾기 | 지도 앱 딥링크 | 앱=딥링크, 웹=지도 URL. **내담자 전용. 장소 데이터 필요(D8)** |
| 일정 변경 문의 | AI가 사유를 정리해 상담사 AI 채널로 중계 | 변경 결정은 상담사 |
| 상담사에게 메시지 | 기존 1:1 채팅방 열기 | 직접 대화 (AI는 그 채팅에 참여하지 않음) |
| 상담사에게 전화 | 상담사 전화번호로 `tel:` 연결 | D11: 채팅과 전화 모두 제공. 상담사 전화번호가 없으면 버튼 숨김 |

### 3.3 F3. 내담자 비서 — 리포트 링크 + 리포트 기반 대화 (사후 피드백 유도)

**트리거:** 리포트가 **상담사 승인·발송**된 시점 (아래 코드 근거 참고)

**흐름**
1. 리포트 링크와 함께 AI가 먼저 말을 건다 (앱 푸시. 웹은 접속 시 대화창에 표시)
2. 리포트의 핵심 서술 1~2개를 인용하며 열린 질문으로 대화 시작
3. 3~6턴 대화 후, 소감/피드백을 가볍게 요청 (건너뛰기 가능)
4. 대화 종료 시 요약해 상담사에게 중계 (동의 시)

**규칙**
- 대화 범위는 **내담자에게 발송된 리포트 본문**에 한정. AI가 EEG 수치나 상태를 새로 해석하거나 진단하지 않는다
- 점수 환원 금지: 피드백 요청에 별점·NPS 같은 숫자 척도 사용 안 함. 자유 서술 + (선택) 3지선다형 범주("도움이 됐어요 / 보통이었어요 / 아쉬웠어요")
- 피드백 형식(D9): 먼저 **3지선다**(도움이 됐어요 / 보통이었어요 / 아쉬웠어요)로 가볍게 묻고, 이어서 대화로 **주관적 이야기**를 자연스럽게 듣는다. 숫자 척도 없음
- 부정 피드백도 포함해 **상담사에게 있는 그대로 전달**한다 (D10). 따라서 첫 대화 동의 화면에 "피드백은 상담사님께 그대로 전달돼요"를 **명시**해 내담자가 알고 남기게 한다
- 위기 표현 감지는 현재 범위 밖 (D4). 2차 안부 대화 출시 전 재논의
- 그룹 세션 리포트는 제외 (타 참가자 정보 노출 위험, 기존 `report_task.py` 그룹 제외 정책과 동일 원칙)

**코드 근거 (재사용)**
- 리포트 상태머신: `pending_analysis → pending_review → completed`. 승인(`approve_report`)은 `completed` 처리 + `sent_at` 스탬프 (`report_service.py`). SDD-066에 따라 **승인과 메일 발송은 별도 경로**이므로, AI 링크 전달 트리거는 "승인 완료"를 기준으로 하되 발송 경로(`report_email_service.py`의 토큰 링크)와 중복되지 않게 조정 필요
- 상담사 `auto_approve_report` 설정(자동 승인 사용자)이 있으면 승인 대기 없이 바로 발송 → 이 경우도 동일 트리거 적용
- 리포트 링크는 기존 토큰 기반 뷰(`participant_token`, `view_report_email`) 또는 앱 내 리포트 화면으로 연결

### 3.4 F4. 내담자 안부 대화 + 상담사 전용 프로파일 (2차)

- 하루 한 번, 메신저처럼 짧은(5~10턴) 감정 대화. 상황 기반 먼저 말 걸기(무응답 3일, 직전 힘든 대화 후속, 상담 직후/전날)
- AI는 경청·공감·열린 질문만. **조언·진단·"항상 곁에 있어요" 금지.** 종료 멘트는 상담사 연결 방향
- 빈도 제어: 하루 최대 1회, 주당 상한, 무응답 시 간격 증가, 방해금지, 끄기/조절
- 대화에서 **상담사 전용 프로파일** 구축 (수면·스트레스 요인·감정 표현·대처·주요 인물/사건). 항목마다 근거 링크와 "AI 추정" 표시, 확정은 상담사. 내담자에게 미노출
- 요약은 동의 범위에서 상담사 AI 채널(아침 브리핑·저녁 리뷰)로 중계

### 3.5 F5. 상담사 브리핑 — 아침 일정 브리핑 / 저녁 상담 정리

**설정 (상담사별)**
| 항목 | 기본값 | 비고 |
|---|---|---|
| 아침 브리핑 시각 | 08:00 | 상담사가 지정. 끄기 가능 |
| 저녁 정리 시각 | 21:00 | 상담사가 지정. 끄기 가능 |
| 요일 | 매일 | 상담 없는 날 건너뛰기 옵션 |
| 채널 | 앱 푸시(→AI 대화창) | 이메일 알림 없음(D2). 웹은 접속 시 대화창에 표시 |


**아침 브리핑 내용 (하루 1회, 일정 시작 전)**
- 오늘 일정 목록: 시각·내담자(**실명 표시**, D12)·회차·유형(온라인/오프라인). **장소·길찾기·연락처는 넣지 않음**
- 각 건 핵심 한 줄: 지난 상담 요약, 세션 사이 변화(안부 대화), 내담자가 남긴 리포트 소감
- 확인이 필요한 항목: 승인 대기 리포트, 미확인 예약(내담자가 확인 안 함), 내담자의 일정 변경 문의

**저녁 정리 내용 (하루 1회, 오늘 상담한 내용 중심)**
- 오늘 진행된 상담별 내용 정리: 다룬 주제, 남은 주제(후보), 특이사항 (세션 AI 요약 기반)
- 불참/취소 현황
- 리포트 상태(생성·승인 대기), 내담자의 리포트 열람·피드백 요약
- 내일 일정 미리보기, 처리할 일(승인 대기 등)

**CTA:** 오늘 일정 보기 · 해당 내담자 요약/기록지 · 리포트 승인 · 일정 변경 문의 확인

**제외한 것:** 건별 임박 알림(2~3시간 전·1시간 전), 길찾기, 내담자 연락 CTA는 상담사 채널에 두지 않는다. 상담사가 내담자에게 연락할 때는 기존 1:1 채팅을 쓴다.

**원칙:** 사실 정보(시각·장소·상태)는 **DB 값을 그대로 인용**하고 LLM은 문장 구성만 한다 (환각 방지). 데이터가 없으면 "정보 없음"으로 명시한다.

### 3.6 F6. 상담사 → 내담자 중계 (제외 확정)

> D6 결정: 상담사와 내담자의 직접 대화는 **기존 1:1 채팅**이 기본이며 AI는 그 채팅에 참여하지 않는다. 아래 중계 기능은 **범위에서 제외**한다. (참고용으로만 남김)

- 상담사가 상담사:AI에게 "이○○ 님께 일정 확인 부탁한다고 전해줘" → AI가 **전달 문구 초안** → 상담사 확인 → 내담자:AI 채널에 전달 문구로 중계
- 임상 개입·진단성 메시지는 중계 금지. 일정·준비·안부 확인 등 **행정·가벼운 안부**로 범위 한정
- 직접 소통은 기존 1:1 채팅 사용이 원칙. 중계는 "AI를 통해 부드럽게 전달"하고 싶을 때의 보조 수단 (제외 확정)

### 3.7 병행 항목 (별도 기획)

- 세션 전 5분 브리핑(A1): 아침 브리핑의 건별 상세 화면으로 흡수 가능
- SOAP 기록지 초안(A3): 독립 SDD
- 내담자 변화 스토리(A7): 3차

### 5.2 신규 필요 (예상)

- **에이전트 코어:** 채널 정의, 컨텍스트 정책 계층(권한별 조회 범위), 허용 도구 레지스트리, 중계 이벤트(요약·동의 플래그·상태)
- **내담자 채널:** 예약 노티 스케줄러·CTA 렌더링, 리포트 승인 이벤트 구독 → 링크 메시지 + 리포트 기반 대화, 피드백 요약·중계, (2차) 안부 대화·프로파일
- **상담사 채널:** 상담사별 아침/저녁 브리핑 스케줄러(개인 지정 시각, KST), 일정/상담 정리 요약 생성(DB 사실 + LLM 문장)
- **스케줄링 주의:** Celery beat는 제거되었고 주기 작업은 **OS cron(`backend/*_cron.py`, `deploy-dev.yml` §5.7~5.9 등록)** 이 실행한다 (`celery_app.py` INFRA-08). 상담사마다 시각이 달라 **매 1분 cron 스윕 + 발송 로그** 방식으로 구현
- **푸시 인프라:** 디바이스 토큰 등록/해지, FCM/APNs 발송, 알림 아웃박스 `push` 채널
- **프론트:** AI 대화 화면(내담자용·상담사용), CTA 버튼, 설정(시각·빈도·동의), 딥링크 라우팅

### 5.3 DB 변경 (예상)

AI 대화방/메시지(채널 구분), 중계 이벤트, 에이전트 알림 설정(상담사 브리핑 시각 등), 발송 로그, 디바이스 토큰, 피드백 요약, 프로파일 항목(2차), **세션 장소 컬럼(D8: 오프라인 세션 생성 시 상담사 기관 주소를 기본값으로 채우고 수정 가능)**. Alembic 마이그레이션 필요.

### 5.4 앱(Capacitor) 전제

- 현재 `frontend/package.json`에 Capacitor 없음 → React SPA를 Capacitor로 감싸는 구조 신규 도입
- 푸시(`@capacitor/push-notifications` + FCM/APNs), BLE, 딥링크(지도·전화), 보안 저장소
- **BLE(D13):** LINK BAND SDK Web에서 Capacitor로 BLE 연결하는 방식과 **동일하게** 구현한다. plan 단계에서 해당 SDK 저장소의 구현(플러그인·연결/재연결·권한 처리)을 확인해 이식 범위를 확정한다
- 푸시 탭 → 해당 AI 대화창 딥링크
- Web Bluetooth 미지원(Safari/Firefox) 제약이 앱에서 해소됨
- **문서 정합:** `종합_기획`(MVP2 "RN 앱 셸"), `MVP_1.5_내담자_앱_기획`(FC.8 푸시 MVP2 이관) 갱신 필요
- 정신건강 앱 스토어 심사: 개인정보·민감정보 심사 대비

|---|---|---|

| **2차** | 내담자 **안부 대화** + 상담사 전용 프로파일 + 브리핑에 세션 사이 변화 합류 | D5(대상 범위) 결정 필요. 위기 감지는 현재 범위 밖(D4)이나 자유 감정 대화 출시 전 재논의 |
| **3차** | 내담자용 변화 스토리, (옵션) 상담사→내담자 중계, 세션 전 브리핑 상세 | |
| (병행) | Capacitor 앱 셸 + BLE + 푸시 | 별도 SDD 트랙. 푸시 활성화의 선행 조건 |
| (별도) | SOAP 기록지 초안 | 독립 SDD |

> **1차 설계 이유:** 안부 대화(프로파일·자유 감정 대화 등 임상 리스크 큼)를 2차로 미루고, 이미 있는 일정·리포트 데이터로 양쪽에 즉시 가치를 주는 흐름부터 검증한다. 위험은 낮고 "AI가 중계한다"는 핵심 구조(채널 분리·정책·동의)는 1차에서 모두 검증된다.

### D5 설명 (미정)
- **질문:** 2차에서 만드는 "안부 대화"(AI가 하루 한 번 먼저 말을 거는 감정 대화)를 **누구에게 켜는가**.
- **선택지 ①** 상담사와 연결된 모든 내담자에게 자동으로 켠다 (내담자가 원하면 끔).
- **선택지 ②** 상담사가 "이 내담자에게는 안부 대화를 켠다"고 내담자별로 지정한 경우에만 켠다.
- 기획자 의견: ②. 임상적으로 안부 대화가 부적절한 내담자(예: 대화가 오히려 불안을 키우는 경우)를 상담사가 제외할 수 있다. 1차(예약 노티·리포트 대화·브리핑)에는 영향 없음.

### 확정 결정에서 파생된 확인 사항
1. **D11 전화번호:** 상담사 `users.phone`이 선택 입력이라 비어 있을 수 있다. 비어 있으면 전화 CTA를 숨긴다. 상담사 프로필에서 전화번호 공개를 안내하고 입력을 유도한다.
2. **D8 주소:** `organization.address`가 nullable이고 개인상담소(상담사 개인 기관)는 주소가 없을 수 있다. 기관 주소가 없으면 `counselor_profile` 주소로 대체하고, 둘 다 없으면 상담사가 직접 입력하도록 한다.
3. **D2 앱 푸시만:** 앱을 설치하지 않았거나 푸시를 거부한 사용자는 AI의 먼저 말 걸기를 받을 수 없다. 기존 리마인더(이메일)는 병행되므로 예약 안내 자체는 유지된다.
4. **D14 MVP1 동시:** 기존 로드맵(MVP1 17주=웹, MVP2 8주=앱)과 다르다. Capacitor 셸·푸시·BLE가 MVP1 범위로 들어오므로 일정 재산정이 필요하다.
