# 플랫폼 관리자 기관 관리 CRUD 기획안

- 작성일: 2026-09-17
- 범위: 기관 등록·조회·수정·비활성화(CRUD) 및 기관 내 상담사 관리의 서비스 기획.
- 상태: **Phase 1 검토안**. 아래 API·필드·삭제 정책은 제안이며 구현 완료를 의미하지 않는다.
- 산출물: 본 문서만 작성. 코드·DB·SDD 번호·외부 업무 시스템은 변경하지 않는다.

## 1. 목표와 권장 방향

- 등록 기관 테이블에서 기관을 선택하면 한 모달 안에서 기관 정보와 상담사 현황을 확인한다.
- 기존 기관 등록·담당자 초대 흐름을 유지하고, 조회 → 정보 수정 → 상담사 관리 → 기관 비활성화 순서로 확장한다.
- **권장: 두 탭 모달 + 부분 수정(PATCH) + 비활성화(deactivate)**.
- 삭제 정책(확정): 데이터는 자산이므로 **물리 삭제·논리 삭제 모두 제공하지 않는다**. 기관 종료는 **비활성화(deactivate)**만 제공하고, 필요 시 이후 단계에서 논리 삭제를 추가한다.
- 대안 검토:
  - 별도 상세 페이지: 복잡한 운영 업무에는 유리하지만 목록과 상세를 자주 오가는 현재 요구에는 과하다. 후속 기능이 커질 때 검토한다.
  - 물리 삭제(hard delete): 데이터 손실 위험이 크므로 제공하지 않는다.
  - 논리 삭제(soft delete): 데이터 보존 측면은 유사하지만 "삭제됨" 상태 관리와 복구 불가한 인식이 생기므로, 이번에는 도입하지 않고 **비활성화**만 사용한다.
- 목록은 테이블·검색·필터·그룹핑을 기본으로 하며 카드형 대시보드나 통계 화면을 추가하지 않는다.

## 2. 현재 구조 — 소스 확인 결과

### 2.1 프런트엔드

- `frontend/src/pages/admin/OrgManagementPage.tsx`
  - 신규 등록: 기관명·전화·주소, 담당자 이름·이메일·전화 입력 → 기관 코드 발급 및 담당자 초대 메일.
  - 화면은 담당자 이름·이메일을 필수 검사한다. 서버는 담당자 없는 기관 등록도 허용한다.
  - 목록: 기관명·기관 코드·전화번호·인증 배지·생성일·초대 재발송 버튼.
  - 행 클릭 동작, 상세 모달, 수정·제거 기능은 없다.
  - `listAdminOrganizations()`로 전체 배열을 읽는다. 검색·필터·그룹핑·페이지네이션은 추가 설계 대상이다.

### 2.2 서버 API와 서비스

- `backend/app/api/v1/admin.py`
  - `require_platform_admin`으로 플랫폼 관리자 역할을 검사한다.
  - 기존 API: `GET /admin/orgs`, `POST /admin/orgs`, `POST /admin/orgs/{org_id}/resend-invite`.
  - `_serialize_org` → `OrganizationAdminResponse`: `id`, `name`, `org_code`, `phone`, `verified`, `created_at`만 반환한다.
  - 주소는 DB에 있으나 관리자 목록 응답에는 없다. `kind`, 담당자, 소유자도 목록 응답에 없다.
- `backend/app/api/v1/org.py`
  - `GET /org/{org_id}`는 기관 정보를 반환하며, 해당 핸들러에 사용자 의존성이 없다. 민감한 담당자 정보를 이 응답에 추가하지 않는다.
  - `GET /org/{org_id}/counselors`, 상담사 초대·재초대·역할 변경·소속 해제는 `_require_org_admin` 대상이다.
  - 플랫폼 관리자는 기관 관리자 역할과 다르므로 관리자 전용 경로를 신설한다.
- `backend/app/services/org_service.py`
  - `get_counselors`는 해당 `org_id`의 `counselor`와 `org_admin` 모두를 반환한다.
  - `update_counselor_role`과 `remove_counselor`도 서비스 내부에서 요청자가 해당 기관의 `org_admin`인지 검사한다. 관리자 라우트만 붙여 그대로 호출할 수 없다.
  - `remove_counselor`는 사용자 삭제가 아니라 `User.org_id = None` 처리이며, `org_admin`이면 `counselor`로 변경한다.
  - `admin_create_organization`, `create_org_with_admin`, `list_organizations`가 있다. `update_organization`·`delete_organization`은 없다.
  - 담당자 없는 등록 분기는 현재 `address`를 생성 서비스에 전달하지 않는다. 기존 누락값을 임의 복원하지 않고 상세 수정에서 보완한다.
- `backend/app/schemas/org.py`
  - 기존 상담사 응답은 이름·이메일·역할·계정 상태·초대 시각 등을 제공하지만 상담사 코드·소속 요약은 없다.
  - 신규 관리자 응답은 필요한 정보를 명시적으로 확장한다.

### 2.3 데이터 구조와 제약

- `Organization`: `name`, `org_code`, `phone`, `address`, `verified`, `verified_at`, `primary_admin_id`, `kind`, `owner_user_id`, `created_at` 등.
- 현재 기관 모델에 비활성화 상태·시각·수정 버전은 없다. 비활성화와 동시 수정 방지는 스키마 변경이 필요하다.
- `primary_admin_id`: 주 담당자인 `org_admin` 사용자 참조. 담당자 개인정보의 원본은 `User`이다.
- `kind=institution`: 일반 기관. `kind=individual`: 개인 상담사의 1인 기관이며 `owner_user_id`가 소유자이다. 담당자와 소유자는 다른 개념이다.
- `User.org_id`는 현재 소속 하나를 가리킨다. 기관별 역할·기관별 정지 상태가 분리된 회원 관계 모델은 아니다.
- 상담사 코드는 `CounselorProfile.counselor_code`를 원본으로 한다. 프로필이 없는 담당자에게 코드를 생성하거나 추정하지 않는다.
- `Session`은 `host_id`를 가지며 직접적인 `org_id`가 없다. `ClientCounselorLink`도 기관이 아닌 사용자 간 연결이다.
- 세션의 ORM 관계에는 참여자·기록·EEG·리포트의 연쇄 삭제(cascade)가 있고, 채팅 모델에도 세션/방 관련 `ondelete="CASCADE"`가 있다. 기관 제거를 사용자·세션 삭제로 구현해서는 안 된다.
- 위 내용은 소스 기준이며 운영 DB의 실제 제약·이관 이력은 확인하지 않았다.

## 3. 목록과 상세 모달 UX

### 3.1 기관 목록

- 기존 테이블 유지. 기관 유형을 추가하고 기관명을 상세 열기 버튼으로 제공한다. 행의 빈 영역을 클릭해도 같은 모달을 연다.
- 검색: 기관명·기관 코드. 필터: 인증 여부, 유형, 상태(운영/비활성화). 기본은 운영 기관.
- 그룹핑: 기본은 없음, 선택 시 일반 기관/개인 기관으로 구분한다. MVP는 전체 로드한 배열을 기준으로 필터·그룹핑한다.
- 초대 재발송·코드 복사 버튼은 행 클릭 전파를 막는다. 개인 기관 또는 담당자 부재 시 담당자 초대 버튼을 비활성화하고 이유를 표시한다.
- 결과 없음과 조회 실패를 구분하고 검색 초기화·다시 시도 기능을 제공한다.

### 3.2 모달 기본 구성

- 데스크톱: 최대 너비 약 960px, 화면 높이 85% 이내. 모바일: 전체 화면에 가까운 모달과 본문 스크롤.
- 고정 헤더: 기관명, 유형·인증 배지, 기관 코드와 복사, 닫기.
- 탭 2개: **기관 정보 / 상담사 (N)**. 기관 정보 탭을 기본으로 연다.
- 기관 정보:
  - 이름, 코드, 전화, 주소, 인증 상태, 생성일(KST).
  - 일반 기관: 주 담당자의 이름·이메일·전화·계정 상태. 참조 없음은 ‘담당자 미지정’.
  - 개인 기관: 소유 상담사의 이름·이메일·상담사 코드. 담당자가 없다는 이유로 오류 처리하지 않는다.
  - '정보 수정', 하단 구분 영역에 '기관 비활성화'. 비활성화는 해당 단계 출시 전 노출하지 않는다.
- 상담사:
  - 이름, 이메일, 상담사 코드, 역할, 계정 상태, 현재 소속명·유형을 테이블로 표시한다.
  - `org_admin`도 포함하되 ‘기관 관리자’, 주 담당자는 별도 배지로 구분한다. 표시 인원은 상담사·기관 관리자 합계임을 안내한다.
  - 이름·이메일·상담사 코드 검색, 역할·계정 상태 필터. 행 메뉴에 역할 변경·소속 해제를 둔다.
  - `active`는 활성, `pending`은 가입 대기, `suspended`는 정지로 표시한다. 알 수 없는 상태는 ‘확인 필요’로 보존한다.
  - 초대 만료는 별도 배지이며 `pending`을 새로운 계정 상태로 바꾸지 않는다. 누락 코드·연락처는 ‘미등록’.
- 두 API는 독립 로딩·재시도한다. 기관 정보 성공 후 상담사 조회가 실패하면 ‘조회 실패’를 표시하며 0명으로 간주하지 않는다.
- 키보드: 기관명 버튼 Enter/Space, 모달 내부 포커스 유지, Escape 닫기, 닫은 뒤 원래 버튼으로 포커스 복귀.
- 미저장 수정이 있으면 닫기 시 ‘계속 편집 / 변경사항 버리기’를 확인한다. 저장 실패 시 입력값을 유지한다.

### 3.3 수정·비활성화 확인

- 수정 가능한 항목: 기관명, 전화, 주소, 인증 상태. 기관 코드·유형·생성일·소유자는 읽기 전용.
- 담당자 개인정보는 사용자 정보이며 기관 수정에 혼합하지 않는다. 주 담당자 교체는 별도 동작으로 제공한다.
- 인증 변경은 사유 필수. 기존 기관 증빙 심사 결과와 다른 수동 조정임을 감사 기록에 남긴다.
- 비활성화: 영향 조회 → 대상 기관명·코드·유형과 차단 사유 확인 → 기관 코드 입력(코드가 없으면 기관명 입력) + 사유 + 보존 안내 동의 → 최종 실행.
- 확인 문구: ‘기관 운영을 종료하고 기본 목록에서 숨깁니다. 계정과 기존 상담 기록은 삭제되지 않습니다. 필요 시 재활성화할 수 있습니다.’
- 최종 버튼명은 ‘기관 운영 종료(비활성화)'. 처리 중 중복 실행을 막고 취소 버튼을 기본 포커스로 둔다.

## 4. CRUD API 제안

- 이하 경로는 기존 API 버전 접두사를 생략한다. 신규 관리자 API는 모두 `require_platform_admin`을 적용한다.
- 기존 기관 관리자 API의 권한을 느슨하게 변경하지 않는다. 공통 도메인 검증은 재사용하되 호출자의 권한 검증과 트랜잭션 경계를 분리한다.

### 4.1 생성·목록·상세

- `POST /admin/orgs`: 기존 등록 유지. 초대 메일 실패와 기관 생성 실패를 구분하고 `invite_sent=false`를 성공 발송으로 표시하지 않는다.
- `GET /admin/orgs`: 기존 배열 응답 유지. `kind`와 담당자 유무를 추가해 유형 필터 및 초대 버튼 판단에 활용한다.
  - MVP는 전체 목록의 클라이언트 검색·필터. 서버 페이지네이션이 필요해질 때 `paginated=true` 등 명시적 선택 계약을 도입하며 기본 배열을 갑자기 객체로 바꾸지 않는다.
  - 향후 정렬은 `created_at DESC, id DESC`로 고정하고 전체 건수와 페이지 정보를 제공한다. 그룹핑의 페이지 범위도 명시한다.
- `GET /admin/orgs/{org_id}` → 200:
  - 기관 기본 필드 + `address`, `kind`, `verified_at`, `primary_admin`, `owner`, `version`.
  - 담당자/소유자 요약에는 `id`, `name`, `email`, `phone`, `role`, `status` 중 필요한 값만 포함. 없으면 `null`.
  - 비활성화 도입 후 `deactivated_at` 추가. 상담 내용·비밀번호·초대 토큰은 제외한다.
- `GET /admin/orgs/{org_id}/counselors` → 200:
  - `{items, total, page, size}`, `q`, `role`, `status`, `page`, `size` 지원.
  - 항목: `id`, `name`, `email`, `counselor_code`, `role`, `status`, `org_id`, `org_name`, `org_kind`, `is_primary_admin`, `is_owner`, 초대 시각·만료 시각.
  - 정렬은 `created_at ASC, id ASC`. 비활성화 예정 영향 인원과 필터된 목록 인원을 혼동하지 않는다.

### 4.2 기관 수정

- `PATCH /admin/orgs/{org_id}` → 200, 수정된 상세 반환. 전체 덮어쓰기(PUT)는 제공하지 않는다.
- 입력: `name?`, `phone?`, `address?`, `verified?`, `reason?`. 수정 버전은 `If-Match`로 전달한다.
- 누락 필드는 유지, `phone`·`address`의 명시적 `null`은 삭제. 기관명 공백·빈 문자열·`null`은 거부한다.
- 길이 제한은 기존 모델과 통일: 기관명 200, 전화 20, 주소 300. 허용되지 않은 필드는 거부한다.
- 인증 false→true 시 서버가 `verified_at`을 기록, true→false 시 비우고 이전 값은 감사 기록에 보존한다. 동일 값 재저장은 시각을 바꾸지 않는다.
- 주 담당자 교체: `PATCH /admin/orgs/{org_id}/primary-admin`, `{user_id, reason}`.
  - 같은 일반 기관 소속의 활성 `org_admin`만 지정한다. 기존 담당자의 역할은 자동 강등하지 않는다.
  - 개인 기관 소유자 변경·유형 변환은 별도 이전 정책이 필요하므로 범위 밖이다.

### 4.3 상담사 관리

- `DELETE /admin/orgs/{org_id}/counselors/{user_id}` → 204: **소속 해제만** 수행한다. 제거 사유는 요청 본문에 전달하며 계정 탈퇴 API를 호출하지 않는다.
  - 대상이 URL 기관 소속인지 검증한다. 진행/예정 세션 또는 활성 내담자 연결이 있으면 이관·종료 선행을 요구하고 409로 차단한다.
  - 주 담당자, 마지막 활성 `org_admin`, 개인 기관 소유자는 해제할 수 없다. 주 담당자는 교체부터 수행한다.
  - 과거 소속 이력을 기록한 후 현재 소속을 해제하며, 권한 캐시와 기존 연결 권한을 재평가한다.
- `PATCH /admin/orgs/{org_id}/counselors/{user_id}` → 200: `{role, reason}`.
  - `counselor` ↔ `org_admin`만 허용. `platform_admin`·`client` 변경은 거부한다.
  - `User.role` 자체가 바뀐다는 점을 확인 UX에 명시한다. 주 담당자/마지막 활성 관리자 강등 및 개인 기관 소유자 역할 변경은 차단한다.
- 상태 변경은 기관별 정지가 아닌 **계정 전체 정지**이다.
  - 기존 `POST /admin/users/{user_id}/suspend`, `/unsuspend`와 서비스 정책을 활용한다.
  - 모달에서 바로 실행하는 기능은 후속 단계로 두고, 우선 사용자 관리 진입을 제공한다. 전체 계정에 미치는 영향을 명시한다.
  - 기존 `unsuspend_user`는 `active`로 설정하므로, 가입 대기 상태에서 정지된 계정의 복구가 가입 절차를 우회하지 않도록 이전 상태 검증을 선행한다.
  - `pending`→`active`는 초대 수락·가입 절차가 수행한다. 임의 상태 PATCH를 제공하지 않는다.
- 상담사 초대 생성은 MVP에서 제외한다. 후속 `POST /admin/orgs/{org_id}/counselors/invite`는 기존 초대 서비스·중복 이메일·재발송 제한·메일 실패 처리 정책을 재사용한다.

### 4.4 기관 비활성화

- `GET /admin/orgs/{org_id}/deactivation-impact` → 200:
  - 소속 계정 수, 활성 연결 수, 진행/예정 세션 수, 보존 대상 기록 수 또는 집계 불가 사유, `blockers`, `can_deactivate`, `version`.
  - 집계 불가를 0으로 반환하지 않는다. 개인정보 본문 없이 범위·건수·차단 이유만 제공한다.
- `POST /admin/orgs/{org_id}/deactivate` → 200: 기관을 비활성화한다.
  - 본문 `{reason, confirmation_value}`와 `If-Match` 필수.
  - 서버는 확인값·기관 유형·최신 연관 데이터를 다시 검사한다. 사전 영향 조회 결과만 신뢰하지 않는다.
  - 비활성화는 상태 변경이며 데이터·계정·기록은 삭제하지 않는다. 이미 비활성화된 기관은 동일 상태를 반환하며 중복 감사 이벤트를 생성하지 않는다.
- 재활성화: `POST /admin/orgs/{org_id}/reactivate` → 200. 사유 필수. 비활성화 사유·시각과 대조해 감사 기록을 남긴다.
- 오류: 인증 없음 401, 관리자 아님 403, 대상 없음/다른 기관 상담사 404, 업무 차단 409, 버전 불일치 412, 입력 오류 422.
- 변경·비활성화·재활성화·소속 해제·역할 변경은 원자적 트랜잭션과 감사 기록을 사용한다. 동시 가입·세션 생성도 같은 기관 잠금/상태 검사 규칙을 따라야 한다.

## 5. 데이터 보존과 안전 정책

### 5.1 비활성화의 의미

- 신규 제안 필드: `deactivated_at`, `deactivated_by`, `deactivation_reason`, `version`. 비활성화 상태는 `deactivated_at`으로 판정한다.
- 기본 목록·기관 검색·기관 코드 가입·가입 승인·초대·새 세션 생성에서 비활성화 기관을 제외/차단한다. 인증 상태와 운영 중단을 같은 값으로 표현하지 않는다.
- 비활성화 기관은 플랫폼 관리자가 상태 필터로 조회한다. 일반 기관 관리자에게 기존 기관 운영 권한을 유지하지 않는다.
- 비활성화는 **상태 변경**일 뿐이며 소속 참조와 과거 데이터를 전부 보존한다. 계정의 전역 `status`·역할을 일괄 변경하지 않는다. 재활성화가 가능하다.
- 기관 상태를 모든 관련 권한 판정에 반영하기 전에는 비활성화 기능을 출시하지 않는다. 소속 기관 중단이 계정 탈퇴나 다른 개인 권한의 소멸을 뜻하지 않는다.
- 기관 코드와 사업자 식별자는 재사용하지 않는다. 자동 영구 파기·물리 삭제는 제공하지 않는다.

### 5.2 대상별 처리

- 상담사·담당자: 계정과 기관 참조 보존. 초대 토큰은 무효화하거나 사용 시 기관 상태 검사로 거부한다. 현재 재발송만으로 과거 토큰이 무효화된다고 가정하지 않는다.
- 내담자: 계정 보존. 활성 `ClientCounselorLink`는 담당 이관 또는 종료를 먼저 완료한다. 타 기관 상담사와의 연결은 변경하지 않는다.
- 진행/예정 세션: 하나라도 영향 범위에 있으면 비활성화 차단. 자동 종료·취소하지 않고 기존 세션 상태 전이로 정리한다.
- 완료 세션·기록·EEG·리포트: 원본·참조·파일 보존. 기관 종료를 이유로 연쇄 삭제하지 않는다.
- 채팅: 방·메시지 보존. 기관 운영 권한으로 접근하던 경로는 차단하고 개인 참여 권한은 기존 정책에 따라 재평가한다. 새 메시지 허용 여부도 같은 권한 기준을 적용한다.
- 기관 증빙·가입 신청·가입 심사 이력: 참조 보존, 미처리 신청의 승인 차단. 기존 상태값을 임의 추가하지 않고 UI에 기관 종료 사유를 표시한다.
- S3 파일·Celery 작업·메일/공유 링크: 물리 삭제를 예약하지 않는다. 기존 작업은 기관 종료 후 권한과 수신 대상을 재검사하며, 기존 링크가 종료 기관 권한을 우회하지 않는지 확인한다.
- 감사 기록: 기관 비활성화 이후에도 식별 가능한 대상 ID와 행위 이력을 보존한다.

### 5.3 귀속 이력과 비활성화 출시 조건

- 현재 상담사의 `org_id`로 과거 세션을 모두 해당 기관 소유라고 단정할 수 없다. 다른 기관에서 생성한 세션이나 이미 이동한 상담사의 기록이 섞일 수 있다.
- 비활성화·소속 해제 도입 전, 생성 당시 기관 귀속 스냅샷 또는 동등한 변경 불가능 이력과 소속 변경 이력을 설계한다. 기존 데이터는 증거가 있는 경우에만 보완한다.
- 귀속 불명 데이터는 ‘확인 필요’로 남기고 자동 이관·삭제·새 담당자 접근 부여를 하지 않는다. 영향 범위 확인이 불가능하면 기관 비활성화를 차단한다.
- 보존은 무기한 보관 결정을 뜻하지 않는다. 데이터 종류별 기존 동의·보관 정책, 종료 후 접근 주체, 파기 승인 책임자를 구현 전 확정한다. 본 기획은 특정 법정 보관 기간을 제시하지 않는다.
- 물리 삭제는 향후 별도 운영 절차로 제한한다. 참조·파일·백업·보존 의무 확인과 별도 승인이 필요하며 일반 DELETE API에 `hard=true` 옵션을 넣지 않는다.

### 5.4 일반 기관과 개인 기관

- 일반 기관: 담당자 교체 → 활성 업무 정리 → 영향 검증 → 비활성화 순서.
- 개인 기관: 조회·기본 정보 수정은 제공하되 소유자 변경·소유자 소속 해제·기관 비활성화는 초기 버전에서 차단한다.
- 개인 기관 비활성화는 개인 상담사 활동 종료/기관 이전 정책과 함께 별도 승인 후 출시한다. 소유자를 일반 기관 담당자로 치환하지 않는다.

### 5.5 감사·권한·동시성

- 기존 `VerificationAudit`의 `target_type`, `target_id`, `admin_id`, `action`, `reason`, `extra`를 활용할 수 있는지 검토해 확장하며, 행위자 ID·대상 기관/사용자 ID·행위·변경 전후 값·사유·서버 시각·요청 식별자를 저장한다.
- 성공한 변경과 감사 기록은 함께 커밋한다. 민감한 상담 내용·비밀번호·초대 토큰은 기록하지 않는다. 개인정보 변경값은 접근 제한·최소화한다.
- 플랫폼 관리자라고 해서 본 모달에서 상담 내용·리포트 전문·채팅 본문을 열람하게 하지 않는다.
- 오래 열린 모달에서 저장하면 버전 충돌을 안내하고 새로 불러온 뒤 재검토하도록 한다. 저장 성공 후 목록·상세·상담사 캐시를 갱신한다.
- 주 담당자 교체·마지막 관리자 보호·비활성화 영향 검사에는 동시 요청을 포함한다. UI 버튼 숨김만으로 권한을 보장하지 않는다.

## 6. 단계별 우선순위와 인수 기준

### 1단계 — MVP: 모달 + 조회

- 기관 관리자용 기존 경로와 분리된 상세·상담사 조회 API, 두 탭 모달, 테이블 검색·필터·유형 그룹핑.
- 인수 기준: 클릭·키보드로 모달 열기, 주소·담당자·개인 기관 소유자·상담사 코드 표시, 누락값·0명·조회 실패 구분, 권한 없는 요청 거부.
- 기존 등록과 초대 재발송은 동일하게 동작하며 재발송 클릭으로 모달이 열리지 않는다.

### 2단계 — 기관 수정

- 기관명·전화·주소·인증 변경, 감사 기록, 동시 수정 방지, 주 담당자 교체.
- 인수 기준: 누락/null 구분, 인증 사유·시각 정합성, 저장 실패 시 입력 유지, 목록 반영, 비활성화 기관 수정 차단.

### 2-1단계 — 상담사 관리

- 역할 변경·소속 해제, 마지막 관리자·주 담당자·개인 소유자 보호.
- 귀속 이력·기존 자료 접근 정책이 검증될 때만 소속 해제 활성화. 미검증 시 조회·역할 변경만 출시한다.
- 인수 기준: 다른 기관 대상 조작 거부, 활성 업무 차단, 계정과 과거 기록 보존, 권한 캐시 재평가.

### 3단계 — 기관 비활성화

- 일반 기관 비활성화, 영향 조회, 다단계 확인, 상태 필터, 모든 진입점의 비활성화 기관 차단.
- 인수 기준: 진행/예정 세션·활성 연결·귀속 불명 데이터 차단, 비활성화 중 동시 가입 차단, 코드·초대·공유 링크 우회 방지, 데이터/파일 보존, 중복 요청 안전성.
- 개인 기관 비활성화·물리 삭제·일괄 비활성화·자동 복구·기관 간 자동 데이터 이전은 제외한다.
