# Mind Breeze 2.0 — 채팅 기능 적용 기획안

> 작성: 2026-09-24 · 대상: 현재(변경된) 시스템에 기존 채팅 기능 재적용 검토

---

## 1. 점검 요약

채팅 기능은 **이미 완성되어 현재 코드베이스에 전부 남아있으나, 내비게이션 진입점이 제거되어 사실상 미사용(비활성) 상태**다. 시스템이 이후 크게 바뀌었지만 채팅 기능이 의존하는 모델·서비스는 전부 살아 있어, **재적용(재노출)은 기술적으로 가능**하다.

### 핵심 발견

| 상태 | 항목 |
|---|---|
| ✅ 구현 완료 | 백엔드(REST 라우터 + WebSocket + DB 마이그레이션 4개) 전부 존재·등록 |
| ✅ 구현 완료 | 프론트엔드(페이지·컴포넌트·Zustand 스토어·API 클라이언트) 전부 존재 |
| ✅ 의존 정상 | `ClientCounselorLink`, `Session`, `SessionParticipant`, `User` 모델 전부 존재 |
| ✅ 라우트 등록 | `/chat`, `/chat/:roomId` (App.tsx) + 백엔드 `chat.router` include |
| ⚠️ 진입점 제거 | 사이드바 메뉴(상담사·내담자·기관·플랫폼 4종)에 "채팅" 항목 없음 → 사용자 도달 불가 |
| ⚠️ 관계 모델 확장 | 상담사↔기관 멤버십(`user_org_membership`)·개인상담소 도입 → 채팅 권한 기준 재정의 필요 |

## 2. 기존 채팅 기능 스펙 (이미 구현된 것)

### 2-1. 방(채팅방) 유형 3종

| 유형 | 설명 | 권한 기준 | 현재 상태 |
|---|---|---|---|
| `direct` | 상담사 ↔ 내담자 1:1 | `ClientCounselorLink` (연결 확인) | 정상 |
| `session` | 세션 기반 방 (세션당 자동 생성) | `Session` / `SessionParticipant` | 정상 |
| `group` | 상담사 + 다수 내담자 | `ClientCounselorLink` + `ChatRoomParticipant` | 정상 |

### 2-2. 구현된 기능 목록

- **REST API** (`/chat/*`): 방 목록/생성/조회, 메시지 목록/전송, 읽음 처리(단건·일괄), 안읽은 수
- **WebSocket** (Socket.IO `/chat` 네임스페이스): 실시간 메시지 브로드캐스트, 읽음 이벤트, 프로필 변경, 알림
- **읽음/안읽음**: 메시지별 `read_by` + `recipient_count`, `ChatMessageRead` 하위호환
- **알림 연동**: 메시지 수신 시 `notify_event("chat_message")` → 알림 센터
- **시스템 메시지**: `system_message_service` (세션 이벤트를 채팅방에 자동 기록)

### 2-3. 프론트엔드 자산

| 구분 | 파일 |
|---|---|
| 상담사 채팅 | `pages/chat/ChatPage.tsx` |
| 내담자 채팅 | `pages/client/ClientChatListPage.tsx` · `ClientChatPage.tsx` · `ClientChatRoomPage.tsx` |
| 컴포넌트 | `components/chat/ChatRoom.tsx` · `MessageBubble.tsx` · `SystemMessage.tsx` |
| 상태/API | `stores/chatStore.ts` · `lib/api/chat.ts` |

| 5 | **밴드 실시간 데이터 WS** (`session_live_namespace`) | WebSocket 인프라가 채팅 WS(`/chat`)와 별도로 확장됨 |

| 7 | **리포트 2종 자동 생성** (SDD-086) | 세션 종료 흐름과 채팅방 종료/보존 정책 정합 |

## 4. 정합성 점검 결과 (적용 가능 여부)

### 4-1. 기술적으로 정상인 항목 ✅

- 백엔드 `chat.py` 라우터가 `api/v1/__init__.py`에 등록되어 있음
- WebSocket `/chat` 네임스페이스가 `ws/__init__.py`에 등록되어 있음
- DB 마이그레이션 4개 존재 (`006_chat`, `012_chat_direct_rooms`, `013_chat_room_participants`, `add_read_by_and_recipient_count`)
- 의존 모델(`ClientCounselorLink`, `Session`, `SessionParticipant`, `User`) 전부 존재·import 가능

### 4-2. 적용 전 해결해야 할 항목 ⚠️

1. **내비게이션 미노출** — 사이드바(4개 역할)에서 "채팅" 메뉴가 빠져 있어 접근 불가. `chatBadge`·`getBadge("채팅")` 로직은 남아 있으나 메뉴 항목 자체가 없음.
2. **내담자 채팅 라우트 미등록** — `ClientChatListPage`/`ClientChatPage`/`ClientChatRoomPage`가 App.tsx에 라우트로 등록돼 있지 않음 (현재는 `ClientAppPage` 내부 pathname 분기로만 참조). 상담사용 `/chat` 라우트만 등록됨.
3. **관계 모델 정합성** — 채팅 권한이 `ClientCounselorLink`(1:1 연결)에 의존하는데, 현재 시스템은 기관 멤버십(`user_org_membership`)·개인상담소 구조로 확장됨. "누가 누구와 채팅할 수 있는가"의 기준을 현재 비즈니스 관계에 맞게 재정의해야 함.
4. **세션 방 생성 시점** — 세션에 `open` 상태가 추가되면서, 세션 방을 언제 만들고 언제 열어둘지(예: 예정 세션부터 vs open 이후) 정책 결정 필요.
5. **실동작 검증 부재** — 코드·DB·WS가 다 있지만, 현재 dev 환경에서 실제로 (가) 상담사-내담자 왕복 메시지, (나) 읽음 표시, (다) 알림 연동이 정상 동작하는지 E2E 확인이 필요.

### 4-3. 결론

**적용은 가능하다.** 채팅 기능 자체는 완성품으로 남아 있고, 깨진 것은 "진입점(내비게이션/라우트)"과 "관계·시점 정책"이다. 코드 대부분을 새로 짤 필요 없이, **재노출 + 관계·정책 정비 + 검증** 수준의 작업으로 재적용 가능.

## 5. 적용 방안 (옵션)

### Option A — 최소 재노출 (1:1 채팅만 재활성화) 

- 사이드바(상담사·내담자)에 "채팅" 메뉴 복원 + 내담자 채팅 라우트 등록
- 기존 `direct`(1:1) 방 위주로 재활성화. 세션/그룹 방은 유지하되 노출 범위는 추후
- ⚙️ 작업량: 소 (내비게이션 + 라우트 + 스타일 정합)

### Option B — 재노출 + 관계·정책 정비 (완전 재적용) 

- A의 내용 + `ClientCounselorLink` 기반 권한을 현재 기관 멤버십 구조와 정합시키고, 세션 방 생성·종료 시점을 `open` 상태머신에 맞게 정비
- 세션/그룹 방까지 활성화 (클래스 참여자 소통 포함)
- ⚙️ 작업량: 중 (권한·정책 + 내비게이션 + 라우트 + 검증)

### Option C — 채팅 재설계 (클래스 실시간 소통 통합)

- 클래스 진행 중 실시간 채팅을 별도로 설계 (LiveKit/클래스 플레이어와 통합)
- ⚙️ 작업량: 대 (기존 채팅 재활용 범위 최소, 신규 설계)

## 6. 의사결정 필요 사항

1. **적용 범위** — 1:1 채팅만? 클래스/세션/그룹 소통까지?
2. **권한 기준** — 채팅 대상을 `ClientCounselorLink`(기존 1:1 연결) 기준으로 유지할지, 기관 멤버십 기반으로 확장할지
3. **세션 방 시점** — 세션 채팅방을 예정 단계부터 열지, `open`(오픈/대기) 이후부터 열지
4. **내담자 진입 UX** — 내담자 채팅을 별도 탭으로 둘지, 세션/홈 화면에 통합할지
